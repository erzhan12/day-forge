# #226: уточнение только что добавленного блока

Проверка 7 ноября 2026 года. Локальный кандидат на базе `3f0374d`. Chat использует настоящий `x-ai/grok-4.3` через настроенный OpenRouter, draft использует `gpt-4o`. Production в этой проверке не менялся.

## Причина и воспроизведение

Историческая audit-запись 268 содержит именно `add` с названием `встречу`, временем 14:00–15:00 и категорией `work`. Replay guard отклонил повторное добавление. Разрешить такое действие означало бы создать дубль вместо изменения существующего блока.

Свежий прогон исходного кода дал другой ответ той же модели: после `запланируй встречу` появился блок 688, 06:00–06:25, Other. На `в 14:00 на час, рабочая` AI спросил название новой задачи и не изменил revision. Это тоже потеря уточнения, но не повтор исторического срабатывания guard. [Raw-ответы до исправления](evidence/issue-226-2026-11-07/before.json) и [сохранённые HTTP-результаты](evidence/issue-226-2026-11-07/before-receipts.json) различают эти случаи. Старый browser harness завершился timeout; результаты запроса извлечены из серверных receipts, а не объявлены успешным smoke.

Причина в `implicit_add`: после успешного ответа без вопроса фраза уточнения получала префикс `добавь `. Модель видела команду `добавь в 14:00 на час, рабочая`. Правило 11 также не объясняло явно, как обработать уточнение после успешного добавления.

## Исправление

Уточнения, начинающиеся с времени HH:MM или длительности с `for`/`на`, после ответа ассистента передаются провайдеру без префикса. Например: `в 14:00 на час, рабочая`, `at 14:00 for an hour, work`, `на час`, `for 30 minutes`. Новые названия `Notes`, `Обед` и `Reading emails 30 min` сохраняют прежнее поведение implicit add.

Hard rule 11 требует найти текущий ID блока и выполнить один `update` только запрошенных полей. Неоднозначный выбор требует вопроса. Replay guard не ослаблен: повторный `add` по-прежнему отклоняется, автоматического превращения `add` в `update` нет. Исходная реплика и raw-ответ остаются в audit.

## Проверка результата

В первом исправленном browser-прогоне AI создал блок 689 на 06:00–06:25, затем вернул `update` с `task_id: 689`. Независимый Inertia GET подтвердил ровно один блок с тем же ID, временем 14:00–15:00 и категорией `work`. [Raw-ответы после исправления](evidence/issue-226-2026-11-07/after.json), [browser-прогон](evidence/issue-226-2026-11-07/refinement-smoke.log).

HTTP-регрессия на русском и английском проходит через настоящий prompt builder, parser, category resolution, guard и запись в БД. Подменяется только SDK completion. Проверяются исходный текст для провайдера, сохранение ID, точные поля, неизменный сосед, исходная audit-реплика и блокировка replay после новой команды `Notes`. Отдельная регрессия сохраняет исходное расписание и revision, если провайдер всё же возвращает повторный `add` на уточнение.

Отрицательный контроль подставляет прежний `implicit_add` из HEAD через временный pytest plugin. Оба HTTP-кейса падают: провайдеру снова передаётся `добавь в 14:00…` или `add at 14:00…`. Production-файлы для этого контроля не заменялись.

## Полные проверки

- `make check`: Ruff, 2683 backend passed, 1 skipped; TypeScript и 1525 frontend passed в 107 файлах. Единственный skip относится к существующему opt-in live comparison.
- `make frontend-build`: успешно.
- Отрицательный контроль: 2 ожидаемых падения, затем 237 профильных тестов проходят на исправленном коде.
- `make e2e-chat`: все 6 сценариев прошли, включая реальное уточнение с сохранением ID и обе ветки Clear. Последний полный прогон завершился с кодом 0.
- `make e2e-draft`: все 4 сценария прошли, включая реальную генерацию и проверку history prompt, отказ 409 без AI и восстановление после 422. Код завершения 0.

Smoke уточнения больше не пропускает проверку, когда первая реплика сразу добавляет блок. Обе ветки обязаны закончиться ровно одним Work-блоком на 14:00–15:00; для немедленного добавления дополнительно проверяется сохранение ID. Вместо фиксированной паузы скрипт ждёт завершения обработки.

Первый полный chat-прогон выявил устаревшее ожидание в smoke Clear: ввод считался доступным до подтверждения исхода запроса. Проверка приведена к текущему durable request contract: Clear убирает spinner и transcript, подтверждённый ответ разблокирует ввод, а неподтверждённый HTTP 500 оставляет recovery и блокировку нового AI-запроса. Ожидание позднего ответа больше не проглатывает timeout.

В ходе исправления smoke Clear один промежуточный прогон остановил этот сценарий из-за неподходящего Playwright matcher `toBeOK` для browser Response. Проверка заменена сравнением HTTP-статуса; последующий полный chat-прогон прошёл. Это ошибка harness, изменений runtime-кода Clear не потребовалось.

Использованы локальный пользователь `playwright` и штатные seed-скрипты. Тестовые расписания оставлены для инспекции согласно стандартному режиму smoke без `--cleanup`. Изменения не опубликованы.
