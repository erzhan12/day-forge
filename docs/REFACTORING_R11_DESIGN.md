# R11: AI chat heuristics, pending intent, and request identity

This note records the R11 research and the narrow replay guard boundary fix in the current worktree on 11 October 2026. It does not implement `pending_intent`, `request_id`, or a broad heuristic removal. R00–R10 remain uncommitted. The last recorded live chat and draft attempts failed to connect to OpenRouter (`docs/REFACTORING_R10.md`), so the fixed completion runs establish application behavior only.

## What the current path knows

`useChat.ts` sends the complete client-held transcript on every turn. Assistant turns carry `is_ask`, `is_error`, and inferred `applied_add_block_ids`. The integer `latestRequestId` only prevents an old response from changing current UI state; it never goes to the server and cannot deduplicate a committed write. A date, owner, or session reset clears the local transcript. A cancelled UI turn can still commit on the server (`frontend/src/composables/useChat.ts:1-2, 190-230, 244-284`).

The view validates roles, lengths, and marker types, then captures schedule revision and a fingerprint of blocks, rules, settings, and categories. The provider call runs outside a write transaction. The server flattens prior client turns into an explicitly untrusted user-role section and keeps the latest turn separate. `apply_implicit_add` rewrites only the provider-bound copy. Category normalization and typed action validation run after the provider response. The view then checks for replayed adds and applies the plan through the shared mutation executor, which rechecks revision and context under the User lock (`backend/ai/views.py:803-851, 957-1038, 1102-1136`; `backend/ai/service.py:372-513`; `backend/schedules/mutations.py:75-94, 204-218`).

The transcript markers are client claims. Validation proves their shape and placement, not that the assistant actually asked or that an earlier action was applied. `applied_add_block_ids` comes from a client-side before/after diff. The replay guard has to infer an open ask chain and accepted work from those claims and the current block titles (`backend/ai/replay_guard.py:214-327`). The model sees role and content from prior turns, without these client markers (`backend/ai/prompts.py:462-490`). `AIInteraction` is best-effort audit: its row can be absent, and `success=True` is set after the mutation transaction. It is neither a durable request identity nor proof, by itself, that a specific mutation committed (`backend/ai/views.py:130-189, 1124-1149`; `backend/ai/models.py`).

## Keep or remove

| Current behavior | Evidence and decision |
|---|---|
| `implicit_add` prefixes a bare activity name for the provider, except commands, questions, short replies, and turns following an ask or error. | Keep. The known `Momentum` then `Notes` case led the model to replay the old add despite prompt rule 11; the rewrite supplies the intended new title to the provider. Tests pin English and Russian bare names, pending answers, and retries (`test_ai_implicit_add.py`; `test_ai_service_chat.py:1103-1133`; `test_ai_views_chat.py:2841-2930`). The verb and reply lists have possible classification errors, but no branch is proved redundant by these tests. |
| `replay_guard` rejects adds whose title is traceable to older handled turns but not the latest turn, with exceptions for pending asks and failed retries. It rejects the entire model output when one add is suspect. | Keep as a safety backstop while prior turns remain client supplied. The view test for `Momentum[2]` proves that the guard prevents a duplicate after a mocked model replay (`test_ai_views_chat.py:2841-2903`). Partial apply and explicit repeat have separate tests (`test_ai_replay_guard.py:118-191`). The R11 boundary fix below is a correction inside this guard, not its removal. Its token overlap can still miss an unrelated hallucinated title or allow a shared-word replay; it is not request idempotency. |
| `category_resolution` maps exact slugs and labels, supplies the sink category for an add, and preserves safe non-category changes while asking about an unresolved update category. | Keep. Removing it would turn known label outputs into parse failures and would lose the partial update behavior. Tests cover Russian labels, an unknown category, malformed values, unknown targets, and original model indices (`test_ai_category_resolution.py`; `test_ai_views_chat.py:526-735`). It deliberately does not translate an inflected word such as `рабочая`. |
| Prompt rules 2, 4, 9, 11, and 12 describe bare names, category slugs, follow-up slots, replay limits, and category answers. | Keep for the present protocol. Their overlap with deterministic checks is defense at different stages, not evidence that either stage is unnecessary. |

No major heuristic has sufficient evidence for deletion in this pass. A narrow candidate for a later ablation is the large command-verb/short-reply exclusion table inside `implicit_add`, after a server-owned pending intent and a live comparison exist. Removing that table now would turn some read-only requests or acknowledgments into adds. Category normalization is not part of that simplification.

R11 did simplify one incorrect boundary inside `replay_guard`. After an error, `_collect_failure_chain_start` now reuses `_collect_ask_chain_start` to exclude the **whole contiguous pending ask chain** from prior replay text, rather than just its last ask. The earlier behavior could treat the original `add Gym` as handled after `How long should Gym be?`, `30 minutes`, `Past or from now forward?`, `past`, an error, and `try again`. It caused an extra ask for still-pending Gym. The revised path retains only the immediately preceding ask text for answer traceability, keeps `applied_add_block_ids` from all ask turns in the chain as evidence against repeating a committed sibling, and refuses to use any guard ask in that chain to whitelist a rejected title (`backend/ai/replay_guard.py:214-327`; `backend/tests/test_ai_replay_guard.py:255-410`). Older clients without applied IDs still fail closed for an existing same-title block. This targeted correction leaves the semantic replay guard in place and does not create server-owned pending intent.

Two concrete gaps define the boundary of the current guard. If the latest user turn says `No, don't add Gym`, a wrong provider `add Gym` output is traceable to the latest text and passes `_is_replay` before older evidence is considered (`backend/ai/replay_guard.py:189-194`). The guard does not understand negation or refusal. Separately, an add may commit while its HTTP response is lost. The frontend then records a synthetic `is_error` bubble for the network failure (`frontend/src/composables/useChat.ts:297-333`). A later `try again` lets the guard exclude that earlier user turn as a failed attempt (`backend/ai/replay_guard.py:214-250, 280-283`), even though the first write committed. These are distinct from the known `Momentum` to `Notes` replay. Do not add a speculative negation regex to hide the first gap. The refusal case needs an explicit intent decision and the lost-response case needs durable request identity.

## Explicit pending intent

Store a server-owned record only when a response asks for missing information or a plan applies some requested changes and leaves others unresolved. The record should include a random opaque intent ID, owner ID, schedule ID and date, action type, selected target block IDs, known field values, missing field names, and an itemized list of accepted changes with their committed block IDs. It should also contain the schedule revision and policy-context fingerprint captured **after** any accepted write, creation and expiry times, and a state such as `open`, `resolved`, `cancelled`, or `stale`. One ask can address the first missing field while the record retains the remaining unresolved actions. Do not infer accepted work from a client-supplied assistant sentence or a title match.

The client may return the opaque ID and its new utterance. The server loads the record by authenticated owner, date, and schedule; checks expiry, state, revision, context fingerprint, and target ownership; and accepts only fields or target choices allowed by the record. The model may interpret the answer, but it cannot add targets or rewrite accepted fields merely because earlier text mentioned them. A fresh explicit command starts a new intent and closes the old one. A refusal or cancellation of a pending action closes it without a mutation. A same-title explicit repeat starts a new request. If the day or its policy context changes between turns, mark the intent stale and ask the user to restate or confirm against the current schedule. Never silently replay accepted siblings. Date, owner, logout, session reset, and explicit thread clear should drop the client reference; the server still enforces scope and expiry. A short expiry such as 15 minutes is a proposed product choice, not a current contract. A refusal on a turn with no pending intent still needs its own current-turn decision; merely adding a pending record does not make arbitrary provider output safe.

The provider should receive a compact, server-built pending summary containing only the permitted action and missing fields. Prior transcript can remain available as untrusted context, but it must not authorize a mutation. The final boundary remains typed schema validation, target ownership, expected revision, context fingerprint, schedule-window checks, and domain planning under the write lock. A pending record is not a substitute for any of these checks.

## Durable request identity is a separate problem

Add a client-generated UUID `request_id` to each submitted chat turn. Keep it stable for transport retries and uncertain outcomes; mint a new one for a deliberate new turn or explicit repeat. Bind it to authenticated user, schedule/date, endpoint, and a canonical hash of the complete request body, including transcript or pending intent ID and expected revision. The current `latestRequestId` remains a UI generation token and must not be reused as this key. A unique database constraint on the scoped ID rejects the same ID with a different body. An identical completed request returns its stored terminal HTTP status and response without another provider call or mutation. Check this identity before rejecting a stale expected revision, so a lost response after a successful commit can be recovered.

Use a durable operation row with `processing` and terminal states, request hash, fenced lease token, and stored response. Reserve it before the provider call. Concurrent identical requests either wait for the first result or return an explicit in-progress response; they must not each apply. A crashed provider call may be retried after a bounded lease expires, but the new worker must claim a new lease token. Before applying, the worker checks that it still owns the token. The operation's terminal result and schedule mutation must commit in the **same** database transaction, under the existing User → Schedule lock. A stale worker cannot apply after another worker claims the lease. On PostgreSQL, the unique key and row locks serialize claims; on SQLite, the writer reservation and bounded busy retry do so. Provider calls remain outside the schedule write lock. Do not rely on process memory, `AIInteraction.success`, or an audit row written after commit.

If the process crashes before the atomic apply transaction, the request remains recoverable and no schedule mutation occurred. If it crashes after commit but before sending the response, a repeat reads the stored result. If the provider returns an error before apply, persist a terminal error for that ID and require a new ID for a user-initiated retry. Retain completed operation identities for the supported retry lifetime; deleting a successful row and later accepting the same ID would break the guarantee. Define retention before rollout, with a permanent minimal tombstone or a documented long-lived uniqueness scope. The semantic replay guard still handles a *different* request ID whose model output copied an older action.

For an uncertain network result, the client must retain the frozen original body and first replay it with the **same** `request_id`. It must not synthesize a new `try again` turn until it knows whether the prior operation committed. A durable terminal operation row committed with the schedule diff is the source of that answer. An `AIInteraction.success` flag cannot supply it because the audit write and success update are best effort and separate from commit.

This design needs its own migration, API contract, and concurrency tests. It should not be folded into a small heuristic cleanup. In particular, test same-ID/different-body rejection, two processes with the same ID, response loss after commit, crash before commit, lease takeover, provider failure, stale expected revision on identical replay, and a fresh ID that explicitly repeats the same title.

## Comparison before a deletion

Build a small anonymized fixture set from existing tests and deliberately chosen examples. Do not export the full user history. Each case records initial blocks with IDs and times, rules, categories, local clock and timezone, transcript, expected actions or ask, and forbidden changes. Include bare English and Russian activities, a bare answer to an ask, retry after provider failure, `No, don't add Gym`, explicit repeat, duplicate titles, partial apply, category wording, a lost response after commit, and a schedule or policy change between turns. Keep a clear expected result for each turn rather than only the final schedule.

The current synthetic corpus has 18 dialogues and 31 turns (`backend/tests/fixtures/ai_dialogues/dialogues.json`; `backend/tests/test_ai_dialogue_corpus.py`). Fixed completions pass through the SDK, view, and planner seams. The baseline report records two false additions in known gaps: a refusal with a wrong model add and a retry after a committed request whose response was lost. It also records two excess asks on model replays. Disabling the replay guard raises false additions from two to four by applying those two replays. Disabling category resolution adds two missed applies: English and Russian category labels return 502. Disabling `implicit_add` changes the provider-bound text but leaves these fixed-output counts unchanged. That last result says nothing about how a live model would respond to the changed prompt. The reports are `/tmp/day-forge-r11/corpus-*.json` and can be regenerated from the corpus test.

Recorded-response tests can prove that a candidate still rejects replay, resolves categories, preserves ownership and revision checks, and does not duplicate a partial apply. They cannot show whether a changed prompt or removed input rewrite makes the live model produce better actions: the fixed completion supplies the model output and bypasses that question.

For live comparison, freeze one provider/model version, temperature, fixture snapshot, prompt hashes, and run order. Use isolated disposable schedules or an offline capture followed by the deterministic planner; never mutate the user's real day. Compare baseline and one candidate at a time on the same 12–20 cases, with two runs per arm if cost allows. Set a token and currency cap before execution and stop at that cap. Record raw response, parsed actions, planner outcome, request time, latency, token usage, provider/model identifier, and estimated cost. No live calls belong in ordinary unit CI. If OpenRouter remains unavailable, mark the live comparison deferred and keep the heuristics.

Score at least two separate primary counts: **false adds** (a block added without current user intent, including replays) and **excess asks** (an ask where the fixture provides enough information to act). Also count missed intended actions, wrong target or category, duplicate application, invalid output, and cost. Review every difference by case. A zero count in a tiny run is useful evidence, not proof of general safety. Remove one branch only when its cases stay correct in deterministic application tests and the live comparison shows no false-add regression or unresolved excess-ask cost. Re-run the same set after each removal.
