# Server-owned pending intent: контракт

22 октября 2026 года. Контракт зафиксирован перед реализацией на основе [R11 design](REFACTORING_R11_DESIGN.md#explicit-pending-intent).

## Состояние и границы

Сервер хранит одно открытое намерение на пользователя и Schedule. UUID принадлежит пользователю, конкретному экземпляру Schedule и его дате. Состояния: `open`, `resolved`, `cancelled`, `stale`. Отдельная монотонная `version` защищает ответы из двух вкладок, даже когда вопрос не меняет revision расписания. Срок жизни составляет 15 минут с момента создания и не продлевается уточнениями.

Намерение содержит исходную пользовательскую реплику, структурированные незавершённые действия, известные значения, недостающие поля, разрешённые target IDs, вопрос и список уже принятых изменений с реальными block IDs. Revision и fingerprint блоков, правил, категорий, окна и timezone сохраняются после принятой части записи. Данные приватные, удаляются с Schedule или аккаунтом; завершённые записи сами не разрешают повтор действия.

`request_id` продолжает идентифицировать один HTTP-turn. Полное тело, включая ссылку на intent, входит в hash. Сохранённый terminal response возвращается до проверки актуальности intent. Переход intent, запись расписания и receipt выполняются в одной транзакции под существующим User lock. Сеть остаётся вне транзакции.

## HTTP

Chat POST сохраняет `request_id`, `expected_revision`, `messages`. Продолжение добавляет `pending_intent_id` (canonical UUID) и `pending_intent_version` (целое >= 1). `intent_action` принимает `continue`, `cancel`, `new`; без ссылки разрешён только `new`, это значение по умолчанию. Ссылка без version и обратная комбинация дают 400 до записи и rate limit.

Ответ содержит `pending_intent: null` либо `{id, version, expires_at, ask}`. Полный сохранённый план клиенту не передаётся. Явная кнопка Cancel pending request посылает `cancel` с новым request_id и не вызывает провайдера. Clear, смена даты, аккаунта, Logout и dispose убирают клиентскую ссылку; новый запрос без ссылки начинает новое намерение. Неопределённый HTTP-результат сначала восстанавливается прежним request_id и неизменным телом.

Чужой, неизвестный, закрытый или устаревший UUID, другая дата/Schedule, expiry, изменение revision/policies либо несовпадение version приводят к 409 без вызова провайдера и без schedule mutation. До вызова это `pending_intent_stale`; изменение расписания или политики во время сети может вернуть существующий `schedule_changed`. Явная отмена проверяет owner, Schedule, state, version и expiry; изменение политики само по себе не мешает закрыть намерение без записи. Параллельный ответ не может ни повторить принятые siblings, ни закрыть более новое намерение.

## Ответ модели и применение

Prompt запрашивает `intent_decision`: `new`, `continue`, `cancel`, `read`, а для вопроса дополнительный `pending_actions`. Это типизированные предложения, а не готовое разрешение записи. Незавершённое действие имеет канонический тип `add`, `update` или `remove`, `task_id`, `target_ids`, `known_fields`, `missing_fields`. Move/resize нормализуются к update; target IDs проверяются по серверному Schedule. Строки и количество элементов ограничены существующими пределами chat.

Для продолжения модель получает серверное summary и последнюю пользовательскую реплику. Разрешено изменять только недостающие поля указанного действия, сохранять известные значения и выбирать target из сохранённого списка. Новые targets, дополнительные actions, изменение уже принятых полей и повтор принятого sibling отвергаются целиком без записи. Обновлённый вопрос также не может расширять разрешённый scope. Новая явная команда начинает отдельный intent; прежняя запись закрывается. Free-text cancellation распознаётся отдельным структурированным `intent_decision`, а её actions отбрасываются; регулярные выражения для отрицания не добавляются. При неверной семантической классификации модели остаётся риск NLU; явная кнопка Cancel работает независимо от модели.

Вопрос старого формата без структурированного плана сохраняется как незавершённый запрос без разрешённых actions. Он не даёт права применить произвольное продолжение. Пользователь должен отменить или очистить этот запрос и заново сформулировать команду. Существующие implicit-add, replay и category guards остаются. Transcript markers и assistant-текст не служат доказательством применения или источником accepted IDs.

Уточнение от 23 октября: разрешённое время и известная длительность однозначно задают вторую границу интервала. Она допускается без отдельного разрешения. Противоречащая длительность, изменение известного времени и выбор произвольного интервала, когда разрешено уточнить только длительность, запрещены. Если после применения действий остаются валидные `pending_actions`, сервер сохраняет их и задаёт нейтральный вопрос даже при `ask: null` модели. Принятые действия и их IDs сохраняются отдельно. Вопрос защитного guard без записи не расходует разрешение незавершённого действия. Результаты production и контейнерной проверки: [отчёт после PR #262](POST_PR262_RELEASE_VERIFICATION.md).

## Проверки

Проверить scope/expiry/version, изменение правил и расписания, принятую часть + оставшийся вопрос, попытку повторить sibling или расширить targets/поля, отказ с ошибочными actions, явную отмену без AI, новую команду, две вкладки, одинаковый и разные request_id, потерю ответа и rollback транзакции. Клиентские проверки охватывают clear/date/account/session, восстановление замороженного тела и отмену. Браузерный прогон выполняется на изолированной базе с реальным AI, включая desktop/mobile; результаты и ограничения дополняются после реализации.
