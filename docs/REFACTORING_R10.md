# R10: текущая статистика и зафиксированный обзор

Выполнено локально 11 октября 2026 года. R11 не начат. Изменения R00–R10 остаются в рабочем дереве без commit и push.

## Что изменилось

До R10 посещение аналитики активного дня пересчитывало и сохраняло `DailyReview`. Та же строка хранила заметки и использовалась как источник статистики для других потребителей. После редактирования или восстановления дня наличие строки само по себе не гарантировало актуальность её агрегатов.

Теперь `compute_review_stats` рассчитывает текущие данные в памяти, а `freeze_review_snapshot` записывает агрегаты только при явной фиксации обзора или в согласованных seed-сценариях. Старый `recompute_review_from_schedule` удалён.

`is_review_snapshot_current(schedule, review)` задаёт общий критерий:

1. Статус расписания равен `reviewed`.
2. Строка обзора существует.
3. Её `reviewed_revision` задан и совпадает с `Schedule.revision`.

Аналитика, streak и AI draft history используют этот критерий. При его нарушении они рассчитывают статистику из текущих блоков без записи обзора. Draft-дни по-прежнему исключены из AI history. История и streak используют eager loading, поэтому число запросов не растёт на каждый день.

## GET и согласованность данных

`GET /analytics/<date>/` не создаёт и не обновляет `DailyReview`. Для обычного посещения после инициализации пользовательских настроек тест проверяет отсутствие INSERT, UPDATE и DELETE.

Настройки, категории и preferences при первом использовании могут создавать свои default-строки. Их инициализация выполняется перед транзакцией чтения. Затем GET получает User через `SELECT FOR UPDATE` и внутри одной транзакции захватывает расписание, упорядоченные блоки, обзор и streak. На PostgreSQL этот lock согласован с писателями R04; на SQLite чтения используют один снимок транзакции. GET не выполняет прежний пустой UPDATE User и не резервирует SQLite writer lock.

Упорядоченный Prefetch используется повторно для расчёта и сериализации блоков. Последующий `.order_by()`, который обходил prefetch и создавал лишний запрос, убран.

## Фиксация обзора и восстановление

На активном дне `mark-reviewed` проверяет `expected_revision`, считает агрегаты и переводит день в reviewed внутри общей транзакции User → Schedule → TimeBlock. Snapshot получает итоговую версию дня, после чего executor увеличивает revision один раз.

Повторный POST для уже reviewed-дня проверяет snapshot под тем же lock до разбора JSON и проверки версии. Если snapshot актуален, он возвращается без изменения revision и timestamps. Notes из повторного POST игнорируются, как прежде.

Если snapshot отсутствует или его revision устарел, повторный POST восстанавливает его на текущей версии дня. Notes сохраняются, revision расписания не увеличивается. Это явный путь восстановления старых reviewed-дней. GET до восстановления показывает текущую статистику и ничего не записывает.

Forward-edit переводит reviewed-день в active. Undo и обслуживание категорий сохраняют свои правила статуса, но изменение revision всё равно лишает старый snapshot актуальности. Старые агрегаты могут оставаться в строке для хранения, однако потребители не показывают их как текущие.

## Заметки и frontend

Добавлен `PATCH /api/analytics/schedules/<date>/notes/`. Он сохраняет строку длиной до 2000 символов и при первом сохранении лениво создаёт `DailyReview` для существующего расписания. Пустая строка очищает notes. Запись заметок использует User → Schedule lock, сохраняет агрегаты и snapshot tag, не меняет revision дня.

Старый маршрут `PATCH /api/analytics/reviews/<pk>/notes/` оставлен для совместимости и использует тот же writer. Новый frontend адресует заметки по дате, поэтому autosave работает при `review.id = null`.

Wire-контракт дополнен `snapshot_kind: current | frozen` и nullable `reviewed_revision`. ID и timestamps также nullable до создания строки. UI показывает `Current progress` или `Reviewed summary`.

Debounce захватывает дату, пользователя и текст. При уходе на другую дату сохраняется outgoing draft; смена пользователя или потеря сессии сбрасывает pending notes. Запрос передаёт захваченный `X-Schedule-User`. Ответы старого контекста не меняют ошибки текущей страницы, включая переход A → B → A.

Записи notes одного дня и пользователя проходят последовательно. `markReviewed` занимает место в той же очереди: ждёт предыдущие сохранения и блокирует последующие до своего завершения. Это защищает новую заметку, введённую во время review, от перезаписи старым телом POST. Barrier освобождается и при ошибке или смене контекста. Очищенные notes передаются явно, поэтому review не возвращает старый текст.

## Миграция

Добавлена `analytics/0003_dailyreview_reviewed_revision.py` с nullable `PositiveBigIntegerField`.

Миграция присваивает существующим reviewed-строкам текущую revision соответствующего расписания. Она сохраняет прежние агрегаты, заметки и timestamps. Active/draft-строки остаются без tag, отсутствующие обзоры не создаются. Новое поле readonly в admin.

Перед применением создан согласованный SQLite backup через SQLite backup API: `/tmp/day-forge-r10/before-r10.sqlite3`. Миграция проверена на отдельной копии базы. Сравнение всех прежних колонок `DailyReview` подтвердило сохранность данных; backfill соответствует статусам и версиям. После этого миграция применена к локальной базе. `makemigrations --check --dry-run` не обнаруживает дополнительных изменений.

Оба seed-сценария фиксируют snapshot после исполнения maintenance, используя фактическую итоговую revision и оставаясь под внешним User lock. Это учитывает и операции без изменения дня.

## Очистка и состояние проекта

Временные блоки удалены или отменены через Undo. Созданный notes/review дня 11 октября удалён под User lock после проверки, что его не было в backup и текст принадлежит R10. Дни 11 и 16 октября возвращены к исходным пустым draft: revision 35 и 12. Версии не откатывались.

Все исходные строки TimeBlock и все прежние поля DailyReview во всей базе побайтно совпали с backup после очистки. Новые snapshot tags сохранены. Audit 314–317 оставлен как след проверки. Интеграционные аккаунты, пользовательские ключи, тема и timezone не менялись.

Harness остановлен; обычный backend запущен на 8006. Временные browser tabs закрыты, viewport reset выполнен. Проект работоспособен после R10. Успешный запрос к живому AI-провайдеру остаётся непроверенным из-за сетевой ошибки.
