# R11: исследование AI-эвристик

Выполнено локально 11 октября 2026 года. Исследовательская часть завершена, ограниченный live-сравнительный прогон отложен из-за недоступности OpenRouter. Крупные эвристики сохранены. Изменения R00–R11 остаются без commit и push. R12 не начат.

## Решение и изменение кода

Удалять `implicit_add`, `replay_guard` и `category_resolution` сейчас нет оснований. Они решают разные задачи: интерпретацию короткой новой команды, защиту от повторения ранее выполненной команды и приведение категории к допустимому slug. Проверка фиксированных ответов показывает последствия отключения двух последних механизмов. Влияние `implicit_add` на живую модель этим способом измерить нельзя.

Исправлен конкретный дефект в `backend/ai/replay_guard.py`. После двух уточняющих вопросов, ошибки ответа и команды `try again` guard считал первоначальную ещё не выполненную команду старым обработанным запросом. Например, цепочка `Add Gym` → вопрос о длительности → `30 minutes` → `Past or from now forward?` → ошибка → `try again` могла получить ещё один вопрос вместо добавления Gym.

Теперь обычный ответ на вопрос и retry после ошибки используют одну границу непрерывной цепочки незавершённых уточнений. Ранее выполненные запросы остаются доказательством replay. ID уже добавленных блоков из partial apply тоже остаются доказательством, чтобы retry не добавлял выполненного соседа второй раз. Для старого клиента без списка ID сохраняется консервативная проверка существующих названий. Название, явно повторённое в последней пользовательской команде, разрешено, как прежде.

Текстом разрешающего вопроса остаётся непосредственно предшествующий вопрос. Более ранний вопрос может упоминать уже выполненную задачу как контекст. Вопрос самого guard, цитирующий отклонённое название, нигде в незавершённой цепочке не разрешает его повторное добавление.

Typed schema, ownership, expected revision, policy context, ограничения времени и доменный planner сохранены. Frontend и миграции в R11 не менялись.

## Корпус и сравнение

Добавлены `backend/tests/fixtures/ai_dialogues/dialogues.json` и `backend/tests/test_ai_dialogue_corpus.py`: 18 синтетических диалогов, 31 пользовательская реплика. Для каждого случая указаны исходные блоки, правила, категории, дата и часы, реплики, происхождение примера из существующих тестов, фиксированный SDK-ответ и ожидаемые блоки. Где нужно, явно заданы запрещённые названия. Точное сравнение блоков ограничивает изменения и в остальных случаях. История пользователей из базы не выгружалась.

Корпус проходит через настоящий chat endpoint, parsing, schemas, category resolution, replay guard, planner и запись расписания. Подменяется только SDK completion. Проверяются outgoing сообщения, точные сохранённые блоки, outcomes, чужие ID, устаревшая revision, русский и английский ввод, уточнения, ошибки, отказ, явный повтор, одинаковые названия и partial apply. При смене даты корпус моделирует очистку transcript, а отдельный случай проверяет повторное использование transcript через API. Очистка сообщений при смене даты отдельно покрыта `frontend/tests/useChat.test.ts`; backend-корпус frontend-код не исполняет.

Ожидаемое текущее поведение отделено от желаемого. Два известных небезопасных сценария намеренно фиксируют существующий результат и учитываются в метриках, а не объявляются безопасными из-за зелёного теста. Метрики этого небольшого набора не оценивают общую частоту ошибок модели.

| Режим фиксированных ответов | Неверные добавления | Лишние уточнения | Реплики с пропущенным применением |
|---|---:|---:|---:|
| Текущий R11 | 2 | 2 | 2 |
| Replay guard отключён | 4 | 0 | 0 |
| Category resolution отключён | 2 | 2 | 4 |
| Implicit add отключён | 2 | 2 | 2 |

Без guard два ошибочных ответа модели применяются. Снижение числа вопросов в этой строке означает пропуск защиты, поэтому не считается улучшением. Без нормализации два ответа с английской и русской метками категорий возвращают 502. При отключении implicit add меняется текст SDK-запроса, но фиксированный ответ остаётся тем же. Равные числа в последней строке не доказывают ненужность rewrite.

Отдельно тот же корпус запущен с guard из HEAD до R11, подключённым временным pytest plugin без изменений production-файла. В единственном отличающемся случае `multi_ask_error_retry` старый guard блокирует Gym, новый добавляет его. Суммарные лишние уточнения и пропущенные применения уменьшаются с 3 до 2; неверные добавления остаются 2. В группе обычных регрессий все три показателя после исправления равны нулю. Ожидаемое падение этого контрольного прогона относится к старому guard, а не к текущему suite.

Воспроизводимый baseline: `uv run pytest backend/tests/test_ai_dialogue_corpus.py -q`. Для диагностического сравнения задать `R11_CORPUS_ABLATION=replay_guard_off`, `category_resolution_off` или `implicit_add_off`. Ablation-прогоны сохраняют наблюдения, но намеренно не требуют совпадения с baseline. Это только тестовые параметры, production-флагов отключения нет. Каталог отчётов задаётся `R11_CORPUS_REPORT_DIR`; в этой сессии использован `/tmp/day-forge-r11/`.

## Оставшиеся проблемы и следующий контракт

1. Если модель отвечает `add Gym` на `No, don't add Gym`, совпадение названия с последней репликой разрешает действие. Guard распознаёт replay, но не смысл отрицания. Корпус отдельно покрывает правильный и ошибочный ответ модели на отказ. Новая регулярка отрицания без проверки не добавлялась.
2. Если запись завершилась, но HTTP-ответ потерян, UI создаёт `is_error`. Новый запрос `try again` может повторить добавление. Проверка revision и смысловой guard не обеспечивают идемпотентность такой цепочки.
3. Transcript принадлежит клиенту. При его очистке или потере guard не знает предыдущий запрос. В браузере первый partial-follow-up ушёл с `turn_count=1`, поэтому ошибочный фиксированный ответ применился (audit 329). Результат отменён через Undo. Повтор с сохранённой цепочкой `turn_count=3` отклонён целиком (331), уже принятый Momentum остался единственным. Это предел текущего контракта, а не доказательство защиты без истории. Причина потери клиентской истории в первом прогоне не установлена.

В `docs/REFACTORING_R11_DESIGN.md` сопоставлены текущий transcript и предложенный серверный `pending_intent`: owner, день, вид действия, выбранные ID, известные и недостающие поля, принятые изменения, revision/context после записи, срок и состояние. Отказ закрывает намерение без записи; изменение дня или политики делает его устаревшим. Клиентский текст помощника не должен авторизовать изменение.

Отдельно спроектирован durable `request_id`: уникальный ID и hash полного неизменяемого запроса, отказ при другом теле, возврат сохранённого результата при идентичном повторе, lease с fencing для конкурирующих исполнителей, атомарная фиксация результата операции вместе с mutation. Provider остаётся вне write lock. `AIInteraction.success` не является доказательством commit. Для неопределённого сетевого результата клиент сначала повторяет замороженное исходное тело с тем же ID. Обе конструкции пока только проект, API и БД их не реализуют.

## Браузер и реальный AI

Локальные Django `:8006` и Vite `:5173`, пользователь `playwright`, timezone UTC, тема Dark 4a. На desktop 1280 × 720 проверены ручное добавление и выполнение, текущая аналитика, заметки и фиксация обзора, Markdown export, переходы Schedule/Settings/Analytics, Cancel/Delete через DOM dialog, Undo и Logout/Login. После AI-редактирования аналитика показала текущие 1/6 и сохранённые `R11 browser notes`.

На обычном backend выполнены реальный chat и generate-draft. Оба вернули 502 `AI service error` с ошибкой соединения с OpenRouter. Независимый GET `https://openrouter.ai/api/v1/models` также завершился `Connection reset by peer`. Provider host `openrouter.ai`, chat model `x-ai/grok-4.3`, draft model `gpt-4o`. Ключи, TLS и настройки провайдера не менялись. Usage и стоимость ответа не получены. Было два логических запроса; число внутренних SDK-попыток отдельно не измерялось.

| Audit | Источник | Результат |
|---|---|---|
| 318 chat, 319 draft | Реальный provider | success=false, ошибка соединения, расписание не изменилось |
| 320–328 | Фиксированные SDK completions | Два уточнения, parse error, успешный retry, bare Notes, блокировка replay, правильный отказ, явный повтор и partial apply |

Временный `/tmp/day-forge-r11/fixed_ai_server.py` заменял только completion для тестового пользователя внутри запроса. Parsing, guards, domain validation, запись и audit работали обычным кодом. Последовательность `Add R11 Gym` → два уточнения → ошибка → `try again` успешно добавила один Gym. Ошибочный повтор старого Gym блокировался. Partial apply сохранил Momentum, конфликтующий Vocal остался pending; ответ, пытавшийся добавить Momentum[2], блокировался. Явная новая команда добавила Vocal. Явный повтор Gym был разрешён и отменён через Undo.

Заглушки подтверждают путь приложения для заданного ответа. Сравнение качества prompt/rewrite на живой модели отложено. Пока оно недоступно, эвристики сохраняются. Протокол ограниченного live-прогона с фиксированными случаями, usage, стоимостью и раздельными метриками описан в design-файле.

Попытка mobile viewport 390 × 844 через документированный API не изменила фактический размер: DOM продолжал показывать 1280 × 720 даже после reload и в новой вкладке. Мобильная проверка R11 не подтверждена. Logout проверен обычным кликом на фактической desktop-ширине. Production frontend не менялся. Override сброшен.

## Очистка

Перед проверкой создан согласованный SQLite backup `/tmp/day-forge-r11/before-r11.sqlite3`. Временные блоки и созданный R11 review удалены под User → Schedule lock с проверкой владельца, дат, названий и отсутствия этих строк в backup. Дни 11 и 16 октября возвращены к исходным пустым draft, revision 50 и 14. Версии не откатывались.

Все 335 исходных строк TimeBlock и 27 DailyReview со всеми колонками совпали с backup после очистки. UserPreferences и UserScheduleSettings также совпали. Audit 318–334 оставлен. Harness остановлен, обычный backend восстановлен на 8006; после очистки пустой день и Logout проверены в браузере. Временные вкладки закрыты, исходная вкладка пользователя сохранена. На проверенной вкладке console errors/warnings не обнаружено. Проект работает после этого этапа; успешный ответ живого AI и мобильный smoke R11 остаются непроверенными.
