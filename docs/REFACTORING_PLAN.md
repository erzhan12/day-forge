Дата: 9 октября 2026 года. Исходное состояние: commit `c62963d`.

Статус на 11 октября 2026 года: R00–R12 выполнены локально. Итоговые suites: 1946 backend-тестов и 1355 frontend-тестов проходят, production build и проверки конфигурации успешны. R12 обновил текущую архитектуру, API, правила и команды, вынес историю в архив и удалил вымышленные fallback-категории frontend. Реальные chat/draft R12 прошли через OpenRouter, AI Undo проверен. Цель: сократить число независимых реализаций правил расписания, убрать неиспользуемый код и снизить стоимость следующего изменения. Количество удалённых строк служит вспомогательной метрикой. Удаление проверок, которые защищают данные пользователя, улучшением не считается.

Все пути ниже указаны относительно корня репозитория. Предлагаемые новые файлы помечены как новые; создавать их следует только при реализации соответствующего этапа.

**2. Причины сложности, которые нужно устранить**

| Причина | Текущие проявления | Целевое состояние |
|---|---|---|
| Несколько путей записи расписания | Ручной API, reorder, restore, AI и draft повторяют проверки и транзакции | Общий механизм записи с явными политиками операций |
| Нет общей версии дня | Undo заменяет более новые данные, локальные guards не защищают другие вкладки | Сервер проверяет ожидаемую версию перед записью |
| Разные источники времени | AI использует сохранённый пояс, UI использует браузер, календари используют UTC | Один пользовательский пояс для всех вычислений |
| Производные данные сохраняются без единого правила актуальности | Активный день может иметь устаревший `DailyReview` | Явное различие актуального расчёта и зафиксированного обзора |
| Копирование инфраструктуры | Несколько crypto, limiter, fetch-state реализаций | Небольшие общие функции и адаптеры провайдеров |
| Страница владеет слишком многими процессами | `Schedule.vue` управляет запросами, undo, геометрией и интеграциями | Отдельные владельцы состояния с явными контрактами |
| История разработки смешана с актуальными правилами | Старые dispatcher-комментарии, устаревшие ограничения | Короткие рабочие правила и отдельный архив решений |

**3. Инварианты, которые сохраняются при рефакторинге**

- Все чтения и записи ограничены текущим пользователем. Неизвестный или чужой ID не раскрывает чужие данные.
- Сохранённое расписание не содержит пересечений; интервалы трактуются как `[start, end)`.
- Обычный ввод соблюдает шаг в пять минут. Для импортированных событий допускаются произвольные минуты. Редактирование названия или выполнения не требует менять их время.
- Ручное создание и создание из события сохраняют текущую политику обрезки по окну дня. AI и шаблоны сохраняют политику отклонения недопустимого времени.
- PATCH и reorder проверяют изменённые границы. Ранее сохранённые блоки вне нового окна дня остаются доступными.
- Политика текущего AI partial apply сохраняется: допустимое подмножество и `outcomes` определяет planner, принятый diff записывается атомарно. Нельзя случайно заменить её на отказ от всей команды или запись по одному действию.
- Вызов внешнего AI-провайдера выполняется вне транзакции БД.
- Forward-edit переводит `draft`/`reviewed` в `active`. Draft не считается ручным подтверждением плана. Особая семантика restore фиксируется отдельно в R05.
- Неуспешная запись не создаёт undo, не увеличивает версию и не оставляет часть изменений.
- Локальная отмена запроса не считается доказательством отмены серверной записи.
- Защита от устаревшего ответа проверяет идентичность запроса и дату. Ошибка одного внешнего источника не очищает успешные данные другого.
- PiP принадлежит корню приложения. Смена страницы не должна уничтожать окно, а явный logout очищает пользовательское состояние.
- В JSON статуса интеграции, props, ошибках и логах нет незашифрованных токенов и паролей.

Размеры служат оценкой объёма проверки: S означает локальное изменение, M затрагивает несколько модулей, L меняет сквозной контракт. Они не являются обещанием сроков.

|---|---|---|---|---|

| R01 | Исправление подтверждённых ошибок | R00 | S | Streak и malformed JSON работают предсказуемо |
| R02 | Удаление мёртвого кода | R00 | S | Убран старый AI-dispatcher и остатки переносов |
| R03 | Общие HTTP, serialization и limiter-функции | R01, R02 | M | Уменьшено дублирование инфраструктуры |
| R04 | Транзакционный исполнитель и версия расписания | R01, R03 | L | Все записи соблюдают общий concurrency-контракт |
| R05 | Безопасное undo и согласованное состояние клиента | R04 | L | Старый снимок не стирает новые изменения |

R06 можно готовить после R01, но изменения настроек, revision и AI-контекста должны иметь согласованный контракт. Перенос кода planner из `ai` в `schedules` не следует смешивать с первой миграцией revision.

Полезная точка остановки: R00–R06. К этому моменту уже должны быть убраны подтверждённые ошибки, мёртвый код, риск устаревшего undo и расхождения времени. Дальнейшая работа оценивается по оставшейся стоимости изменений.

Контракт:

**R05. Защитить undo и убрать промежуток между записью и обновлением props**

Файлы: `frontend/src/composables/useSchedule.ts`, `useUndo.ts`, `useChat.ts`, `useDraft.ts`, `useDrag.ts`, `useBlockCompletion.ts`, `frontend/src/pages/Schedule.vue`, `backend/schedules/api.py`, типы и тесты этих модулей. Новый модуль при необходимости: `useScheduleMutations.ts`.

Первая версия сохраняет snapshot-undo. Она должна устранить потерю данных до переделки хранения истории.

- [x] Undo-запись хранит снимок до операции и ожидаемую revision состояния после неё. Snapshot фиксируется перед принятой операцией, новая revision берётся из серверного ответа.
- [x] Restore передаёт ожидаемую revision. Конфликт сохраняет серверные данные и сообщает, что расписание изменилось; автоматическая повторная отправка старого snapshot запрещена.
- [x] Решить последовательность нескольких undo. Успешное восстановление создаёт новую revision, поэтому следующая запись стека не может продолжать ожидать свою историческую цифру. Обновлять ожидание только для подтверждённой непрерывной цепочки undo текущего дня.
- [x] При конфликте, неизвестном результате записи или изменении вне этой цепочки инвалидировать небезопасную часть стека. Нельзя просто подменить всем записям revision из последнего GET.
- [x] Для первого этапа сохранять текущую status-политику restore: он не становится forward-edit. Если день успели отметить reviewed после сохранения undo, revision должна отклонить устаревшее восстановление. Возврат исторического статуса дня потребует отдельного контракта.
- [x] Создать один владелец жизненного цикла mutation: `idle → saving → synchronizing → idle`, с отдельной веткой конфликта. Новая запись не использует props, которые ещё не подтверждены сервером.
- [x] Сначала дождаться reload через callbacks/Promise и проверку даты. Затем, если единый response содержит достаточное состояние, обновлять локальный canonical snapshot прямо из ответа. Не оставлять два равноправных источника блоков.
- [x] Ошибка reload после успешного POST не означает rollback. Сохранять различие «запись выполнена, отображение не обновлено» и «запись отклонена»; не повторять POST автоматически.
- [x] AI и draft регистрируют undo по фактически принятому diff. Ask/no-op/отклонённая запись не создают undo.
- [x] Для completion не повторять постоянные ошибки 400/403/404 и revision-conflict. Повтор сетевого запроса разрешать только при определённой идемпотентности; потерянный ответ после commit требует reconciliation.
- [x] Очистить состояние при logout, смене пользователя и недействительной сессии. Смена даты изолирует очередь и историю по дню, не переносит результат на другой экран.

Проверки: две вкладки; A→B→undo B→undo A; навигация во время записи/reload/undo; rapid completion; успешный POST и неуспешный reload; старый AI-ответ; concurrent category deletion; день с off-grid блоком.

Следующее улучшение, отдельный PR после измерения пользы: undo через обратный diff вместо `delete all + bulk_create`. Сохранять ID существующих блоков обязательно. Для восстановления удалённых блоков сначала выбрать протокол серверного журнала операций или другого надёжного учёта идентичности. Произвольный ID из клиентского snapshot не даёт права заново создать или перезаписать строку. Полноценный server-side undo не является обязательной частью первой версии.

Готово, когда устаревший snapshot не уничтожает новую задачу, несколько последовательных undo работают, а новая mutation не стартует со старым canonical snapshot.

**5. Отдельные решения после основного маршрута**

| Решение | Что выяснить | Рекомендуемый исход по умолчанию |
|---|---|---|
| PostgreSQL вместо SQLite | Ошибки блокировок, число параллельных записей, ресурсы deployment, результаты concurrency-suite | Не менять БД ради самого рефакторинга; выбрать явно до масштабирования |
| Архивирование категории | Нужно ли сохранять исторические названия и цвета, что означает delete для пользователя | Сначала сохранить нынешнюю семантику; archive оформить отдельной feature |
| Server-side undo journal | Нужны ли undo между устройствами и восстановление после reload | Сначала revision + безопасный локальный стек |
| Отдельное приложение preferences | Есть ли реальная выгода кроме перестановки файлов | Сначала отделить API/serializers в текущем приложении; миграцию model ownership отложить |
| Отключаемые интеграции в deployment | Должен ли экземпляр работать без Google/Habitica credentials | При необходимости ввести явные enabled flags; для включённого провайдера сохранить строгую проверку |
| Удаление тем/интеграций | Фактическое использование и стоимость поддержки | Сохранить возможности до появления данных |
| Lazy-loading страниц и hashed assets | Время загрузки, кеширование, поведение старой вкладки после deploy | Отдельная оптимизация после стабилизации API-контракта |

Для PostgreSQL нужен отдельный план: backup и проверка восстановления, перенос данных с сохранением PK, настройка sequence после импорта, runtime dependency/config, CI на PostgreSQL и проверка блокировок. Сам факт перехода не исправляет пути записи, обходящие общий сервис.

Для category archive нужно заранее определить отображение в исторических днях, разрешённость восстановления через undo, поведение templates/travel rules и расчёт лимита активных категорий. Простая замена DELETE на `is_archived=True` без этих решений неполна.

Для lazy assets сначала проверить фактическую поддержку manifest/versioning текущими Django/Inertia/Vite связками. Изменение имён файлов должно идти вместе с `base.html`, collectstatic и проверкой обновления старых вкладок.

**8. Миграции, совместимость и откат**

- Additive migrations выполняются раньше, чем код начинает требовать новые поля в API. Проверка revision становится обязательной после перевода всех writers и клиентов.
- Перед migration проверить backup/restore на копии базы. Для SQLite использовать согласованную копию через backup API или остановленный writer, а не произвольное копирование активного файла.
- При откате новой frontend-версии сохранить backend, который продолжает обслуживать безопасный revision-контракт. Старый writer, игнорирующий revision, нельзя возвращать незаметно.
- Откат schema с удалением revision или пользовательских полей не является штатным первым действием. Предпочитать исправление вперёд либо maintenance-откат согласованного набора компонентов.
- Смену cache-key namespace можно откатить отдельно: старые записи доживают TTL. Ни один вариант ключа не должен смешивать пользователей, Google accounts или timezone scopes.
- Перенос crypto сохраняет настройки и формат ciphertext. Замена ключей и повторное шифрование находятся вне этого плана.
- Сохранить CI-проверки security/deployment и запрет записи raw AI prompts в production. Декомпозиция модулей не должна менять эти ограничения.
- Для каждой переходной compatibility-ветки указывать условие удаления и PR, который её удалит. Постоянная поддержка старого и нового механизма удваивает работу и не завершает рефакторинг.

| Метрика | Как измерять | Требуемый результат |
|---|---|---|
| Реализации записи расписания | Перечень реальных writers и вызываемых сервисов | Один транзакционный механизм, явные adapters/policies |
| Потеря данных от stale snapshot | Regression-сценарий из аудита | Ни одной записи при конфликте revision |
| Число стартовых запросов | Network trace без интеграций и со всеми интеграциями | Нет запросов списков отключённых источников |
| Запросы к БД | Query capture для load/create/reorder/restore/review | Нет новых запросов на каждый блок из-за рефакторинга |
| Скорость suite | Одинаковая машина и настройки | Устранена повторная дорогая авторизация API fixtures |
| Warning noise | Вывод полных suites | Неожиданные предупреждения видны, известный шум устранён |
| Повторение инфраструктуры | Реальные потребители limiter/serializer/fetch-controller | Один алгоритм на общую задачу |
| Удалённый код | Diff и отсутствие исполняемых ссылок | Удалена старая реализация после перевода потребителей |
| Изменяемость правила | Пример изменения общей проверки времени | Одно место реализации и contract-tests |
| Качество AI | Один набор диалогов, фиксированные условия сравнения | Нет новых недопустимых mutations при сокращении эвристик |

Не устанавливать обязательный процент сокращения строк: новые контракты и regression-тесты могут временно увеличить diff. Этап считается завершённым, когда уменьшилось число мест, которые требуется согласованно менять, и старая реализация удалена.

Остановить расширение рефакторинга, если новый общий модуль требует множества флагов для несвязанных сценариев, создаётся для одного потребителя без понятной границы ответственности или переносит сложность без удаления дублирования. Следующий шаг тогда состоит в уточнении поведения, а не в добавлении ещё одного слоя.
