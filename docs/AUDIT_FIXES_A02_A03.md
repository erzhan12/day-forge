## A02: завершение записи после смены страницы

Раньше mutation owner принадлежал одному экземпляру страницы. При переходе A → B → A новый GET мог вернуть старые данные до commit. Уничтоженный владелец правильно игнорировал свой поздний ответ, но новый владелец не узнавал об изменении.

Добавлен [scheduleWriteCoordinator.ts](../frontend/src/composables/scheduleWriteCoordinator.ts). Он предоставляется через Vue injection в корневом `FocusIndicatorHost` и переживает смену Inertia-страниц. Это состояние одного экземпляра приложения, без module-global хранилища, localStorage или нового серверного журнала.

Координатор хранит для аккаунта и даты pending-записи, минимальную подтверждённую revision, признак неопределённого результата и дополнительные поля для reload. Он не хранит названия или снимки блоков. [useScheduleRevision](../frontend/src/composables/useScheduleRevision.ts) регистрирует запись до отправки и завершает её ticket после обработки ответа.

Повторно открытый день блокирует редактирование до завершения прежнего запроса. Если GET уже содержит достаточную revision и результат определён, этот снимок принимается. Иначе обновляется только текущий совпадающий аккаунт и день. Успех на A не вызывает reload страницы B. POST автоматически не повторяется.

Подтверждённая revision сохраняется в координаторе до очистки сессии. Это защищает и обратный порядок: POST завершился, пока прежняя страница ещё открыта, а старый GET навигации создал новую страницу позже. При неопределённом результате нужен успешный reload; definite 4xx отказ позволяет использовать прежний снимок. Ошибка reload или ответ ниже подтверждённой revision оставляют запись заблокированной.

Новые props не снимают блокировку раньше `onFinish` самой синхронизации. Иначе watcher мог начать следующую запись, а поздний callback прежнего reload вернуть phase в `idle`. Этот порядок закреплён тестом, который пытается записать между обновлением props и `onFinish`.

Для Analytics сохраняются поля `review` и `streak`, чтобы возврат после mark-reviewed обновлял показатели вместе с расписанием. Login, явный session reset и смена пользователя очищают записи координатора. Старые tickets не возвращают их после очистки. Уничтоженный owner не читает изменившийся scope и не может очистить координатор нового аккаунта.

Регрессии находятся в [useScheduleRevision.test.ts](../frontend/tests/useScheduleRevision.test.ts) и [FocusIndicatorHost.test.ts](../frontend/tests/FocusIndicatorHost.test.ts). Fixture действительно размонтирует и создаёт новый page owner под сохранённым root provider. Это компонентная проверка lifecycle, не запуск настоящей Inertia-навигации в браузере.

Координатор действует в текущем приложении. Он не заменяет cross-tab sync или durable request identity. При потере сетевого ответа GET сверяет доступное серверное состояние; он не доказывает, что ещё работающий серверный обработчик уже прекратил работу. Эти ограничения сохраняют значение для отдельного проекта request identity из R11.

## A03: чтение существующего дня без SQLite writer reservation

[schedule_view](../backend/schedules/views.py) сначала пытается получить готовый день в read transaction. В одном снимке читаются и сериализуются Schedule, упорядоченные TimeBlock, каталог категорий, настройки дня, UI preferences и наличие подходящего шаблона. Существующий полностью подготовленный день не вызывает `UPDATE User` и не требует SQLite writer reservation.

На SQLite транзакция сохраняет read snapshot. На PostgreSQL `SELECT FOR UPDATE` пользователя сохраняет порядок относительно поддерживаемых policy/schedule writers. PostgreSQL-путь проверен чтением кода; живой PostgreSQL в этой задаче не запускался. Lazy integration bootstrap остаётся отдельной загрузкой, он не объявляется частью снимка расписания.

Если дня или обязательных first-use строк ещё нет, они создаются под существующим `run_user_maintenance`. Снимок для ответа и флаг `created` захватываются до освобождения User lock. Два одновременных первых посещения создают один день; только запрос, создавший Schedule, получает one-shot auto-draft signal. Создание недостающих настроек для старого дня этот сигнал не включает.

Исчерпанная write-блокировка и SQLite `locked`/`busy`, возникшие внутри view, дают HTTP 503 с `Retry-After: 1` и текстом `Schedule temporarily unavailable. Please try again.` Другие ошибки БД продолжают подниматься как ошибки, не скрываются за этим ответом. Контроль не распространяется на ошибку auth/session middleware до входа во view.

Шесть новых регрессий в [test_schedule_mutations_sqlite.py](../backend/tests/test_schedule_mutations_sqlite.py) используют копии тестовой SQLite БД и независимые соединения:

- Существующий день читается при чужом `BEGIN IMMEDIATE`.
- В WAL-режиме другой connection завершает commit между чтением Schedule и TimeBlock; ответ сохраняет прежние revision и блоки согласованно.
- Два first visits получают один Schedule и один auto-draft signal.
- Заблокированное создание возвращает 503 без частично созданного дня.
- Старый день с недостающими policies получает настройки без auto-draft.
- Блокировка такого bootstrap возвращает 503 и сохраняет прежний день.

Новых моделей и миграций нет. Рабочая БД не менялась в ходе этой задачи. Запись и revision validation продолжают использовать прежний общий executor.

### Основные сценарии через HTTP

Runner `/tmp/day_forge_http_smoke_a02_a03.py` использует `Django Client(enforce_csrf_checks=True)`, новую временную SQLite БД и синтетического пользователя. Пройдены 32 проверки: login и CSRF, Schedule и Settings, категория, ручное создание/редактирование/reorder/удаление, stale 409, переход на другой день и обратно, импорт, completion, chat, Undo, notes, review, удаление категории, восстановление устаревшего обзора, шаблон, draft и logout.

В этот же сценарий включён чужой SQLite writer: существующий Schedule возвращает 200 с прежним снимком, новый день возвращает 503 без создания строки, после освобождения writer его повторное открытие возвращает 200.

Chat и draft проходят реальный application service/apply path с двумя фиксированными ответами SDK. Состав отправляемых SDK messages и сохранение защиты импортированного названия проверены. Реальных provider-запросов не было; эти проверки не измеряют качество или доступность модели.

Логи полных проверок и HTTP runner находятся в `/tmp/day-forge-a02-a03/`. Runner и временные БД не входят в постоянный suite и могут исчезнуть при очистке временных файлов.

### Ограничение браузера

В предыдущем запуске встроенный браузер отклонил открытие `http://localhost:5173/accounts/login/` по политике безопасности URL. Ответ запретил обход через другие браузерные поверхности, raw CDP или косвенные команды. Сведений об изменении этой политики нет; повторный обход не выполнялся.

Основные сценарии в браузере, реальные Back/Forward, визуальное состояние при задержанном POST и мобильная ширина остаются непроверенными. HTTP и Vue lifecycle tests не считаются browser smoke. Для закрытия этого ограничения нужен разрешённый браузерный сеанс.
