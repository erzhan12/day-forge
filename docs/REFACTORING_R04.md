# R04: транзакции и версия расписания

`Schedule.revision` обозначает версию блоков и статуса дня. Миграция `0008_schedule_revision` добавляет поле со значением 0 для существующих дней. Последующие изменения увеличивают его один раз на операцию. Изменение заметки обзора не меняет revision.

## Пути записи

| Путь | Защита |
|---|---|
| Ручное создание, импорт события | `execute_schedule_mutation`, создание дня внутри транзакции, проверка пересечений и текущих настроек |
| PATCH и DELETE блока | Проверка владельца, expected_revision, блоки и статус в одной транзакции |
| Reorder | Проверка полной кандидатной раскладки под общей блокировкой |
| Restore / Undo | Проверка expected_revision, восстановление целиком; одинаковый набор полей сохраняет ID и revision |
| AI chat | Revision и снимок правил, категорий, окна дня и timezone проверяются после ответа провайдера |
| AI draft | Revision, контекст шаблона/правил/настроек и пустота дня проверяются внутри транзакции применения |
| Mark reviewed | Изменение статуса и review атомарны; повтор REVIEWED возвращает сохранённый результат до разбора JSON |
| Удаление категории | Общая блокировка пользователя, обработка затронутых дней в порядке ID, bump каждого изменённого дня |
| Django admin | Расписания, блоки и AI-политики доступны для просмотра. Прямая запись, обходящая контракт, отключена |
| Seed/reset/cleanup | Явный maintenance-исполнитель под теми же блокировками; очистка сохраняет строку дня и монотонность revision |
| Настройки, правила, шаблоны, каталог категорий | Общая блокировка User согласует изменения политик с проверкой AI-контекста |

Обычный ORM остаётся доступен для создания тестовых fixtures и миграций. Новый поддерживаемый writer приложения должен проходить через исполнитель; прямые `save`, `update`, `delete` и bulk-операции над расписанием вне этой границы не являются допустимым путём записи.

## Исполнитель

`execute_schedule_mutation` принимает ожидаемую версию и callback с заблокированным расписанием и блоками. Порядок блокировок: User, Schedule, TimeBlock. Для нескольких дней используется стабильный порядок ID.

Первая SQL-операция транзакции резервирует запись пользователя. Затем условный UPDATE проверяет revision, до чтения изменяемого состояния. Это позволяет SQLite сериализовать writers без попытки повысить устаревший read snapshot до write lock. На PostgreSQL тот же порядок удерживает блокировки строк.

Исполнитель сравнивает состояние до и после callback, увеличивает revision только при изменении блоков или статуса и собирает ответ до commit. В ответе находятся `schedule`, `blocks` и `revision` одной операции. Последующая запись другого запроса не может изменить уже собранный snapshot.

Исключения и error responses откатывают всю операцию. SQLite busy/locked допускает до трёх попыток всей транзакции. Callback не должен обращаться к провайдеру или создавать внешние побочные эффекты, которые нельзя откатить. После исчерпания попыток клиент получает контролируемый конфликт.

## HTTP и интерфейс

Ручные операции, AI chat/draft и завершение обзора передают `expected_revision`. Отсутствующая, некорректная или устаревшая версия возвращает 409 с `code: schedule_changed` и сообщением в `errors.detail`. Сервер не подставляет актуальную revision за старую вкладку.

Frontend хранит версию в контексте текущей страницы и даты. Ответ другой даты не обновляет этот контекст. Конфликт не запускает повтор записи с новой версией: интерфейс обновляет данные и сообщает об отказе. Completion toggle также прекращает автоматические повторы при 409.

До получения соответствующих обновлённых props после успешной записи новая мутация блокируется. Это исключает отправку новой revision со старым набором блоков. Полный перенос UI на единый локальный snapshot и дальнейшая защита истории Undo остаются задачей R05.

## Развёртывание

1. Остановить все старые backend workers, которые не увеличивают revision.
2. Сделать резервную копию БД и применить миграцию.
3. Развернуть согласованные backend и frontend, затем запустить workers.
4. Старая открытая вкладка получит контролируемый отказ и должна обновиться. Не включать совместимый режим записи без revision.

Обратная миграция удаляет поле версии. Для отката нужны остановленные writers и согласованный предыдущий релиз. Миграция вперёд не меняет существующие блоки, обзоры и AI-аудит.

## Проверки

Результаты полного прогона и браузерных сценариев записаны в разделе R04 файла `REFACTORING_PLAN.md`. Отдельные тесты используют обычный Django Client без автоматической подстановки revision. Существующие доменные тесты используют `RevisionClient`, который моделирует предварительную загрузку актуального дня; он существует только в тестах.

Конкурентные тесты открывают независимые SQLite-соединения на отдельной копии БД: два изменения с одной версией, DELETE против PATCH, создание против draft на пустом дне, удаление категории против редактирования и исчерпание retry при удерживаемой write-блокировке. Миграционный тест сверяет содержимое старых таблиц, включая review и AI-аудит.
