# 0035 — Fix overnight external calendar events fading as "past" while still running

## Context

Pre-existing frontend correctness bug surfaced during the feature 0026 review
(tracked in `tasks/todo.md` § Follow-ups, "External calendar"):

> Overnight external events fade as 'past' while still running. `frontend/src/utils/externalEventPast.ts` compares only the *clock* minutes of `ev.end` against `nowMinutes`, with no day-delta fold. An event running `23:00 -> 00:30 (+1 day)` has an end whose local wall-clock is `00:30` = 30 minutes, which is <= any daytime `nowMinutes`, so it renders faded/past even though it is still in progress.

### Verified root cause (confirmed against current code)

`frontend/src/utils/externalEventPast.ts`:

- `isoToLocalMinutes(iso)` (lines 4-7) returns `new Date(iso).getHours() * 60 + new Date(iso).getMinutes()` — LOCAL minutes-since-midnight, **dropping the calendar date**.
- `isExternalEventPast(ev, viewedDate, today, nowMinutes)` (lines 16-27), for the today case (`viewedDate === today`, non-all-day, `nowMinutes !== null`), returns `isoToLocalMinutes(ev.end) <= nowMinutes` (line 26).
- For an event whose `end` is on the NEXT local calendar day, `isoToLocalMinutes(ev.end)` collapses to a small value (e.g. `30` for `00:30`) and compares `<=` a daytime `nowMinutes`, so the still-running overnight event is wrongly marked past.

### Verified contract / inputs

- `NormalizedEvent` (`frontend/src/types/calendar.ts`, lines 6-14): `title`, `start: string`, `end: string` (ISO8601), `calendar_name`, `all_day: boolean`, `external_uid`, `account_label`. No type change is being made.
- Caller `frontend/src/components/ExternalEventsPanel.vue` (`eventIsPast`, lines 44-51) calls `isExternalEventPast(ev, viewedDate.value, today.value, props.nowMinutes)` where:
  - `viewedDate` = the schedule date (`YYYY-MM-DD`), from `toRef(props, "date")` defaulting to `todayString()`.
  - `today` = `computed(() => todayString())` — LOCAL today, `YYYY-MM-DD`.
  - `nowMinutes` = minutes since LOCAL midnight of today (`number | null`; `null` off-today or before the first tick; default prop `null`).
- Existing semantics interpret each ISO instant via its LOCAL wall-clock (`new Date(iso).getHours()...`). The test fixtures in `frontend/tests/externalEventPast.test.ts` use NAIVE ISO strings (no `Z`), which `new Date` parses as local. This local-clock interpretation MUST be preserved — do NOT switch to UTC-absolute comparison, which would change behavior for the existing naive-ISO tests and (differently) for `Z`-suffixed wire data.

## Files to change

1. `frontend/src/utils/externalEventPast.ts` — production fix (fold the day delta into the end-minutes before comparing).
2. `frontend/tests/externalEventPast.test.ts` — extend with the overnight regression cases (failing test authored FIRST).

No backend, no API, no type change. Frontend-only.

## Algorithm — the fix

The only branch that changes is the today/timed/`nowMinutes !== null` branch. All
other branches (`viewedDate < today` → true; `viewedDate > today` → false;
`ev.all_day` → false; `nowMinutes === null` → false) stay **exactly as they are**.

### Fold the day delta into end-minutes

Replace the final `return isoToLocalMinutes(ev.end) <= nowMinutes` with a comparison
that folds a whole-day offset onto the end-minutes:

```
foldedEndMinutes = dayDelta * 1440 + isoToLocalMinutes(ev.end)
return foldedEndMinutes <= nowMinutes
```

where `dayDelta` is the integer number of LOCAL calendar days from `today` to the
LOCAL calendar date of `ev.end`:

- `ev.end` on the same local day as `today` → `dayDelta === 0` → behaves exactly like today (unchanged for the existing tests).
- `ev.end` on a LATER local day (the overnight case, e.g. `23:00 -> 00:30 +1d`) → `dayDelta >= 1` → `foldedEndMinutes >= 1440 + 30`, which exceeds any same-day `nowMinutes` (`0..1439`) → returns `false` (correct: still running).
- `ev.end` on a PRIOR local day (`dayDelta <= -1`, e.g. a stale/misordered row whose end precedes today) → `foldedEndMinutes <= -1440 + …` which is `< 0 <= nowMinutes` → returns `true` (correct: past).

`nowMinutes` is always minutes-since-local-midnight-**of-today** (`0..1439`), and the
panel only fades on the today view, so anchoring the fold to `today` (not to
`ev.start`'s date) is correct: `dayDelta === 0` is "today", the reference frame
`nowMinutes` lives in.

### `dayDelta` — DST-safe integer day difference (specify precisely)

Do NOT compute `dayDelta` with a naive `(msEnd - msToday) / 86400000` on the raw
instants and floor/round — that can be off by one across a DST boundary because a
civil day spanning a spring-forward/fall-back transition is 23h or 25h long.

Instead, anchor BOTH dates to LOCAL midnight and then divide+round:

1. Parse `today` (`YYYY-MM-DD`) into its numeric year/month/day. The string is already
   a local calendar date, so split on `-` and build `todayMidnight = new Date(y, m - 1, d)`
   (JS `Date(y, monthIndex, day)` constructs a LOCAL-midnight instant; month is
   0-based).
2. Parse `ev.end` into a `Date` (`endDate = new Date(ev.end)`), then build
   `endMidnight = new Date(endDate.getFullYear(), endDate.getMonth(), endDate.getDate())`
   — LOCAL midnight of `ev.end`'s local calendar day. Use the `getFullYear`/`getMonth`/
   `getDate` accessors (local), matching the existing local-clock interpretation.
3. `dayDelta = Math.round((endMidnight.getTime() - todayMidnight.getTime()) / 86400000)`.

Because both operands are local-midnight instants, their ms difference is
`N * 86400000 ± (DST offset in ms)` where the DST term is at most ±1h — far below the
0.5-day rounding threshold — so `Math.round` yields the exact integer civil-day delta
even across a DST transition. This is the DST-safe anchoring the implementer must not
regress into a raw-instant subtraction.

**Mandate: use `Math.round`, not `Math.floor` / `Math.trunc`.** On a fall-back
(25h) civil day the anchored difference is `N*86400000 + 3600000`; `Math.floor` →
`N` (ok) but on a spring-forward (23h) day it is `N*86400000 - 3600000`, where
`Math.floor` → `N-1` (WRONG). Only `Math.round` is correct in both directions. This is
the load-bearing reason for the rounding choice.

**Testability limitation (accepted, by-construction guarantee).** The existing suite
uses **naive ISO** fixtures (no `Z`) precisely so every instant parses to the same
local wall-clock in any runner timezone — the suite is deliberately TZ-independent and
there is **no** vitest TZ pinning (`vitest run`, no config). A naive same-TZ test
therefore cannot exercise a real DST transition: without a spring/fall boundary,
local-midnight differences are always exact `86400000` multiples, so `Math.floor` and
`Math.round` are indistinguishable and a `Math.floor` regression would still go green.
Verifying the round-vs-floor distinction would require pinning `TZ` (e.g.
`America/New_York`) and a DST-boundary fixture — **out of scope** for this cosmetic
fade fix, and it would break the suite's TZ-independence. The DST-safety is guaranteed
**by construction** (local-midnight anchoring + `Math.round`, argued above), documented
here as a bounded decision rather than pinned by a unit test. The implementer must not
substitute `Math.floor`/`Math.trunc` on the strength of "the tests still pass".

### Keep `isoToLocalMinutes` as-is

`isoToLocalMinutes(ev.end)` still returns the LOCAL minutes-since-midnight of the end
instant (`0..1439`); the fold adds the whole-day offset on top. Do NOT touch its body.

### Do NOT add `ev.start` logic

The past test keys off `end` only. `ev.start` is not used by `isExternalEventPast`
and there is no justification to introduce start-based logic. Leave `ev.start` out of
this function.

## Representable "now" states (enumerate for test design)

`nowMinutes` is minutes-since-LOCAL-midnight-**of-today** and is only ever non-null on
the today view. Therefore, within the today/timed branch, the representable states are:

- `nowMinutes ∈ [0, 1439]` on the current local day (today).
- There is **no** representable "now is 01:00 on the day AFTER an overnight event
  ended" state through this function. Concretely, the reachable ended-overnight case is
  the event's own end-morning: an event `Apr-06 23:00 -> Apr-07 00:30` viewed on
  `today = Apr-07` with `nowMinutes` past 00:30 has its `end` on **today** (`dayDelta ===
  0`), so it is arithmetically identical to the existing same-day `ended-before-now`
  test and needs no new fixture. A strictly-prior-day `end` (`dayDelta < 0`) arises in
  two distinct call shapes, which must not be conflated:
  - **Whole viewed date is in the past** (`viewedDate < today`): the function returns
    `true` at the very top and the fold is never reached. This is the normal past-day
    panel and is already covered by the existing `past-date all-past` test.
  - **Viewing today, but an event's `end` sits on a prior local day** (`viewedDate ===
    today`, so neither top guard fires and the fold IS reached, with `dayDelta < 0`):
    the panel does not produce this in normal flow (a today-view event list would not
    contain an event that already ended on an earlier calendar day), so it is a
    defensive edge — but it *does* execute the fold, so the negative-`dayDelta` path
    must still return `true`. **This is exactly Slice 3.1's shape** (`viewedDate ===
    today` with a `05-06` end), which is why that test is the guard for this path.
  So the negative-`dayDelta` fold is a defensive guard for a non-primary input, not a
  user-facing state — but it is genuinely exercised by Slice 3.1, not dead code.

Consequences for the new tests:

- The overnight **still-running** case (`today 23:00 -> tomorrow 00:30`, daytime or
  late-evening `nowMinutes`) must assert `false`. This is the bug reproduction.
- A **prior-day end** case (`end` on yesterday, `dayDelta === -1`) must assert `true`
  (symmetric edge — negative delta stays past). This guards the fold's sign handling.
- No "next-day 01:00 now" fixture is authored, because that now-state is not
  representable through this function (documented above); attempting it would
  mis-model the contract.

### Known limitation — stale `today` across a live midnight rollover (pre-existing, deferred)

`ExternalEventsPanel.vue` derives `today` as `const today = computed(() => todayString())`
(≈ line 42). `todayString()` reads `new Date()` and is **not** reactive, so the `computed`
has zero reactive dependencies and is evaluated once at mount and cached — it never
recomputes. If the panel stays mounted across local midnight, `today` remains yesterday's
date until a remount or date navigation. This is **pre-existing**: the current code already
feeds that frozen `today` into the `viewedDate </>/=== today` string comparisons, and this
fold merely adds one more consumer (the `dayDelta` arithmetic) of the same value. It does
**not** worsen the reported bug — the user-facing symptom ("overnight event fades as past
**while still running**", same-day, mid-run) is fully fixed by the fold because `today` is
correct for the whole day the panel was mounted. The *inverse* rollover case (an event that
genuinely ended overnight staying un-faded after midnight until navigation) is a distinct,
broader panel-reactivity defect affecting all of the panel's today-relative rendering, not
just overnight events.

**Deliberately deferred, not fixed here.** A proper fix plumbs the fresh
`useNowMinutes().nowDate` (which the Schedule parent already tracks and updates at rollover,
but does **not** currently pass to the panel) into `ExternalEventsPanel` as a prop and
derives `today` reactively from it (e.g. `props.nowDate ?? todayString()`), plus a
rollover-coverage test. That touches the panel props + the parent wiring — outside this
plan's `externalEventPast.ts`-scoped fold. Tracked as a follow-up in `tasks/todo.md`
§ Follow-ups ("ExternalEventsPanel `today` computed is non-reactive — stale across live
midnight rollover"). Surfaced by codex during ext-plan-review of this plan.
