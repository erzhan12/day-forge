# 0032 — Block checkbox: keep UI/server in sync on failed completion toggle (issue #104)

## Context

On the Schedule page, toggling a `TimeBlock`'s completion checkbox can show
"Failed to update" while the checkbox stays visually flipped — UI and server
diverge. Root cause: `frontend/src/components/TimeBlock.vue` `toggleCompleted()`
(lines 135–157) fires one `updateBlock(id, {is_completed: !props.block.is_completed})`;
on failure it sets `errorMessage = "Failed to update"` and does **not** revert.
The checkbox is a native `<input type="checkbox">` bound `:checked="block.is_completed"`
with `@change="toggleCompleted"`, rendered in **two** branches — timeline/expanded
view (lines 237–242) and compact/list view (lines 201–206), both binding the same
way. The browser flips the native control on click; when the prop `block.is_completed`
does **not** change (no reload on failure), Vue does not re-apply `:checked`, so the
DOM stays flipped while the reactive source is stale.
`useSchedule.updateBlock` → `apiFetch` (`frontend/src/composables/useSchedule.ts`
lines 7–17, 44–49) only calls `router.reload({only:["blocks","schedule"]})` on
success, so a failure leaves props stale and the native control desynced.

This change scopes an **optimistic + retry-with-backoff + cancel-and-restart**
mechanism to the completion toggle path only. No API contract change, no shared
retry util, no offline queue.

## Desired behaviour (from ticket)

| Situation | UI | Persistence |
| --- | --- | --- |
| Toggle clicked | Checkbox flips immediately (optimistic) | PATCH starts |
| Transient failure | Stay flipped; silent background retries | Retry with backoff |
| All retries exhausted | Revert checkbox to last known server value; show clear error | Stop |
| Success (any attempt) | Keep flipped; clear any pending error | Done (reload) |

## Binding decisions (from user interview)

1. **Retry cadence — pinned exactly:** **4 attempts total** (1 initial + 3 retries).
   Backoff **waits between attempts** are `[300, 1000, 3000]` ms — i.e. attempt 1
   immediate; on `{ok:false}` wait 300 ms → attempt 2; wait 1000 ms → attempt 3;
   wait 3000 ms → attempt 4. **No wait after attempt 4** (it is the last attempt;
   its failure triggers revert). The ticket's trailing "/6s" is NOT used — do not
   add a 5th attempt. Define these as named constants (e.g.
   `TOGGLE_RETRY_DELAYS_MS = [300, 1000, 3000]`, so `attempts = delays.length + 1 = 4`).
2. **Transient set — ALL failures retry.** Do NOT special-case 4xx vs 5xx. Every
   `{ok:false}` result triggers the retry chain: a network error (no `status`) OR
   any HTTP non-2xx including 4xx. **Accepted tradeoff (document in code comment):**
   a genuine validation 4xx now takes the full backoff duration
   (300+1000+3000 = 4.3 s) before the error surfaces. Simplicity per user's explicit
   choice.
3. **Rapid re-toggle — cancel-and-restart with the latest desired value.** A new
   click while a chain is in flight ABORTS the in-flight chain and starts a fresh
   chain targeting the newest desired `is_completed`. The displayed checkbox always
   reflects the last click. Implement via an incrementing **generation counter**:
   each new toggle bumps a module-local (component-instance) `generation` ref; a
   running chain captures its generation at start and, after every `await` (the
   PATCH and each backoff sleep), checks `if (myGen !== generation.value) return`
   to bail out silently without touching state. This supersedes any in-flight chain.
4. **Visual feedback — subtle muted / "saving…" state.** Flip optimistically
   immediately; apply a `saving` class to the checkbox (and/or block) while a chain
   is in flight; clear on success; revert on final failure.
5. **Scope — checkbox completion toggle ONLY.** Do NOT touch `saveTitle`/edit or
   `handleDelete`/delete flows. Do NOT extract a shared retry util — keep the logic
   inline in the toggle path in `TimeBlock.vue`.
6. **Success sync — keep the existing `router.reload({only:["blocks","schedule"]})`.**
   The optimistic local value already matches the confirmed server value, so the
   reload produces no visible flash. Do NOT switch to local-only patching that drops
   the reload.

## Design: driving the displayed checked state

Because the checkbox is bound to a **prop** (`:checked="block.is_completed"`), the
optimistic flip needs a **local reactive override** in `TimeBlock.vue`.

- Add a local ref `displayedCompleted = ref(props.block.is_completed)` as the single
  source of truth for the **displayed** checked state. Both checkbox branches bind
  `:checked="displayedCompleted"` instead of `:checked="block.is_completed"`
  (timeline line 239 and compact line 203). The two `title-completed` /
  `completed` visual bindings that reflect completion (block `completed` class at
  line 186, `.title-completed` at lines 221 and 255) should also read
  `displayedCompleted` so the strike-through/opacity match the optimistic state
  during the chain — verify all four sites and switch each from
  `block.is_completed` to `displayedCompleted`.
- **Re-sync on prop change after reload:** `watch(() => props.block.is_completed, (v) => { displayedCompleted.value = v })`.
  When a chain succeeds and `router.reload` refreshes `blocks`, the prop updates and
  the watcher re-aligns `displayedCompleted` with the confirmed server value (no-op
  visually since they already match). On final failure, revert is done explicitly
  (see algorithm) — the watcher does NOT fire on revert because the prop never
  changed, so the revert must set `displayedCompleted.value` back manually.
  - **Implementation divergence (shipped):** the watcher is **`saving`-guarded**
    (`if (!saving.value) displayedCompleted.value = v`). While a local chain is in
    flight the optimistic value must win, or an *older* chain's late reload would
    clobber a *newer* click. This replaces the "accepted transient" reasoning at
    §7's sub-bullet below — the transient is now actively prevented, not tolerated.
    A **second** watcher on `props.block.id` handles index-keyed row reuse
    (`Schedule.vue :key="idx"`): on id change it aborts the in-flight chain, bumps
    `generation`, and re-aligns `displayedCompleted`/`saving`/`errorMessage` to the
    new block so a reused instance never shows the old chain's state.
- **Native-control desync guard:** setting `displayedCompleted` back to the prop
  value on revert re-applies `:checked` because the bound value actually changes
  (flipped → original), so Vue re-renders the native control — this is the fix for
  the "DOM stays flipped" bug. No template ref / manual `.checked` manipulation is
  required as long as the displayed value genuinely toggles on revert. (If a future
  edge case shows Vue skipping the DOM update because the reactive value round-trips
  to its pre-optimistic value within one tick, add a `titleInput`-style template ref
  to each checkbox and force `el.checked = displayedCompleted.value` in
  `nextTick()` after revert — note this as a fallback, not the default.)

## Algorithm — `toggleCompleted()` rewrite

State added to `<script setup>` in `TimeBlock.vue`:
- `displayedCompleted = ref(props.block.is_completed)` — displayed checked state.
- `saving = ref(false)` — drives the muted/"saving…" class.
- `generation = ref(0)` — cancel-and-restart epoch counter.
- `const TOGGLE_RETRY_DELAYS_MS = [300, 1000, 3000]` — module/const scope.

`toggleCompleted()` steps (replaces lines 135–157):

1. `if (isDisabled()) return`.
2. Compute `const desired = !displayedCompleted.value` (base the flip on the
   **displayed** value, not the prop — a rapid re-toggle mid-chain must flip
   relative to what the user currently sees).
3. **Optimistic flip:** `displayedCompleted.value = desired`.
4. **Supersede any in-flight chain:** `const myGen = ++generation.value` (the bump
   invalidates the previous chain; capture the new epoch).
5. `errorMessage.value = ""`; `saving.value = true`.
6. Capture `const snapshot = undo?.snapshotBlocks()` and
   `const scheduleDate = props.date` **at chain start** (preserves issue #21 date
   binding — bind to the date active when the request started).
7. Capture the last-known server value for revert:
   `const serverValue = props.block.is_completed` — captured at chain start; the
   prop is only updated by a successful `router.reload`, so this is the correct
   "last confirmed server value" for the revert target.
   - **Superseded-chain reload vs live watcher (~~accepted transient~~ — now guarded, see Design note above):** a superseded
     chain A whose attempt already succeeded fired `router.reload` before bailing at
     the guard (step 8b). When that reload lands mid-live-chain B, the prop
     `props.block.is_completed` changes and the `watch` (step below / § Design)
     re-aligns `displayedCompleted` to the newly-loaded server value. Because A only
     ever PATCHed A's own `desired` and B is a genuine re-toggle *back*, the reloaded
     server value equals A's `desired`, which is the opposite of B's optimistic
     value — so the watcher could momentarily move `displayedCompleted` off B's
     optimistic flip. This is an **accepted sub-frame transient**, not a clobber: B's
     own confirmed success then fires its own `router.reload` (or, on B's failure, B
     reverts to *its* captured `serverValue`), and B's next await-guard/optimistic
     value re-establishes the correct displayed state. The window is one reactivity
     tick and the terminal state is always B's, never A's. No extra guard needed.
8. Loop `for (let attempt = 0; attempt < TOGGLE_RETRY_DELAYS_MS.length + 1; attempt++)`:
   a. `const result = await updateBlock(props.block.id, { is_completed: desired })`.
   b. **Stale-guard after await:** `if (myGen !== generation.value) return` — a
      newer toggle superseded this chain; bail silently, do NOT touch `saving`,
      `errorMessage`, `displayedCompleted`, or push undo (the newer chain owns all
      state). `updateBlock` on success already triggered `router.reload`; that is
      acceptable (idempotent refresh) — the superseding chain will reload again.
   c. If `result.ok`:
      - Push undo **only on confirmed success**: if `undo && snapshot`, compute the
        action label from `serverValue` (`serverValue ? "Unchecked" : "Checked"` —
        note: derive from the pre-toggle server value, matching the current
        `props.block.is_completed`-based label at lines 145–146) and
        `undo.pushUndo({ description, type: "toggle", previousBlocks: snapshot, scheduleDate, silent: true })`.
      - `errorMessage.value = ""`; `saving.value = false`.
      - `return`. (`updateBlock` already fired `router.reload`; the prop will
        refresh and the watcher re-aligns `displayedCompleted` — no flash.)
   d. If `!result.ok` and this is **not** the last attempt
      (`attempt < TOGGLE_RETRY_DELAYS_MS.length`): `await sleep(TOGGLE_RETRY_DELAYS_MS[attempt])`,
      then re-check the stale-guard `if (myGen !== generation.value) return`, then
      continue the loop (silent — no error shown mid-chain).
   e. If `!result.ok` and this **is** the last attempt: fall through past the loop.
9. **All retries exhausted (loop completed without success):**
   - Re-check stale-guard once more: `if (myGen !== generation.value) return`.
   - **Revert:** `displayedCompleted.value = props.block.is_completed` (re-applies
     `:checked` to the native control — the desync fix). *Implementation note:* the
     revert reads the **live prop**, not a `serverValue` captured at chain start, so a
     `router.reload` that landed mid-chain (e.g. a superseded concurrent write) is
     picked up instead of clobbered. The undo **label** derives from `desired` (the
     value this chain writes), not the prop, so a rapid re-toggle can't mislabel it.
   - `saving.value = false`.
   - `errorMessage.value = "Failed to update"` (keep the existing copy so the
     `.block-error` div at line 262 and existing test string still match; the
     `error shown once` requirement is satisfied because only the final failing
     chain reaches here and superseded chains bail at the guard).

`sleep` helper: a small inline
`const sleep = (ms: number) => new Promise((r) => setTimeout(r, ms))` in
`<script setup>` (not exported, not shared).

### Preserved invariants
- `undo.pushUndo({... type:"toggle", silent:true})` fires **only after a confirmed
  success** (step 8c) — never optimistically, never on a superseded chain.
- Issue #21 date binding: `scheduleDate`/`snapshot` captured at chain start (step 6).
- `router.reload` on success stays in `useSchedule.apiFetch` — untouched.
- Title-edit and delete flows in `TimeBlock.vue` are untouched.
