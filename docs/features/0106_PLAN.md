# 0106 — Dark 4a UI fixes: stack timeline, controls, calendar card, empty day

Fix the current Day Forge UI in the existing **Dark 4a** theme against the Design Mentor spec (`SPEC.md`, Russian, updated version) and its independent review (`spec-opinion.md`). No new theme and no product rewrite. Research was done on `origin/main` at `4e29a2b`, which is also the deployed build (`<meta name="frontend-version">` on the live login page).

Owner decisions (final):

1. Work only inside Dark 4a. Spec colours and sizes were sampled from "before" screenshots, so every value is mapped to a real token below. Classic, Strategic and Light Premium must not regress.
2. New UI strings are English, matching the current UI: `Free · 2h 50m`, `Log out`, `No template for Sunday`, `Add to schedule`.
3. **Hard constraint:** calendar events are NOT rendered on the schedule timeline automatically. An event enters the day only through the explicit "Add to schedule" action. Free-gap computation keeps ignoring non-added events.

Facts that shape the plan:

- There is no Tailwind. Styling is scoped SFC CSS plus one token vocabulary in `frontend/src/app.css` (`:root` `:24`, `classic` `:95`, `strategic` `:144`, `light_premium` `:206`, `dark_4a` `:251–307`).
- `layoutForTheme` (`frontend/src/utils/layoutProfile.ts:5–7`) returns `"4a"` only for `dark_4a`. `Timeline4a`, `TimeBlock4a`, `GapSlot4a`, `NowLine4a`, `ExternalRail4a` and `RailSection` mount only there. `TimeBlock.vue`, `GapSlot.vue`, `AddBlockForm.vue`, `DateNavigator.vue`, `CommandBar.vue`, `ExternalEventsPanel.vue` and every Settings panel are shared by all themes.
- Contrast figures below are computed from source values with the WCAG formula.

## Guarantees

**Other themes do not regress.**

1. Token edits touch only the `dark_4a` block. The two new tokens are defined only there and read only by Dark 4a-prefixed rules.
2. All shared control styling goes into one new section of `app.css`, the **Dark 4a control skin**, in which every selector starts with `html[data-theme="dark_4a"]`. The class names are inert in other themes. Skin selectors must out-specify the scoped rules they override (for example `.show-indicator-btn:hover:not(:disabled)`).
3. Scoped SFC rules for shared components are written as `html[data-theme="dark_4a"] .x` (the scoping attribute lands on the last compound). `:global(html[…]) .x` is banned; it caused A.9.
4. Structural changes ride existing 4a-only seams or new opt-in props whose defaults keep today's behaviour: the stack layout lives behind `layout === "4a"`; `GapSlot.vue` is not edited; `TimeBlock.vue` gets a `density` prop defaulting to `"full"`; `RegenerateDraftButton` gets `showReason` defaulting to `true`; `ExternalEventsPanel` changes copy only in the embedded (rail) branch and, through a new `layout` prop, in the Dark 4a centre variant; `TimeBlock.vue` gets an opt-in `tooltip` prop defaulting to `false`; the Log out move is gated on `dark_4a`.
5. There is no deliberate cross-theme change. Log out moves to Settings in Dark 4a only; the other themes keep today's Schedule footer and its styles (question 10).
6. Tests, written first in Phase 1:
   - `frontend/tests/dark4aScope.test.ts` (new): "leaves the :root, classic, strategic and light_premium token blocks unchanged" (pinned declaration maps); "defines --border-control and --control-on-bg only in the dark_4a block"; "prefixes every selector of the control skin section with html[data-theme=\"dark_4a\"]"; "no Vue file uses :global(html…) followed by a descendant selector" (static scan in the style of `accentContrast.test.ts`).
   - `frontend/tests/semanticContrast.test.ts` (extend): in `dark_4a`, `--text-secondary`, `--text-muted`, `--text-faint` ≥ 4.5 on `--bg-page`, `--bg-panel`, `--bg-input`; `--border-control` ≥ 3.0 on the same three; `--control-on-bg` ≥ 3.0 on `--bg-panel`; `--accent-contrast` ≥ 4.5 on `--control-on-bg` and on `--accent` (the helper parses only hex/rgb, so the accent is compared as the pinned sRGB `#fd7562` with a comment pointing at `app.css:269`).
   - `frontend/tests/dark4aTextFloor.test.ts` (new): the 4a-only SFCs contain no `font-size` or `font` shorthand below 13 px and no `color:` using `#6a6e75`. A static scan cannot see shared components, so the binding check is the browser sweep in `check-dark4a-day-fit.mjs` (Phase 8): on Schedule (wide and 390 px, rail open, a past event, the Todoist retry and calendar empty/error states stubbed) and on every Settings topic in Dark 4a, every visible text node has computed `font-size ≥ 13px`; contrast is asserted for the listed foreground/surface pairs (tokens, the darkest stop of each category gradient behind block text, `TimeBlock4a.vue:44–49`), not by generic paint analysis; overlays (`Schedule.vue:595–608`) are inspected manually; disabled controls are exempt.

### 1 + 3. One stack rule for the schedule column

**Today.** `computeRenderBounds` picks a linear axis `[renderStart, renderEnd]`. `buildBaseDisplayItems` emits blocks, gaps and inert spacers; only the two edge gaps carry `render_minutes = 30`. `createTimelinePresentation` places each item at `(start − axisOrigin) × 2` with height `renderedMinutes × 2`, hour ticks at `(minute − axisOrigin) × 2` (`useTimelinePresentation.ts:101–104`) and the now line the same way, with one special case for the leading stub (`:113–130`). Drag converts pixels to minutes linearly (`useDrag.ts`, `updatePreview`, `minute = axisOrigin + px / pxPerMinute`) and clamps at `axisOrigin`, so a block cannot be dragged earlier than 30 minutes before the first block in one gesture. Dragging moves a block and keeps its duration; there is no resize gesture.

**New pure module `frontend/src/utils/timelineStack.ts`.** `buildTimelineStack(items, pxPerMinute)` takes the unchanged output of `buildBaseDisplayItems`.

1. Walk the items in order with a running `y = 0`.
2. For each item, `raw = (render_minutes ?? duration_minutes) × pxPerMinute`.
3. Height: block → `max(raw, MIN_BLOCK_PX)`; gap or spacer → `min(semantic minutes × pxPerMinute, GAP_CAP_PX)`, where `GAP_CAP_PX = STUB_MINUTES × pxPerMinute` and semantic minutes is the final interval after trimming and coalescing. In stack mode `render_minutes` is ignored for gaps (it can be 0 for a corrected tail, `scheduleTime.ts:230–233`); edge stubs still come out at 60 px, so they are not collapsed a second time. Gaps shorter than 30 minutes stay on the scale (question 2).
4. Record a segment `{ kind, startMin, endMin, topPx: y, heightPx, compressed, stretched }`, then `y += heightPx`, where `compressed = heightPx < (endMin − startMin) × pxPerMinute` (true for capped mid-day gaps and for both edge stubs). A leading stub's segment spans its semantic range `[windowStart, firstStart)`.
5. Blocks are flagged `compact` when `heightPx < COMPACT_BELOW_PX`. At 2 px/min that is every block under 18 minutes, so a 15-minute block (30 px) is compact.

Outputs: positioned items (`topPx`, `heightPx`, `compact`, `compressed`), `segments`, `canvasHeightPx = y`, and the two mappings below.

Invariants (each is a test):

- `top[i + 1] === top[i] + height[i]`: no overlaps and no holes.
- Blocks ≥ 28 px; gaps ≤ 60 px.
- Height is non-decreasing in duration among blocks and among gaps. Across types, a gap of 14 minutes or more is never lower than a shorter block of at most 30 minutes. The 28 px floor and the 60 px cap take precedence over cross-type monotonicity outside that range (question 2).
- On an off-today day with no overlaps and no item clamped or compressed, the pixel geometry equals today's linear layout.

**Drift.** Each clamped item adds `heightPx − raw` (positive for a stretched block, negative for a capped gap) to everything below it. The next gap does not absorb a stretch.

**`timeToPx(minute)`.** Take the first segment in stack order with `startMin ≤ minute < endMin` and interpolate linearly inside it. Membership is resolved first; only a minute contained in no segment falls back: before the first segment start → 0, at or after the maximum semantic end of all segments (an enclosing legacy block can end after the last stacked segment) → `canvasHeightPx`.

**`pxToTime(px)`.** The inverse over the same segments. Both maps are total and finite: only `px` is clamped first (`px ≤ 0` → first segment start, `px ≥ canvasHeightPx` → maximum semantic end), so pointer overshoot under pointer capture never yields `NaN` and the window clamp, snap and cascade see a real minute.

**Hour labels.** One tick per full hour, at `timeToPx(hour)`, emitted when the hour lies inside a block, inside an uncompressed gap, or exactly on a segment start. Hours strictly inside a compressed segment (capped gap, edge stub) or a spacer are skipped, so the fixture's ticks are 05:00, 10:00, 12:00, 15:00 and 16:00, so labels never spread over collapsed hours; the gap row's own range text covers them. Inside a stretched block the tick is interpolated.

**Now indicator.** `nowLineTopPx = timeToPx(now)`. Inside a capped gap or a stretched block the line moves proportionally through the rendered height. This generalises today's leading-stub case for stack mode; linear mode keeps its branch. In stack mode `buildTimelineStack` first coalesces time-contiguous `type === "gap"` items (today's trailing split at "now" from `pushTrailingGap`, `scheduleTime.ts:206–221`) into one logical gap; inert spacers are never merged and never clickable. The merged gap's height is `min(full interval × pxPerMinute, 60)`, ignoring the split items' `render_minutes`; it keeps the "later" hint when it ends at the window end, and its `add-here` range is the merged in-window interval. One free interval is therefore never two 60 px rows and the canvas does not change height as the clock moves; linear layouts keep the split. `nowVisible` in stack mode: the selected date is today and some segment actually contains `now` (membership, not the last segment's end, which can precede an enclosing overlapping block's end), so a legacy out-of-window block keeps the line as in linear mode (today's same-date guard, `useTimelinePresentation.ts:113–122`, stays). When the now label's box would intersect an hour label, the hour label is hidden (the now label wins).

### 10. Education colour

Colours live in user rows, and Education is not a seeded category (A.12), so a seed fix cannot reach it. The spec asks for exactly this migration (SPEC.md §10: recolour only Education rows equal to Health). It writes theme-independent data, so Education changes in every theme; that is why the target is `amber` (`#D97706`, ≥ 3:1 on every theme panel) and not `#F59E0B`, which fails the light themes (question 4). It ships last, in its own PR, and runs only after the owner confirms question 4. Migration `backend/schedules/migrations/0012_education_color.py` (`RunPython`):

1. For each user, find the categories whose current label matches `health` and `education` under `Lower(Trim(label))`, the same normalisation as the per-user unique constraint (`backend/schedules/models.py:192–194`). Slugs are not used: they are frozen at creation (`backend/schedules/categories.py:152–153`) while labels can be renamed (`:154–164`).
2. Only when both exist and both have `color_id == "emerald"`, set Education to `amber`.
3. Touch nothing else: Health, other categories, other colours and users without the collision stay as they are.

The migration is irreversible: `RunPython` gets no reverse callback, so Django refuses to unapply it and an image rollback keeps it applied (a `noop` reverse would let it be unapplied and re-run); no predicate can tell migrated rows from pre-existing or later deliberate amber. Recovery: rehearse on a private copy first. Automated restore writes only the affected categories' `color_id` values from the pre-deploy backup (never a whole-database restore, `deployment/README.md:278–281`); the rehearsal checks that a post-backup schedule write survives; it is allowed only while category writes are provably paused from the backup through the restore; once writes have resumed, each affected row is reconciled with its owner, because `Category` keeps no edit history and a later deliberate amber cannot be told apart. `amber` exists in older images' palettes, so an image rollback tolerates the data. Running migrations needs explicit confirmation (`.claude/rules/code-style.md`). No palette or seed change. 

## D. Open questions (defaults apply if the owner says nothing)

1. **Dragging on the non-linear axis.** Default: freeze the piecewise axis map at drag start; the layout does not jump, and a capped gap is coarse (about 1.8 px per 5-minute step in a 170-minute gap) with the ghost label as the readout. Alternative: expand the column to the true scale for the duration of a drag — precise drops, but the layout jumps under the pointer.
2. **Cross-type monotonicity vs the floor and the cap.** The spec fixes the 28 px floor, the scale and the 60 px cap, and also says a longer gap is never lower than a shorter block. Both ends conflict: a 10-minute gap (20 px) is lower than a 5-minute block (28 px), and a 70-minute gap (60 px) is lower than a 40-minute block (80 px). Default: floor, scale and cap win; cross-type monotonicity holds for gaps ≥ 14 minutes against blocks ≤ 30 minutes, which covers the spec's 70-minute vs 25-minute example; short gaps stay unlabeled clickable slivers. Alternative: floor every gap at 28 px, which adds 18 px for each 5-minute gap between blocks (the fixture uses 5-minute gaps; the app default is 10, `frontend/src/utils/blockGap.ts:1–2`).
3. **Text floor.** Default (spec): 13 px minimum and `#9CA3AF` for all secondary text; `--text-secondary`, `--text-muted` and `--text-faint` all become `#9ca3af` in Dark 4a, so hierarchy rests on size and weight. Alternative (review): keep a 12 px tier in `#8E9299` (5.29–5.69:1) for axis labels and meta.
4. **Education: `#F59E0B` vs `#D97706`, and how to apply it.** Default: the existing `amber` id, `#D97706` (5.58:1 on the page, distinct from Health and from the accent), through the guarded migration in C.10. `#F59E0B` would need a new palette entry on both sides and fails the pinned 3:1 audit on Classic white (2.15:1) and Light Premium `#FFFDF8` (2.11:1). The migration writes shared data (Education changes in every theme), so it ships in its own PR and runs only after the owner confirms. Alternative for the data: no migration; the owner picks amber once in Settings → Categories.
5. **390 px header and panes.** Default: the header keeps wrapping, with the secondary buttons at 32 px and the icon buttons at 40 px; the rails stay unmounted below 1024 px, and in Dark 4a the calendar panel falls back to the centre position under the timeline (C.4) so the card and its explicit `Add to schedule` are reachable. Alternative: a calendar drawer.
6. **Coarse-pointer targets.** Default: visual sizes follow the spec (28 / 32 / 36 px) on every pointer type, and the checkbox, `×`, gap `+` and rail buttons get hit areas of at least 24 × 24 CSS px from real wrapper elements that do not change layout (C.1, compact block row). Alternative: a 40 px block floor under `@media (pointer: coarse)`.

Alternative: start at the gap start and end 25 minutes later (`DEFAULT_AUTO_DURATION_MINUTES`, `backend/ai/mutation_planner.py:60`), capped by the gap end, applied in `handleAddHere4a`.
12. **Completed block.** Default: in Dark 4a drop the whole-card `opacity: 0.6` (`TimeBlock.vue:297–299`) and show the title struck through in `--text-secondary` with the filled checkbox, so the text keeps 4.5:1. Classic is unchanged.

14. **Checkbox sizes.** Default (spec): 16 px on blocks and tasks, 18 px in Settings. The review preferred 16 px everywhere.
15. **True time overlaps.** Default: none can be stored (C.1); the stack renders any that appear one under another.
