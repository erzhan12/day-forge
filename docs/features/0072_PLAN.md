# 0072 — Focus Indicator Opacity, Persistent Ownership, and Explicit Close

GitHub issue #189. Extend the Document Picture-in-Picture focus indicator with account-persisted content opacity, explicit close controls, and lifetime independent of `Schedule.vue`. The PiP remains open through Inertia page changes and idle gaps. A device-local intent flag supports restore after a hard reload, but Chrome’s transient-activation rule means restoration occurs only when the user next clicks **Show indicator**, never automatically.

## Ownership Design

Use a persistent application-shell provider rather than an Inertia page layout or module singleton.

`app.ts` currently has no page `layout` assignments and returns each page component directly. Introducing Inertia persistent layouts would require assigning the same layout to Schedule, Settings, Analytics, and every future authenticated page; one omitted page would silently reintroduce PiP teardown. A module singleton would survive page swaps but would move timers and Vue lifecycle outside component scopes, complicate test isolation, and make disposal on a real application unload unreliable.

Create `FocusIndicatorHost.vue` as the stable root around Inertia’s `<App>`. It creates and provides one focus-indicator controller while the inner Inertia page changes. This gives Vue-owned cleanup on a real root unload without tying cleanup to any page component.

The controller will:

1. Retain the last published schedule date and a copied block snapshot.
2. Own its own `useNowMinutes` instance and derive active/progress/gap state with the existing helpers from `utils/focusIndicator.ts`.
3. Keep updating while Schedule is unmounted, so a block ending during a Settings/Analytics visit transitions to the existing gap or `—` state without closing.
4. Accept reactive snapshots from `Schedule.vue`; publish `effectiveBlocks` while mounted, then publish canonical `props.blocks` during Schedule teardown so an abandoned drag preview is not retained.
5. Expose the same `focusIndicator` lifecycle object and derived refs used by the current `defineExpose` seam.
6. **Logout / unauthenticated-page guard (privacy).** Because `logout()` is an Inertia visit (`Schedule.vue:708-710` → `router.post("/accounts/logout/")`) that lands on the Inertia `Login` component (`backend/schedules/views.py:29,67-69`), the root host does **not** unmount on logout — the SPA persists — so a retained prior-user block snapshot could keep an open PiP showing that user's next-block title after logout (violating the 0049 privacy invariant). **Detect the unauthenticated transition by `usePage().component === "Login"`, NOT by "no user in `page.props`"** — authenticated Inertia responses emit no user/auth marker (`backend/schedules/views.py:103-139`, `frontend/src/types/index.ts:142-146` — only `ui_preferences`/`schedule_window` props), so a `props`-absence test would fire on every authenticated page and break the stay-open core. On a positive `component === "Login"` transition the controller calls the explicit-close path (`cleanup()`): clear the retained snapshot, close any open PiP, and clear the device restore flag. A test must prove logging out closes an open PiP and drops the snapshot.
7. **Uninitialized-page safety (Inertia timing).** The host is an ancestor of `<App>`; do **not** let an uninitialized/absent `usePage()` state (before the initial page resolves) trigger any close/clear or a spurious logout-cleanup — read `component`/props defensively and act only on a definite, initialized value. An absent `ui_preferences` yields retain-last/default opacity (§ Preference and Opacity Contract); an absent/undefined `component` is a no-op, never a "logout." This neutralizes both the prop-absence false positive and any first-paint race that could clear the restore flag before initialization.

This adds one lightweight 60-second sampler when a retained schedule is today. That is lower risk than moving Schedule’s established clock, notification, drag, and rendering consumers into a shared owner. Direct component tests that mount `Schedule.vue` outside `app.ts` may use a component-scoped fallback controller, but production must receive the host-provided controller and have an integration test proving the wrapper is present.

## Preference and Opacity Contract

Use the name `focus_indicator_opacity`. It clearly scopes the preference to this product surface without coupling the database/API name to the Document PiP implementation.

**Constant location (avoid circular import).** `preferences.py` already imports `UserPreferences` from `models.py` (`preferences.py:16`), so `models.py` MUST NOT import the min/max/default from `preferences.py` — that would be a `models → preferences → models` cycle. The model validators need the bounds, so make **`models.py` authoritative** for `FOCUS_INDICATOR_OPACITY_{MIN,MAX,DEFAULT}` (or a dependency-neutral `templates_mgr/constants.py` that neither imports); `preferences.py` and `api.py` import the bounds from there. The frontend `focusIndicatorOpacity.ts` mirrors them under a `SYNC ALERT` comment (same convention as `DEFAULT_CHAT_SUGGESTIONS` in `preferences.py`).

- Storage type: `FloatField`.
- Default: `0.70`.
- Inclusive domain: `0.20` through `1.00`.
- UI precision: `0.01`, displayed as an integer percentage.
- Model validators and PATCH validation enforce the domain. PATCH rejects booleans, non-numbers, non-finite values, and out-of-range numbers with a stable `focus_indicator_opacity` field error rather than silently accepting a malformed client.
- Read-side normalization remains non-writing: finite numeric values are clamped to the inclusive domain; malformed/non-finite values fall back to `0.70`.
- A migration adds the non-null field with default `0.70`, thereby backfilling existing rows.
- The device-local “should be open” flag is never added to `UserPreferences` or any API payload.

The complete account data flow is:

1. `UserPreferences.focus_indicator_opacity`.
2. `get_user_preferences()` normalizes it into `UserPreferencesDTO`.
3. `ui_preferences_payload()` and `_prefs_to_dict()` emit it for GET, PATCH, and all Inertia pages.
4. `UiPreferences` types it as `focus_indicator_opacity?: number` (optional, matching the defensive `chat_suggestions?: unknown` / `ui_preferences?` boundary at `frontend/src/types/index.ts:119-146` so a partial/stale prop is safe at the type boundary; `focusIndicatorOpacity.ts` owns the runtime guarantee).
5. `FocusIndicatorHost` watches `page.props.ui_preferences.focus_indicator_opacity`.
6. `useFocusIndicator.setOpacity()` updates the PiP document’s CSS custom property without reopening.
7. `SettingsAppearancePanel` previews each range input immediately, PATCHes through `usePreferences`, then reloads only `ui_preferences` to reconcile with the account value.

If `ui_preferences` is absent during a partial/stale Inertia response, retain the last known opacity; use `0.70` only when no valid value has ever been received.

## PiP Transparency Algorithm

**Achievable effect (calibrate expectations).** A Document Picture-in-Picture window is a normal, OS-owned opaque window — its backing is **not** transparent to the desktop. CSS `opacity` on our document content therefore composites the view toward the **PiP window's own backstop** (the browser/`Canvas` window background), not the live desktop/app behind the window. The deliverable is precisely the acceptance criterion — *"content opacity 70% (whole view, not bar-only)"* — i.e. the whole Day Forge surface (bar, labels, remaining time, idle/error state, X, and its background) rendered translucent so it reads as a faded, less-obtrusive overlay. The issue-summary phrasing "app/desktop shows through" is aspirational shorthand; do not plan or QA against literal desktop see-through (that is the documented out-of-scope "true OS-window transparency").

1. Define a PiP CSS custom property with fallback `0.70`.
2. Keep `html` and `body` transparent.
3. Make `.fi-root` fill the entire document **vertically and horizontally** (`height: 100%` / stretch, not the current auto-height shrink-wrap centered by the flex `body` at `useFocusIndicator.ts:16-17`), paint the existing `Canvas` background, and apply the custom-property opacity once to that root — so the whole window surface, not a centered strip, is the translucent layer.
4. Keep the bar, remaining time, gap labels, idle state, error state, and X button inside `.fi-root`, so content and background are composited as one translucent document surface.
5. Remove or raise the existing secondary text opacity declarations (`.fi-remaining`, `.fi-next-remaining`, and `.fi-neutral` at `useFocusIndicator.ts:35-57,73-77`) so they do not multiply the new whole-root `0.70` layer into unreadably faint text.
6. Cache the current normalized opacity in the lifecycle object. On open, set the property before mounting the view. While open, `setOpacity()` writes the property on the existing PiP document; it must not call `requestWindow()`, close the window, or remount the Vue app.

The Chrome/OS title bar is outside the PiP document and remains browser-owned and opaque. Only Day Forge’s document content and background are faded.

## Close and Reload State Machine

Use a strict-only-on-true localStorage key such as `day-forge:focus-indicator:should-be-open`.

**The flag MUST have an observable consumer (no dead state).** Restore-after-reload never auto-opens (gesture rule), and `open()` behaves identically regardless of the flag — so a flag that nothing reads would be inert write-only state. Its one legitimate consumer: after a reload with the flag still `true` and the PiP not open, the controller exposes a derived `shouldRestore = supported && !isOpen && flag===true`, and `ShowIndicatorButton` reflects it as a distinct **restore affordance** (an accessible hint / label variant such as an `aria-description` "Reopen focus indicator" or a subtle restorable state) while still opening on the single click. This keeps the acceptance criterion "one click restores it if the user had not closed it" behaviorally distinct from a first-ever open, and gives the flag a tested output. If the product prefers zero visual change, the minimum bar is still that a test asserts `shouldRestore` toggles the header's accessible state; a flag with no asserted consumer is not acceptable.

**Sequencing of `cleanup()` vs `dispose()` (avoid a misleading intermediate).** The explicit-`cleanup()` / non-intent-`dispose()` split and the `onUnmounted` rewire land together **in Phase 3 with the persistent host**, where ownership actually moves off `Schedule.vue`. Do not rewire `onUnmounted(cleanup)` → `dispose()` in Phase 2 while `Schedule.vue` still owns the composable — that would leave navigation still closing the PiP but now stranding a `true` flag, an intermediate state Phase 3 immediately rewrites. Phase 2 adds the `dispose()` method and flag semantics as covered units; Phase 3 wires them into the host lifecycle.

### Open

1. Read the device flag into controller state, but never call `requestWindow()` during setup, mount, a watcher, or page navigation.
2. The header’s click must synchronously reach `open()`; `requestWindow()` remains before any asynchronous detour so transient activation is preserved.
3. Retain the existing unsupported, already-open, pending-open, and epoch guards.
4. Write the device flag `true` only after the window is fully styled, mounted, listening for `pagehide`, and marked open.
5. A rejected or partially failed first open does not create a new true flag. An existing restore flag may remain true so the user can retry explicitly.

### Explicit close

Expose the existing `cleanup()` surface as the explicit-close path:

1. Clear the device flag.
2. Increment the epoch and cancel ownership of any pending request.
3. clear the generic open error.
4. Unmount the secondary app, detach listeners, close the PiP, and set `isOpen=false`.

Both the in-PiP X and the open header’s **Hide indicator** action call this path.

### Browser PiP chrome close

The PiP `pagehide` handler treats normal PiP-window `pagehide` as explicit closure:

1. Clear the device flag.
2. Tear down local app/listener state without calling `close()` again.
3. Set `isOpen=false`, causing a mounted Schedule header to return to **Show indicator**.

### Main-window reload/unload

A hard reload commonly destroys the browser-owned PiP window. Preserve intent by separating root disposal from explicit cleanup:

1. Main-document `beforeunload`/`pagehide` marks the opener as unloading; `pageshow` resets that guard for BFCache restoration.
2. If PiP `pagehide` occurs while the opener-unloading guard is set, release window/app state but do not clear the device flag.
3. `onUnmounted` calls a new non-intent `dispose()` path that invalidates pending requests and closes/releases resources without clearing the flag.
4. The new page reads the surviving flag but performs no request.
5. The next **Show indicator** click calls `requestWindow()` under that click’s transient activation and restores the window.
6. After X, Hide, or browser-chrome close, the cleared flag remains false across reloads until the user explicitly clicks **Show indicator** again.

Storage failures must never break the PiP; they fall back to current-tab memory and cannot promise cross-reload restoration.

The flag is device-global, not user-scoped. Explicit close, Hide, browser-chrome close, and the logout guard all clear it, so the normal path never leaks it across users. The one residual edge — user A's browser is killed without logout, then user B logs in on the same device — surfaces only the `shouldRestore` **hint** to B (the retained snapshot is memory-only and gone after the process death, so no block data leaks). Close even the hint by clearing the flag on the `Login`-transition guard (and on login). (Namespacing the key per user id is **not** implementable from current props — no user identifier reaches the frontend, `types/index.ts:142-147` exposes only `ui_preferences`/`schedule_window`; that option would need a new Inertia auth prop outside this plan's file list.) A test asserts the flag does not survive a user switch.
