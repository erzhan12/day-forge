## Context

+ Django on :8006 + Vite on :5173) and **must run serially** (shared per-user
`ai_cmd_rl` / `ai_draft_rl` rate-limit counters). Therefore behavioural
verification of the harness refactor (Phase B) is a **manual step the user
runs** — see § Verification. In-repo we verify only: `node --check <file>`,
`make typecheck`, `make lint`, `make test-backend`, and careful read-diffs that
each extracted helper is behaviour-identical to what it replaced.

### Phase A — N+1 regression pytest (item #8). Standalone, classic TDD, ship first.

Guards the PR #15 fix: `build_draft_user_message` reads `past.daily_review` for
each history schedule; without `select_related("daily_review")` that is one
extra query per past day. Replaces the `// TODO: N+1 sanity` comment block in
`ai-draft-on-empty-day.mjs:268–272` (delete that comment as part of this phase
and point it at the new test in a one-line note).

New file `backend/tests/test_ai_views_draft_nplus1.py`:
- **CRITICAL — stub the LLM network layer, NOT `run_draft`.** The view builds
  `history` as a fully-evaluated list comprehension
  (`[s async for s in Schedule.objects...select_related("daily_review")]`,
  `backend/ai/views.py:862–877`) and passes it into `run_draft`. The
  `.daily_review` dereference that `select_related` optimises happens **inside**
  `run_draft → build_draft_user_message` at `backend/ai/prompts.py:299`
  (`getattr(past, "daily_review", None)`). If the test stubs
  `ai.views.run_draft` wholesale (the pattern `test_ai_views_draft.py` uses),
  that dereference **never runs**, so removing `select_related` would change the
  captured `analytics_dailyreview` count from **1 → 0** (the JOIN disappears),
  **not 1 → N** — the test would not exercise the N+1 path at all and the RED
  step "observe count > 1" would be false. Instead, patch the provider call so
  the **real** `run_draft`/`build_draft_user_message` executes (dereferencing
  `.daily_review` per past day) while no network I/O happens:
  `monkeypatch.setattr("ai.service._get_client", lambda: fake)` (the exact seam
  `test_ai_service_draft.py:94` uses) where `fake.chat.completions.create`
  returns a canned draft JSON payload. Confirm at implementation time by reading
  `service.py:run_draft`; the invariant is **`build_draft_user_message` must run
  for real** so the history rows are actually dereferenced.
- **Set `LLM_API_KEY` in the test.** `run_draft` short-circuits with
  `AIUnavailableError` if `settings.LLM_API_KEY` is empty
  (`backend/ai/service.py:292-293`) **before** it builds the prompt — a clean
  test env would 503 and never walk the history. Set `settings.LLM_API_KEY =
  "sk-test"` via the pytest-django `settings` fixture (any non-empty string; the
  stubbed client never uses the value). The old assumption "LLM settings are
  irrelevant since `run_draft` is stubbed" **no longer holds** — both
  `LLM_API_KEY` and `LLM_HISTORY_DAYS` now matter.
- Need a weekday `Template` so the 422 precondition passes; POST target must be
  a **weekday** date so `slot_type_for_date` matches. **The existing `template`
  fixture is defined in `test_ai_views_draft.py:40` (function-scoped), NOT in
  `conftest.py` — it is not visible to other test modules** (`fixture not found`).
  Either
  (a) **move** `template` (and any `URL`/`_post` helper it needs) into
  `backend/tests/conftest.py` so both modules share it, or (b) define a local
  `template` fixture in `test_ai_views_draft_nplus1.py`. Prefer (a) if it does
  not disturb the existing draft tests; otherwise (b).
- Seed **N past schedules** (use `settings.LLM_HISTORY_DAYS = 3` via the
  `settings` fixture, then seed 3 consecutive prior days) each with
  `status ∈ {active, reviewed}` **and** a related `DailyReview` row (so the
  `.daily_review` access is a real reverse-one-to-one that would trigger an
  extra query without `select_related`). Dates must be `< parsed_date` and
  `>= parsed_date - LLM_HISTORY_DAYS`.
- **CRITICAL — the async view cannot demonstrate the N+1 as a query *count*; it
  demonstrates it as a *crash*. Split the test into two layers.** The view
  (`ai_generate_draft`) is `async def`; `run_draft` (async) calls the **sync**
  `build_draft_user_message` directly, which lazily derefs `.daily_review`
  (`prompts.py:299`). With `select_related` the reverse-one-to-one is **cached**
  → no query, no problem. Without it, that lazy ORM access runs **inside a
  running event loop with no `sync_to_async` bridge**, and — since
  `DJANGO_ALLOW_ASYNC_UNSAFE` is **not set** in this repo (verified: absent from
  `backend/`, `pytest.ini`, `pyproject.toml`, `conftest.py`) — Django raises
  **`SynchronousOnlyOperation`**, surfacing as a **500**, *not* N extra queries.
  So `select_related` here is **load-bearing for correctness**, not merely perf.
  Design the two layers accordingly:
  - **Layer 1 — view GREEN + perf guard (async view POST).** Wrap
    `auth_client.post(...)` in `django.test.utils.CaptureQueriesContext(connection)`
    (`from django.db import connection`). Assert `resp.status_code == 200`
    **first** (a 4xx/5xx would skip/abort the history walk and make the count
    assertion vacuous), then assert the number of captured queries whose SQL
    contains `analytics_dailyreview` is exactly **1** (the single JOIN'd SELECT
    — filter `ctx.captured_queries` on `"analytics_dailyreview" in q["sql"]`).
    **RED signal for this layer:** removing `.select_related("daily_review")`
    from the view makes the POST raise `SynchronousOnlyOperation` → the
    `status_code == 200` assertion fails (the test client re-raises the view
    exception, or you get a 500). That is the regression this layer catches —
    do **not** expect "count == N" here; expect the status assertion to flip.
  - **Layer 2 — N+1 query-count proof (SYNC, prompt-builder level).** To prove
    the *query-count* semantics cleanly, add a **sync** test (no event loop, so
    lazy ORM access is allowed): build the history queryset **without**
    `select_related`, wrap `build_draft_user_message(schedule, template,
    list(qs), rules, now)` in `CaptureQueriesContext`, and assert the
    `analytics_dailyreview` count is **N** (=3 for 3 reviewed history days);
    then repeat **with** `.select_related("daily_review")` and assert **1**.
    This is the classic red→green N+1 demonstration and is not subject to the
    async-unsafe crash because it runs in a sync context.

Notes:
- `LLM_DRAFT_MODEL` etc. are irrelevant (the network client is stubbed), but

  `settings` fixture (see the CRITICAL note above). Do **not** rely on the old

  runs for real (only its network client is faked) and 503s on an empty

- SQLite is the test DB; `CaptureQueriesContext` works there (unlike
  `select_for_update`, which SQLite strips — see `test_ai_views_draft.py`
  `TestApplyLocksScheduleRow` docstring). Query capture is backend-agnostic.

### Phase B — Harness refactor: `test-utils.mjs` + `backend/scripts/seed_*.py` + consts + preflight (items #4 + #5 + #7 + #3). Biggest phase, one PR, touches every script.

**B1. `frontend/scripts/playwright/test-utils.mjs`** — exports (behaviour-identical
to the drifted inline copies observed in the read scripts):
- `BASE`, `USERNAME`, `PASSWORD`, `REPO_ROOT` — the shared constants (`BASE =
  "http://localhost:5173"`, `USERNAME = "playwright"`, `PASSWORD =
  "playwright-pw-do-not-use-in-prod"`, `REPO_ROOT = resolve(process.cwd(), "..")`
  — the exact form the scripts already use, e.g.
  `ai-chat-date-change-resets-thread.mjs:42`; do not shorten to a bare `cwd`).
- `fail(...)` — **the scripts do NOT share one `fail()` semantic** (verified):
  there are **three** distinct shapes. (1) **push** — most `failures.push(msg)`
  and print a verdict at the end. (2) **throw** — `analytics-unfreeze-on-edit.mjs:74-76`,
  `skipped-tasks-today-aware.mjs:104-106`, `draft-prompt-history-suffix.mjs:141-143`,
  `todoist-complete-refresh.mjs:46-48` `throw new Error(msg)`. (3) **exit** —
  `compact-timeline-stubs.mjs:28-30` and `todoist-integration.mjs:30-32` call
  `process.exit(1)` inside `fail()`. A single push-only helper would **change
  control flow** for the throw/exit scripts. Therefore export **three** variants
  and let each script keep its existing shape: `makeFailAggregator()` →
  `{ failures, fail }` (push), `failFast(msg)` that `throw`s, and
  `failExit(msg, code=1)` that `process.exit(code)`s. Do **not** convert a
  `process.exit`/`throw` script to push semantics in this pure-extraction phase —
  preserve each call site's control flow exactly. (The `process.exit →
  process.exitCode` conversion needed for Phase-D `--cleanup` `finally` teardown
  is a **deliberate Phase-D change**, called out there — NOT done here.)
- `login(page)` — the inline login is **not identical across all 21 scripts**
  (verified): most goto `${BASE}/accounts/login/` (`waitUntil: "networkidle"`)
  and fill `#username`/`#password`, but `theme-switch-persistence.mjs:64-66`
  fills `input[name="username"]`/`input[name="password"]` and omits
  `networkidle`. Forcing every script onto `#username` would change selectors and
  violate B4's same-selectors rule. Make the shared `login(page, opts?)` accept
  the selector/wait variant (default `#username` + `networkidle`; the
  name-attribute + no-networkidle path for theme-switch), OR leave
  theme-switch's login inline and migrate only its consts/`preflight`. Decide in
  B4 per read-diff; the invariant is **no selector or wait-condition changes**.
- `preflight()` — item #5: `fetch(BASE + "/accounts/login/", { method: "GET" })`
  with a clear "start them with `make run` / `make frontend-dev`" message on
  failure. **Use GET, NOT HEAD** — `login_view` is
  `@require_http_methods(["GET", "POST"])` (`backend/schedules/views.py:35`), so a
  HEAD request returns **405 on a healthy stack** and would make a status check
  fail spuriously. Must fail on **both** `ECONNREFUSED` **and a non-2xx/3xx
  status**: the dev stack reaches Django through Vite's proxy
  (`frontend/vite.config.ts`), so a running Vite fronting a **dead Django**
  returns a non-2xx response rather than throwing `ECONNREFUSED` — checking only
  the connection error would let a half-up stack through to a cryptic later
  failure. `process.exit(2)` on either.
  Call at the top of every script (currently only 5/21 have any preflight, and
  those check the *user* via shell — keep that behaviour too; see B4).
- `postWithCsrf(page, url, body)` — wraps the `page.evaluate` fetch that reads
  the `XSRF-TOKEN` cookie → `x-xsrf-token` header (used by the direct-POST
  scripts `ai-command-*`, `ai-draft-409`). Keep the exact
  `document.cookie.match(/XSRF-TOKEN=([^;]+)/)` + `decodeURIComponent` logic and
  the `{ error: "no XSRF-TOKEN cookie present" }` early-return.
- `seed(scriptName, env)` — item #7: shells out via `execSync("uv run python
  backend/manage.py shell -c \"import runpy; runpy.run_path('backend/scripts/<scriptName>.py',
  run_name='__main__')\"", { cwd: REPO_ROOT, env: { ...process.env, ...env } })`
  — **the B3 default mechanism** (do NOT use `shell < file`; B3 rejects it).
  Pass per-scenario parameters (username, date parts, block specs) through the
  `env` option as `SEED_*` vars so the Python seeder stays parameterised, not
  string-interpolated. Note the Node `execSync` `env` semantics: **omitting `env`
  inherits `process.env`; passing `env` REPLACES it entirely**, so the seeder
  must spread `{ ...process.env, ...perScenario }` (otherwise the subprocess
  loses `PATH`, `VIRTUAL_ENV`, etc. and `uv run` breaks). Preserve the existing
  `{ stdio: "inherit" }` vs `{ encoding: "utf8" }` distinction (seeds that only
  mutate vs seeds that read back state).
- Named wait/poll consts (item #3) — replace scattered magic numbers with
  descriptive names, e.g. `WAIT_FOR_PATCH_MS`, `WAIT_FOR_INERTIA_SETTLE_MS`,
  `WAIT_FOR_THREAD_SETTLE_MS`, `WAIT_FOR_DRAFT_OVERLAY_MS`, plus response-wait
  timeouts (`RESPONSE_TIMEOUT_MS`, `DRAFT_RESPONSE_TIMEOUT_MS = 60_000`). Map
  each existing literal to a name; **keep the numeric value identical** so
  timing behaviour does not change. Where two scripts used different values for
  the same semantic wait, preserve both as distinct named consts (do NOT
  unify values — that would be a behavioural change; note the divergence in a
  comment so a follow-up can reconcile deliberately).

  that line — do **not** reuse a mode called `reset` (no such mode exists; the

**B3. Seed invocation mechanism** — decide between `manage.py shell -c "import
runpy; runpy.run_path('backend/scripts/seed_x.py', run_name='__main__')"`,
`manage.py shell < seed_x.py`, or a lightweight custom management command.
**Default to the `-c "…runpy.run_path(…, run_name='__main__')"` form**, not the
stdin redirect and **not** a bare `exec(open(...).read())`:
- `manage.py shell` launches an **interactive console** (IPython when installed,
  else the plain `code.interact` REPL); piping a file over stdin is a REPL-fed
  input stream, not a script-runner — behaviour differs between the IPython and
  plain backends (prompt echoing, non-zero exit on trailing EOF) — a footgun.
- A bare `exec(open(...).read())` (or `shell < file`) runs the file's code under
  Django's **shell command-module globals**, where `__name__` is **not**
  `"__main__"` (verified: Django's `shell` command execs the `-c` payload with a
  namespace built from the command module's globals + `get_namespace()`, e.g.
  `exec(options["command"], globals())` in
  `django/core/management/commands/shell.py` — exact line varies by Django
  version; confirm against the installed version at implementation time). So a
  seeder guarded by the
  idiomatic `if __name__ == "__main__": main()` would **silently no-op** — the
  guard never fires. Using `runpy.run_path(path, run_name="__main__")` sets
  `__name__ == "__main__"` inside the seeder, so the guard fires as intended,
  the file runs with a clean module namespace, and there is no REPL. This also
  composes with the seeder-unit-test design (below): pytest imports the seeder
  module under its real module name — `__name__ != "__main__"` — so the guard
  does **not** fire on import, and the test calls `main()` itself.
Document the chosen convention in the seeder file header and RULES.md. If a
cleaner default emerges (e.g. a one-line `runscript` management command), record
the choice; otherwise the `runpy.run_path(run_name="__main__")` form is the
convention.

**Deliberate invocation-line change — flag for the B4 read-diff reviewer:** every
one of the 20 seed-using scripts today calls the **`-c "<inline python>"`** form
(`execSync(\`uv run python backend/manage.py shell -c "${script}"\`, …)`) with
the Python source string-interpolated inline. Switching to the B3 default
(`shell -c "import runpy; runpy.run_path('backend/scripts/<name>.py',
run_name='__main__')"`) — or whichever mechanism is chosen — moves the Python
body **out of the inline string into a file** and is therefore a real change at
the shell-invocation layer for **every** migrated script, even though the
executed Python is semantically identical. This
is expected drift, not a regression: the read-diff in B4 must treat the changed
invocation line as an intended difference, not flag it. **Env-var passing must
be confirmed to work with the chosen mechanism** before mass migration: the
inline `-c` form string-interpolated per-scenario values directly; the extracted
seeder must instead read parameters via `os.environ[...]` and the `.mjs`
`execSync` must pass them through the `env` option. **Node `execSync` env
semantics:** omitting `env` inherits `process.env`; passing `env` **replaces** it
entirely — so pass `{ ...process.env, ...SEED_* }` (spread `process.env` so the
subprocess keeps `PATH`/`VIRTUAL_ENV` for `uv run`, then add the per-scenario
`SEED_*` keys). Prove this on **one** script (e.g. `ai-command-add-block`)
end-to-end before migrating the rest — the mechanism + env-passing is the
load-bearing risk, not the extraction.

**B4. Migrate all 21 scripts** to import from `test-utils.mjs` and call the
seeders. Each script shrinks to: import consts+helpers → `await preflight()` →
`seed(...)` → scenario logic (locators, wire assertions, DB read-back via a
snapshot seeder) → verdict. **Keep every assertion and every seed date exactly
as-is.** Do not "improve" scenarios in this phase — pure extraction.

**Verification per touched file (verification-first, NOT classic TDD):**
`node --check <file>` before (baseline passes) and after every migration;
`make typecheck` (scripts are `.mjs`, unaffected, but confirm nothing else
broke); read-diff each script against its pre-refactor version asserting the
extracted helper produces byte-identical runtime behaviour (same selectors,
same magic-number *values*, same seed SQL, same stdout markers). Behavioural
end-to-end proof is the user's manual serial run (§ Verification).

**Seeder unit coverage (the seeders ARE testable — do not leave them
read-diff-only).** The `backend/scripts/seed_*.py` files are the load-bearing
risk (env-var parsing, date math, `SEED_BLOCKS_JSON` decode, stdout-marker
contract, idempotence) and — unlike the `.mjs` scripts — need **no browser or
LLM** to test. Structure each seeder so its logic is importable (a `def main()`
reading `os.environ`, guarded by `if __name__ == "__main__": main()` — which
fires under the B3 `runpy.run_path(run_name="__main__")` invocation but NOT on
pytest import), then add a small `backend/tests/test_seed_scripts.py`
(pytest-django, `@pytest.mark.django_db`) that imports each seeder module. **How
to make `backend/scripts/*.py` importable from the test:** `backend/scripts/` is
not a package on the test path today — either add an `__init__.py` and ensure
`backend` is on `pythonpath` (check the pytest config; the suite already imports
`ai`/`schedules`/etc. from `backend`, so a `scripts/__init__.py` + the existing
path config is the low-friction route), or load each file via
`importlib.util.spec_from_file_location`/`module_from_spec` (no package needed).
Confirm the chosen mechanism against `pyproject.toml`/`pytest.ini`'s
`pythonpath`/`DJANGO_SETTINGS_MODULE` at implementation time. The test then sets
the `SEED_*` env vars (e.g. via `monkeypatch.setenv`), calls `main()` directly,
and asserts: (a) the expected
rows exist with the expected field values, (b) the exact stdout markers are
printed (capture with `capsys`), (c) idempotence — a second call with the same
env does not duplicate rows / still prints the same markers. This is a green
gate for Phase B alongside the `node --check` sweep.

**Expected (intended, do-not-flag) diffs the read-diff reviewer will see:**
- **Seed invocation switches from `-c "<inline python>"` to the B3-chosen
  mechanism** (default `-c "import runpy; runpy.run_path('backend/scripts/<name>.py',

- `waitForTimeout(<literal>)` replaced by `waitForTimeout(<NAMED_CONST>)` where

The read-diff **must still flag**: any changed selector, any changed numeric wait

### Phase D — `--cleanup` flag (item #6). Small.

Add an opt-in `finally`-block teardown to the shared `seed`/teardown helper in
`test-utils.mjs`:
- Parse `--cleanup` from `process.argv` (default **off** — a failed run must
  leave the seeded schedule in the DB for post-mortem inspection).
- When set, on exit delete the seeded schedule(s) for the script's date(s) via
  a `seed_cleanup.py` seeder (or a `SEED_MODE=cleanup` branch) — delete the
  `Schedule` (cascades `TimeBlock`, `DailyReview`, `AIInteraction`). Run it in
  each script's existing `finally` block, guarded by the flag.
- **`process.exit()` skips `finally` — cleanup will NOT run for the exit-style
  scripts.** `compact-timeline-stubs.mjs:28-30`, `todoist-integration.mjs:30-32`,
  and any other `fail()` that calls `process.exit()` (plus the top-level
  `process.exit(1/2)` on the seed-preflight failure path several scripts use)
  terminate the process immediately, bypassing the `finally` teardown. For
  `--cleanup` to be reliable, those scripts must first be converted to set
  `process.exitCode` and `return`/`throw` (letting control reach `finally`)
  instead of `process.exit()`. Either (a) scope Phase D to only the scripts that
  already reach `finally` and **explicitly list** the exit-style scripts as
  not-yet-cleanup-capable, or (b) include the `process.exit → process.exitCode`
  conversion for the exit-style scripts as part of Phase D (a real control-flow
  change — call it out, it is NOT pure extraction). Do not silently ship a
  `--cleanup` flag that no-ops on a third of the scripts.
- **The teardown boundary must wrap the whole seed→scenario span, not only the
  existing inner `try/finally`.** Several scripts seed **before** entering (or in
  a separate earlier block from) the `try` that owns the browser (e.g.
  `ai-chat-token-race.mjs` seeds in the `:54` try, launches the browser at `:74`);
  a failure after seeding but outside the cleanup-bearing `finally` would leak
  the seeded rows. For `--cleanup` to be reliable, register the teardown at an
  **outer** boundary that covers from the moment of seeding onward — either wrap
  `seed(...) + scenario` in one top-level `try/finally`, or register the cleanup
  via a `process.on("exit"|"beforeExit")` / signal handler keyed on the flag.
  (Still default-off; the default preserves rows for post-mortem.)
- Document the flag in the README (Phase C) and RULES.md, including which scripts
  honour it.

**Verification (verification-first):** `node --check` on the touched helper +
scripts; a manual run of one script with and without `--cleanup`, checking the
DB row is deleted only when the flag is passed (user-run, since it needs the
dev stack).
