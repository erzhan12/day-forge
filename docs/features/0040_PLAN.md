# Plan 0040 — Migrate async-boundary regression coverage to backend pytest

## Context

The `/command/` AI endpoint (`ai_command`, `backend/ai/views.py`) is UI-dead:
feature 0007 routed `CommandBar.vue` through `useChat` → `/chat/` (`ai_chat`),
leaving `/command/` + `useAI.ts` orphaned. A **separate follow-up** wants to
delete `/command/`, the three `ai-command-*.mjs` Playwright scripts, and
`useAI.ts`.

Those three scripts (`ai-command-add-block.mjs`, `ai-command-mass-move.mjs`,
`ai-command-rollback-on-overlap.mjs`) are today the only place that pins the
feature-0009 **async-boundary regression contract**:

- `_Rollback` (raised inside `_apply_actions_sync`, which runs in a worker
  thread via `await sync_to_async(_apply_actions_sync, thread_sensitive=True)(...)`)
  must **re-raise across the asgiref boundary** so the async view's
  `except _Rollback as rb: return rb.response` fires and the surrounding
  `transaction.atomic()` rolls back.
- No sync ORM leaks into the async path (a `SynchronousOnlyOperation` leak
  surfaces as a raised exception / HTTP 500, so any passing `status==200/400/409`
  assertion through the real async view guards it implicitly — no separate
  string-check test is needed).

Deleting `/command/` deletes those scripts and loses that net. **This task
migrates the coverage to deterministic, no-LLM backend pytest first**, so the
later removal loses nothing, and closes the deferred `tasks/todo.md` item
"Explicit regression test for `_Rollback` propagation across `sync_to_async`".

**Scope: backend tests only.** Do NOT remove `/command/`, the `.mjs` scripts,
or `useAI.ts` in this task. No production code changes. No LLM tokens spent
(all LLM calls are monkeypatched at the `ai.views.run_command` /
`ai.views.run_chat` seam). No dev stack required.

### Slice 1 — Explicit `_Rollback`-propagation contract test
File: `backend/tests/test_ai_views.py`.

**Purpose (narrow, deliberate):** document the *asgiref re-raise contract*
directly at the unit level — that `_Rollback` raised inside `_apply_actions_sync`
survives the `await sync_to_async(..., thread_sensitive=True)(...)` hop with its
stashed `JsonResponse` intact. It does **not** re-prove `transaction.atomic()`
rollback of a partial write: that DB-restoration-after-a-real-write path is
already covered through the view by `test_persist_validation_error_rolls_back_with_action_index:1071`
and `test_mid_batch_failure_rolls_back:248`, so duplicating it here is
unnecessary (this is the answer to the "no slice detects `atomic()` removal"
review finding — that coverage exists elsewhere).

1. **Synchronous** `def` test, standard `@pytest.mark.django_db` (NOT
   `transaction=True`). The repo deliberately has **no `pytest-asyncio`** (see
   `pyproject.toml`, `RULES.md`, and the 0009 plan's "pytest-asyncio is NOT
   needed" note); an unmarked `async def` test is never driven and silently
   no-ops. `transaction=True` is unnecessary because the assertions observe the
   raised exception + its response only (no committed-DB state), and the
   fingerprint-mismatch branch raises *before* any write. Create the `Schedule`
   explicitly in the body (do not rely on async fixtures).
2. **Drive the exact view boundary** so the test proves the *re-raise across the
   thread hop*, not a plain in-thread call. Define a local
   `async def _run(): return await sync_to_async(ai.views._apply_actions_sync, thread_sensitive=True)(schedule, result, expected_fingerprint="stale-garbage", interaction_id=None)`
   and invoke it with `async_to_sync(_run)()` inside
   `pytest.raises(ai.views._Rollback) as excinfo`. This reproduces the same
   asgiref nesting the sync Django test client uses for async views:
   `async_to_sync` installs a `CurrentThreadExecutor`, so the nested
   `sync_to_async(..., thread_sensitive=True)` schedules `_apply_actions_sync`
   back onto the caller's (pytest) thread — reusing pytest-django's per-test
   connection + outer transaction (seeded rows visible, nested `atomic()` works,
   no thread-affinity / `SynchronousOnlyOperation` error). It is the `SyncToAsync`
   **exception re-raise** boundary — not a literal DB worker thread — that this
   pins. Use `async_to_sync` from `asgiref.sync` — the established pattern in
   `test_ai_service_draft.py:33` (which comments that a bare `async def test_` is
   avoided on purpose).
3. Trigger: a **stale/garbage `expected_fingerprint`** with a non-empty
   `parsed_actions` — the fingerprint mismatch is checked before `plan_mutations`,
   so no blocks/rules setup is needed.
   `result = AICommandResult(raw_response_text="{}", parsed_actions=[<one add>], explanation="x")`.
4. Assert `excinfo.value` is a `_Rollback`, `excinfo.value.response.status_code == 409`,
   and `json.loads(excinfo.value.response.content) == {"errors": {"detail": "schedule_changed"}}`.
5. Import note: add `import ai.views` (or `from ai import views as ai_views`) at
   the test-file top if not present, so `ai.views._apply_actions_sync` /
   `ai.views._Rollback` resolve.
6. **Mutation check** (must target the re-raise, per review): change the
   fingerprint-mismatch `raise _Rollback(...)` at `_apply_actions_sync` ~625 to
   `return` — confirm the test FAILS (no exception surfaces); revert. Note this
   mutation proves the raise is *required*; the green path itself is what proves
   the exception actually propagates *through* the `async_to_sync(sync_to_async(...))`
   wrapper (a direct sync `_apply_actions_sync(...)` call would also raise, but
   would not exercise the asgiref boundary — so keep the wrapper, do not simplify
   the call to a bare sync invocation).

### Slice 2 — Command overlap full-contract (EXTEND the existing test)
File: `backend/tests/test_ai_views.py`. Rather than add a second near-identical
overlap scenario, **extend and rename the existing
`test_add_rejected_when_overlapping_existing_block:344`** (both engines flagged a

overlapping add → `_post` → 400 → one seeded block survives) and add the three
missing `ai-command-rollback-on-overlap.mjs` assertions. Suggested new name:
`test_add_rejected_when_overlapping_existing_block_rolls_back_and_preserves_status`.

1. Existing body already: seeds one `TimeBlock`, `_patch_run` an overlapping add,
   asserts `400` + `action_index == 0` + one block survives. Seed the schedule
   `status = Schedule.Status.REVIEWED` (not the default DRAFT) so the
   status-unchanged assertion in step 2 discriminates.
2. **Add** assertions:
   - `"overlap" in resp.json()["errors"]["detail"]`.
   - the surviving block is the seeded one (assert by pk, not just count).
   - `AIInteraction.objects.get(schedule=today_schedule).success is False`.
   - `today_schedule.refresh_from_db(); today_schedule.status == Schedule.Status.REVIEWED`
     — a successful apply calls `mark_active_on_edit()` (reviewed → active), so
     status staying REVIEWED proves the rejected apply rolled back before that
     line (a DRAFT seed would leave the assertion vacuous).
3. **Mutation check** (must target the `_Rollback` handler, per review): in
   `ai_command`, change `except _Rollback as rb: return rb.response` to re-raise
   `rb` (so the handler no longer converts the rollback into the 400 response);
   confirm the extended test FAILS (status/rollback asserts break); revert. Do
   NOT rely on flipping the overlap `PlanError` branch — that would prove overlap
   detection, not the async-view re-raise/return contract.
