# 0034 — Hardening: `restore_blocks` 500s on non-string per-block `category`

## Context

`POST /api/schedules/<date>/blocks/restore/` (`restore_blocks` in
`backend/schedules/api.py`) validates each block entry inside a per-block
`for i, entry in enumerate(blocks_data)` loop. The `title`, `is_completed`,
and `sort_order` fields are all guarded with type checks (`isinstance`),
but `category` is checked directly against the `VALID_CATEGORIES` **set**
with no prior type guard. Because `in`-testing against a `set` hashes the
operand, a non-hashable per-block `category` (a `list` or `dict`) raises an
uncaught `TypeError`, which surfaces as an HTTP **500** instead of a
structured **400**.

This is the third instance of the same bug class:
- #103 — `create_block` (fixed).
- #119 — `block_detail` (fixed in PR #120).
- #121 — `restore_blocks` (this plan). Deferred from PR #120 to keep that
  PR scoped to `block_detail`; tracked in `tasks/todo.md` § Follow-ups.

The fix mirrors the already-fixed sibling call sites: add an `isinstance`
type guard **before** the enum membership check.

## Current buggy code — verified

`backend/schedules/api.py`, inside the `restore_blocks` per-block loop
(verified lines **752–759**):

```
# Category
category = entry.get("category", "other")
if category not in VALID_CATEGORIES:          # <- TypeError if list/dict
    choices = ", ".join(sorted(VALID_CATEGORIES))
    return JsonResponse(
        {"errors": {"category": f"Invalid category (block {i}). Choose from: {choices}."}},
        status=400,
    )
```

The **immediately-following** sibling (`is_completed`, verified lines
**762–767**) already guards its type and uses the `(block {i})` error-suffix
convention:

```
is_completed = entry.get("is_completed", False)
if not isinstance(is_completed, bool):
    return JsonResponse(
        {"errors": {"is_completed": f"is_completed must be a boolean (block {i})."}},
        status=400,
    )
```

The `title` guard (verified lines **721–724**) is the other in-loop
precedent and also uses the `(block {i})` suffix. The already-fixed
`block_detail` call site (verified lines around **336–347**) establishes
the string-type precedent (`if not isinstance(data["category"], str)`).

## Files to change

### 1. `backend/schedules/api.py` — add the type guard (production code)

In the `restore_blocks` per-block loop, insert an `isinstance(category, str)`
guard **between** `category = entry.get("category", "other")` (verified line
753) and the existing `if category not in VALID_CATEGORIES:` check (verified
line 754). The guard returns a structured 400 that mirrors the per-block
error style already used in the loop (note the `(block {i})` suffix used by
`title` and `is_completed`):

- Condition: `not isinstance(category, str)`.
- Response: `JsonResponse({"errors": {"category": f"Category must be a string (block {i})."}}, status=400)`.

The existing enum check (`if category not in VALID_CATEGORIES:`) stays
unchanged directly below the new guard. No other logic in the loop, the
overlap check, or the atomic apply block changes. The all-or-nothing restore
behaviour (validate every entry first, then delete-all + `bulk_create` inside
`transaction.atomic()`) is untouched.

**Also defer `Schedule.objects.get_or_create` past validation (pre-existing
side-effect, same class as #103).** Today `restore_blocks` calls
`schedule, _ = Schedule.objects.get_or_create(user=request.user, date=parsed_date)`
at **verified line 709 — *before* the per-block validation loop**. On a
**nonexistent date**, that persists an empty `Schedule` row *even when a later
block fails validation and the request 400s* — so the "mutates nothing" claim
below is false as the code stands. This is the identical side-effect that #103
fixed in `create_block` by deferring `get_or_create` until after type
validation (obs: "Fixed Schedule side-effect bug in create_block: defer
get_or_create until after type validation").

The `schedule` variable is **never** referenced in the validation loop
(713–782) nor the overlap check (784–790). Its **first** use is the
instance-build at verified line **802** (pre-`atomic()`), followed by
**822**/**823** inside the `transaction.atomic()` block (verified atomic start
line **818**) and the result-query `filter(schedule=schedule)` at verified line
**829** — all **after** full validation. So the `get_or_create` call moves
safely to **immediately before the atomic apply** (just before verified line
798, the `t0 = time.monotonic()` line). After the move, any validation 400
(the new `category` type guard included) returns before a `Schedule` is
created, making the all-or-nothing / "mutates nothing" contract literally
true for new dates too.

## Algorithm (the guard)

1. `category = entry.get("category", "other")` (unchanged; default `"other"`).
2. **NEW:** if `category` is not a `str`, return a 400 with
   `{"errors": {"category": "Category must be a string (block {i})."}}`.
   This runs before any `in VALID_CATEGORIES` test, so an unhashable value
   never reaches the `set` hash and never raises `TypeError`.
3. if `category not in VALID_CATEGORIES`, return the existing
   "Invalid category (block {i}). Choose from: …" 400 (unchanged).

4. **Deferred:** `Schedule.objects.get_or_create` (moved out of its current
   line-709 position to just before the atomic apply) runs only after every
   block passed validation and the overlap check, so a validation 400 creates
   no `Schedule`.

Because the guard returns before **any** DB write — both the block
delete-all/`bulk_create` **and** (after the §1 move) the `Schedule`
`get_or_create` now run only past full validation — the all-or-nothing restore
contract is genuinely preserved: an invalid `category` on any block 400s the
whole request and mutates nothing, including on a date that had no `Schedule`
row yet. (Before this plan, `get_or_create` at line 709 ran first, so the
"mutates nothing" claim held only for the block rows, not the parent
`Schedule` — see §1.)

## What could break / risk notes

- **Test-file location mismatch:** the issue names `test_views.py`; the real
  class is in `test_restore.py`. Adding to the wrong file would orphan the
  test from its fixtures/helper. Add to `test_restore.py` (§2).
- **Repro value choice:** a non-string that *is* hashable (e.g. `int` `5`,
  or `None`) would be caught by the existing `not in VALID_CATEGORIES` branch
  and already 400s — it would **not** reproduce the crash. The regression
  test must use an **unhashable** value (`list`/`dict`) to exercise the
  `TypeError` path the guard fixes.
- **`get_or_create` move (§1):** the only behavioural change beyond the guard.
  Safe because `schedule` is unreferenced until the atomic apply (verified
  802/822/823); the sole observable effect is that a *new* date whose restore
  400s no longer leaves an orphaned empty `Schedule`. Existing dates are
  unaffected (`get_or_create` is a no-op create when the row exists). The
  `select_for_update().get(pk=schedule.pk)` at line 822 still has its row —
  `get_or_create` runs immediately before the `transaction.atomic()` block.
- **No migration, no model change, no frontend change** — pure view-layer
  input hardening plus one `Schedule`-creation reorder and one doc-row edit.
