## Technical Requirements

The permutation matters: to actually go RED on the current comparator (`a.sort_order - b.sort_order`, `scheduleTime.ts:71`), the input must be ordered `[{sort_order: 1, …}, {sort_order omitted, …}]` at the **same** `start_time`. Correct behavior (omitted coalesced to `0`) must reorder these to `[omitted, defined]`; the current code computes `1 - undefined = NaN`, which `Array.sort` treats as "equal" and — being stable — leaves the wrong input order `[defined, omitted]`, so the assertion fails until `?? 0` is added. Do **not** use input order `[omitted, defined]`: NaN-as-equal + stable sort already preserves it, so that permutation passes on the current code and never drives the change. Also: the "omitted" row must be a plain structural object literal with **no** `sort_order` key (or `delete` it) — do **not** build it with the file's existing `block()` helper (`scheduleTime.test.ts:22-33`), which defaults `sort_order: 0`; a defaulted `0` makes the current comparator compute `1 - 0` and the test passes green, never driving `?? 0`. The plain structural literal (missing `sort_order`) will produce a transient TypeScript error against the still-`TimeBlock[]`-typed signature until the GREEN generic lands — this is expected and harmless (vitest/esbuild does not type-check; `vue-tsc` runs only in Verification, after GREEN); do not "resolve" it by reverting to `block()`. In `DailyExportDialog.test.ts`, test:

1. The textarea is seeded with the exact formatter result for its `date` and `blocks`.
2. Changing the note while the preview is pristine regenerates the markdown and appends the normalized `note:` line.
2b. **Sequential** pristine note changes each regenerate (type note A → preview shows A, then note B → preview shows B): the regeneration must compare against the *latest* generated snapshot, not only the mount-time one, so `lastGeneratedSnapshot` is updated on every auto-regen. (Guards against a naive `watch`-on-generated-markdown dirty flag that passes tests 2–3 then freezes the preview after the first note change.)
3. The first manual textarea input marks the preview dirty; later note changes preserve the manual text.
3b. Editing the textarea so it once again equals a prior generated snapshot does **not** clear the dirty flag — a subsequent note change must still not clobber the (coincidentally-matching) manual content.
4. Copy calls mocked `navigator.clipboard.writeText()` with the current edited textarea value and briefly displays `Copied`.
5. Clipboard **rejection** (`writeText` returns a rejected promise) focuses and selects the textarea so manual Cmd+C remains possible, and surfaces a visible failure hint instead of `Copied`.
6. Clipboard **absent** (`navigator.clipboard` is `undefined` — the default in this repo's jsdom test env, and the real state over plain HTTP) does **not** throw: the same focus/select fallback and failure hint run. This is a distinct test from the rejection case because accessing `navigator.clipboard.writeText` on an undefined `clipboard` throws a synchronous `TypeError`, which a promise `.catch()` alone never catches.
7. `Copied` clears after its timeout, and the pending timer is cancelled on unmount (no post-unmount state update / leak).
7b. Unmounting while a `writeText` promise is still in flight (use a deferred/never-resolved-until-after-unmount mock) must not update component state when it later settles — this drives the mandated is-mounted guard (without this test a TDD-only implementation may omit the guard).
7c. A second copy attempt while the first `Copied` timer is still pending must replace/clear that prior timer so the newer success/failure feedback is not erased early by the stale timer.
8. Remounting the dialog (close then reopen) resets the note to blank and regenerates the preview from props.
9. The close button and backdrop self-click emit `close`; clicks inside the dialog do not.
10. The dialog exposes `role="dialog"`, `aria-modal="true"`, and an accessible name via `aria-label` (matching the `AddToScheduleDialog.vue:164` precedent).

Test isolation: tests 4–5 stub `navigator.clipboard.writeText` via `vi.stubGlobal`. Test 6 needs `navigator.clipboard` **absent** — which is jsdom's pristine default (this env ships no Clipboard mixin and there is no clipboard shim/`setupFiles`), so test 6 asserts against the default rather than stubbing anything. The load-bearing piece is an `afterEach(() => vi.unstubAllGlobals())`: `vi.restoreAllMocks()` alone does **not** revert `stubGlobal`, so without the unstub a prior test's stub leaks a defined `clipboard` into test 6 and the failure path never runs (order-dependent). If you prefer test 6 to be self-contained regardless of ordering, `vi.stubGlobal('navigator', { ...navigator, clipboard: undefined })` inside the test also works — but it is redundant given the afterEach.

4. Implement preview ownership with `lastGeneratedSnapshot` and an explicit dirty flag:

   - On mount, generate from the props and an empty note; assign the result to both the textarea and snapshot.

   - Never reset dirty state because the note changed.

5. Implement clipboard handling:

   - Guard availability before use so that both a synchronous throw (`navigator.clipboard` undefined → `TypeError` on property access) and a rejected `writeText` promise land in the same failure path. Canonical form: inside a `try/catch`, call `navigator.clipboard.writeText(value)` **without** optional chaining — accessing `.writeText` on an undefined `clipboard` throws synchronously and the `catch` handles it. Do **not** write `navigator.clipboard?.writeText(value)`: with `?.` an absent `clipboard` short-circuits to `await undefined`, which resolves successfully, the `catch` never fires, and the code falsely shows `Copied` — the exact outcome the absent-API test forbids. (Equivalent alternative: an explicit `if (!navigator.clipboard) throw` before the call; pick one form, not the `?.` one.)
   - Show `Copied` briefly after success. Any transient status timer (the `Copied` timer **and** the failure-hint timer, if the hint auto-dismisses) must be tracked and cleared both on unmount and at the start of each new copy attempt (so a rapid second copy replaces, not races, the prior timer) — no post-unmount or stale-timer state update leaks.
   - Because `writeText` is awaited, the component may unmount before it settles: guard the post-`await` status update behind an "is still mounted" check so a late resolve/reject does not write to a torn-down component.
   - On failure (rejection **or** absent API), focus the textarea, call its native selection method, and surface a brief visible failure hint (so the user knows to Cmd+C) instead of `Copied`.
   - Do not add network calls, persistence, or legacy clipboard dependencies.
