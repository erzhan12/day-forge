# Technical Implementation Plan — GitHub Issue #161

`block_detail` parses PATCH JSON and performs membership checks without enforcing the object-shaped request contract or request-size limit used by sibling endpoints. Add the same guards so malformed or oversized payloads return stable client errors before validation or database mutation.

## Edit Points

- `backend/tests/test_views.py` — `TestBlockDetail`
- `backend/schedules/api.py` — `block_detail(request, pk)`, PATCH branch
- `docs/api.md` — PATCH block error table (~lines 117-119): add the `413 body "Request body too large."` row and clarify the `400 body` case now also covers non-object JSON, matching the `reorder_blocks` table (~line 203).

## TDD: Red–Green–Refactor

### 1. RED — Add failing regression tests first

In `TestBlockDetail`:

- Add a parameterized test over `[], None, "oops", 123, True, False, "start_time"`, serialized with `json.dumps`. Include the booleans (`bool` subclasses `int`, so `"start_time" in True` also raises today) and a field-name string (`"start_time"` — passes the `in` check then `data[field]` raises); a `data`-value denylist would miss these, whereas the `isinstance(data, dict)` guard covers them all.
- For every payload, PATCH the existing block and assert:
  - HTTP 400.
  - Exact response: `{"errors": {"body": "Request body must be a JSON object."}}`.
  - After refreshing from the database, the block’s persisted fields **and `schedule.status`** match snapshots taken before the request. `schedule.status` is essential: the array/string no-op path still calls `mark_active_on_edit()`, which flips the default `draft` fixture to `active` — a block-column-only snapshot would miss that mutation.
- Add an oversized PATCH-body test mirroring `TestCreateBlock.test_oversized_body_returns_413` (assert 413 + the `"Request body too large."` envelope) and add the same no-mutation snapshot assertions used above (the mirrored create test asserts status+envelope only).
- Run the new `TestBlockDetail` tests and confirm they fail today: scalar/bool/field-name-string payloads currently raise `TypeError` (the default `Client(raise_request_exception=True)` re-raises rather than returning 500) and `[]`/`"oops"` return a misleading 200, while the oversized body is not rejected early.

### 2. GREEN — Add the minimal guards

In `block_detail`, after the DELETE branch and before parsing PATCH JSON:

1. Call `_reject_oversized_body(request)`.
2. Return its response immediately when non-`None`.
3. Keep the existing `json.loads(request.body)` and invalid-JSON handling.
4. Immediately after successful parsing, add `if not isinstance(data, dict):` returning the exact sibling-endpoint 400 envelope.
5. Ensure this type guard appears before `pending` creation and every membership check such as `"start_time" in data`.

Run the targeted tests and confirm all invalid payloads and oversized bodies are rejected before transaction entry, model saving, or `mark_active_on_edit()`.

### 3. REFACTOR — Align with sibling endpoints

Compare the final guard sequence with the bare-`JsonResponse` siblings `create_block` (api.py:68-81), `reorder_blocks` (api.py:525-538), and `restore_blocks` (api.py:749-762). Keep guard ordering, status codes, envelope shape, and message text identical. Do **not** model on `schedule_settings` (it lives in `settings_api.py:21-37` and adds a `Cache-Control: private, no-store` header the block endpoints do not use). Avoid unrelated validation or endpoint changes.
