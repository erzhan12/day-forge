# 0084 — Resolve AI category labels and localised forms to slugs (issue #209)

## Context

In multi-turn chat, naming a category in the user's own language fails the whole
turn with **HTTP 502** and shows an internal validation string to the user:

```
AI chat response failed action validation:
action[0]: changes.category must be one of ['health', 'other', 'personal', 'work']
```

Repro (`frontend/scripts/playwright/ai-chat-clarifying-question.mjs`, real provider):
turn 1 `запланируй встречу` → block created; turn 2 `в 14:00 на час, рабочая` → 502.
The model puts the user's own word (`рабочая`) into `changes.category` instead of
the slug `work`. The English turn `at 14:00 for an hour, work` → 200.

Root causes (verified):

- `backend/ai/schemas.py:154-158` (update `changes.category`) and `:253-256`
  (top-level `category`) accept only an **exact** slug. There is no
  slug/label normalisation anywhere in `backend/ai/`, so even the label `Work`
  is rejected.
- `backend/ai/service.py:392-405` (`run_chat`) and `:275-285` (`run_draft`) raise
  `AIParseError` if **any** action fails, dropping the whole turn/draft.
- `backend/ai/views.py:79` maps `AIParseError` → 502, and `:1208` (chat) / `:969`
  (draft) return `{"errors": {"detail": str(e)}}`. The frontend shows `detail`
  verbatim (`frontend/src/utils/errorMessage.ts:8`).
- `backend/ai/prompts.py:108-115`: the chat `update` description lists
  `category` but never says it must be the **slug**. Hard rule 4 (`:159`, draft
  `:256`) renders `slug (label)` pairs via `_category_text` (`:43-45`), which
  invites label or free-text output.

## Decisions (agreed)

1. **Resolution:** exact slug → case-insensitive slug or label → otherwise unresolved.
2. **Unresolved on `add`** (chat and draft): fall back to the sink slug. This
   matches Hard rule 4's "Default to `other` if unclear".
3. **Unresolved on `update`:** drop `category` from `changes` and apply the rest.
   If `category` was the only change, drop the action. In **both** cases chat
   **asks which category was meant**, so the drop is never silent. Never
   quietly recategorise an existing block to the sink.
4. **Scope:** chat **and** draft, through one shared helper.
5. Remaining genuine `AIParseError`s (bad JSON, bad times, unknown keys) keep
   **502**. The provider did return malformed output, so 502 Bad Gateway stays.
   Only the user-facing message becomes generic; the detail goes to the audit row.

## Changes

### 1. New module `backend/ai/category_resolution.py`

- `resolve_category(value, categories) -> str | None`
  - `categories`: list of `(slug, label)` pairs. When the caller has no
    per-user catalog, use the `prompts._DEFAULT_CATEGORIES` pairs.
  - Non-`str` value → `None`. Leave it to schema validation, which still rejects
    it as malformed.
  - Step 1: `value` in slugs → return it unchanged.
  - Step 2: `key = value.strip().casefold()`. Return the first slug whose
    `slug.casefold()` or `label.strip().casefold()` equals `key`. Usually at
    most one matches: slugs are unique per user, and labels are unique
    case-insensitively per user (`unique_user_category_label_ci`,
    `backend/schedules/models.py:191-193`). That constraint uses SQL
    `Lower(Trim(...))`, though, and SQLite's `LOWER` folds ASCII only, so
    `Работа` and `работа` can coexist while Python `casefold` matches both.
    Therefore the **first match in catalog order wins**, which also covers the
    `_DEFAULT_CATEGORIES` fallback.
  - Otherwise `None`. No fuzzy matching, stemming or translation: inflected
    forms like `рабочая` are handled by the prompt (§3), and the fallback below
    covers the model misbehaving anyway.
- `normalize_action_categories(actions, categories, sink_slug, known_task_ids) -> NormalizeResult`
  - A pure function. Returns a **new** list (never mutates the input list or
    its dicts) plus a tuple of
    `UnresolvedCategory(original_index, task_id, value, dropped: bool)`
    records.
  - Leave untouched: entries that are not dicts, and actions whose category is
    present but not a `str` (except `null` on an add, see below). They keep failing validation exactly as today.
  - `add`:
    - `category` = `resolve_category(...)`, or `sink_slug` if unresolved.
    - An absent `category` key, or `"category": null`, also gets `sink_slug`,
      per Hard rule 4's "Default to `other` if unclear". These are the only
      cases where the value is supplied rather than rewritten. Any other
      non-str value on an add is left untouched and still fails validation.
    - Add fallbacks are never recorded: they are expected behaviour, not
      something to ask about.
  - `update` whose `changes` is a plain dict with a `str` `category`:
    - **Resolved:** rewrite it to the slug.
    - **Unresolved, other changes remain:** remove the key and keep the
      action. Record `UnresolvedCategory(..., dropped=False)`, so the user is
      told (§4) instead of the block being quietly retimed with its old
      category.
    - **Unresolved, `category` was the only change:** drop the action from
      the returned list and record `UnresolvedCategory(..., dropped=True)`.
      Drop only when the action would otherwise be valid. Guard: run
      `validate_action_shape(action, allowed | {value}, allow_untimed_add=True)`
      on the original action; it must return no errors, and `task_id` must be
      in `known_task_ids`. If either check fails, leave the action untouched
      so it fails validation (502) as today. A malformed action or unknown
      block never turns into a 200 question.
  - Other action types carry no category and pass through as-is.
- Logging: `logger.debug` only, with action type, `task_id` and outcome
  (`rewritten` / `sink` / `dropped`). **Never log the unresolved value**: it is
  the user's own wording, and the audit row's `raw` already holds it.

- Shared: build `category_pairs` and `sink_slug` once per call, exactly as the
  prompt call already does (`:248`, `:340`):

  the `is_sink` slug or `"other"`. The helper must use the **same** fallback
  the prompt renders, so an empty list uses the defaults. The existing

- `run_chat`: after `validate_chat_response_envelope` passes (`:381-386`) and
  before the per-action loop (`:394`), run `normalize_action_categories` on
  `parsed["actions"]`, with `known_task_ids = {b.id for b in blocks}`.
  Validate and return the **normalised** list.
- `AIChatResult` (`:102`): add `unresolved_categories: tuple = ()` (default keeps
  the positional construction in the tests, e.g.
  `AIChatResult("{}", [...], "Changed", None)`, working). Update its docstring
  (`:105-108`): `parsed_actions` may now be empty with `ask` null **and**
  `unresolved_categories` non-empty. That is a server-ask turn, not chit-chat.
- `run_draft`: normalise before `validate_draft_response` (`:280`). Guard with
  `isinstance(parsed, dict) and isinstance(parsed.get("actions"), list)` so
  envelope errors still come from the validator. Pass the normalised actions
  through to `AIDraftResult`, with `known_task_ids = set()`. `run_draft`
  explicitly discards any `unresolved` records: a draft `update` could still
  produce a `dropped=False` record, but `validate_draft_response` rejects any
  non-add anyway.
- Normalising before validation means `raw_response_text` keeps the model's
  original word for the audit row, while `parsed_actions`/`actions_json` and the
  apply path see only slugs.
- Invariant: if every action was an update dropped for its category, `actions`
  becomes `[]`, `ask` is `null` and `unresolved_categories` is non-empty. The
  view handles this (§4) before its chit-chat branch. The envelope rule "ask is
  null when actions is non-empty" is unaffected: a non-empty model `actions`
  already implies `ask` was `null`.
- **One index space.** "`parsed_actions`" means the **normalised** list
  everywhere:
  - every downstream consumer: `find_replayed_actions`, `_apply_actions_sync`
    with its live-catalog category recheck (`views.py:789-801`),
    `plan_mutations`, `create_titles`, and every `_action_error` /
    `PlanError` `action_index`;
  - the stored `actions_json` and the response/`outcomes_json` `action_index`.

  `docs/api.md:378` ("Zero-based index into the model's `parsed_actions`")
  stays true for every variant. Dropped updates get **no** outcome entry,
  because they have no index in that list. Instead they are recorded in the
  chat audit payload under `unresolved_categories` (§4), keyed by
  `original_index`, the position in the model's own `actions` inside `raw`.
  That field lives in a separate, explicitly named index space, so the two
  never mix.

### 3. `backend/ai/prompts.py`

- Chat `update` description (`:108-113`): add one sentence. `changes.category`
  must be a category **slug** from Hard rule 4 — never the label or the user's
  own wording, whatever language the user writes in (e.g. a user saying
  "рабочая" means slug `work`).
- Chat Hard rule 4 (`:159`) and draft rule 4 (`:256`): state that the value
  emitted is the **slug** (the part before the parentheses), not the label.
  Keep `_category_text`'s `slug (label)` rendering; the label is what lets the
  model map the user's wording.
- **Append chat Hard rule 12** after rule 11 (rule 11 spans `:199-215`, so
  the new text starts at `:216`). Per `RULES.md:165`, append and never renumber.

  > 12. When the previous assistant turn asked "Which category should X use:
  > …?" **and the latest user turn answers that question**, resolve the answer
  > by coreference to that block and re-emit it as a single update with only
  > `changes.category` set to the chosen **slug**; do not add a new block. Map
  > the answer to the slug via the labels in rule 4 even when the user answers
  > in their own language or wording (e.g. "рабочая" → `work`). Any other
  > latest turn (a new command that ignores the question) is handled normally
  > under rule 11.

  Also amend the two coreference parentheticals **in place**: rule 2(iii)
  ("Hard rule 3 primarily, and Hard rule 9b only when…") and rule 11(a)
  ("(Hard rules 2(iii), 3, 9b–9d)"). Each gains "12 when the prior ask was a
  category question", per the stay-aligned convention (`RULES.md:165`).
  Editing inside a rule is allowed; renumbering is not. The
  `(other than asking what to add)` count pinned by
  `test_ai_prompts_command_chat.py:380` must stay 2.

  The scoping clause matches rule 2(iii) (`:147-154`) and rule 11(a)
  (`:203-206`). Without it, a user who ignores the question and sends a fresh
  command could be coerced into a category update on the asked-about block.
  The "map via labels" sentence stops a re-ask loop: if the model echoed the
  user's wording again, the answer would itself be a dropped category-only
  update and be asked about again. Any repeat still costs a user turn, never a
  server loop, and typing a listed label always resolves (§1 step 2).

  The answer turn arrives with `is_ask: true`, because `useChat.ts:211` sets it
  from `ask !== null` regardless of `applied`. So `implicit_add`
  (`implicit_add.py:305`, `RULES.md:166`) and the replay guard
  (`replay_guard.py:235`, `RULES.md:162`) already stand aside. Without this rule a bare
  "Work" could be read as a fresh bare-name add. Hard rule 2 exception (iii)
  already routes an answer to a pending ask through coreference, and rule 12
  just names the target shape.

    - This covers the issue #209 repro exactly: the time change applies, and

## Risks

- **Slug/label cross-match:** a value could equal one category's slug
  case-insensitively and another's label. That can't happen with an exact
  slug (step 1 wins first); for the case-folded step, catalog order decides.
  Categories number at most 8 (`MAX_CATEGORIES`) and are user-curated, so this
  is accepted.
- **Sink fallback on add:** it may file a clearly-intended category under
  `other`. This matches existing Hard rule 4 behaviour; the prompt fix (§3)
  is the main lever.
- **Accepted category-ask losses** (consistent with existing precedent):
  - (a) When `_build_resolution_ask` wins in the apply branch, the category
    question is not re-asked later. The block keeps its old category, and only
    the audit row records it.
  - (b) If a sibling `remove` of the same `task_id` runs in the apply branch,
    the ask reads "that block".
  - (c) Only the first unresolved record is asked about when several blocks
    are unresolved.
  - (d) In the applied-plus-ask branch the model's `explanation` may claim
    the category change. It shows up in the undo label (`useChat.ts:262`,
    `pushUndo`), not the bubble, which shows the ask.
- **English-only server ask:** the category ask is English-only, consistent with
  every other server-built ask. Localising server asks is out of scope.
