# Feature 0031 — Periodic background refresh for external calendars (CalDAV + Google)

## Context

Today the unified external-tasks sidebar auto-polls Todoist + Habitica on a
tab-visibility-aware cadence (`useExternalTasksPoll`, `EXTERNAL_TASKS_POLL_INTERVAL_SECONDS`,
`external_tasks_poll_interval` prop, each source's silent `refreshTasks`). The two
external **calendar** panels (CalDAV via `useCalendar`, Google via `useGoogleCalendar`)
only fetch on mount and on date navigation — a user who leaves the day view open never
sees new/changed calendar events without a manual reload.

Goal: connected external calendars refresh on the **same** periodic, tab-visibility-aware,
date-anchored cadence that Todoist/Habitica already do, reusing the existing poll
mechanism rather than adding a second one.

### Decisions baked into this plan (from research)

1. **Single unified poller, not a parallel calendar poller.** `useExternalTasksPoll`
   already accepts a generic `refresh: (date) => void | Promise<void>` fan-out callback
   and owns the timer + visibility-pause + date-restart logic. Calendars join the same
   poll tick. The composable is renamed to reflect it now covers tasks + calendars
   (see Cycle 5 / "Frontend — composable rename"). One timer, one visibility listener,
   one interval knob.

2. **Calendar polls force `refresh=1` (cache bypass), mirroring tasks.** The task poll
   forces `refresh=1` because otherwise freshness is capped at the server cache TTL
   (`CALDAV_CACHE_TTL_SECONDS` / `GOOGLE_CACHE_TTL_SECONDS`, both default `300`), which
   would make a 60s poll largely pointless. Calendars adopt the same rule. **This
   requires a backend change**: unlike the Todoist/Habitica task views, the CalDAV and
   Google `events` views do **not** currently read a `?refresh=1` query param — they
   return the cache unconditionally on a hit. See Cycles 1–2.

3. **Rate-limit / cost note.** CalDAV = 1 upstream iCloud call per poll tick per
   connected user. Google = 1 upstream call **per connected Google account** per tick
   (multi-account: `GoogleCalendarAccount` is multi-row). The poll reuses the same
   `EXTERNAL_TASKS_POLL_INTERVAL_SECONDS` interval as tasks (default `60`), so no new
   env var and no new independent cadence. Do not add a separate calendar interval —
   the one knob keeps the "leave the day open" cost predictable. Neither calendar
   provider is a documented per-minute-throttled API the way Habitica is, so 60s is safe.

### Frontend — silent refresh in the calendar composables

- `frontend/src/composables/useCalendar.ts` — factor the existing `fetchEvents(date)`
  body into a private `_fetchEvents(date, { force = false, silent = false })`, exactly
  mirroring `useTodoist.ts`/`useHabitica.ts` `_fetchTasks`:
  - `force` → append `?refresh=1` to the `/api/calendar/events/${date}/` URL.
  - `silent` → skip the `state.loading = true` flip so existing events stay visible
    during a background refresh (no skeleton flash). The atomic commit, the
    dual commit-token guard (`latestRequestedEventDate` + `eventsRequestSeq`), the
    AbortController swap, and the `state.error = null` clear are all unchanged.
  - Keep `fetchEvents(date)` as the initial/date-change loader:
    `_fetchEvents(date, { force: false, silent: false })`.
  - Add `refreshEvents(date)`: `_fetchEvents(date, { force: true, silent: true })`.
  - Export `refreshEvents` from the returned object.

- `frontend/src/composables/useGoogleCalendar.ts` — same split as above against
  `/api/calendar/google/events/${date}/`. Preserve the Google-specific terminal-path
  logic (200-with-`account_errors`, the `503` disconnected branch) — **with one
  silent-mode divergence** (see below). Add and export `refreshEvents`.
  - **`silent` gates two things, not one.** (1) It skips the `state.loading = true`
    flip (no skeleton). (2) On the **whole-request-failure** branch (the non-503,
    non-ok terminal path — i.e. a **transport/HTTP-level** failure of the whole request:
    network drop, or a non-200/non-503 status like 500/502/504 — that today does
    `state.events = []` / `state.accountErrors = []` before setting `state.error`), a
    silent refresh must **NOT** blank `state.events` / `state.accountErrors` — it sets
    `state.error` only and leaves the last-good events on screen. **Note the scope of this
    branch:** an *all-accounts-provider-fail* result is **not** here — the backend returns
    HTTP **200** with an empty `events` list plus `account_errors[]` (`gcal_sync/views.py`
    ~line 240), so it flows through the `result.ok` success path (which legitimately sets
    `state.events = []` and surfaces the per-account errors), not this non-ok branch. This
    branch fires only on a genuine whole-request transport/HTTP failure. Rationale: the
    initial/date-change
    `fetchEvents` (non-silent) keeps the blank-on-failure behavior, but a **background
    poll** that blanks the panel on every transient provider blip (network drop, 502,
    504) would flash the Google events to empty for a full poll interval, then restore
    on the next success — a visible regression that `useCalendar.ts` and `useTodoist.ts`
    do **not** have (their generic-error paths already leave the list untouched; only
    the `503` disconnected path blanks — see `useTodoist.ts:150-167`,
    `useCalendar.ts:99-114`). Aligning Google's silent path with them is the whole
    point of a *silent* refresh. The `503` disconnected branch still blanks under
    silent (a real disconnect is not transient).
  - **Known limitation (out of scope for a full fix):** the success path replaces the
    whole list (`state.events = body.events`), and the server omits a per-account
    failure from `merged` while surfacing it in `account_errors`. So a *single*
    transient account failure on an otherwise-successful poll still drops that
    account's events for one interval (the panel shows its error banner). True
    per-account retention (merging the failed account's stale events forward) is a
    larger change to the merge model and is **explicitly not** in this feature — note
    it, do not build it. (The all-accounts-fail case is the same shape: it returns a 200
    with empty `events` + `account_errors`, so the success path blanks to empty and shows
    the banners; not addressed here either. The whole-request-failure fix above targets
    only genuine transport/HTTP failures, which is the case that most obviously should
    keep last-good events during a silent poll.)

  - Call `googleCalendar.refreshEvents(date)` only when
    `googleCalendar.state.statusKnown && googleCalendar.state.connected`.

- The poll `refresh` callback passed to the (renamed) poller fans out to **both**
  tasks and calendars from one place. **Prescribed shape (do not fold calendars into
  `refreshExternalTasks`):**
  - `refreshExternalTasks(date)` stays **task-only** — it remains the single fan-out
    point for tasks and is the handler wired to the manual task-Refresh button

    `externalPollActive = tasksBranch || calendarsBranch` is true. If the callback called
    `refreshExternalTasks(d)` unconditionally, then a tick that fired only because a
    **calendar** is visible (task rail **closed**) would still poll connected
    Todoist/Habitica — regressing the existing task gating, which polls tasks *only while
    the rail is open*. That is not free: Habitica costs two upstream calls per tick and is

    Gating each fan-out by its own branch keeps task polling rail-gated and calendar
    polling panel-visibility-gated. Factor `tasksBranch` and `calendarsBranch` as the two
    named computeds that also compose `externalPollActive` (below) so the callback and the
    `active` predicate cannot drift. `refreshExternalTasks` (task fan-out) and
    `refreshExternalCalendars` (calendar fan-out) each remain the single fan-out point for
    their own concern (the code comment at line 305 warns that two copies of a fan-out
    drift silently).

    over-broad calendars branch (e.g. bare `externalConnected`) does **fire a real

## Algorithm (poll tick, end state)

1. Poller timer fires every `external_tasks_poll_interval` seconds (default 60), only
   while `active` is true.
2. `pollOnce` early-returns if `document.hidden` (tab in background) — unchanged.
3. `pollOnce` calls `refresh(currentDate)`, which **gates each fan-out by its own
   activity branch** (NOT both unconditionally — the per-source `statusKnown && connected`
   guards are not enough on their own; see the fan-out bullet in *Files to change*):
   - `if (tasksBranch.value) refreshExternalTasks(date)` → per-source
     `todoist.refreshTasks` / `habitica.refreshTasks` (further gated on
     `statusKnown && connected`), each hitting `?refresh=1&…` silently. **Skipped entirely
     when the task rail is closed** even if a calendar drove this tick — otherwise a
     calendar-only tick would poll rail-closed Habitica and burn its rate budget.
   - `if (calendarsBranch.value) refreshExternalCalendars(date)` → per-source
     `calendar.refreshEvents` / `googleCalendar.refreshEvents` (further gated on
     `statusKnown && connected`), each hitting the calendar events endpoint with
     `?refresh=1` silently. **Skipped when no calendar panel is visible** even if the task
     rail drove this tick.
4. Each `refreshEvents` runs silent (no skeleton), forces server cache bypass, and
   atomically commits the fresh event list under the existing dual commit-token guard so
   an interleaving date navigation can never clobber a newer fetch.
5. On tab re-focus (`visibilitychange` → visible) the poller fires one immediate
   `pollOnce` — unchanged; now also refreshes calendars.
