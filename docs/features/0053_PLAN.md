# 0053 — Configurable global day window (issue #110)

## Context

Today the working-day window `06:00–23:00` is hardcoded in two independent
places and enforced inconsistently across the app:

- Backend: `backend/ai/prompts.py:30-31` (`DAY_START = "06:00"`, `DAY_END = "23:00"`).
  `templates_mgr/api.py` imports these (`_DAY_START_T` / `_DAY_END_T`, lines 15/50-51)
  and enforces them on template blocks; `ai/mutation_planner.py` imports them and
  **rejects** (does not clamp) AI actions against them (`day_start` / `day_end` params
  on `plan_mutations`). The prompt strings themselves are baked into module-level
  f-strings `SYSTEM_PROMPT_CHAT` / `SYSTEM_PROMPT_DRAFT` at import time.
- Frontend: `frontend/src/utils/scheduleTime.ts:4-7` (`DAY_START` / `DAY_END` /
  `DAY_START_MINUTES = 360` / `DAY_END_MINUTES = 1380`), consumed as module-level
  constants by `useDrag.ts`, `AddToScheduleDialog.vue`, `CategoryBreakdown.vue`,
  `GapSlot.vue`, `Schedule.vue`, and the timeline layout functions in
  `scheduleTime.ts` (`filterVisibleBlocks`, `computeRenderBounds`, `buildBaseDisplayItems`,
  `pushTrailingGap`, `clampToDay`).

Enforcement is currently uneven:
- Manual create/PATCH (`schedules/http.py:validate_time_range`, `validate_block_times`)
  check only `start < end` and 5-minute granularity — **NOT** day bounds.
- Template validation (`templates_mgr/api.py:122`, function `validate_template_blocks`
  at `templates_mgr/api.py:76`) and the AI planner (`ai/mutation_planner.py`) **DO**
  enforce the hardcoded bounds (by rejection).
- CalDAV / Google / Todoist / Habitica event & task placement have **NO** bounds
  enforcement; `create_block_from_event` (`schedules/api.py:154`) is the sanctioned
  off-grid path and only checks `start < end`. Feature 0026 deliberately lets
  from-event blocks land **outside** the window (e.g. a `00:00–00:30` calendar event
  clamped to the day start) — see the collision note in enforcement item 6.

This feature makes the window per-user configurable (default `06:00–23:00`, no
behavior change for existing users), introduces a single backend
`ScheduleWindow` value object consumed by every validator/planner, threads the
saved window to the frontend via an Inertia prop, and refactors the frontend
timeline functions to **accept** bounds rather than import module constants.

**Placement note (per `tasks/todo.md:156`)**: do NOT add these fields to
`templates_mgr.UserPreferences`. A second unrelated preference in `templates_mgr`
is explicitly called out as the junk-drawer pattern to avoid. Instead add a new
`schedules.UserScheduleSettings` model — schedule-window policy lives with the
schedules domain.

### Window rules (canonical, shared by every surface)

- Format: `HH:MM`, 24-hour.
- Both bounds aligned to the 5-minute grid (`minute % 5 == 0`).
- Same calendar day, `start < end`. **Overnight windows (e.g. `20:00–04:00`) are
  NOT supported** — rejected at validation.
- Default: `day_start = 06:00`, `day_end = 23:00`.

### Clamp / reject / skip / no-mutate semantics (which surface does which)

The issue's "a newly-calculated interval that crosses one boundary is clamped"
rule is **not** uniform across surfaces — the planner historically *rejects*, and
that behavior is intentionally preserved. Explicit per-surface policy:

- **Manual create, calendar/CalDAV/Google from-event placement, external-task
  timed placement** → **clamp-one-boundary**: if a new interval crosses exactly
  one boundary, clamp that boundary; if the clamped interval stays non-empty
  (`start < end`) create it, otherwise (**fully outside**) **skip** (do not create)
  and report skipped to the UI. Clamp only the boundary that crosses — never
  rewrite the opposite, in-window boundary.
- **Manual PATCH / drag / reorder** → validate/clamp **only the boundary the
  client actually changed**. An unchanged stored boundary — including legacy
  out-of-window / off-grid (feature 0026) — is **never revalidated or rewritten**.
  So a PATCH of `end_time` on a stored `05:00–07:00` block with a narrowed
  `08:00` day-start keeps `start=05:00` untouched. Metadata-only edits (title,
  category, completion, sort_order) always stay valid.
- **AI (draft + chat)** → **reject, do not clamp**. Silently rewriting the model's
  proposed times is worse than surfacing an actionable error; the system prompt
  already asks the model to respect the window. The existing planner/`_apply_add`
  reject behavior is retained, only re-keyed off the per-user window.
- **Narrowing** the window does **NOT** auto-edit, crop, or delete existing blocks
  or templates. Blocks outside the new window stay **visible** on the timeline
  (see the `filterVisibleBlocks` note in Phase 2B — real stored blocks always
  render; only gap/stub synthesis and render bounds use the window).

Add `UserScheduleSettings`:

  invariant — so a bare `objects.create(day_start=time(6,3))` would otherwise persist

  (a) `models.CheckConstraint(check=Q(day_start__lt=F("day_end")), name="schedule_window_start_lt_end")`

  `save()`-based write — the PATCH API, admin ModelForm, `objects.create`, and
  `instance.save()`. **Caveat (state explicitly):** `QuerySet.update` / `bulk_create` /
  `bulk_update` bypass `save()` **and** Python validation, so they escape the grid check
  — the `CheckConstraint` still catches an inverted pair at the DB, but not off-grid. No
  code path in this feature writes settings via bulk ops (only the PATCH API and admin,
  both `save()`-based); note this boundary in `RULES.md` so a future bulk writer doesn't
  silently bypass validation.

(`makemigrations schedules`) — includes the table and the `CheckConstraint`.

### `backend/schedules/window.py` (new — the ONLY backend window representation)

Add a frozen value object + canonical lookup, structurally mirroring
`templates_mgr/preferences.py`:

- `@dataclass(frozen=True) class ScheduleWindow` with fields `day_start: datetime.time`,
  `day_end: datetime.time`. Convenience derived accessors used by call sites:
  `start_str` / `end_str` (`"%H:%M"`), `start_minutes` / `end_minutes` (int minutes
  since midnight).
- `DEFAULT_DAY_START = datetime.time(6, 0)` / `DEFAULT_DAY_END = datetime.time(23, 0)`
  and `DEFAULT_WINDOW = ScheduleWindow(DEFAULT_DAY_START, DEFAULT_DAY_END)` — these
  are the **only** sanctioned static constants; they are defaults/test helpers, not
  runtime policy read by validators.
- `validate_window(day_start_str, day_end_str) -> tuple[ScheduleWindow | None, dict | None]`:
  parse `HH:MM` (format error), 5-minute grid check, same-day + `start < end`
  (rejects overnight because a same-day `start < end` cannot be overnight), returns
  structured `{field: message}` errors keyed by `day_start` / `day_end`.
- `get_schedule_window(user) -> ScheduleWindow`: `get_or_create` the row with
  defaults, return frozen DTO. Same **single-user request-scoped contract**
  docstring as `get_user_preferences` (no looping / N+1).
- `clamp_boundary(start, end, window, *, clamp_start, clamp_end) -> tuple[time, time] | None`:
  clamp **only** the boundaries flagged (`clamp_start` → `start = max(start, day_start)`;
  `clamp_end` → `end = min(end, day_end)`). Return `None` (→ caller skips as
  fully-outside) when either **(a)** the result is empty (`start >= end`), **or (b)** a
  flagged boundary lands entirely past the *opposite* bound — a supplied `start > day_end`
  or supplied `end < day_start`. Case (b) matters because a one-sided clamp only pulls a
  value toward the window from the near side: without it, changing the start of a legacy
  `23:30–23:50` block to `23:35` (window `06:00–23:00`) would be accepted unclamped even
  though `23:35` is wholly past `day_end`. So each flagged boundary must be **inside
  `[day_start, day_end]`** after clamping, not merely on the correct side of its own
  bound. Whole-interval placement (manual create, from-event) passes both flags;
  changed-boundary PATCH passes only the flag(s) for the boundary the client sent — this
  is what prevents the "PATCH `end_time` silently rewrites the inherited `start`" bug
  while still catching a changed boundary that jumps past the far edge.

The `ai.prompts` module-level `DAY_START/DAY_END` become a default fallback only
(referenced by `DEFAULT_WINDOW` construction/tests), never runtime policy read by
validators.

### `backend/schedules/admin.py`

Register `UserScheduleSettings` (admin + optional inline on User), mirroring
`UserPreferencesAdmin`. The admin form inherits `clean()` validation, so it cannot
save an invalid window through the admin UI either.

### Skip signal contract (backend → frontend)

A "fully outside the window, not created" outcome needs a shape the client can
distinguish from an overlap/validation 400. Current client behavior:
`frontend/src/composables/useHttp.ts:84-100` discards non-`errors` fields on a 400
and treats any 2xx as success (and `AddBlockForm.vue`/`useSchedule` push an undo on
success — a false undo if nothing was created). **Do not nest `code`/`window` inside
the `errors` object**: `ApiResult.errors` is typed `Record<string, string | string[]>`
(`useHttp.ts:22-26`) and `AddBlockForm.vue:72-73` does `Object.values(errs).join(...)`,
so an object value would type-fail and render `"[object Object]"`. Define the contract
as a **422 with top-level sibling fields**:
**`422 {"skipped": true, "code": "outside_window", "detail": "...", "window": {"start","end"}, "errors": {...string map...}}`**
(distinct from a `400` overlap/validation and a `200` create). Update `useHttp.ts` to
surface the top-level `skipped`/`code`/`window` fields on the `ApiResult`, and have
`AddBlockForm.vue` / `AddToScheduleDialog.vue` / `useSchedule` **branch on
`code === "outside_window"` BEFORE the `errors` flatten** — mapping it to the
non-blocking "Skipped — outside your day window HH:MM–HH:MM" notice and pushing **no**
undo. (A `200 {"skipped": [...]}` batch shape is the alternative for multi-item
from-event/calendar responses that partially skip — pick per call site; single-block
create uses the `422` form.)

## Phase 2B — Frontend (window as data, timeline accepts bounds)

### `frontend/src/utils/scheduleTime.ts`

Refactor the timeline functions to **accept bounds as parameters** instead of reading
module constants:
- Keep `DAY_START` / `DAY_END` / `DAY_START_MINUTES` / `DAY_END_MINUTES` exported
  **only as defaults / test helpers**, not as runtime policy.
- Add a `ScheduleWindow`-shaped param (e.g. `{ startMinutes, endMinutes, start, end }`)
  threaded through `computeRenderBounds`, `computeTrailingAnchor`,
  `buildBaseDisplayItems`, `pushTrailingGap`, `clampToDay`. Default the param to the
  static constants so existing call sites and unit tests keep compiling during the
  migration, then update real call sites to pass the prop-derived window.
- **Stored-block geometry must NOT be clamped to the window.** Simply exempting
  `filterVisibleBlocks:47-53` is insufficient — two more formulas currently clip to the
  window and would corrupt a legacy out-of-window block:
  - `computeRenderBounds:101-108` does `firstStart = max(blockStart, windowStart)` /
    `lastEnd = min(blockEnd, windowEnd)`. A stored `06:00–07:00` block under a narrowed
    `08:00–23:00` window becomes `max(360,480)…min(420,end)` → an **inverted / negative
    duration**.
  - `buildBaseDisplayItems:223-230` clamps each block's rendered rect to the window
    (the 0026 visible-slice behavior).

  Specify instead: **stored blocks render at their true geometry, never clamped to the
  window** — this retires the 0026 overlapping display-clamp (a `00:00–06:30` from-event
  slice is now shown at full true height, not clipped at the day start). Compute the
  extents in two steps to avoid an out-of-window block polluting the stub/now math:
  1. **Base** = the existing `computeRenderBounds` stub/now logic run over the
     **window-overlapping subset** of blocks only (a wholly-outside block must not feed
     the trailing-anchor / compression math, or it produces inverted/truncated base
     bounds).
  2. **Expand** to include every stored block's true geometry:
     `renderStart = min(baseStart, min(all block starts))`,
     `renderEnd = max(baseEnd, max(all block ends))`.
  Do **not** union raw `windowStart`/`windowEnd` (that blows a tight in-window day out to
  the full window and wipes the compact edge stubs). A fully in-window day keeps its
  existing tight, stub-compressed bounds unchanged; an out-of-window block expands the
  canvas to stay on-screen at correct size.
  **Flow-layout spacer:** the timeline lays items out sequentially, so an out-of-window
  block sitting before the window's first in-window item needs an **inert spacer**
  occupying the gap between them — otherwise later items render at the wrong vertical
  offset, or the outside interval becomes a clickable "add here" gap. Specify the spacer
