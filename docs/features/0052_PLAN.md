# 0052 — Deployment CI: add the documented backend Ruff gate

## Context

Issue #137: the deploy pipeline (`.github/workflows/deploy.yml`) omits the
backend Ruff lint step that `README.md` documents as the canonical backend
lint command (`uv run ruff check backend/`). Lint regressions can therefore
reach image build/push and deployment ungated. This change adds that command
as a required step in the deploy workflow's `test` job, positioned so a lint
failure gates everything downstream (pytest, frontend checks, and the
`build-and-push` / `deploy` / `health-check` jobs that transitively depend on
`test`).

This is a CI/workflow-only change: no application code, no DB migration, no
frontend build. The only content touched is a GitHub Actions workflow file and
(if needed) README wording.

### Verified current state (main @ 25c67e8)

- `uv run ruff check backend/` currently exits **0** ("All checks passed!").
  The three `I001` violations referenced in the issue
  (`backend/ai/views.py:7`, `backend/tests/test_ai_views.py:7`,
  `backend/tests/test_ai_views_chat.py:8`) are **already fixed**. This plan
  does NOT re-fix them; it only verifies the exit-0 precondition holds.
- `README.md:108` already documents `uv run ruff check backend/` (under
  "Lint / type-check"). The CI step must use this **identical** command string
  so README and CI stay aligned. No README change is expected; confirm the
  string matches and only edit README if a divergence is found.
- The `test` job in `deploy.yml` currently has steps in this order:
  `checkout` → `Install uv` → `Set up Python` (3.14) → `Install backend deps`
  (`uv sync --frozen`) → `Run backend tests` (`uv run pytest backend/tests/ -q`)
  → `Set up Node` → `Install frontend deps` → `Frontend prod audit` →
  `Frontend type-check + tests`.
- `build-and-push` has `needs: test`; `deploy` has `needs: build-and-push`;
  `health-check` has `needs: deploy`. So gating the `test` job gates the entire
  downstream chain including image build/push and deploy.

## Files to change

- `.github/workflows/deploy.yml` — add one step to the `test` job:
  - **Name:** `Run backend lint` (or `Backend lint (ruff)`).
  - **Command:** exactly `uv run ruff check backend/` (identical to README:108).
  - **Position:** immediately **after** the `Install backend deps`
    (`uv sync --frozen`) step and **before** the `Run backend tests`
    (`uv run pytest ...`) step. Ruff needs the synced env; placing it before
    pytest means a lint failure short-circuits the job before tests, frontend
    checks, and the whole downstream build/deploy chain.
- `README.md` — **only if** the documented command diverges from the CI step
  (it currently does not). Keep both referencing `uv run ruff check backend/`.

No other files. Do not touch `pyproject.toml` / ruff config — the command and
its rule set are already correct (exit 0 today).

## Implementation order (TDD / red → green → refactor)

This is a CI change, so the "test" is the workflow itself. The red→green→refactor
cycle is realized by driving an intentionally-introduced Ruff violation through
the command and confirming the new gate catches it **before** build/push.

Follow this order strictly. Do **not** write the workflow fix first and
"verify later."

> **Workflow-trigger constraint (load-bearing for CI observation).**
> `.github/workflows/deploy.yml` triggers on `push: branches: [main]` and
> `workflow_dispatch` **only** (see `on:` block, deploy.yml:3-11). A push to a
> throwaway/feature branch therefore triggers **nothing** — it cannot be used
> to observe the gate. The **primary** RED proof is the local non-zero exit of
> the command (step 2), which is deterministic and needs no CI run. Any
> optional CI-level observation must use `workflow_dispatch` on the branch that
> carries the change, and — because a `workflow_dispatch` run that stays green
> would proceed all the way through `deploy` — it must only ever be run with
> the intentional violation **present** (so the run is guaranteed to fail at the
> lint step and never reach `build-and-push`/`deploy`). Never dispatch a
> green-tree run of this workflow from a non-main ref as part of this
> verification.

### Red (prove the command can fail)

1. **Establish the exit-0 precondition (baseline green of the command):**
   run `uv run ruff check backend/` locally and confirm it prints
   "All checks passed!" and exits `0`. This confirms the issue's already-fixed
   scope note and that a fresh violation is the only way to make it fail.
2. **Introduce an intentional Ruff violation** in a backend file to serve as
   the failing test. Use a minimal, unambiguous violation that Ruff's default
   config flags — e.g. an unused import (`F401`) added at the top of a throwaway
   spot such as `backend/ai/views.py`, or reorder an import block to trip
   `I001`. Confirm locally that `uv run ruff check backend/` now **exits
   non-zero** and reports the violation. **This local non-zero exit is the
   authoritative RED state** — it proves the command (and therefore the future
   step) can fail. Keep this violation in the tree for step 3's Green-time CI
   check; it is removed in step 5.

### Green (add the gate, observe it fire, then make the real tree pass)

3. **Add the `Run backend lint` step** to `.github/workflows/deploy.yml` in the
   position specified above, using the exact `uv run ruff check backend/`
   command. (The step must exist before any CI-level failure can be observed —
   this is why the "observe the CI lint step fail" check lives here in Green,
   not in Red.)
4. **(Optional) Observe the gate fire in CI:** with the step now present **and**
   the step-2 violation still in the tree, trigger the workflow via
   `workflow_dispatch` on the branch carrying the change and confirm the `test`
   job **fails at the `Run backend lint` step**, that later steps (pytest,
   frontend) do not run, and that `build-and-push` (`needs: test`) shows as
   skipped so the image build/push and `deploy` jobs never start. This is the
   CI-level red observation; it is optional because the local non-zero exit in
   step 2 plus GitHub Actions' step-fails-job / `needs:`-gates-dependents
   semantics already guarantee the behavior. Do **not** attempt this via a plain
   branch push — the `push` trigger is `main`-only and would not run.
5. **Remove the intentional violation** from step 2 so the working tree is
   clean. Re-run `uv run ruff check backend/` and confirm exit `0` again.
6. **Validate the YAML** is well-formed (e.g. `python -c "import yaml,sys;
   yaml.safe_load(open('.github/workflows/deploy.yml'))"` or an actionlint pass
   if available) so the new step doesn't break workflow parsing.

### Refactor (align docs, tidy)

7. **Confirm README ↔ CI command parity:** the CI step command string must
   equal `README.md:108`'s `uv run ruff check backend/` verbatim. If README
   already matches (expected), no edit. If it diverges, update README so both
   reference the identical command.
8. Re-read the final `test` job step ordering to confirm: `uv sync --frozen`
   → **`uv run ruff check backend/`** → `uv run pytest backend/tests/ -q` →
   Node/frontend steps, and that `build-and-push`/`deploy`/`health-check`
   `needs:` chain is unchanged.

## Acceptance criteria (from issue #137)

- `uv run ruff check backend/` is a required step in the deploy workflow's
  `test` job.
- The command exits `0` locally and in GitHub Actions on the clean tree
  (the three `I001` violations are already resolved on main; this plan verifies
  rather than re-fixes them).
- An intentionally introduced Ruff violation causes the workflow `test` job to
  fail at the lint step, **before** image build/push (`build-and-push`) or
  deployment (`deploy`) — enforced by the existing `needs:` chain.
- README and CI reference the identical backend lint command
  (`uv run ruff check backend/`).

## Risks / what could break

- **Step placement:** if the step is added after pytest instead of before,
  lint failures would still gate build/push (job-level failure) but would waste
  the pytest run. Placing it before pytest is the intended, fail-fast behavior.
- **Command drift:** hardcoding a different ruff invocation (e.g. adding
  `--select` or a path other than `backend/`) would break README↔CI parity.
  Use the exact README string.
- **Env availability:** ruff must run after `uv sync --frozen` so the pinned
  ruff from the lockfile is present; running it before the sync would fail with
  a missing-tool error unrelated to lint findings.
