# 0066 — PiP next-block title and countdown during between-block pauses

## Technical requirements

- Limit the change to the Document Picture-in-Picture focus indicator.
- Preserve the active unfinished-block state from feature 0049: progress bar plus remaining minutes, with no block title.
- Add a next-block state only while the indicator is idle:
  - Show the nearest block whose `start_time` is strictly after now.
  - Include completed blocks; never filter on `is_completed`.
  - Show its title and minutes until its start.
  - Render an empty or whitespace-only title as `Untitled`.
  - Format the countdown through `formatRemainingMinutes`, retaining the accepted `Xm left` / `Xh left` copy.
  - Do not render a progress bar for this countdown.
- Preserve the existing neutral state (`—` plus screen-reader text `No active block`) when no valid later block exists.
- Preserve the `nowDate === null` guard so schedules viewed on dates other than today cannot drive the next-block state.
- Keep `PIP_TITLE` equal to the generic `Focus`; only the PiP body may contain the next block’s title.
- Treat malformed scheduling data conservatively:
  - "Unparseable" here means `timeToMinutes` returns a non-finite result (`NaN`) — its contract is `time.split(":").map(Number)`, so a non-`HH:MM` string yields `NaN`. This is the same finite-result convention already used by `progressRatio` and `findCurrentBlock`; the plan does not claim stronger validation (out-of-range values like `09:60` still parse to a finite minute, and non-string inputs are precluded because the backend serializes `start_time`/`end_time` as `TimeField` strings, so `TimeBlock.start_time`/`end_time` are always strings).
  - An unparseable (non-finite) start prevents next-block selection because chronological ordering cannot be trusted.
  - A selected future block with an unparseable end or zero/negative duration yields no next-block state.
  - The computed minutes until start must be finite and strictly positive.
- Use strict red-green-refactor in every code phase: add the failing tests first, verify that they fail for the expected missing behavior, add only the minimal implementation needed to pass, then refactor while keeping the targeted tests green.

## Helper contract and selection algorithm

Add `nextBlockAfter(blocks: TimeBlock[], nowMinutes: number | null, nowDate: string | null): TimeBlock | null` to `frontend/src/utils/focusIndicator.ts`.

The helper must operate as follows:

1. Return `null` immediately when either `nowMinutes` or `nowDate` is `null`. `nowDate` is the existing today-only signal; it is not a block-date comparison.
2. Parse every block’s `start_time` through `timeToMinutes`.
3. If any start is non-finite, return `null`. A malformed start makes it impossible to prove which block is chronologically nearest, so the helper fails closed.
4. Retain only blocks whose parsed start is strictly greater than `nowMinutes`. A block whose start equals now is not “next.”
5. Sort the retained candidates without mutating the input:
   - Numeric start minute ascending.
   - `sort_order` ascending for equal starts, matching the repository’s deterministic schedule ordering.
6. Return `null` when no future candidate remains.
7. Inspect the first candidate only. Parse its end and require a finite, strictly positive `end - start` duration. Return `null` for unparseable, zero-duration, or negative-duration candidates rather than skipping to a later block.
8. Return the candidate without examining `is_completed`.

`nextBlockAfter` is called only when `indicatorActive` is false. This preserves active-state precedence and also handles a completed block containing now: `activeUnfinishedBlock` makes the indicator idle, while the strict future-start filter excludes the completed block being traversed and selects the nearest later start.

Note on malformed-duration blocks (no leak): a block whose duration is zero/negative/unparseable is never treated as the *active* block — `findCurrentBlock`'s half-open filter `start <= now < end` (`scheduleTime.ts`) matches no minute for an empty (`end <= start`) or `NaN` interval, so `activeUnfinishedBlock` never returns it. When such a block *contains* now its start is `<= now`, so it also fails the strict-after filter and is not a next-block candidate; and if its *start* is unparseable the whole-list guard returns `null`. There is therefore no path where a malformed block is "in progress" while the gap advertises a later title. Backend `TimeBlock.clean()` additionally rejects `start_time >= end_time` at validation time (a `clean()`/`full_clean()` check, not a DB constraint), making malformed spans near-impossible in stored data.

`Schedule.vue` derives minutes until start as the selected block’s parsed start minus `nowMinutes`. It returns `null` unless that result is finite and greater than zero. Formatting remains the responsibility of `FocusIndicatorView.vue`.
