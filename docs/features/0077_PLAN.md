# 0077 — User-timezone-aware calendar-day & analytics boundaries (issue #193)

## Problem

Persisted `UserScheduleSettings.time_zone` is the source of truth for AI `now()`
(draft/chat/placement) since feature 0071/#183. But three other code paths still
derive "today" from a *different* clock and ignore the stored setting:

- `backend/schedules/views.py`
  - `root_redirect` (line 33): `today = datetime.date.today().isoformat()` — host-OS
    local date (= UTC on the prod deploy, `settings.py:90` `TIME_ZONE = "UTC"`).
  - `login_view` post-auth redirect (line 60): same `datetime.date.today()`.
- `backend/analytics/views.py` (line 144): future-date gate
  `today = timezone.localdate()`; `parsed_date > today` → 400 "Analytics is past-only."
  (`timezone.localdate()` honours `settings.TIME_ZONE = "UTC"`, not the user's zone.)
- `backend/analytics/services.py`
  - `compute_review_stats` (line 60–61): default `now = timezone.localtime()`.
  - `compute_streak` (line 158–159): default `today = timezone.localdate()`, walks
    backward from yesterday over `ANALYTICS_STREAK_WINDOW_DAYS`.

**Consequence:** around UTC midnight a non-UTC user (Asia/Almaty UTC+5, America/
Los_Angeles UTC-8) is redirected to the wrong calendar date. `schedule_view`
(`views.py:80`) does `get_or_create` (and may set `auto_draft_pending`), so the wrong
date becomes a persisted empty/drafted day. Analytics rejects the user's real local
today as "future," and skip-block / streak boundaries roll over hours early or late.

**Already correct — do NOT touch:** AI views (`backend/ai/views.py:750,894,1124`) do
`timezone.localtime(timezone.now(), resolve_time_zone(schedule_settings.time_zone))`
after `get_schedule_settings(user)`. This plan copies exactly that pattern into the
three lagging paths.

## Design decision

### Shared helper — location + signature

Add to `backend/schedules/window.py` (alongside the existing `resolve_time_zone` +
`get_schedule_settings`, the two functions the issue mandates we reuse). No new module:
`window.py` already owns every timezone/window resolver and both dependencies live
there, so a new file would only fragment the single source of truth.

```python
def user_local_now(user) -> datetime.datetime:
    """User-local aware ``now`` from persisted settings.

    Mirrors the AI-view pattern (ai/views.py:750,894,1124): loads settings via
    ``get_schedule_settings`` and resolves the IANA zone via ``resolve_time_zone``
    (which falls back to UTC on missing/corrupt values). Returns an aware datetime
    in the user's zone.
    """
    settings = get_schedule_settings(user)
    return timezone.localtime(timezone.now(), resolve_time_zone(settings.time_zone))


def user_local_date(user) -> datetime.date:
    """User-local calendar date. Thin ``.date()`` over ``user_local_now``."""
    return user_local_now(user).date()
```

Two functions (not one returning a tuple) because callers want different things:
redirects and the future-date gate want the *date*; the analytics stats layer wants
the *datetime instant* (`compute_review_stats` needs `now.time()` to decide partial-day
skips). `user_local_date` delegates to `user_local_now` so the resolver logic lives in
exactly one place. Both go through `get_schedule_settings` → `resolve_time_zone`, so the
deliberate UTC fallback for missing/corrupt settings is preserved identically to AI.

Requires adding `from django.utils import timezone` to `window.py` (not currently
imported there).

### Services approach — pass `now`/`today` in from the view (thin services)

`compute_review_stats(schedule, *, now=None, ...)` and `compute_streak(user, *,
today=None)` already accept an injected instant/date and are covered by
`test_analytics_services.py` using fixed `NOON = datetime.datetime(2026,5,3,12,0,0)`
and `TODAY = datetime.date(2026,5,3)` constants (deterministic, no freezegun).

**Chosen:** the *view* resolves the user-local instant/date once via the shared helper
and passes it into the services. Services keep their existing `None`-default fallback
(`timezone.localtime()` / `timezone.localdate()`) unchanged.

Justification:
- Single source of truth: the request boundary already has `request.user`; the helper
  is a view-layer concern. Pushing `get_schedule_settings(user)` into the services would
  give the analytics endpoint two settings lookups per request (`analytics_view` already
  needs settings for the `schedule_window` prop, `views.py:37` import) and couple the
  DB-only, HTTP-agnostic service layer back to per-user settings resolution.
- Testability: the existing service tests inject `now=`/`today=` directly — that seam is
  preserved untouched. New coverage of the *wiring* (does the view pass the right local
  date?) belongs at the view layer and is exercised via `monkeypatch` of the view
  module's `timezone` — the pattern `test_analytics_views.py` already uses (`monkeypatch`
  on `Schedule.objects.select_for_update`, line 394).
- The helper's `user_local_now`/`user_local_date` are themselves unit-tested in
  `test_schedule_window.py` (or `test_analytics_services.py` if that is where window
  helpers live — see Tests to add), so the resolver + fallback is pinned once.

`analytics_view` calls both `recompute_review_from_schedule` (which forwards `now=` to
`compute_review_stats`) and `compute_streak` (via `_streak_payload`). Both call sites
must be threaded with the local instant/date.

**Where `recompute_review_from_schedule` / `_streak_payload` are called:** need to read
their exact call sites in `analytics_view` during GREEN and pass `now=`/`today=` through.
`_streak_payload(user)` (`views.py:99`) currently takes only `user`; extend it to accept
and forward a `today` (or resolve internally from `user` via the helper — pick forwarding
to match the "view resolves once" rule).

**MANDATORY single clock read (review B-P2-1):** `analytics_view` resolves the user-local
instant **exactly once** and derives the date from it — never call both `user_local_now`
and `user_local_date` (two independent `timezone.now()` reads can straddle local midnight
and disagree at the exact boundary this feature targets, and it doubles the
`get_schedule_settings` DB hit):

```python
now_local = user_local_now(request.user)   # single wall-clock read
today = now_local.date()
```

Pass `now=now_local` into `recompute_review_from_schedule(...)` and `today=today` into
`compute_streak` (via `_streak_payload`). This is a GREEN requirement, not a REFACTOR nicety.

**`schedule_view` invariant (review B-P2-2):** `schedule_view` has **no clock of its own**
(it only does `datetime.date.fromisoformat(date)`), so the redirect is the *sole authority*
for "today" and the date it chooses is what `get_or_create` persists — this is intentional
and matches pre-existing behaviour; no change to `schedule_view` is needed.

## Freeze-time convention note

The repo has **no** `freezegun` / `time_machine` dependency. Deterministic time in tests
is done two ways, both reused here:
1. Services: inject `now=`/`today=` kwargs (see `test_analytics_services.py` `NOON`,
   `TODAY`).
2. Views: `monkeypatch.setattr(...)` on the module's `timezone` (see
   `test_analytics_views.py:394`). Here we patch `schedules.window.timezone.now`
   (a `lambda: FIXED_AWARE_UTC`) because every changed path resolves "now" through the
   `window` helper. Patch `now` (returns aware UTC) rather than `localtime`, so the real
   `timezone.localtime(now, tz)` conversion is exercised end-to-end.
