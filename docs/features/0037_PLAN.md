# 0037 — De-duplicate `extractErrorMessage` across HTTP composables

## Description

The helper `extractErrorMessage(errors)` is copy-pasted into **12**
composables under `frontend/src/composables/`. Every body is logically
identical; the only difference is a hardcoded fallback string. One
composable (`useAnalytics.ts`) has already generalized the helper with a
`fallback: string` parameter and calls it in two places with different
strings.

This is broader than issue #66's named 4 composables (`useTodoist`,
`useTodoistAccount`, `useCalendar`, `useCalendarAccount`) — all 12 copies
are folded in.

**Goal:** extract one shared helper to
`frontend/src/utils/errorMessage.ts` with signature
`extractErrorMessage(errors, fallback)`, import it in all 12 callers
(each passing its own previous fallback string), delete every local copy,
and add a unit test for the shared helper. **No user-visible error string
may change.**

## Canonical extracted helper

`frontend/src/utils/errorMessage.ts` (new file, named export — matches the
existing `utils/` convention; there is **no** barrel/`index.ts`, so import
directly from the module path):

- Signature: `extractErrorMessage(errors: Record<string, string | string[]> | undefined, fallback: string): string`
- Body is exactly the already-generalized `useAnalytics.ts` version:
  1. `if (!errors) return fallback`
  2. `if (typeof errors.detail === "string") return errors.detail`
  3. `const first = Object.values(errors).flat()[0]`
  4. `return typeof first === "string" && first ? first : fallback`

The `errors` param type is verified identical across all 12 copies:
`Record<string, string | string[]> | undefined`.

## Unit test — `frontend/tests/errorMessage.test.ts`

Assert the shared helper's four branches:
1. `errors === undefined` → returns the passed `fallback`.
2. `errors.detail` is a string → returns `errors.detail` (ignoring the
   fallback).
3. `errors.detail` absent but another key holds a non-empty string (incl.
   nested arrays via `.flat()`, e.g. `{ field: ["boom"] }`) → returns that
   first flattened string.
4. `errors` present but yields no usable string (e.g. `{}`, or
   `{ field: [] }`, or first value is an empty string) → returns the
   `fallback`.

Include a case proving `detail` wins over other keys, and a case proving
an empty-string first value falls through to `fallback` (guards the
`&& first` truthiness check).

5. **Empty-`detail` asymmetry (preserved behavior — pin it).**
   `{ detail: "", field: ["boom"] }` returns `""` (empty string), NOT the
   fallback and NOT `"boom"` — because branch 2 (`typeof errors.detail === "string"`)
   is true for `""` and returns it immediately, short-circuiting the
   `.flat()` scan. Every current copy behaves this way, so the shared
   helper must too. Add an explicit test asserting this exact result so a
   future "tidy-up" that adds `&& errors.detail` to branch 2 (changing
   user-visible output) is caught.

Work strictly **red → green → refactor**. Do not implement the helper and
then bolt tests on afterward.

1. **RED — write the failing helper test first.**
   Create `frontend/tests/errorMessage.test.ts` importing
   `extractErrorMessage` from `../src/utils/errorMessage` (match the exact

   (the `useAnalytics` two-arg version). Re-run `npm test`; the new test
   passes. Existing composable tests still pass (local copies untouched
   so far).

3. **REFACTOR — migrate callers one at a time, staying green.**
   For each of the 12 files: delete the local `extractErrorMessage`, add
   the import, thread the correct fallback into every call site (preserve
   `statusToMessage(...) ?? ...` composition exactly). After **each** file,
   run its matching existing test where one exists
   (`useAI.test.ts`, `useCalendar.test.ts`, `useCalendarAccount.test.ts`,
   `useChat.test.ts`, `useDraft.test.ts`, `useAnalytics.test.ts`,
   `useGoogleAccount.test.ts`, `useGoogleCalendar.test.ts`,
   `useHabitica.test.ts`, `useHabiticaAccount.test.ts`,
   `useTodoist.test.ts`, `useTodoistAccount.test.ts`) so a regression
   is caught immediately; then run the full suite. (`useHttp`, the only
   caller-family file without its own composable test, has no
   `extractErrorMessage` copy, so nothing is left unguarded.)

   **Fallback-literal regression guard (mandatory — this is the whole
   point of the refactor).** `vue-tsc` only proves the arg *count*
   (`Expected 2 arguments, but got 1`); it does NOT prove the *value*.
   No existing composable test asserts these fallback strings today, so a
   swapped/typo fallback — especially between the near-identical
   `useCalendar.ts` (`"Calendar fetch failed"`) and `useCalendarAccount.ts`
   (`"Account operation failed"`) — would pass `npm test` + `vue-tsc` +
   the leftover-def grep while silently changing a user-visible string.
   Assert the exact previous fallback string at **every call site that
   resolves its message through `extractErrorMessage`** (not one per
   file — the account composables have two such sites,
   `useHabiticaAccount.ts:107,154`, `useTodoistAccount.ts:104,151`,
   `useCalendarAccount.ts:107,154`; a single per-file assertion + the
   file-level grep below cannot localize a typo at the *second* site).
   Add the assertion if the existing test does not already cover it.
   Note these are **characterization guards**, not red-first TDD steps:
   written against the *current* local helper they pass immediately
   (green), because the local copy already returns the same fallback for
   `errors: {}`. Their job is to fail the instant the migration threads a
   wrong/swapped literal into that call site. Write each one **before**
   editing its composable so the guard is in place when the swap could
   happen. (The genuine red→green cycle is the new
   `frontend/tests/errorMessage.test.ts` in step 1, which fails because
   the module does not yet exist.)

   **Reaching the fallback branch matters — pick the status deliberately.**
   `extractErrorMessage` only runs (and only returns the fallback) for
   certain inputs, which differ by call-site shape:
   - **Bare / 503-ternary sites** (`useHabiticaAccount`, `useTodoistAccount`,
     `useCalendarAccount`, `useGoogleAccount`, and the `: extractErrorMessage(...)`
     branch of `useChat.ts:257` / `useAI.ts:86`): mock a failed result with
     `errors: {}` (no `detail`, no usable value) and — for the two ternary
     sites — a status **other than 503**. The assertion then pins the
     file's fallback literal.
   - **`statusToMessage(...) ?? extractErrorMessage(...)` sites**
     (`useDraft.ts:97`; `useHabitica.ts:172,226`; `useTodoist.ts:167,221`;
     `useGoogleCalendar.ts:147`; `useCalendar.ts:142`): `statusToMessage`
     wins for the statuses it handles (e.g. Habitica/Calendar 401/502/504;
     Draft 422/429/503 — Draft 409 early-returns at `useDraft.ts:90-94`
     before either helper runs), so those never reach `extractErrorMessage`.
     Drive a **`default`-branch status** (`statusToMessage` returns `null`
     — any status not in its `switch`, or `undefined` on a network
     failure) together with `errors: {}` so control actually falls through
     to the shared helper's fallback. Do **not** reuse the existing
     401/502 mocks for this assertion — they assert the `statusToMessage`
     string and would not guard the shared helper at all.
   - **`useAnalytics.ts` is exempt** from adding new assertions: its two
     call sites (`:45` → `"Could not mark this day reviewed."`, `:64` →
     `"Could not save notes."`) are already parameterized and are NOT
     edited by this refactor. Note the two literals are *distinct*, so if
     its tests are ever touched, keep them site-specific.
