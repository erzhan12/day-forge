# 0068 — AI Chat Duration Resizing for Existing Time Blocks

## Scope and Design Decision

Implement duration changes only through `POST /api/ai/schedules/{date}/chat/`. Do not change manual editing, drag-resize, frontend controls, or `PATCH /api/blocks/{id}/`. No database migration is required.

Choose **Option B: schema + deterministic planner**, extended with a dedicated relative field:

| User intent | AI resize field | Backend calculation |
|---|---|---|
| “shorten X to 20 min” | `duration_minutes=20` | Existing start + 20 minutes |
| “change Y to 1 hour” | `duration_minutes=60` | Existing start + 60 minutes |
| “make lunch 30 min longer” | `duration_delta_minutes=30` | Effective current duration + 30 minutes |
| “make it 15 min shorter” | `duration_delta_minutes=-15` | Effective current duration − 15 minutes |

`duration_delta_minutes` is necessary because allowing only `duration_minutes` would still force the model to read the existing interval and perform relative arithmetic. With separate absolute and signed-relative fields, the model extracts a number and intent while the backend owns all time arithmetic. The tradeoff is a larger AI action schema and additional planner provenance, but it avoids prompt-only arithmetic errors and requires no public API or persistence-model changes.

Duration-based resize actions preserve the block’s effective start and derive only a new end. They must not include `start_time` or `end_time`; this prevents contradictory anchoring rules. Existing boundary-based resize actions remain valid and unchanged.

**Phase coupling:** the three phases (schema accept → planner resolution → prompt guidance) must ship as a single unit. Landing Phase 1 alone (schema accepts `duration_minutes`/`duration_delta_minutes` on resize) while the planner still ignores them would let a live chat duration-resize reach `compute_move_resize_times`, fall back to the block's own times, keep `time_requested=False`, and surface as a silent `applied` no-op. Do not merge Phase 1 to `main` without Phase 2.

## Behavioral Contract

- A `resize` must contain `task_id` and exactly one resize mode:
  - At least one of `start_time` or `end_time`.
  - `duration_minutes`.
  - `duration_delta_minutes`.
- `duration_minutes` on a resize is a positive plain integer and a multiple of `GRID_MINUTES`.
- `duration_delta_minutes` is a non-zero signed plain integer and a multiple of `GRID_MINUTES`.
- Both fields use `is_plain_int()` so booleans are rejected even though Python treats `bool` as an `int`.
- `duration_minutes` retains its existing meaning on an untimed chat `add`; it remains invalid on explicit adds, moves, updates, and removes.
- `duration_delta_minutes` is valid only on `resize`.
- An absolute duration below five minutes is rejected by schema validation. A relative delta whose computed duration is below the five-minute floor, zero, or negative is rejected by the planner without modifying the block.
- **All duration arithmetic and the duration-end reason-code decisions (interval / window / granularity) use the integer `derived_end_minutes`** (via `_minutes_from_time`), never a `datetime.timedelta` + `datetime.time` add (the bare-move pattern at `mutation_planner.py:241-252` would silently persist `10:00–11:00` for a 25 h duration if copied — its `wrapped` flag only fires when the rolled `.time()` is `<= new_start`). (Overlap/`unresolved_conflict` are a separate, later decision that legitimately compares candidate intervals built from `new_end` — see below — so "reason-code decision" here means the duration-end verdict, not the overlap verdict.) `derived_end_minutes` is the **single source of truth**: it is the (possibly out-of-range) true value those checks read, and it is what flows through same-task chaining. **Chain-poison exception:** if a same-task duration action's `derived_end_minutes` is outside `[0,1439]`, the task's chain is poisoned so any later same-task action (relative delta, bare move, or metadata update) deterministically rejects `out_of_window` rather than chaining off a clamped stand-in (GREEN `_normalize_actions` step 4). Separately, the `UpdateMutation.new_end` `datetime.time` is a **representability-safe reconstruction** = `_time_from_minutes(clamp derived_end_minutes into [0, 1439])` — needed because `_time_from_minutes` builds `datetime.time(hour, minute)`, which raises for hour ≥ 24 (`mutation_planner.py:425`) and cannot hold negative minutes. The `[0,1439]` clamp keeps that object constructible for the downstream consumers that legitimately need a real end — `_build_candidate` and the overlap fixpoint (`mutation_planner.py:782-801`) compare candidate intervals built from `new_end`, and `find_slot` (`936`) reads it. `new_end` is **never the value the reason-code (interval/window/granularity) decisions are made on** — those read the unclamped `derived_end_minutes` — and because an out-of-range duration is rejected by the ladder (on the integer), its clamped `new_end` is never the surviving value of an accepted action.
- **Derived duration ends are REJECTED, not clamped, when out of window.** This deliberately follows the existing *derived*-boundary policy (`mutation_planner.py:705-708`, "a derived bare-move end is checked but never silently clamped"), NOT the *supplied*-end clamp policy (`mutation_planner.py:714`, `clamp_boundary`, exercised by `test_ai_views_chat.py:1051-1074`). Rationale: a duration request produces a backend-derived end the user never named, exactly like a bare move; silently clamping "make it 3 h longer" down to `day_end` and reporting it fully `applied` would hide that the user got far less than asked. A computed end past `day_end` (or ≥ midnight) rejects with `reason_code="out_of_window"` and the block is left untouched.
- **Deterministic check precedence for the derived end, all in integer space on the unclamped `derived_end_minutes`** (resolves the granularity-vs-interval collision AND the ≤ 0 / ≥ 1440 representability crash): (0) **effective-start guard** — but ONLY for an *inherited* `start_supplied` start that would clamp (`start < day_start`); such a start clamps at `mutation_planner.py:713`, and since `derived_end_minutes` was computed from the pre-clamp start, letting it clamp would silently shorten the requested duration → `reason_code="out_of_window"`. A **standalone** duration resize has `start_supplied=False`, never clamps its start, and skips this guard; then (1) computed duration `<= 0` or `< GRID_MINUTES` → `reason_code="interval"` — covers every non-positive duration, including end minutes ≤ 0 (the `[0,1439]` clamp is what keeps `_time_from_minutes` constructible for such a value; the `interval` verdict is decided on the unclamped integer, so the clamped end is never the applied result); then (2) `derived_end_minutes > day_end` or `< day_start` or `>= 1440` (past midnight) → `reason_code="out_of_window"`; then (3) off-grid end → `reason_code="granularity"`. The interval/granularity collision only arises on a **legacy off-grid block** (external-event blocks may carry arbitrary minutes): e.g. block `12:00–12:33` (33-min, off-grid end), relative delta `−30` → duration 3 min, derived end `12:03` — sub-five-minute AND off-grid, so `interval` (the floor) wins over `granularity`. A ≥5-min off-grid derived end (e.g. that same block, delta `−0`... i.e. `12:00–12:33` `+0` is a no-op; use `12:00–12:33` `+30` → `13:03`, 63-min, off-grid) reports `granularity`. (Note: a schema-valid **absolute** `duration_minutes` is ≥ 5 and grid-aligned, so on an on-grid start it can never trip the floor or granularity; the collision is inherently a relative-delta-on-legacy-off-grid-block case. Only the changed end is grid-checked, never the unchanged start, per `mutation_planner.py:699`.)
- If the resized interval overlaps a neighbour that is **unchanged this turn**, the existing planner overlap fixpoint owns resolution: reject the resized block's time change (`reason_code="overlap"`, `mutation_planner.py:799-801`), restore its original interval, leave the neighbour untouched, report the conflicting task id, and use the existing server-owned resolution question. If the overlap is against **only** other block(s) also changed this same turn, the existing fixpoint rejects it with `reason_code="unresolved_conflict"` (`mutation_planner.py:803-807`) instead. (The `changed_vs_unchanged` pass runs first and `continue`s, so a target overlapping *both* an unchanged and a changed neighbour reports `overlap`, not `unresolved_conflict` — `mutation_planner.py:799-802`.) Either way: do not cascade, shift, shorten, or resize neighbouring blocks.
- Duration intent normalizes to an `end_time` mutation via a new `duration_derived_end` provenance flag (analogous to the existing `bare_move_derived_end`) plus the integer `derived_end_minutes`. This flag makes the derived end count as requested end-time work in `time_requested` (`mutation_planner.py:683, 892`) so the action is **never** a silent `applied`-with-empty-`applied_fields` no-op. The derived END is validated by a **dedicated duration branch** inserted into the check ladder with the integer precedence above (interval → out_of_window → granularity), not the supplied-end branches — the actual existing ladder is wrapped-bare-move (`688-690`) → supplied-window (`691-698`) → supplied-grid (`699-701`) → interval `start >= end`, ungated (`702-704`) → bare-move-derived-window (`705-708`) → `clamp_boundary` (`709-714`); the duration end must never reach that `clamp_boundary`. The duration branch handles ONLY the end: the block's START (which a same-turn earlier move may have supplied and which is inherited via `mutation_planner.py:522-523`) still flows through the existing supplied-start grid/window/clamp checks unchanged. Duration actions share the existing overlap fixpoint. A standalone duration action reports only `end_time` as applied and leaves `start_time` unchanged; but when it is chained after a same-turn `move` that supplied a `start_time`, the merged mutation still persists that `start_time` change too (both boundaries apply) — the "only end_time" statement is about the duration action's own contribution, not a suppression of a chained move's start.
