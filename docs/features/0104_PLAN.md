# 0104 — Relative-add guard recovery

Fix three server bugs that turn an AI chat clarification into a dead end. With one existing block, Gym 07:30–09:30, the reported conversation was:

1. User: “add Vocal, then Stretching, then Breakfast. without gap, one after another”
2. Assistant: “Which existing block should the new block be placed after?”
3. User: “vocal starts at 0945”
4. Server: `409 pending_intent_scope`, “The reply changed the pending request. Please restate it.”

The fix must distinguish sequential-add idioms from existing-block placement, save a bounded scope when the relative-add guard interrupts executable adds, and recognize natural clock answers. Timing remains the model’s responsibility: the guard may decide whether to ask, but must never infer or insert a slot from user text.

### Replay-guard boundary

Fresh replay-guard questions have the same empty-scope symptom when the model supplies no `pending_actions`:

- `_replay_guard_response`, `backend/ai/views.py:305`, marks every action skipped with `reason_code="replay_guard"`.
- `unresolved_items`, `backend/ai/pending_intents.py:359`, explicitly excludes those outcomes.
- `finish` therefore saves `items=[]` for that fresh ask. A continuation with an existing scope instead retains it through `guard_blocked`.

Replay-guard recovery is **out of scope**. Its rejected actions may be copied from an earlier request, so deriving permissions from them could authorize precisely the replay being rejected. Add a regression proving the new relative-guard mechanism never runs for this path. Recovery from an empty replay scope continues to require cancellation/clearing and a fresh command.

## Documentation and decisions

Update:

- `RULES.md:66` and `:74`: idiom handling, recoverable fresh relative-guard scope, unchanged continuation limits and no text-derived placement. `:66` currently says the newest reply that names any block decides the anchor; add the start-clause exception, the clock answer to the generic time question, and the rule that a scope failure consults the guard in a no-write probe (identity gate included) before returning 409.
- `docs/api.md:143–158`: distinguish server-derived relative-guard scope from old-format model questions; describe supported clock answers and unchanged error codes; note that a reply failing the scope check can return a 200 guard question instead of 409 `pending_intent_scope`.
- `docs/ARCHITECTURE.md:43–45`: record scope derivation ownership, the internal guard-to-intent handoff and the probe.
- `docs/AI_PENDING_INTENT.md:23–29`: clarify fresh guard scope, preservation of existing scope during repeated questions, and the probe precedence with its known limitations.

Decisions:

- **No schema migration.** `PendingIntent.items` is already a JSON field (`backend/ai/models.py:51`) supporting the required known/missing fields.
- **No empty-scope exception or backfill.** Existing empty intents cannot safely be reconstructed from client history. They retain cancellation/clearing and restatement behavior.
- **Use an internal response marker.** Inferring provenance from question wording or any empty-outcome ask could accidentally grant scope to model or replay questions.
- **Derive add permissions only.** Do not synthesize new edit/remove permissions for other actions withheld by a relative-guard turn. Preserve existing structured pending work and whole-turn no-write behavior.
- **Keep replay recovery separate.** Its rejected actions are not reliable evidence of the current request.
- **Guard question before scope 409, never before a write.** A continuation that fails the scope check consults the relative guard in a no-write probe, and only when every reply action is an add matching the title and category of a distinct saved add (so the next answer can actually be accepted). The alternative, relaxing `matching_item` so untimed adds pass, would reopen the auto-placement bypass that `test_missing_placement_cannot_be_bypassed_by_an_untimed_add` pins.
- **Known limitation: untimed independent sibling.** On a continuation every pending add needs explicit times. `[Vocal timed, Reading untimed]` still returns 409 because the guard has nothing to ask about Reading. Giving siblings a different item shape would need a second permission model; pinned by a test instead.
- **Known limitation: withheld non-add actions.** A remove/update returned in the same guard-blocked turn is not carried into the scope (it could be represented as an exact-value item with `missing_fields: ["confirmation"]`, since all action fields are within `FIELDS`, but that auto-applies an edit on an unrelated answer). The user restates it. Open for the owner to overrule.
- **Known limitation: greedy matching with repeated titles.** Two saved adds with the same title but different known durations can reject a valid answer depending on action order (`matching_item:233`, `constrain_actions:299`). Pre-existing behavior for model-authored scopes too; not changed here.
- **Known limitation: a probe question keeps no partial answer.** A reply such as “Gym, 30 minutes” with an untimed add gets the guard's time question and leaves `items` unchanged (existing `guard_blocked` behavior); the next continuation prompt is built from the saved summary (`service.py:432–435`), so the model no longer sees “30 minutes”. The anchor survives because the guard reads the client transcript. Saving the extra field would mean accepting data from a reply that failed the scope check.
- **Derived duration is locked.** A duration derived from the model's rejected interval becomes a known field, matching the planner precedent; a reply that changes the length returns 409.
- **A clock answer to the generic time question is authoritative.** For a request with several relations (“after Gym and before Lunch”) no single anchor is defined and the guard checks none today. The ways out today are a reply that restates one relation (“after Gym”, which becomes the active request and is anchor-checked, `relative_add_guard.py:116–128`) or a fresh add with explicit times and no relation words, which is unchecked. Step 3 green 6 therefore accepts a recognized clock reply with fully timed adds without anchor checks, even if the chosen time contradicts one of the original relations. Per-relation anchor checks would need an ownership rule for several adds and several relations and can dead-end again (“Vocal before Gym and Stretching after Gym”); rejected for this fix. A single resolved anchor keeps constraining clock answers as today.
- **Keep clock recognition bounded.** A general natural-language time parser or model-prompt workaround would enlarge the change without fixing scope persistence.

## What could break

- Overbroad idiom filtering could hide genuine placement constraints. Mixed-clause and quoted-title tests must stay green.
- Duration derivation could lock an invalid value or allow a changed known duration. Test absent, invalid and valid duration sources plus continuation mismatches.
- Rebuilding scope during a continuation could duplicate permissions, lose siblings or relax known fields. Verify repeated asks, partial completion and accepted-sibling replay rejection.
- Broad clock matching could accept quantities or bypass an earlier anchor. Negative clock tests must cover both current and historical anchor resolution.
- Skipping start clauses in the anchor scan could drop a genuine anchor answer phrased as a clause, or keep one that should be dropped. Test the same-title, partial-completion, anchor-beside-clause and bare-title cases.
- The clock escape for the generic time question accepts times that contradict one of several relations. Keep it limited to a recognized clock reply with every add fully timed; the first turn and non-clock replies must still ask.
- The derived-versus-model duplicate rule could drop a legitimate sibling or keep a placement lock. Test the same-title duplicate, the differing-duration sibling and the next-answer round trip.
- The no-write probe could reach the apply path or mask a genuine scope violation behind a question. Assert no write with a silent guard, and that guard-clean out-of-scope actions still return 409.
- An internal marker leaking into JSON could change durable responses. Assert the response shape and identical-request replay behavior.
