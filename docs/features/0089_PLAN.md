# Feature 0089 — MCP connector for daily report export

> **Learning path.** You (Erzhan) haven't built an MCP server before and will implement this yourself, one small step at a time. Each step = one concept + what to write + how to verify. Do them in order; don't skip ahead.

## Context

Feature 0088 shipped a read-only daily export HTTP API (`GET /api/export/daily/<date>/`, `backend/schedules/export_api.py`) authenticated by a personal Bearer token (`dfx_…`, `backend/schedules/export_tokens.py` / `export_auth.py`). Issue #290 wants an **MCP server** in front of that API so an LLM client (claude.ai custom connector, Claude Code, Grok Bot) can pull a day's schedule as a tool call. The MCP server is a thin, **stateless proxy**: one tool, `get_daily_report`, that forwards the caller's export token to the existing endpoint and maps HTTP results to MCP results. No new auth, no new storage, no server-side LLM egress. OAuth is out of scope — the export token is the only credential.

## MCP concepts primer (read once before Step 0)

- **MCP server** — a process that advertises *tools* to an MCP *client* (the LLM host). We only need tools.
- **Tool** — a named function with a JSON input schema and a text/structured result. Ours: `get_daily_report(date)`.
- **Transport** — stdio (local child process) or **Streamable HTTP** (one HTTP endpoint, client POSTs JSON-RPC). We use Streamable HTTP because the server runs remotely behind Caddy.
- **Streamable HTTP + stateless + json_response** — client POSTs a JSON-RPC request to one path (`/mcp`), gets one `application/json` body back. *Stateless* = no server-side session between requests; *json_response* = single JSON reply, not an SSE stream. Simplest mode, exactly right for a stateless proxy and trivial to put behind Caddy.
- **JSON-RPC lifecycle**: `initialize` → `notifications/initialized` → `tools/list` → `tools/call`.
- **Tool error vs protocol error** — a **protocol error** is a JSON-RPC error (malformed request, unknown method). A **tool error** is a normal result with `isError: true` + human-readable text; the model *sees* it and can react. Business failures (401/404/5xx/timeout from the export API) must be **tool errors**, so the model can tell the user what went wrong.

### Pinned-SDK reality check (before writing real code)

- Install the official Python SDK, package name **`mcp`**. Pin `mcp>=2.3,<3`.
- In 2.x FastMCP was renamed: `from mcp.server.mcpserver import MCPServer`. `mcp.server.fastmcp` raises `ModuleNotFoundError` on 2.x — ignore old tutorials.
- Key API (verify against the *installed* version — read the source / `help()`):
  - `MCPServer(name=...)` with a `@server.tool()` decorator.
  - `server.streamable_http_app(streamable_http_path="/mcp", json_response=True, stateless_http=True, transport_security=TransportSecuritySettings(...))` → a Starlette ASGI app.
  - `server.run_streamable_http_async(host=..., port=...)`.
  - `from mcp.server.transport_security import TransportSecuritySettings` (`enable_dns_rebinding_protection`, `allowed_hosts=[...]`, `allowed_origins=[...]`; host patterns like `"host:*"`).
  - **Reading incoming HTTP request headers from a tool** (needed for the caller's `Authorization`): via the tool's `Context` param, roughly `ctx.request_context.request.headers["authorization"]`. The exact path changed across versions — **confirm on the pinned version** (bites in Step 3).

## Decisions (with reasons)

| Decision | Choice | Why |
|---|---|---|
| Package location | **Top-level `mcp_server/`** (sibling to `backend/`) | Separate ASGI process; keep it out of the Django tree. **Never** name it `mcp/` — that shadows the SDK import. |
| Separate container vs in-process | **Separate container**, own thin Dockerfile | A hang/crash in the proxy must not take down the web app; independent `mem_limit`/restart; keeps the SDK dep out of the Django image. |
| Dependency management | **Dedicated `mcp` dependency group** in `pyproject.toml`: `mcp>=2.3,<3` **and `httpx`** (mcp 2.3 depends on `httpx2`, not `httpx`) | The prod web image builds `uv sync --no-dev`, so the SDK must live in a group only the MCP image installs. |
| MCP → Django call path | **Internal Docker URL** `http://web:8006`, not the public URL | No hairpin through Caddy/TLS; token stays on the private network. **Must** send `Host: dayforge.habitreward.org` + `X-Forwarded-Proto: https` (prod `DEBUG=0` enforces `ALLOWED_HOSTS` + proxy-SSL — same trick the compose healthcheck uses). |
| Host header / `allowed_hosts` behind Caddy | `TransportSecuritySettings(enable_dns_rebinding_protection=True, allowed_hosts=MCP_ALLOWED_HOSTS)` read from env: prod = `["dayforge.habitreward.org"]` only; local dev adds `localhost:*`/`127.0.0.1:*`. Matching `allowed_origins` (in Step 9, check in Caddy access logs whether claude.ai sends an `Origin` header and add it if needed; `https://dayforge.habitreward.org`; requests without `Origin`, e.g. Claude Code, pass) | Caddy forwards the public Host; DNS-rebinding protection must accept it and reject the rest. |
| `get_reports_range` (≤14 days) | **Defer** | Ship one tool first; add range once the single-day path is proven. (Open decision.) |
| IP-allowlist Anthropic egress `160.79.104.0/21` | **No** | Would block Claude Code and Grok Bot (other IPs). The token is the real gate. |
| Rate limiting | **Defer in-app; rely on token, optional Caddy `rate_limit`** | The export read is a cheap owner-scoped DB read; a dedicated limiter is premature. |
| Logging | Log **method, tool, date, upstream status, latency** — never the `Authorization` header/token | Bearer credential must never hit logs (log `auth=present/absent` only). |
| Health endpoint | `GET /mcp/health` → `200 {"status":"ok"}` registered with the SDK's `@server.custom_route("/mcp/health", methods=["GET"])`, in the same Starlette app as `/mcp` | `/mcp` only answers POST; compose/Caddy need a cheap GET probe. |

### Step 1 — Minimal "hello" server *(exploratory)*
**Concept:** prove the full lifecycle against a trivial tool before auth/export.
**Write:** `mcp_server/app.py` with an `MCPServer`, one `@server.tool()` `ping` returning a fixed string, and `build_app()` returning `streamable_http_app(streamable_http_path="/mcp", json_response=True, stateless_http=True, transport_security=...)`. `mcp_server/__main__.py` runs `uvicorn.run(build_app(), host="0.0.0.0", port=8007)` so `python -m mcp_server` serves it. Do NOT use `run_streamable_http_async(...)` here: it builds its own app from its own kwargs, so the `json_response`/`stateless_http`/`transport_security` passed to `build_app()` would be silently dropped (defaults: SSE responses, stateful sessions, and with host `0.0.0.0` DNS-rebinding protection off).
**Verify:**
- `npx @modelcontextprotocol/inspector` → point at `http://localhost:8007/mcp` (Streamable HTTP). Confirm connect → list `ping` → call returns your string.
- Raw curl to feel the wire format:
  ```
  curl -s http://localhost:8007/mcp \
    -H 'Content-Type: application/json' \
    -H 'Accept: application/json, text/event-stream' \
    -d '{"jsonrpc":"2.0","id":1,"method":"initialize","params":{"protocolVersion":"2025-06-18","capabilities":{},"clientInfo":{"name":"curl","version":"0"}}}'
  ```
  then `tools/list`, `tools/call`. (Copy the exact `protocolVersion` the Inspector sends.) No tests yet.

### Step 2 — Real `get_daily_report` proxying the export API
**Concept:** the tool makes one `httpx` GET to the export API and returns its result — it adds nothing to the data model.
**Write (in `mcp_server/`):**
- `config.py` — env with defaults: `DAYFORGE_API_BASE` (`http://web:8006`), `DAYFORGE_API_HOST` (`dayforge.habitreward.org`, sent as `Host`), `MCP_REQUEST_TIMEOUT` (`10`), `MCP_PORT` (`8007`).
- Replace `ping` with `get_daily_report(date: str, ctx: Context)`: `date` is `today`, `yesterday` or `YYYY-MM-DD` (describe it in the docstring — the model reads it). Validate locally first (regex `^(today|yesterday|\d{4}-\d{2}-\d{2})$`, else a tool error, no upstream call). `yesterday`: the proxy does not know the user's time zone, so call `today` first, take the returned `date`, subtract one day, then request that date (two upstream calls; test it). Build `GET {BASE}/api/export/daily/{date}/?format=json` with headers `Host`, `X-Forwarded-Proto: https`, forwarded `Authorization` (Step 3). On 200, return both a readable text block (the `markdown` field) and the structured fields (`date`, `completed_count`, `planned_count`, `blocks`).
**Verify:** run the web app (`make run`/compose) + the MCP server with `DAYFORGE_API_BASE=http://localhost:8006` and a real `dfx_…` token; call from Inspector for a seeded date; confirm counts match a direct curl of the export endpoint. (If you prefer strict TDD, start the Step 5 unit test here against mocked httpx.)

### Step 3 — Auth: forward the caller's token
**Concept:** the MCP server is not a credential store — it reads the request's `Authorization: Bearer dfx_…` and forwards it verbatim to the export API, which already validates it (`export_auth.resolve_export_owner`). Never parse/store/log the token.
**Write:** read the header off the request context (confirm the exact path on the pinned SDK). Absent → **tool error** "Missing Authorization. Provide an `Authorization: Bearer <export token>` header." Present → forward unchanged. Ensure no log line contains the header/token (log `auth=present/absent`).
**Verify:** Inspector without a token (tool-error message) → with a valid token (data) → with garbage (generic 401 from Step 4).

### Step 4 — Error mapping
**Concept:** translate upstream HTTP outcomes into MCP **tool errors** with safe, non-leaking messages.
**Write** one mapping helper used by the tool:

| Upstream | Tool-error message |
|---|---|
| 200 | *(success)* |
| 400 | "Invalid date — use `YYYY-MM-DD` or `today`." (safe pass-through) |
| 401 | "Authentication failed. Check your Day Forge export token." (generic — never reveal malformed vs revoked) |
| 404 | "Report not found." (export returns 200 for an empty day, so 404 means a routing/base-URL bug — log the URL server-side) |
| 5xx | "Day Forge is temporarily unavailable. Try again shortly." |
| `httpx.TimeoutException` / `ConnectError` | same "temporarily unavailable" |

All returned as results with `isError: true`, **not** protocol errors.
**Verify:** via the Step 5 tests (write those first for this step).

**Catch-all (round 3):** also catch the base `httpx.RequestError` and any other exception, and map any status not listed above (e.g. 301 from `SECURE_SSL_REDIRECT` if `X-Forwarded-Proto` is lost, 403, 429) to the generic "temporarily unavailable" tool error. Never return `str(exc)`: it would leak the internal URL `http://web:8006`.

### Step 5 — Tests (TDD from here: failing test first)
**Concept:** three layers in `mcp_server/tests/`, independent of the Django `backend/tests/` suite (which pins LocMemCache). The root pytest config sets `DJANGO_SETTINGS_MODULE` and `pythonpath=["backend"]` (pyproject.toml), so run these with `-p no:django`.
1. **Unit — mocked upstream** (`test_tool.py`): mock httpx (e.g. `respx` or a monkeypatched `AsyncClient`). Assert 200 JSON → structured result with matching counts; and header propagation (`Authorization` forwarded, `Host: dayforge.habitreward.org`, `X-Forwarded-Proto: https`).
2. **Auth** (`test_auth.py`): missing header → tool error; present → forwarded verbatim; token never appears in captured logs.
3. **Error mapping** (`test_errors.py`): parametrized 400/401/404/500/timeout → expected text + `isError: true`.
4. **Protocol smoke** (`test_protocol.py`): drive the ASGI app in-process with `httpx.ASGITransport(app=build_app())` — no sockets. Walk `initialize` → `notifications/initialized` → `tools/list` (assert `get_daily_report` + schema) → `tools/call` (upstream mocked) → assert a well-formed result. This is the regression guard across SDK bumps. `httpx.ASGITransport` does not run ASGI lifespan, so wrap the test in `async with server.session_manager.run():` (or `asgi-lifespan`'s `LifespanManager`); otherwise requests fail because the session manager is not started.
**Verify:** `uv run --group mcp pytest -p no:django mcp_server/tests -q`.

**Singleton note:** `build_app()` must use one module-level `server` and be called once per process (and once per test module). `streamable_http_app()` creates a new session manager on each call and `session_manager.run()` is single-use, so a fresh app per test fails with "Task group is not initialized".
