# Feature 0081 — user-local `now` in the mark-reviewed snapshot freeze

## Context

Feature 0077 wired the user's persisted timezone into `analytics_view` (the GET
panel) but not into `mark_reviewed` (the POST that freezes the snapshot).

`analytics.services.compute_review_stats(schedule, *, now=None, ...)` defaults to
`now = timezone.localtime()` — the **server** zone (`settings.TIME_ZONE` is
`"UTC"`), not the user's. Its "skipped" rule is day-boundary sensitive:

- past day → every uncompleted block is skipped;
- today → only blocks with `end_time < now.time()` are skipped;
- future day → never skipped.

So for any user away from UTC, the POST froze a snapshot computed on a different
day than the panel they had just been looking at. Because `mark_reviewed`
**freezes** the row, the disagreement is permanent — a later GET serves the
persisted (wrong) numbers rather than recomputing.

Reported five times over by the `cursor/critical-bug-investigation-*`
automation, which opened five byte-identical draft PRs (#198, #201, #204, #205,
#206 — diff hash `98850210dfbf`), one per day between 2026-09-06 and
2026-09-10. All five were closed in favour of this branch: the bug was real, but
each was based on a `main` that had since taken 0077, 0078, 0079 and 0080, and
none was landable as-is.

## Change

`backend/analytics/views.py`, `mark_reviewed`:

1. Resolve `now_local = user_local_now(request.user)` once, right after the
   schedule 404 lookup.
2. Pass `now=now_local` to all three `recompute_review_from_schedule(...)` call
   sites — the pre-lock REVIEWED back-compat recompute, the under-lock REVIEWED
   back-compat recompute, and the ACTIVE freeze. All three persist a snapshot,
   so all three must agree with the GET.

### Deliberate divergences from the five closed PRs

- **Use the `schedules.window.user_local_now` helper**, don't inline
  `get_schedule_settings` + `timezone.localtime`. Those PRs copied the inline
  form from `analytics_view` along with its comment explaining that the helper
  is avoided there because that view *needs the settings object anyway for
  `schedule_window`*. Nothing in `mark_reviewed` needs it, so the justification
  does not carry over and the copied comment would have been false.
- **Do not pass `categories=`.** `analytics_view` passes it because it already
  holds the catalog; when omitted, `compute_review_stats` resolves
  `ordered_categories(schedule.user)` itself — the same value. Passing it here
  would save a query, not fix a correctness gap, and belongs to a different
  change.

### Placement

`now_local` is resolved once before the branches rather than at each call site,
so all three share one instant. The cost is one idempotent `get_schedule_settings`
`get_or_create` on the DRAFT-400 path as well — the same tradeoff `analytics_view`
documents for its own pre-gate resolution.

## Tests

New `TestMarkReviewedUsesUserTimezone` in `backend/tests/test_analytics_views.py`
(the class had no timezone coverage; these mirror the existing GET-side
`TestAnalyticsFutureGateUsesUserTimezone` patterns and its `_freeze` helper).

1. **East of UTC** — at UTC `2026-05-03T20:00` Almaty is already `05-04T01:00`,
   so a May-3 schedule is a past day and its uncompleted 22:00–23:00 block must
   be counted skipped. On UTC `now`, May 3 is still today and 22:00 has not
   arrived, so it would not be.
2. **West of UTC** — the mirror: at UTC `2026-05-04T03:00` Los Angeles is still
   `05-03T20:00`, so May 3 is today there and the same block has not ended —
   not skipped. On UTC `now` it would be.
3. **Symmetry** — GET panel and POST freeze report the same `planned_count`,
   `completed_count` and `skipped_count` for one user/date/zone. Asserts the two
   agree rather than pinning a literal, so it keeps its meaning if the skipped
   rule itself changes.

All three fail on `main` (the symmetry case fails `0 == 1`) and pass with the
change.
