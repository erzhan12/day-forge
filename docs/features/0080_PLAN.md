# Feature 0080 — Chat: bare noun/gerund defaults to untimed add

## Context

In multi-turn AI chat (`POST /api/ai/schedules/<date>/chat/`), adding a block currently requires an explicit verb ("Add Gym"). A bare noun / noun-phrase / gerund naming an activity ("Gym", "Reading emails", "Team meeting") is classified as ambiguous and the model returns an `ask:` clarifying question ("When?"). This is unnecessary friction: the app already has a deterministic auto-placement path (feature 0067) that places a block with omitted times into the next free forward slot.

The desired behavior: when the latest user turn is a bare activity-naming noun/noun-phrase/gerund with no other recognizable intent (not a move/remove/resize/update referent, not a question, not a greeting), the model defaults to an **untimed `add`** using the text as the block title, omitting `start_time`/`end_time`, letting the backend auto-place it. Category defaults to the sink slug (`"other"`) when not inferable. This must **not** weaken the chit-chat/question guard, the referent-required guards (Hard rules 3/6/9b), or the untrusted-transcript guard.

The change is confined to the **chat system prompt wording**. No schema change, no dispatch/auto-placement change. Both already support the untimed-add shape.

- The model's classification is **stubbed** — tests assert that a given canned model envelope survives service validation and produces the expected `AIChatResult.parsed_actions` / `.ask`. This is exactly how `TestChatUntimedAdd` (lines 422–461) pins the untimed-add shape today.

**Testing reality:** `build_system_prompt_chat` is a pure function whose exact text is directly assertable. True intent-classification ("Gym" → untimed add) depends on the live LLM and is **not** deterministically testable here. Therefore the feature is verified in two deterministic layers, both offline:

- **(a) Prompt-text assertions** — the new instruction sentence(s) are present and correctly worded in the rendered chat system prompt, and the preserved guards remain intact (no accidental deletion/weakening).
- **(b) Behavior tests** — stub the model's chosen envelope (untimed add / no-op chit-chat / ask) with `patch_client` and assert `run_chat` returns the matching `AIChatResult`. This confirms that *when the model does default a bare noun to an untimed add, the service accepts it*, and that chit-chat/question no-ops and referent-required asks still round-trip. It does **not** assert the LLM's classification decision (untestable without a real provider call, which is forbidden).

## Prompt-rule change (exact wording & placement)

**Placement decision.** The new instruction is an **addition to the `add` action's "automatic" mode bullet** (lines 68–77) — the natural home for *how to shape an untimed add* — paired with a **narrow carve-out appended to Hard rule 2** (the ask-gating clause) that names bare-noun input as an explicit *exception* to asking. This dual placement is chosen because:

- The `add`-bullet edit describes the **shape** (untimed add, omit times, title = the noun, category = sink default) next to the existing automatic-mode text it reuses — no new top-level rule needed, keeping the rule list stable.
- The Hard-rule-2 edit is where the *decision to ask vs. not* lives; adding the carve-out **there** (rather than as a new rule) makes it read as a scoped exception to that exact clause, so it cannot be misread as overriding the referent guards (rule 3), the untrusted-transcript guard (rule 6), or 9b — all of which live in separate rules and are untouched.
- We deliberately do **not** add a new numbered rule, to avoid renumbering rules 3–10 and disturbing the direction-answer protocol references.

**Edit 1 — append to the `add` "automatic" mode bullet** (after the existing sentence ending "…but NEVER invent a start_time. Supplying only one of the two time fields is invalid.", lines 76–77). Insert:

> When the latest user turn is nothing but a bare activity name — a noun, noun phrase, or gerund with no imperative/edit verb, time, or reference to an existing block (e.g. "Gym", "Reading emails", "Team meeting") — treat it as an automatic add: use the user's text verbatim as `title`, OMIT both time fields, and default `category` to "{sink_slug}" unless the activity clearly maps to another category. Do NOT ask "when?" for a bare activity name — the backend will place it in the next free slot. This bare-name→add default applies to a FRESH bare-name turn only: if the previous assistant turn asked a clarifying question, follow Hard rule 2's exception (iii) below instead (resolve the pending ask by coreference, do not create a new add). Absent a pending clarifying question, a bare activity name that merely happens to match an existing block's title is still a NEW add (the user gave no edit verb): do not reinterpret it as an update/move/remove of that block.

**Edit 2 — append to Hard rule 2's ask-gating clause** (immediately after "…(Pure chit-chat / 'thanks' turns may return both empty actions AND `ask: null`.)", line 122). Insert:

> A latest turn that is only a bare activity name (a noun, noun phrase, or gerund naming something to do, with no other intent) is NOT unresolved: default it to an automatic untimed add (see the `add` action above) rather than asking. This exception is scoped precisely: (i) it does NOT change greetings or questions — those still return empty `actions` with `ask: null` (chit-chat) or a plain answer (question), never an add; (ii) it does NOT change a vague edit that references an existing block but omits the detail ("make it later") — that still asks per Hard rule 3; and (iii) it does NOT apply when the previous assistant turn asked a clarifying question — a bare name arriving as the ANSWER to a pending ask (e.g. the assistant asked "which block did you mean?" and the user replies "Gym") must be resolved as that answer via coreference — Hard rule 3 (referent identification) primarily, and Hard rule 9b only when the prior ask was a direction question ("earlier or later?") — not turned into a new add.

**What these edits deliberately do NOT touch** (regression-guarded by prompt-text assertions in the test plan): Hard rule 3 (referent required for move/remove/resize/update), Hard rule 6 (untrusted-transcript guard), Hard rule 9b (originally-requested-interval recovery), and the chit-chat/question no-op sentence already in rule 2. `{sink_slug}` is interpolated from the function's `sink_slug` argument, consistent with rule 4.
