# 0038 — useAnalytics fallback-literal guard tests

## Context

PR #128 tail item (`tasks/todo.md` line 174, raised by claude-review, P3/TESTING).
The feature-0037 error-dedup migration added "fallback-literal guard" tests to the
11 composables whose call sites were edited. `useAnalytics.ts` was **exempted** from
that migration (its call sites were not touched), so it received **no guard test**.

Unlike every other composable, `useAnalytics` has **two distinct fallback literals**:

- `markReviewed` — `"Could not mark this day reviewed."`
  (`frontend/src/composables/useAnalytics.ts:38`)
- `saveNotes` — `"Could not save notes."`
  (`frontend/src/composables/useAnalytics.ts:57`)

Because the two literals differ, a future accidental swap between them is caught by
**neither** a guard test nor the fallback-preservation grep. This plan adds two
minimal characterization/guard tests — one per method — that pin each exact literal.

This is a **test-only** change. No production code in `useAnalytics.ts` is modified.

## Relevant files

- `frontend/src/composables/useAnalytics.ts` — source under test (read-only reference).
  - `markReviewed(date, notes?)` — on `!result.ok`, sets
    `lastError.value = extractErrorMessage(result.errors, "Could not mark this day reviewed.")`
    (lines 36–39).
  - `saveNotes(reviewId, notes)` — on `!result.ok`, sets
    `lastError.value = extractErrorMessage(result.errors, "Could not save notes.")`
    (lines 54–59). `saveNotes` currently has **no** error-path test at all.
- `frontend/tests/useAnalytics.test.ts` — **the only file edited by this plan.** Add
  two tests here.
- `frontend/src/utils/errorMessage.ts` — `extractErrorMessage(errors, fallback)`:
  returns `errors.detail` if a string; else the first flattened value if a non-empty
  string; else `fallback`. An **empty** `errors: {}` therefore returns the fallback.
- `frontend/tests/useDraft.test.ts` — sibling guard pattern to mirror (its
  `describe("useDraft fallback-literal guard", ...)` block, lines 131–152). Note the
  sibling mocks `requestJson`; `useAnalytics.test.ts` instead mocks the global
  `fetch` — the new tests must follow the **local** file's `fetch` mocking style.

## Mocking shape (match the existing `useAnalytics.test.ts` conventions)

The existing file does **not** mock `requestJson`. It:
- `vi.mock("@inertiajs/vue3", ...)` for `router.reload` (top of file).
- Stubs the global `fetch` per test via `vi.stubGlobal("fetch", vi.fn()...)`.
- Provides an `errJson(status, body)` helper (lines 18–24) returning
  `{ ok: false, status, text: () => Promise.resolve(JSON.stringify(body)) }`.
- `beforeEach` calls `clearError()` to reset the module-level `lastError` ref
  (state is module-level; both methods share the same `lastError`).

The new guard tests reuse `errJson` and mock `{ ok: false, status: 500, errors: {} }`:
`errJson(500, { errors: {} })`. Rationale for the shape (mirrors the todo-item spec
"mock `{ ok: false, status: 500, errors: {} }`"):
- `status: 500` — an arbitrary error status. (Unlike `useDraft`/`useAI`, `useAnalytics`
  has **no** status→message gate, so *every* `!result.ok` path already reaches
  `extractErrorMessage` regardless of status; `500` is used only to match the todo-item
  spec `{ ok: false, status: 500, errors: {} }`.)
- `errors: {}` — empty map → `extractErrorMessage` falls through to the fallback,
  which is exactly the literal being pinned.

The wire body passed to `errJson` must nest the errors under an `errors` key
(`errJson(500, { errors: {} })`) so `requestJson` parses `result.errors` as `{}` —
matching how the existing `markReviewed surfaces 400 errors` test constructs its body
(`errJson(400, { errors: { detail: "draft" } })`).

## Implementation order (TDD)

Work follows **red → green → refactor**. Because production code is unchanged and
already returns the correct literals, "red" here means: write the assertion **first**
and confirm it exercises the fallback path (the test would fail if the literal were
ever swapped). There is no production edit to make these pass — the value is the
regression pin itself. Do **not** add or alter any `useAnalytics.ts` code.

1. **Slice 1 — `markReviewed` fallback literal (red → green).**
   In `frontend/tests/useAnalytics.test.ts`, add a test (inside the existing
   `describe("useAnalytics", ...)` block, or a new
   `describe("useAnalytics fallback-literal guard", ...)` mirroring `useDraft.test.ts`
   lines 131–152 — either placement is acceptable; a dedicated `describe` with a
   short comment referencing feature 0037/0038 is preferred for grep-ability):
   - Stub `fetch` with `vi.fn().mockResolvedValue(errJson(500, { errors: {} }))`.
   - Call `const { markReviewed, lastError } = useAnalytics()`, then
     `const result = await markReviewed("2026-04-18")` (bind `result`, matching the
     existing `const result = await …` pattern at `useAnalytics.test.ts:79`).
   - Assert `result.ok === false` and
     `expect(lastError.value).toBe("Could not mark this day reviewed.")`.
   - Run `cd frontend && npm test -- useAnalytics` → confirm the new assertion runs
     and passes (green). Sanity-check red by mentally noting a swapped literal would
     fail the exact-string match.

2. **Slice 2 — `saveNotes` fallback literal (red → green).**
   Add a second test in the same block:
   - Stub `fetch` with `vi.fn().mockResolvedValue(errJson(500, { errors: {} }))`.
   - Call `const { saveNotes, lastError } = useAnalytics()`, then
     `const result = await saveNotes(7, "x")` (bind `result`).
   - Assert `result.ok === false` and
     `expect(lastError.value).toBe("Could not save notes.")`.
   - This is also the **first** error-path test for `saveNotes` (it previously had
     only the happy-path `saveNotes PATCHes the right URL and body` test).
   - Re-run `cd frontend && npm test -- useAnalytics` → both new tests green.

3. **Refactor while green.** If a dedicated `describe` block was added, ensure its
   `beforeEach` resets state the same way the outer block does (`clearError()`, and
   clear/stub `fetch`). Because `lastError` is module-level and shared across both
   methods, each test must start from a cleared `lastError` (the existing outer
   `beforeEach` already calls `clearError()`; if placing the new tests in a **new**
   top-level `describe`, replicate that reset). Keep the tests minimal — no new
   helpers beyond the existing `errJson`.

Forbidden: implementing/altering production code then adding tests afterward. The
production literals already exist; the tests are the deliverable and must be authored
as guards first.
