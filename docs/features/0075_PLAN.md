# Technical implementation plan — GitHub issue #109

Reshape the AI chat `update` action to issue #109's nested wire contract
(`changes` object + top-level `placement_direction`), replacing the existing
flat `update` shape. This is a **backend-only** reshape of a **server-internal**
action vocabulary. No migration, no frontend changes (see "Surface reality").

## Surface reality (verified against the repo)

- **The mutation surface is chat only.** The `/command/` endpoint was removed in
  feature 0044 — there is no `backend/ai/urls.py`, and the only AI routes are
  `ai_generate_draft` and `ai_chat` (`backend/day_forge/urls.py:90-97`). Issue
  #109's acceptance criterion "Command and chat endpoints share the same schema
  and planner path" is interpreted against current reality: **chat** is the sole
  block-mutating endpoint and already routes model output through
  `schemas.validate_action_shape` → `mutation_planner.plan_mutations`. Draft
  (`ai_generate_draft`) accepts only `add` actions (`schemas.py` draft branch),
  so `update` never applies there and the draft prompt is untouched.
- **AI actions never cross the client wire.** `frontend/src/composables/useChat.ts`
  POSTs `{messages:[...]}` and reads back `{blocks, explanation, ask, applied,
  partial, outcomes}` (`useChat.ts:195-247`); `data.blocks` is the whole
  post-turn schedule, not a list of mutations. There is no action union, no
  `update`/`direction`/`placement_direction`, and no action serializer anywhere
  under `frontend/src`. The action shape is produced by the LLM and consumed by
  the backend planner only — so **the reshape requires no frontend code change**.
- **Canonical planner types** are `CreateMutation`, `UpdateMutation`,
  `DeleteMutation`, aggregated into a `MutationDiff` (`mutation_planner.py:89,
  103, 123, 157`). There is no `BlockMutation` symbol; this plan uses the real
  names.
- **Tests run from `backend/tests/`** (`pyproject.toml [tool.pytest.ini_options]`,
  `pythonpath=["backend"]`). `backend/ai/tests.py` is a 1-line uncollected stub —
  **do not** add tests there; all new tests go under `backend/tests/`.

## Contract and invariants

- Reshape the public `update` action to allow only:
  - Top level: `type`, `task_id`, required `changes`, and optional `placement_direction`.
  - Inside `changes`: one or more of `title`, `category`, `start_time`, `end_time`.
  - `placement_direction`: `later`, `earlier`, or `exact`. Preserve the existing
    rule that placement guidance must accompany a **time** change — i.e.
    `placement_direction` is rejected unless `changes` contains `start_time`
    and/or `end_time` (today's rule for the flat `direction`, `schemas.py:167-179`).
- Reject the former flat `title`, `category`, `start_time`, `end_time`, and
  `direction` keys at the top level of an `update`. No compatibility adapter for
  the flat shape.
- Reject every unknown key at **both** levels of `update` (top level and inside
  `changes`), including `is_completed` and `sort_order` wherever they appear.
- Keep legacy `move` and `resize` valid on their **current** wire shapes, and add
  strict top-level key allowlists for `move`, `resize`, **and `remove`** so a
  mis-shaped `{"type":"move","changes":{...}}` / `{"type":"remove","changes":{...}}`
  (or any stray key incl. `direction`/`placement_direction`) is **rejected**,
  never silently ignored (today only `add` has an allowlist — `_ADD_ALLOWED_KEYS`,
  `schemas.py:27,79`; `remove` is guarded only by the generic
  `direction`-on-non-update rule at `schemas.py:185-186`, so once that rule is
  reworked for `placement_direction`, `remove` must gain its own allowlist or it
  becomes a silent-ignore hole).
- Patch semantics (unspecified fields untouched):
  - Omitted **metadata/interval** fields remain unchanged; presence is tracked
    separately from value so an absent key never clears state. (Exception: a
    start-only change *derives* a new `end_time` to preserve duration — see the
    F3 bullet below; this is intentional, not a cleared field.)
  - Category changes only when `category` is present in `changes`.
  - **`start_time` alone preserves the block's effective duration.** This is a
    **behavior change for `update`**: today `compute_move_resize_times`
    (`mutation_planner.py:245-261`) preserves duration on a start-only shift for
    `move` **only** — a start-only `update` currently keeps the original
    `end_time` (changing the duration). Phase 2 extends the duration-preserving
    branch to `update`, including the wrap-past-midnight guard
    (`new_end <= new_start` → `wrapped=True`, lines 258-260).
  - Explicit `start_time` and `end_time` together define the exact interval.
  - Title trimming continues (`update_title.strip()`); title→ID matching stays the
    LLM's responsibility (no backend fuzzy matching).
- Keep the planner ORM-free. Persist the entire turn as one `MutationDiff`, one
  `transaction.atomic()` + `select_for_update` block
  (`views.py::_apply_actions_sync` / `_persist_mutation_diff`), i.e. one Undo
  unit. Undo itself is **frontend-only** (`useChat` pushes one undo snapshot per
  applied turn); the backend guarantee this plan asserts is "one diff / one
  transaction," verified in backend tests, not a backend "Undo entity."

## Phase 2 — Planner canonicalization and chat-view integration

### Canonicalization boundary

All wire→planner translation stays in
`backend/ai/mutation_planner.py::_normalize_actions` (not schema, not views):

- Nested `update.changes` → one `UpdateMutation`, carrying only explicitly
  supplied title/category/start/end changes plus the optional
  `placement_direction` (mapped to the planner's existing `direction` field).
- Legacy `move`/`resize` keep their external shapes; `_normalize_actions` +
  `compute_move_resize_times` fold them into the same `UpdateMutation` path (as
  today).
- Downstream ordering, overlap, day-window, and diff logic consume only the
  canonical `CreateMutation`/`UpdateMutation`/`DeleteMutation` — never raw public
  action dicts.
