# 0109 — Draft action cap follows the template limit

Fixes [issue #222](https://github.com/erzhan12/day-forge/issues/222) with the issue's chosen option B.

## Problem

Template validation accepts up to `MAX_TEMPLATE_BLOCKS = 50` blocks (`backend/templates_mgr/api.py`). A draft emits one explicit-time `add` per block, but `validate_draft_response` reused the chat cap `MAX_ACTIONS_PER_COMMAND = 20` (`backend/ai/schemas.py`). A valid 21–50-block template therefore produced either a 502 parse error, which still spent a draft rate-limit token, or a draft that silently lost blocks. Draft rule 2 (feature 0082) forbids dropping past template blocks, so a dense template late in the day forced more than 20 actions. The draft prompt never mentioned a cap.

## Decision

Decouple the draft cap from the chat cap instead of shrinking templates (option A, rejected in the issue: it removes working functionality and needs a data fix-up).

1. `backend/templates_mgr/limits.py` holds `MAX_TEMPLATE_BLOCKS = 50`. The module is ORM-free, following `templates_mgr/preference_defaults.py`, so `ai/schemas.py` can import it without pulling views and models into a validation module. `templates_mgr/api.py` imports it from there; no second literal exists.
2. `ai/schemas.py` adds `DRAFT_ACTION_HEADROOM = 10` and `MAX_DRAFT_ACTIONS = MAX_TEMPLATE_BLOCKS + DRAFT_ACTION_HEADROOM` (60). The headroom covers blocks the model adds from history. `validate_response_envelope` takes an explicit `max_actions`, and `validate_draft_response` passes `MAX_DRAFT_ACTIONS`.
3. Chat keeps `MAX_ACTIONS_PER_COMMAND = 20` in `validate_chat_response_envelope`, `pending_intents.py` and `views.py` (`applied_add_block_ids`). Chat's limit on dense days is out of scope.
4. Draft prompt rule 8 states the cap from the constant. It says every template block fits and tells the model to leave out history-derived additions rather than template blocks. This keeps rule 2 intact.

## Timeout budget

The estimate below counts tokens and assumes a throughput. It is not a latency measurement; a mocked response cannot measure one, and no real provider was called.

| Draft size | Output (compact JSON) | Output (indented JSON) |
|---|---|---|
| 20 adds | ~630 tokens | ~1,000 tokens |
| 50 adds | ~1,500 tokens | ~2,450 tokens |
| 60 adds | ~1,800 tokens | ~2,900 tokens |

Counts come from serialised synthetic actions at about 3.5 (compact) and 3.0 (indented) characters per token. At 60–100 output tokens per second, typical for `gpt-4o`, a 60-add draft takes about 18–50 s plus prompt processing. The 15 s `LLM_REQUEST_TIMEOUT` is not safe; it is marginal even for a 20-add indented reply.

Add `LLM_DRAFT_REQUEST_TIMEOUT` (float seconds, default `60`, `<= 0` raises `ValueError` at import), used only by `run_draft`. Chat keeps `LLM_REQUEST_TIMEOUT`, which also sizes the chat request lease. Drafts do not use `ChatRequest`.

Considerations:

- The OpenAI SDK retries a timeout twice by default (`max_retries=2`), so the worst-case wall time is about three times the setting plus backoff. This already applies to chat. The draft view is async and holds no database lock during the provider call. Neither Caddy, uvicorn nor the frontend (`useHttp.requestJson`) sets a shorter limit.
- `deploy.yml` does not pass `LLM_REQUEST_TIMEOUT` or the new variable, so production uses the code default.

## Apply path

`_apply_draft_sync` already runs every add in one `execute_schedule_mutation` call: one transaction, one planner pass under the draft policy, one revision bump. No per-day block limit below 60 exists in `schedules/`. Tests cover a 60-add apply (one revision bump) and a 60-add draft whose last add overlaps (400, no rows, revision unchanged).

## Tests

- `backend/tests/test_ai_draft_action_cap.py`: derived constants, prompt text, validator at and one over the cap, `run_draft` timeout and cap, and endpoint tests that patch `ai.service._get_client` so the real validator runs: a 50-block template yields all 50 blocks, 60 adds apply in one revision, 61 adds return the generic 502 with no writes, and an overlapping 60-add draft writes nothing.
- `backend/tests/test_templates_api.py::TestTemplateBlockCap`: POST and PUT at 50 succeed; at 51 they return 400 with the cap message and leave the stored template unchanged.
- `backend/tests/test_ai_service_chat.py::TestParsing::test_chat_action_cap_stays_at_twenty`: 20 chat actions pass, 21 fail, and chat still passes `LLM_REQUEST_TIMEOUT`.
- `backend/tests/test_settings_validation.py`: the timeout default is 60 and non-positive values raise.

## Out of scope

- Chat's 20-action cap on dense days.
- Spending the draft rate-limit token before the provider call: unchanged by design (RULES.md: a provider attempt spends the budget). With the new cap a full template no longer hits the parse error.
- Disabling SDK retries for drafts.
