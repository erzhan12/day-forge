# Fix #183 — Persisted User Timezone and One-Time Browser Mismatch Prompt

Persist an explicit IANA timezone on each user’s schedule settings and use it as the sole source of user-local time for AI draft context, chat/focus context, and apply-time placement. Browser timezone becomes advisory UI input only: it can trigger a dismissible one-time prompt but never silently changes the stored setting.

## Persisted-Timezone Contract and Resolution

- Add `time_zone = CharField(max_length=64, default="UTC")`.
- Accept only strings resolvable by `zoneinfo.ZoneInfo`. Empty, malformed, or unknown identifiers receive the stable field error `"Must be a valid IANA time zone."` To keep that message stable, run the IANA check inside `clean()`/the API validator — do **not** rely on `CharField(blank=False)`/`max_length`, whose built-in blank/length messages would surface ahead of the IANA one. The `"UTC"` default is always resolvable (`tzdata` is a Django dependency — verified 598 zones present, `ZoneInfo("UTC")` never raises), so the default-row `get_or_create` path never trips validation.
- **Two distinct shared helpers, not one** — deliberately different behavior:
  - a **raising validator** (`ZoneInfo(value)` → re-raise as a `ValidationError`/400 field error) used by `UserScheduleSettings.clean()` and the PATCH view;
  - a **safe resolver** (`ZoneInfo(value)` → `datetime.UTC` on failure) used only by the AI runtime `now()` sites.
  Both share the same caught exception tuple (`ZoneInfoNotFoundError`, `ValueError`, `OSError`, defensive `TypeError`); centralize the tuple, **not** the raise-vs-fallback behavior.
- Add a frozen settings DTO containing the existing `ScheduleWindow` plus `time_zone`. `get_schedule_settings(user)` performs one `get_or_create`; `get_schedule_window(user)` delegates to it and returns only the window.
- Runtime resolution order is exact (uses the **safe resolver**, never the raising validator):
  1. Resolve the persisted `time_zone` with `ZoneInfo`.
  2. If the row was bypassed/corrupted (e.g. a value written via `QuerySet.update()` skipping `full_clean()`) or timezone data is unavailable, fall back to `datetime.UTC` **by identity** — not via `settings.TIME_ZONE`.
  3. Never consult request `client_tz`, including on the fallback path.
- Legacy `client_tz` fields are ignored rather than rejected, preserving compatibility with feature 0070 clients while removing their authority.
- **PATCH becomes a partial update over `{day_start, day_end, time_zone}`** (today it hard-requires both window bounds; `backend/schedules/settings_api.py:39-43`). Rules:
  - `day_start`/`day_end` must be supplied **together or both omitted** (never a half-window). A **lone** window bound is a 400 — this preserves the existing `test_patch_missing_field_returns_400_and_leaves_row_unchanged` (`test_schedule_settings_api.py:178`) `missing-day_start`/`missing-day_end` cases unchanged. Both omitted → keep the stored window.
  - `time_zone` is **independently optional**; omitted → keep the stored timezone. This enables (a) a still-open pre-0071 tab that sends only `{day_start, day_end}`, and (b) the **mismatch prompt's timezone-only** `{time_zone}` PATCH — so updating the zone never round-trips (and never clobbers) a day-window that another tab changed since page load.
  - **An empty body `{}` (nothing updatable) stays a 400** — at least one of the window pair or `time_zone` must be present. This keeps the existing `{}` (`missing-both`) case at `test_schedule_settings_api.py:178` green as-is; only its rationale changes (no updatable field), not its status.
  - Only a **present-but-invalid** `time_zone` yields `400 {"errors":{"time_zone":...}}`. An **omitted** `time_zone` is never validated and never written — so a window-only PATCH re-uses the stored zone untouched.
  - The **stable IANA error message is owned by the API-layer validator** (it fully controls the raw input string and runs before any model write). The model `clean()` is a backstop and may raise Django's own blank/`max_length` message for absurd inputs — model-layer tests assert *rejection*, not the exact string, for blank/overlong; the exact `"Must be a valid IANA time zone."` is pinned only at the API boundary.
  - **Out of scope — corrupt stored `time_zone`:** every row persisted through the app carries a valid zone (enforced by `clean()`/`save()`→`full_clean()`), so a normal window-only PATCH's `save()` re-validates a *valid* stored zone and returns 200. A genuinely corrupt zone is reachable only via an out-of-band `QuerySet.update()`, which `models.py:110-112` already documents as an unsupported validation bypass — no special "don't-500-on-corrupt-tz" machinery is added (an earlier draft's `full_clean(exclude=["time_zone"])` idea does not work anyway: `full_clean()` always calls `Model.clean()` without the exclusion).

### The Three `now()` Sites

1. **Draft context — `backend/ai/views.py:914`**
   - Load the persisted settings once after existing validation/precondition/rate-limit ordering.
   - Attach its window to the schedule, resolve its timezone, and localize a fresh `timezone.now()` before `run_draft(...)`.
   - Do not parse or use the optional draft `client_tz` body.

2. **Chat/focus context — `backend/ai/views.py:1145`**
   - This is the issue’s former `~1111` “focus” call: the current time passed into `run_chat(...)`, not a separate focus-indicator backend.
   - Load settings once for the prompt boundary, attach the window, and localize `timezone.now()` with the stored timezone.
   - Ignore any conflicting `data["client_tz"]`.

3. **Chat placement — `_apply_actions_sync`, `backend/ai/views.py:756-763`**
   - Under the existing transaction and locks, re-read one persisted-settings DTO so both the day window and timezone are current at apply time.
   - Resolve the stored timezone, sample a fresh `timezone.now()`, and pass the localized result to `_earliest_start()`.
   - Remove the `client_tz` parameter from `_apply_actions_sync` and its callers. The fixed prompt lookup plus one fresh apply-boundary lookup is intentional, not an N+1, and allows a timezone change made during an LLM call to affect placement immediately.

UTC storage and unrelated UTC timestamps, cache timestamps, and account-verification timestamps remain unchanged.
