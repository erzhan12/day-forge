# 0054 — AI chat: partially apply safe fields and propose one conflict resolution

## Context

Today the AI-chat apply path is all-or-nothing. `ai_chat`
(`backend/ai/views.py`) calls `run_chat` (LLM), then
`_apply_actions_sync` runs the pure final-state planner
`plan_mutations` (`backend/ai/mutation_planner.py`). `plan_mutations`
returns **either** a `MutationPlan` (everything valid → persist all)
**or** a single `PlanError` (any violation → `_Rollback`, nothing
persists). The wire envelope is `{blocks, explanation, ask, applied}`.

Issue #111 changes the apply semantics: when a turn contains
independent **safe** metadata changes (`title`, `category`) **plus** an
invalid/conflicting **time** change on the same or different blocks,
persist the safe fields immediately, skip only the unsafe time fields,
and continue the chat with **one** server-generated resolution proposal
(a concrete free slot) or **one** direction question. The response may
now carry `applied=true`, `partial=true`, **and** a non-null
server-generated `ask` simultaneously.

The work extends the final-state planner to emit **structured
field-level outcomes** instead of a single pass/fail, adds a
deterministic **`FreeSlotFinder`**, threads `partial` + `outcomes`
through the view/envelope/audit, and pins the combined
`applied+partial+ask` case in frontend + backend tests. AI changes
still apply immediately; **Undo remains the safety mechanism** (one
Undo entry per persisted turn, existing frontend `pushUndo`).

Dependencies merged & stable (verified in code): #38 (final-state batch
planner + concurrency guard — `plan_mutations`, `snapshot_apply_context`,
fingerprint guard), #110 (authoritative per-user window —
`get_schedule_window`, `ScheduleWindow`, `clamp_boundary`).

**Dependency #109 is NOT merged — its scope is folded into this plan as
Phase 0 (below).** Verified against the real tree
(2026-08-21): `ALLOWED_ACTION_TYPES = {"add", "move", "remove",
"resize"}` (`schemas.py:19`) — there is **no `update` action type**, no
`direction`/`placement`/`patch` token anywhere in `backend/ai/`.
`_REQUIRED_FIELDS` has no metadata-edit action for existing blocks;
`move`/`resize` require only `task_id` + a time field and cannot carry
`title`/`category`. `UpdateMutation` (`mutation_planner.py:99`) carries
only `action_index/task_id/new_start/new_end/start_supplied/end_supplied/
bare_move_derived_end/wrapped`; `UpdateDiffEntry` (`:123`) carries only
`block_id/start_time/end_time/action_index`. `title`/`category` exist
only on the create path (`CreateMutation`, `CreateDiffEntry`). **Today
there is no mechanism to rename or recategorise an existing block via
chat.** Phase 0 introduces that canonical `update` action end-to-end,
with its own red-first TDD cycle (Cycle 0), before any partial-apply
work builds on it.

## Terminology (field taxonomy)

- **Safe / metadata fields**: `title`, `category`. Independent of time;
  may always apply even when time is rejected.
- **Time fields**: `start_time`, `end_time` (and the placement
  `direction` intent from #109: `later` / `earlier` / `exact`). These
  are the only fields subject to window/overlap/interval rejection.
- **Outcome status vocabulary** (per action):
  - `applied` — every requested field for this action persisted.
  - `partial` — ≥1 field persisted AND ≥1 field skipped.
  - `skipped` — no field from this action persisted.

## Phase 0 — Introduce the canonical `update` action (#109 scope, folded in)

**Why this phase exists.** #109 is unmerged (see Context). The whole
feature depends on a single action that can carry a metadata edit
(`title`/`category`) **and** a time edit (`start_time`/`end_time` +
placement `direction`) for an existing block, so the partial-apply logic
has a per-field surface to accept/reject. This phase adds that action
end-to-end. It is a strict prerequisite for Phase 1.

### 0A. Schema layer (`schemas.py`)

- Add `"update"` to `ALLOWED_ACTION_TYPES` →
  `{"add", "move", "remove", "resize", "update"}`.
- Add `_REQUIRED_FIELDS["update"] = ("task_id",)` — `task_id` is the only
  mandatory field; every editable field is optional so a turn may carry
  any subset of `{title, category, start_time, end_time, direction}`.
- Extend `validate_action_shape` for `type == "update"`:
  - `task_id` must be a positive int.
  - **At least one** of `{title, category, start_time, end_time}` must be
    present (reject an empty patch as a shape error).
  - If present: `title` non-empty str; `category ∈ allowed_categories`;
    `start_time`/`end_time` valid `HH:MM` **format** only (reuse the
    existing `_is_hhmm` check `add`/`move` use). **Do NOT enforce the
    5-minute grid (or any window/interval rule) here** — a shape error
    aborts the whole turn (`run_chat` → `AIParseError`) before planning,
    which would defeat the partial-apply guarantee. Off-grid /
    out-of-window / granularity are skippable time-field rejections owned
    by the planner layer (Phase 1C), never by `validate_action_shape`.
  - `direction`, if present, ∈ `{"later", "earlier", "exact"}`; it is
    only meaningful alongside a time field. Default `"exact"` when a time
    field is present without a `direction`.
- Keep `move`/`resize`/`add`/`remove` schemas unchanged (backward compat;
  the model may still emit them, and Phase 1 treats `move`/`resize` as a
  pure time intent with no metadata part).

### 0B. Planner intake (`mutation_planner.py` `_normalize_actions`)

- Extend `UpdateMutation` with the metadata + placement carriers:
  add `new_title: str | None`, `new_category: str | None`,
  `direction: str` (default `"exact"`), and keep the existing time
  fields. `title`/`category` default `None` (= "not requested this
  turn"), distinct from an empty-string request (rejected at 0A).
- In `_normalize_actions`, handle `action["type"] == "update"`:
  build an `UpdateMutation` from whichever of
  `{title, category, start_time, end_time, direction}` the action
  supplied. `start_supplied`/`end_supplied` mirror today's `move`/`resize`
  bookkeeping. A metadata-only `update` (no time field) sets
  `start_supplied = end_supplied = False` and reuses the block's snapshot
  times as `new_start/new_end` (so the candidate map is well-formed;
  Phase 1C only treats a block as time-changed when a time field was
  actually supplied — see `changed_time_ids`).
- **Start-only `update` end derivation (FIX).** Verified against
  `compute_move_resize_times` (`mutation_planner.py:185–197`): end is
  derived **only** for `kind == "move" and "end_time" not in action` —
  there is **no** end-derivation path for a start-only `update`. Pin the
  rule: a start-only `update` (`start_time` supplied, `end_time` omitted)
  **inherits the block's existing snapshot `end_time` unchanged**
  (`new_end = block.end_time`, `end_supplied = False`). This means the
  duration shifts (the block keeps its original end), which is the
  intuitive "start it at HH:MM, keep the rest" edit and avoids
  re-deriving a duration the user never asked to change. (If instead the
  duration-preserving `move` semantics are desired for `update`, extend
  `compute_move_resize_times` to also cover `kind == "update"` — but the
  plan pins **inherit-existing-end** for `update` to keep the two intents
  distinct.) Either way the derived/inherited end is settled **before**
  the clamp/overlap validation in §1C, and because it is unsupplied it is
  never clamped (see §1C step 1).
- `move`/`resize` continue to build `UpdateMutation` with
  `new_title = new_category = None`, `direction = "exact"` (pure time
  intent). This keeps a single internal mutation type.
- **Merge must carry metadata forward (FIX — R2).** Verified against
  `_normalize_actions` (`mutation_planner.py:454–471`): the merge does
  `merged_updates[task_id] = UpdateMutation(...)`, **replacing** the whole
  struct for a `task_id` and today carrying forward only
  `start_supplied`/`end_supplied`/`bare_move_derived_end`/`wrapped` from
  `prev`. With 0B adding `new_title`/`new_category`/`direction` to
  `UpdateMutation`, a later same-turn `move`/`resize` on the same
  `task_id` (which sets `new_title = new_category = None`,
  `direction = "exact"`) would **wipe** an earlier `update` action's
  title/category/direction. The merge MUST **preserve** the previously-set
  `new_title`/`new_category`/`direction` from `prev` unless the newer
  action explicitly supplies them — same carry-forward discipline as
  `start_supplied`/`end_supplied`. Concretely, when the newer action's
  `new_title` is `None` (metadata not requested this turn), keep `prev`'s
  `new_title`; likewise `new_category`; and keep `prev`'s `direction`
  unless the newer action carries a non-default one alongside a supplied
  time field. Cycle 2's merged-fields test covers update-then-move on one
  `task_id` asserting title/category (and direction) survive the merge.

### 0C. Diff carrier (`mutation_planner.py` `UpdateDiffEntry`)

- Extend `UpdateDiffEntry` with `title: str | None` and
  `category: str | None` (both `None` = "don't touch this field"), plus
  **PER-BOUNDARY write/validation state** (FIX — R2), NOT a single
  `time_changed` flag: `start_changed: bool` and `end_changed: bool`
  (each True iff that boundary's edit was ACCEPTED and should be written +
  validated). Keep `block_id/start_time/end_time/action_index`.
- **Why per-boundary, not a single `time_changed` (FIX — R2).** The
  executor's `full_clean(exclude=["start_time","end_time"])` today
  excludes BOTH boundaries so an inherited off-grid boundary never fails
  `validate_five_minute_granularity` (`schedules/models.py:166–167`,
  `validators.py:4–10`). The planner validates ONLY the boundaries the
  user supplied (`mutation_planner.py:534–563`). A one-sided accepted edit
  (e.g. start-only) whose OTHER boundary is inherited off-grid must
  persist without re-validating the untouched side — a single
  `time_changed=True` that pulls BOTH fields back into `full_clean` would
  re-validate the unsupplied off-grid side and roll back the whole atomic
  apply, killing already-accepted metadata. So each side is tracked
  independently: `start_changed` is True only when the start edit was
  accepted (and on-grid); `end_changed` only when the end edit was
  accepted. A metadata-only entry sets both False.
- When the planner accepts a metadata-only update, it emits an
  `UpdateDiffEntry` with `start_changed = end_changed = False`, the
  requested `title`/`category`, and `start_time`/`end_time` = the
  **CHAIN-EFFECTIVE** times (R4-FIX-4), NOT the raw `snapshot_by_id`
  times. Verified against `_normalize_actions`
  (`mutation_planner.py:434–441`): `chain_effective[task_id]` tracks the
  live post-merge times, so if a same-turn `move`/`resize` on the same
  `task_id` shifted the block, the metadata-only entry must carry those
  post-move times (not the pre-move snapshot). These times are still
  **not written to the DB time columns** when both `*_changed` are False
  (the executor skips both assignments — §0D); they matter for the diff's
  self-consistency and any re-read, so use `chain_effective[task_id]` when
  present and fall back to the snapshot time only when the block had no
  time mutation this turn.
- **`_build_diff` must EMIT a metadata-only entry (R4-FIX-4).** Verified
  against `_build_diff` (`mutation_planner.py:725–733`): today it emits an
  `UpdateDiffEntry` **only when the times differ** from the snapshot.
  A metadata-only accepted update (time skipped, title/category changed)
  has unchanged times, so the current time-diff gate would **drop** the
  entry and the metadata write would be lost — Cycle 0 could not go
  green. Extend the gate: `_build_diff` MUST emit an `UpdateDiffEntry`
  when **either** the times changed **OR** `title`/`category` is
  requested (non-`None`), carrying `title`/`category`,
  `start_changed=False`/`end_changed=False` for the metadata-only case,
  and the chain-effective times.
- A start-only accepted edit whose end was inherited (see §0B) emits
  `start_changed = True, end_changed = False`; the reverse for an end-only
  edit; a both-sides accepted edit sets both True.

### 0D. Executor (`views.py` `_persist_mutation_diff`)

- For each `UpdateDiffEntry`: set `block.title`/`block.category` when the
  entry carries a non-`None` value; assign `block.start_time` **only when
  `start_changed` is True** and `block.end_time` **only when `end_changed`
  is True**. Build the `full_clean` `exclude` list **per boundary** (FIX
  — R2): include `start_time` in validation **only when `start_changed`
  is True** (accepted + on-grid); include `end_time` **only when
  `end_changed` is True**; otherwise keep that side in the `exclude` list.
  The rationale: the block may carry an **inherited off-grid boundary**
  (e.g. a legacy or upstream-derived time that would fail
  `validate_five_minute_granularity`) on the side the user did NOT touch;
  validating that untouched side would roll back the whole atomic apply
  and kill the accepted `title`/`category` and the accepted opposite
  boundary. A one-sided accepted edit (`start_changed=True,
  end_changed=False`) therefore validates only `start_time` and leaves
  the inherited `end_time` in `exclude`. For a **metadata-only** accepted
  entry (both `*_changed` False) both time fields stay excluded —
  preserving today's `full_clean(exclude=["start_time","end_time"])`
  behaviour for the fully time-skipped path.

### 0E. Chat system prompt (`prompts.py` `build_system_prompt_chat`)

- Document the `update` action: to rename/recategorise/retime an
  existing block the model emits **one** `update` carrying `task_id` plus
  any subset of `{title, category, start_time, end_time, direction}`. It
  MUST NOT compute free slots itself — the backend owns conflict
  resolution and slotting (expanded in §2G).
- **`direction` is never a standalone action.** A `direction` without any
  `{title, category, start_time, end_time}` is an empty patch (shape
  error → whole-turn abort). When the user accepts a server slot proposal
  ("yes" / "move it later"), the model re-emits the block as an
  `update`/`move` carrying the **concrete HH:MM times the server
  proposed**, optionally with a `direction` hint — never a bare
  `direction`.

## Phase 1 — Data layer: planner outcomes + FreeSlotFinder

Pure-function phase; no ORM, no view wiring. Everything here is
snapshot-in / dataclass-out and unit-testable in isolation.

### 1A. New result dataclasses in `mutation_planner.py`

Add (all `frozen=True`):

- `ActionOutcome` — per-resolved-candidate outcome record (one per
  merged `task_id` for updates, one per source action for creates; see
  §1C step 6). There is **no** separate `FieldOutcome` type; the
  field-level detail lives in the `applied_fields`/`skipped_fields`
  tuples on `ActionOutcome`:
  - `action_index: int`
  - `task_id: int | None` (None for a skipped/failed `add`). **Applied-add
    `task_id` (pinned):** an APPLIED `add` carries `task_id=None` (or the
    real DB id resolved AFTER persist) — NEVER the planner's negative
    `temp_id = -(action_index+1)` (`mutation_planner.py:505`), which is an
    internal placeholder and MUST NOT leak into the outcome/audit payload.
  - `status: str` (`applied` | `partial` | `skipped`)
  - `applied_fields: tuple[str, ...]` — fields **actually written to the
    `MutationDiff`**: a subset of `{title, category, start_time,
    end_time}`. `direction` is placement *intent* only, is NEVER
    persisted in a `MutationDiff` entry, and MUST NOT appear in
    `applied_fields` (nor in `skipped_fields`).
  - `skipped_fields: tuple[str, ...]` — requested-but-not-accepted fields
    from the same `{title, category, start_time, end_time}` set;
    `direction` never appears here either.
  - `reason_code: str | None` (`overlap`, `window`, `out_of_window`,
    `unresolved_conflict`, `direction_required`, `interval`,
    `granularity`, `unknown_task`)
  - `conflicting_task_ids: tuple[int, ...]` (real DB ids only; never
    another user's — see § Cross-user safety)
  - `suggestion: SlotSuggestion | None` (from `FreeSlotFinder`)
  - `attempted_direction: str | None` (`later` | `earlier` | `exact` |
    `None`) — **the placement direction a skipped time intent tried
    (R4-FIX-1).** Populated whenever a time skip triggered a
    `FreeSlotFinder` search (i.e. the time intent requested a concrete
    move and was skipped), regardless of whether the finder returned a
    slot. This is REQUIRED because when `FreeSlotFinder` returns `None`
    (no free slot in the requested direction), `suggestion` is `None` and
    the attempted direction would otherwise be lost — but
    `_build_resolution_ask` (§2C no-slot branch) must name it ("No free
    LATER slot fits <title>…"). Set to the requested `direction`
    (`later`/`earlier`/`exact`) on a slot-searching skip; `None` when no
    slot search ran (fully applied, metadata-only, or a non-move skip).
- `SlotSuggestion`: `start_time: datetime.time`, `end_time:
  datetime.time`, `direction: str` (`later`|`earlier`), OR the
  direction-required sentinel (`direction_required: bool` with no times).

**JSON serialization contract (used by §2D envelope and §2E audit).**
Both frozen dataclasses need a JSON-safe form because they carry
`datetime.time` fields and are embedded in `outcomes` (envelope) and the
audit `ai_response` payload. Add a single canonical serializer alongside
the dataclasses in `mutation_planner.py`:

- `action_outcome_to_dict(o: ActionOutcome) -> dict` producing:
  `{"action_index": int, "task_id": int|None, "status": str,
  "applied_fields": [str], "skipped_fields": [str],
  "reason_code": str|None, "conflicting_task_ids": [int],
  "attempted_direction": str|None (R4-FIX-1),
  "suggestion": slot_suggestion_to_dict(o.suggestion) | None}`.
- `slot_suggestion_to_dict(s: SlotSuggestion|None) -> dict|None`:
  `None` → `None`; a concrete slot →
  `{"start_time": "HH:MM", "end_time": "HH:MM", "direction": str}`;
  the direction-required sentinel →
  `{"direction_required": true}` (no times). Times are formatted with
  `t.strftime("%H:%M")` so the JSON carries strings, never `time`
  objects. Tuples serialize as JSON arrays.
- §2D builds the envelope `outcomes` via `[action_outcome_to_dict(o) for
  o in plan.outcomes]`; §2E persists the **same** list into the dedicated
  bounded `AIInteraction.outcomes_json` `JSONField` (NOT into the
  truncated `ai_response` TEXT — see §2E truncation-safety note). One
  serializer, two call sites — no divergent shapes. Cycle 4's audit test
  asserts the serialized shape (times are `"HH:MM"` strings, `suggestion`
  nested dict or `None`) and that `outcomes_json` round-trips as valid
  JSON even for a large (many-action) turn.
- `PartialPlan` — the new richer return type from `plan_mutations`:
  - `diff: MutationDiff` (only the **accepted** subset, exactly what
    the executor persists)
  - `outcomes: tuple[ActionOutcome, ...]` — one per **resolved
    candidate** (per `task_id` for updates after `_normalize_actions`
    merges same-`task_id` actions; per source action for creates, which
    never merge; **and one per `remove` action** — FIX R2). See §1C step 6
    "Provenance when multiple actions target one `task_id`" and the
    delete-outcome rule.
  - `overall_status: str` (`applied` | `partial` | `skipped`) — derived
    across **all** outcomes **including deletes** (FIX — R2): `applied`
    iff every outcome is `applied`; `skipped` iff no outcome is `applied`
    or `partial` (nothing persisted across all actions); else `partial`.
    A remove-only turn (all delete outcomes `applied`) is therefore
    `applied`; a remove-plus-skipped-time turn is `partial`.

Keep `PlanError` for **structural** failures that still abort the whole
turn (unknown task_id, schema-shape failures the schema layer missed) —
those remain `_Rollback` conditions, not partial applies. Time
validity/overlap/window are NOT `PlanError` anymore; they become
skipped time fields with an outcome.

### 1B. Split field-level accept/reject in the planner

Rework the normalize→candidate→validate→diff pipeline so it computes an
**accepted subset** rather than an all-or-nothing plan.

**Canonical action model.** After Phase 0 each existing-block edit is an
`update` action that may carry any subset of `{title, category,
start_time, end_time, direction}` (introduced in Cycle 0, not assumed
pre-existing). A `move`/`resize` remains a pure time intent with no
metadata part. Internally split each action's fields into two intents:

1. **Metadata intent** (`title`/`category`): always accepted (subject
   only to the schema-shape check already done in `validate_action_shape`).
2. **Time intent** (`start_time`/`end_time`/`direction`): subject to the
   final-state conflict-component algorithm below.

`add` actions have a metadata part **and** a time part, but per the
issue a fully out-of-window `add` has **no independent fields to
preserve** → skip the whole action, emit `skipped` outcome
(`reason_code=out_of_window`). A partially-in-window `add` clamps (see
one-sided overflow) if a non-empty interval remains; otherwise skipped.

**Exact-conflict / out-of-window `add` — no direction loop (R4-FIX-3).**
A skipped `add` (new block, exact-time conflict or out-of-window, no
`direction`) has **no `task_id`** (it was never persisted) and the `add`
schema carries **no `direction` field**, so the two-step
direction-answer flow — which recovers the desired interval from a prior
turn keyed on an existing block and re-emits it — does **not** apply to
adds and MUST NOT loop with repeated direction questions. Adopt option
(a): a conflicting/out-of-window `add` is simply **skipped and reported**
(`status="skipped"`, `reason_code=overlap` or `out_of_window`,
`task_id=None`, `suggestion=None`, `attempted_direction=None`). The
planner does **NOT** invoke `FreeSlotFinder` for an `add` and never emits
a `direction_required` sentinel for one. §2C's ask names the skipped add
**by its title** via the `action_index`-keyed create-title source (the
`title_map` from R3-FIX-3) and asks the user for a concrete free time —
there is no earlier/later FreeSlotFinder proposal for adds. The
direction-answer turn for an add is just the user re-emitting the `add`
with an adjusted concrete desired interval they picked; the server
validates that concrete add like any other add (accept if it fits, skip
+ re-ask if it still conflicts).
`remove` participates in final-state validation but has no metadata/time
split (it either deletes or, if it re-introduces an overlap-free final
state, is accepted; removes are never "skipped for safety" — a remove
only reduces occupancy).

**Shape-level aborts are NOT part of the skip surface (FIX — R3-FIX-6).**
A structurally-malformed action — e.g. an `add` with
`start_time >= end_time` (`schemas.py:100–107`), a bad `HH:MM`, or an
empty `title` — is a **shape error** that raises `AIParseError` and
aborts the **whole turn** before planning (`service.py:386–396`), so a
sibling metadata `update` in the same turn does **not** partial-apply.
This is distinct from **off-grid** times (a value-valid `HH:MM` that
fails the 5-minute grid), which are value-valid and handled — skippably —
at the planner layer (§1C). Only **value-valid-but-policy-rejected** time
fields (off-grid, overlap, out-of-window) are skippable while metadata
applies; malformed shapes remain whole-turn aborts and are intentionally
outside the partial-apply surface.

### 1C. Final-state conflict-component algorithm (step-by-step)

Goal: decide which **time** mutations are accepted such that the final
candidate schedule is overlap-free, **order-invariant**, and validated
against the **final candidate** (not sequential intermediate state).
Metadata always applies regardless of the time decision.

Definitions:
- Build the candidate map exactly as `_build_candidate` does today:
  start from snapshot blocks; apply deletes (remove keys); apply
  merged time updates (mutated `start/end`); add create temp-ids.
- `changed_time_ids`: candidate ids whose **time** was mutated this turn
  (updates that supplied/derived a time change) ∪ create temp-ids.
  Metadata-only updates are NOT in this set.

Steps:

1. **Per-mutation intrinsic validation** (window / granularity /
   interval / wrap). Run `_validate_update` / `_validate_create` logic
   per changed-time mutation. A mutation whose own time is intrinsically
   invalid (out of window, off-grid, start≥end, wraps midnight):
   - **Clamp only for window overflow** (not for off-grid/wrap/interval —
     those are hard rejections; see below), and **only on a boundary the
     user actually SUPPLIED** — never silently mutate a boundary the user
     didn't touch. Compute the two booleans explicitly from which
     **supplied** side overflows, against the real
     `clamp_boundary(start, end, window, *, clamp_start, clamp_end)`
     signature (`window.py:107`, verified):
     - `clamp_start = start_supplied and start < window.day_start`
     - `clamp_end = end_supplied and end > window.day_end`
     (`start_supplied`/`end_supplied` are the `UpdateMutation` bookkeeping
     from §0B / today's `move`/`resize` intake.) An unsupplied boundary
     is passed through unchanged (its matching `clamp_*` is False), so a
     start-only `update` whose end was inherited (see §0B) never has its
     end clamped, and vice-versa. Call `clamp_boundary(new_start,
     new_end, window, clamp_start=clamp_start, clamp_end=clamp_end)`.
   - **Boundary note (intentional).** A one-sided time edit
     validates/clamps ONLY the supplied boundary; if the UNSUPPLIED
     inherited boundary was already outside the window it is passed through
     untouched (the edit neither introduces nor is responsible for that
     pre-existing state) — this mirrors the shipped 0053 supplied-only
     validation in `_validate_update`
     (`mutation_planner.py:534–563`) and the issue's clamp-one-boundary
     rule. We do NOT reject the edit or force the whole block in-window.
   - **Far-side overflow is NOT clampable → reject (FIX — R2).** Clamp
     only fixes **near-side** overflow (`start < day_start`, `end >
     day_end`). A **supplied** boundary that lies fully outside the window
     on the **far** side — a supplied `start > day_end`, or (symmetric) a
     supplied `end < day_start` — is not clampable: neither `clamp_start`
     nor `clamp_end` fires for it, so `clamp_boundary` would leave that
     boundary untouched. Such a supplied far-side boundary MUST **reject**
     the time intent (`reason_code=out_of_window`) and revert to snapshot
     (update) / drop (create), **retaining today's supplied-side window
     rejection** in `_validate_update` (`mutation_planner.py:534–551`) so
     that, e.g., a start-only edit to `23:30` with a later inherited end
     does not persist past the window. Detect this **before/alongside**
     the near-side clamp: `start_supplied and start > window.day_end`, or
     `end_supplied and end < window.day_start` → reject (do not clamp).
   - **Bare-move derived end stays window-checked (FIX — R3-FIX-1).** The
     per-boundary rewrite above keys the window policy on
     `start_supplied` / `end_supplied` only, but a bare `move`
     (`end_supplied=False`) derives its end from the block's duration
     (`bare_move_derived_end=True`, `compute_move_resize_times`
     `mutation_planner.py:185–197`). That **derived** end must be treated
     as window-checked exactly like a *supplied* end — the live planner
     already guards the end when `end_supplied OR bare_move_derived_end`
     (`mutation_planner.py:543–551`). So the window-policy predicate for
     the end boundary is **`end_supplied OR bare_move_derived_end`** (and
     symmetrically the start predicate remains `start_supplied`),
     mirroring the live invariant. If a bare move's derived end exceeds
     `day_end`, the time intent is **REJECTED** as `out_of_window` (revert
     to snapshot) — do **NOT** near-side-clamp a derived end (clamping a
     boundary the user never supplied would silently shrink the moved
     block's duration), and do **NOT** let it persist past the window
     (`clamp_boundary` with both flags false returns the times unchanged
     — `window.py:116–126` — and `TimeBlock.clean` enforces only
     `start < end`, not the window — `schedules/models.py:182–191`). The
     Cycle-2 bare-move-derived-end-past-window test asserts skip /
     `out_of_window` (not clamp, not persist).
   - **Both-sides overflow** (`clamp_start and clamp_end`, i.e. the block
     straddles both window edges): this is still a single
     `clamp_boundary` call with **both** booleans True — the function
     clamps `start` up to `day_start` and `end` down to `day_end` in one
     call and returns the intersection, or `None` if it collapses. There
     is no separate "two-sided contract"; the one call covers it.
   - **`None` return = time intent rejected**, not clamp-success:
     `clamp_boundary` returns `None` when the block is fully outside the
     window (`start > day_end` or `end < day_start`) or the clamped
     interval collapses to `start >= end`. On `None`, mark the time
     intent rejected (`reason_code=out_of_window`) and revert to snapshot
     (update) / drop (create) — do **not** treat `None` as a slot.
   - If clamp yields a non-empty in-window interval, replace the
     mutation's candidate times with the clamped interval and continue.
   - **Non-window intrinsic invalidity** (off-grid `granularity`,
     `start≥end` `interval`, midnight `wrap`) is **not** clampable — mark
     the time intent rejected with the matching `reason_code`
     (`granularity`/`interval`/`window` for wrap), revert to snapshot
     (update) / drop (create). Clamp is attempted **only** when the sole
     problem is window overflow and the interval is otherwise grid-valid.
2. **Build overlap graph on the post-clamp candidate.** Nodes = all
   candidate blocks. Edge between two blocks iff `times_overlap`. This
   graph is rebuilt each fixpoint round from the **currently accepted**
   candidate (reverted time changes have their block back at its
   snapshot time and are no longer in the accepted changed set).
3. **Resolve overlaps deterministically, order-invariant — in TWO
   ordered sub-passes per round.** Maintain a working set
   `accepted_changed ⊆ changed_time_ids` of time changes still accepted
   this round (a time change reverted for any reason is **removed** from
   `accepted_changed` before the next round, so its block is no longer
   treated as a changed contributor).
   - **Sub-pass 3a — changed-vs-unchanged FIRST.** For each overlapping
     pair `(a, b)` where **exactly one** of `{a, b}` is in
     `accepted_changed`: the changed block collides with an **unchanged**
     block. **Skip the changed block's time intent** (revert to snapshot
     time / drop create), remove it from `accepted_changed`.
     `reason_code=overlap`, `conflicting_task_ids=[the unchanged block's
     real id]`. (No cascade — the unchanged block is never moved.)
     Resolving these first means a change that overlapped **only** an
     illegal change (which is itself rejected here vs an unchanged block)
     is re-evaluated after that illegal change reverts — see step 4.
   - **Sub-pass 3b — changed-vs-changed, only among STILL-accepted
     changes.** After 3a, for each overlapping pair `(a, b)` where
     **both** are still in `accepted_changed`: two requested time
     mutations genuinely collide. Mark **both** time intents UNRESOLVED
     (`reason_code=unresolved_conflict`, **order-invariant** — never pick
     a winner by action order). Revert both to snapshot time / drop both
     creates and remove both from `accepted_changed`.
     `conflicting_task_ids` lists the other changed block's id (temp
     create ids are omitted from the surfaced list; report only real DB
     ids).
   - Pairs where **neither** is in `accepted_changed` → a pre-existing
     overlap in the snapshot the user didn't touch; leave untouched (not
     this turn's problem; matches today's `_RANK_INHERITED` behaviour).
4. **Recompute (fixpoint) until the accepted subset is overlap-free.**
   Reverting a change alters the candidate and can **clear** overlaps
   that only existed because of a now-reverted change. Loop steps 2–3 on
   the updated candidate until a full round produces **no new
   rejections**. **Rebuild-each-round rule (FIX — R2):** each round MUST
   rebuild the changed-vs-final overlap graph from the **currently
   accepted** candidate (step 2) — neither sub-pass (3a nor 3b) may
   traverse edges built BEFORE that round's reversions. Batch-collect a
   round's rejection set from the current accepted graph, apply all its
   reversions, then rebuild before the next round, so a cascading survivor
   is never rejected on a stale edge or by pair-visitation order.
   **Critical cascade case the fixpoint must handle:** a **legal** change
   A that overlaps **only** an **illegal** change B (where B is
   independently rejected in 3a against an unchanged block C) must NOT be
   marked `unresolved`. On the first round B is reverted (3a, B-vs-C); the
   next round rebuilds the graph with B back at its snapshot time, A no
   longer overlaps anything, so A **survives as `applied`**. Because each
   round only ever reverts (never re-applies) a bounded set of
   changed-time mutations, the loop is monotone and terminates.
   **Termination bound (FIX — R2):** a single 1-change-vs-unchanged
   overlap takes TWO rounds — one that reverts plus one terminal clean
   round with no new rejections — so the guard bound is
   `len(changed_time_ids) + 1`, NOT `len(changed_time_ids)` (the latter is
   off-by-one and would fire on the primary case). Equivalently, guard by
   counting only **rejecting** rounds (≤ `len(changed_time_ids)`).
   Assert/guard the round count with the correct `+ 1` bound.
5. **Compute accepted diff.** After the fixpoint:
   - Metadata for every update: always in the diff (title/category).
   - Time for an update: in the diff **only if** its time intent
     survived (accepted or clamped).
   - Creates: in the diff only if not dropped.
   - Deletes: always in the diff (removes only reduce occupancy).
6. **Emit `ActionOutcome` per resolved candidate** (per merged `task_id`
   for updates, per source action for creates, **and one per `remove`
   action** — see the provenance rule below and the delete-outcome rule
   at the end of this step):
   - `applied_fields` = fields actually in the accepted diff for that
     candidate; `skipped_fields` = requested-but-not-accepted.
   - `status` per the vocabulary. `reason_code` from the rejection that
     hit the time intent (or `None` if fully applied).
   - `suggestion` = `FreeSlotFinder` result for skipped time intents
     that requested a concrete move **with a positive, grid-valid
     duration** (see 1D duration gate — R2). An interval-invalid, wrapped,
     or off-grid-duration skip gets **no** suggestion (`suggestion=None`);
     its `reason_code` stays and §2C's no-suggestion branch produces the
     ask. For `unresolved_conflict`,
     **no auto-suggestion** — the assistant will ask a direction/choice
     question in Phase 2 (the issue offers ONE best resolution; two
     mutually-conflicting requested moves get a clarification, not a
     guess).
   - `attempted_direction` (R4-FIX-1) = the placement `direction`
     (`later`/`earlier`/`exact`) of a skipped time intent whenever a
     `FreeSlotFinder` search was triggered for it — set it **regardless
     of whether the finder returned a slot**, so that when the finder
     returns `None` (no free slot in the requested direction) the
     attempted direction survives on the outcome for §2C's no-slot ask to
     name it. Leave it `None` when no slot search ran (fully applied,
     metadata-only, `unresolved_conflict`, or an interval-invalid/wrapped/
     off-grid skip that the duration gate blocked from the finder).

   **Provenance when multiple actions target one `task_id` (FIX —
   merged-update mismatch).** Verified against `mutation_planner.py`
   `_normalize_actions` (~:462–471): multiple `move`/`resize`/`update`
   actions on the **same** `task_id` in one turn collapse into a
   **single** `UpdateMutation` (last-write-wins), and `action_index` is
   overwritten with the **latest** contributing action's index;
   `changed_ids = set(merged_updates.keys())` is keyed by `task_id`, not
   by original action index. The plan resolves the mismatch by pinning
   **outcomes are emitted per resolved `task_id`, not per raw source
   action-index**: one `ActionOutcome` per resolved candidate id. Its
   `action_index` carries the **latest** (merged) action's index — the
   same value `_normalize_actions` keeps on the surviving
   `UpdateMutation` — so the outcome is traceable to the mutation that
   actually ran. `applied_fields`/`skipped_fields` reflect the **merged**
   result (the final field set that survived last-write-wins + the
   fixpoint), not the pre-merge per-action requests. Metadata from
   earlier merged-away actions that survived into the merged mutation is
   attributed to that single outcome. **The merge preserves earlier-set
   `new_title`/`new_category`/`direction` (§0B FIX — R2): a later
   `move`/`resize` on the same `task_id` does NOT null out an earlier
   `update`'s metadata**, so the merged outcome's `applied_fields`
   correctly include the surviving title/category. (A skipped/dropped
   `add` has no `task_id`; it keeps its own per-action outcome with
   `task_id=None`.)

   **Delete outcomes (FIX — R2).** Verified against
   `mutation_planner.py:140`: `remove` actions always enter `MutationDiff`
   as a `DeleteMutation` (deletes list) — removes only reduce occupancy
   and are never skipped for safety. Each `remove` action therefore emits
   **one** `ActionOutcome` with `status="applied"` (or `"skipped"` only
   for a structural miss such as an unknown `task_id`, handled as a
   `PlanError` abort — a genuinely-planned remove is always `applied`),
   `task_id` = the removed block's real id, empty `applied_fields`/
   `skipped_fields` (a delete has no per-field split), `reason_code=None`,
   no `suggestion`. Deletes MUST be included in the `overall_status`
   rollup (see §1A) so a **remove-only** turn resolves to
   `overall_status="applied"` (not undefined) and a **remove-plus-skipped-
   time** turn resolves to `"partial"`.

Order-invariance test hook: `plan_mutations([A,B]) == plan_mutations([B,A])`
in accepted-diff + outcomes (modulo action_index labels) for the
two-requested-move conflict case.

### 1D. `FreeSlotFinder` (`backend/ai/free_slot.py`)

Pure function; **no second LLM call** — backend owns scheduling safety.

Signature (conceptual):
`find_slot(desired_start, desired_end, direction, window,
occupied_intervals) -> SlotSuggestion | DIRECTION_REQUIRED | None`

- `occupied_intervals`: the **final accepted** candidate blocks' `(start,
  end)` (i.e. after Phase-1C fixpoint, excluding the block being placed),
  so a proposal never collides with what actually persisted this turn.
- `duration = desired_end - desired_start` (preserve the requested
  duration; do not shrink).
- **Duration gate (FIX — R2): only suggest for a valid grid duration.**
  A skipped time intent whose desired interval is itself
  interval-invalid (`desired_end <= desired_start`), wrapped past
  midnight, or off the 5-minute grid can never yield valid grid
  boundaries by preserving that duration, so `FreeSlotFinder` must NOT be
  invoked for it. `find_slot` produces a slot **only when** `duration` is
  **positive** and a **multiple of `GRID_MINUTES` (5)**; otherwise it
  returns `None` (emit NO suggestion — the `reason_code` from §1C step 1,
  i.e. `interval`/`window`(wrap)/`granularity`, is retained, and §2C's
  no-slot / no-suggestion branch produces the ask). The caller in §1C
  step 6 therefore requests a suggestion only for a **grid-valid,
  positive-duration** skipped concrete move; interval-/wrap-/granularity-
  shaped skips get no suggestion (never a bogus one).
- **Grid must match the planner's enforced granularity so a proposed
  slot is never rejected on the follow-up move turn.** The planner
  validates times via `schedules.validators.validate_five_minute_granularity`
  (`mutation_planner.py:16`, ranks `_RANK_GRANULARITY`), i.e. the
  enforced granularity is **5 minutes**. Do not hardcode a bare `5`
  literal that could drift from that source: define
  `GRID_MINUTES = 5` in `free_slot.py` with a comment citing
  `validate_five_minute_granularity` as its authority, and add a guard
  test (Cycle 1) asserting every `FreeSlotFinder` output start/end passes
  `validate_five_minute_granularity` (so if the validator's granularity
  ever changes, the test fails loudly rather than the finder silently
  proposing rejectable slots). Work in integer minutes-since-midnight
  using `window.start_minutes` / `window.end_minutes`; because
  `GRID_MINUTES` divides 60 and `window.start_minutes`/`end_minutes`
  derive from grid-valid `HH:MM` window bounds, every emitted boundary
  lands on a 5-min mark.

Algorithm per direction:

- **`later`**: start the candidate at `desired_start` rounded UP to the
  next 5-min grid mark; step `+5` min each iteration; for each candidate
  `[s, s+duration)`, accept the first that (a) lies fully within
  `[window.start_minutes, window.end_minutes]` and (b) does not overlap
  any `occupied_interval`. Stop when `s + duration > window.end_minutes`
  → return `None` (no slot). **Never** return a slot earlier than
  `desired_start`.
- **`earlier`**: candidate end aligned so `[s, s+duration)`; step `-5`
  from `desired_start` rounded DOWN; accept first non-overlapping
  in-window slot. Stop when `s < window.start_minutes` → `None`. **Never**
  return a slot later than `desired_start`.
- **`exact`**: the user asked for a specific time with no direction and
  it conflicts. Do **not** pick a side. Return the
  `DIRECTION_REQUIRED` sentinel → Phase 2 turns it into a "search
  earlier or later?" `ask`.

Window guarantees: candidates are generated only within
`[window.start_minutes, window.end_minutes]`; the finder can never
cross the configured window. Returns `None` when no valid slot exists in
the requested direction.

`SlotSuggestion` carries HH:MM `start_time`/`end_time` +
`direction`. Convert minutes → `datetime.time` via
`divmod(mins, 60)`.

## Phase 2 — API / executor / envelope / audit

Depends on Phase 1. Wires the planner's `PartialPlan` through the view.

### 2A. `_apply_actions_sync` (`views.py`)

- Call `plan_mutations` → now returns `PartialPlan | PlanError`.
  `PlanError` still `_Rollback`s (structural abort). `PartialPlan`:
  - `_persist_mutation_diff(locked_schedule, locked_blocks,
    plan.diff)` — persists **only** the accepted subset in the existing
    single `transaction.atomic()`. Executor persists exactly the
    planner's diff and makes **no policy decision**.
  - `mark_active_on_edit()` only if the diff is non-empty (something
    persisted). If the accepted diff is empty (everything skipped),
    persist nothing but still return outcomes (no `_Rollback`).
  - Return `plan.outcomes` + `plan.overall_status` to the async view
    (stash on a small result object, or return from the `sync_to_async`
    call — return a value rather than raising, since nothing rolls back).

### 2B. `_persist_mutation_diff` metadata support

Extend `UpdateDiffEntry` (Phase 1) and this function to also persist
`title` / `category` when the accepted diff carries them (currently it
only sets `start_time`/`end_time`). Metadata-only update entries skip the
time assignment **and keep both time fields in `full_clean(exclude=...)`**
so an inherited off-grid boundary cannot roll back the accepted metadata
(see §0D). **Per-boundary validation (FIX — R2):** include `start_time`
in `full_clean` only when `start_changed is True`, and `end_time` only
when `end_changed is True` (accepted + on-grid); a one-sided accepted
edit validates ONLY the changed side and leaves the untouched (possibly
inherited off-grid) side excluded, so the one-sided edit persists without
rolling back on the other boundary.

### 2C. Server-generated `ask` from outcomes

New helper `_build_resolution_ask(outcomes, window, title_map) -> str |
None` (views.py or a small `ai/resolution.py`). **Contract (FIX-10):** the
helper receives a **user-scoped `title_map`** so it can name the
conflicting block(s) in the ask — `ActionOutcome` carries **no** title,
so a title lookup is required. The map is scoped to
`schedule=locked_schedule` (Cross-user safety), so it can never name
another user's block. **Skipped-create coverage (FIX — R3-FIX-3).** A
skipped/conflicting `create` has `task_id=None` and its temp id is never
persisted, so a bare `dict[int, str]` block-id→title map cannot name it.
The `title_map` must therefore carry create titles too, keyed by
**`action_index`** (the create's source action), in addition to real
block ids — concretely
`title_map: dict[str, str]` keyed as `f"block:{id}"` for existing blocks
and `f"action:{action_index}"` for creates, OR two maps
(`block_titles: dict[int, str]` + `create_titles: dict[int, str]` keyed
by `action_index`). Build both from the locked snapshot (existing block
titles) and `parsed_actions` (create titles by action index). The helper
resolves an outcome's display title by `task_id` when present, else by
`action_index` for a `task_id=None` create. (An equally acceptable

  "Renamed and recategorised; move it to the nearest free slot at

  the user's language for the metadata part, but the server `ask` is a
  fixed template. Acceptable per issue: chat shows a short summary.)
- If any outcome is `direction_required` (exact-time conflict) → ask
  "Should I look for an earlier or later slot?"
  **Two-step flow (FIX — R3-FIX-2).** A `direction_required` outcome has
  **no concrete slot yet** — `FreeSlotFinder` returned the
  `DIRECTION_REQUIRED` sentinel precisely because no side was chosen, so
  there is no HH:MM to accept on this turn. The flow is therefore:
  (1) **exact-conflict turn**: server returns `direction_required` and
  asks earlier/later; (2) **direction-answer turn**: the user's reply
  ("later" / "earlier") re-supplies the originally-rejected desired
  interval **plus** the chosen `direction`, so the server now runs
  `FreeSlotFinder` **with that direction** and returns a **concrete
  HH:MM proposal** (or the no-slot ask if none fits — §2C no-slot
  branch); (3) **acceptance turn**: the user accepts that concrete
  proposal via an `update`/`move` carrying the real proposed
  `start_time`/`end_time`. The concrete slot is computed on the
  **direction-answer turn**, never fabricated on the exact-conflict turn.
  The Cycle-4 exact-conflict-direction test covers this two-turn
  sequence (exact conflict → direction ask → direction answer → concrete
  proposal).
- **No-slot / no-suggestion branch (FIX-9 + R2):** if a skipped time
  intent has **no `suggestion`** and no `direction_required` sentinel —
  because `FreeSlotFinder` returned **`None`** (no free slot in the
  allowed direction within the window — including the case where the user
  already answered "later"/"earlier" and still no slot fits) **or**
  because the desired interval was itself interval-invalid / wrapped /
  off-grid so no suggestion was ever generated (§1D duration gate — R2) —
  `_build_resolution_ask` MUST still return a **non-null** message. For
  the no-free-slot case, state no free slot exists in the requested
  direction, naming the direction from the outcome's
  `attempted_direction` (R4-FIX-1) — `ActionOutcome.suggestion` is `None`
  here, so the attempted direction (`later`/`earlier`) MUST come from
  `attempted_direction`, not `suggestion` (e.g. "No free {later|earlier}
  slot fits <title> within your day window; the rename was applied — pick
  a specific time or free up space." — the `{later|earlier}` token is
  `attempted_direction`). For the interval-invalid/off-grid case, state the requested
  time was invalid and ask for a valid one (e.g. "That time range for
  <title> isn't valid; the rename was applied — give a start/end on a
  5-minute boundary."). It must **never** silently return `ask=null` on a
  partial/skip turn — a skipped time always yields either a concrete
  proposal, a direction question, an unresolved-conflict choice, or this
  no-slot/no-suggestion message.
- **Skipped `add` (conflicting / out-of-window) — R4-FIX-3.** A skipped
  `add` outcome (`task_id=None`, `suggestion=None`,
  `attempted_direction=None`, `reason_code` `overlap`/`out_of_window`) is
  NOT routed through the earlier/later FreeSlotFinder flow (adds get no
  server slot proposal — see §1B/§1C). Instead the ask **names the add by
  its title** via the `action_index`-keyed create-title source
  (`title_map`, R3-FIX-3) and asks the user for a concrete free time
  (e.g. "<title> doesn't fit at that time; the rest was applied — give it
  a specific start/end time."). This is a distinct branch from the
  no-slot move message (which has an `attempted_direction`); the add
  branch never names a direction and never proposes a slot.
- If any outcome is `unresolved_conflict` (two requested moves) → ask
  which of the two to move (name both by title via `title_map`; **only**
  blocks the user themselves referenced this turn — no cross-user
  leakage).
- Priority when multiple: pick ONE (issue: one proposal or one

## FreeSlotFinder algorithm — worked reference

Window `06:00–23:00` → `start_minutes=360`, `end_minutes=1380`.
Desired `[16:00,17:00)` (`960–1020`, duration 60), conflict with an
existing block `16:00–17:30`, direction `later`:

1. Round `960` up to grid → `960`.
2. `s=960`: `[960,1020)` overlaps `[960,1050)` → reject.
3. `s=965,970,...`: keep stepping +5 until `[s,s+60)` clears
   `[960,1050)` → first clear at `s=1050` (`17:30`) →
   `[1050,1110)` = `17:30–18:30`, in-window, non-overlapping → **accept**.
4. Suggestion `{start:"17:30", end:"18:30", direction:"later"}`.

`earlier` mirrors: step `-5` from `960`; first `[s,s+60)` fully before
`960` (or clearing all occupied) and `≥ start_minutes` → accept; if
`s < 360` before a clear slot → `None`.

`exact` (no direction, exact conflict) → `DIRECTION_REQUIRED` → server
`ask` = "earlier or later?".
