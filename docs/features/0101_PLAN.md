# 0101 — Harden task_id on Todoist and Habitica complete endpoints (issue #308)

## Context

`POST /api/todoist/tasks/<task_id>/complete/` and `POST /api/habitica/tasks/<task_id>/complete/` put `task_id` into the upstream provider URL with no format check and no percent-encoding:

- Todoist: `backend/todoist_sync/service.py::complete_task` builds `f"{TODOIST_BASE_URL}/tasks/{task_id}/close"`.
- Habitica: `backend/habitica_sync/service.py::complete_task` builds `f"{HABITICA_BASE_URL}/tasks/{task_id}/score/up"`.
- The only guard is the `<str:task_id>` route in `backend/day_forge/urls.py`, which rejects `/` and nothing else.

Django decodes the path before routing, so a percent-encoded `?`, `#` or `..` can reach the service as a literal and change which provider path is called. Impact is low (authenticated, CSRF-protected, POST-only, fixed host, user's own token). This is defence in depth; it was found by reading the code (see #308) and has not been reproduced against the real providers.

## Decisions (agreed)

1. **Validate at the view, not with a stricter route.** Keep `<str:task_id>` in `backend/day_forge/urls.py` and add a short comment explaining why. A stricter `re_path` or a converter that raises `ValueError` yields Django **404** (often HTML), not 400 with the JSON error envelope. The required contract is 400 for ids that reach the view.

2. **400 envelope.** Same shape as a bad date on the tasks endpoints: `_envelope("Invalid task id.", 400)` → exactly `{"errors": {"detail": "Invalid task id."}}` (no `code` or `meta`). Do **not** use `resource_error`. Validate the id **before** the 503 "no account" check, matching the date-parse order on GET tasks. A malformed id must not call the provider, including when the user has no account. Authentication, CSRF and method guards stay on the decorators, ahead of this check.

3. **Id formats.** Validators live in `backend/todoist_sync/schemas.py` and `backend/habitica_sync/schemas.py` as `is_valid_task_id(task_id: str) -> bool`. Use `re.fullmatch`, not `re.match` (Python `$` can succeed before a trailing newline).
   - Todoist: `^[A-Za-z0-9_-]{1,64}$` (ids look like `6X7rfFVPjhvv84XG`).
   - Habitica: canonical hyphenated UUID only. Accept mixed case. Reject `urn:uuid:`, braces, and 32 hex digits without hyphens (regex plus `uuid.UUID(task_id)` with `str(parsed) == task_id.lower()`).

4. **Service layer.** In each `complete_task`, build the path with `urllib.parse.quote(task_id, safe="")` (same pattern as `backend/gcal_sync/service.py`). The service does **not** apply the full format check, so a service-level test can still pass an unexpected character and assert encoding. It **does** reject the exact ids `.` and `..` with `ValueError` and no upstream request: `quote` leaves those characters unchanged, and `requests` then normalises `/tasks/../close` to `/close` (and `/tasks/./close` to `/tasks/close`). This closes a direct-caller gap that encoding alone does not. Update the Todoist `complete_task` docstring that currently calls the id opaque and says it is built straight into the URL.

5. **Tests (red, then green).**
   - View, both providers, mock `*.service.requests.post`: malformed ids return 400, exact envelope `{"errors": {"detail": "Invalid task id."}}`, `post` is not called. Cases: `%3F` (`?`), `%23` (`#`), `..`, `%2E%2E`, `%25` (`%`), over-long (Todoist: 65 allowed characters; Habitica: a non-UUID / 65-character string). Raw unencoded `?` and `#` are not used in HTTP tests (they start a query or fragment).
   - Also assert 400 for a malformed id **without** a connected account (validation precedes the 503). Preserve existing 503 tests that use a valid id.
   - Empty id: `<str:>` is `[^/]+`, so `/tasks//complete/` is **404** at routing. Unit-test the validator with `""`. Assert HTTP 404 and that `post` is not called.
   - `%2F` (slash after decode) is also 404 with no upstream call. This is a deliberate exception to the issue's "400 for %2F-decoded separators" test list, because the value never reaches the view. Record it in the OpenSpec requirement. Do not invent route handling just to turn that 404 into 400. A twice-encoded slash (`%252F`) reaches the view as a literal `%` and is 400.
   - Valid Todoist id still hits exactly `.../tasks/6X7rfFVPjhvv84XG/close` (existing test). Add a Habitica end-to-end test that a canonical UUID hits exactly `.../tasks/<uuid>/score/up` (exact URL, not only a suffix).
   - Service-level: `complete_task(..., "abc?x")` POSTs a URL containing `abc%3Fx` with the `/close` or `/score/up` suffix intact. `complete_task(..., "..")` and `"."` raise `ValueError` and do not call `post`.
   - Unit tests: Todoist lengths 1 and 64, accepted `_`/`-`, rejected length 65 and whitespace; Habitica mixed-case letters, unhyphenated form, `urn:`/braces.
   - **Existing Habitica view tests** post to `/api/habitica/tasks/task-id/complete/` (`test_complete_invalidates_cache`, `test_complete_error_mapping`, `test_complete_maps_improperly_configured_to_500`). `task-id` is not a UUID and would 400 after the fix; change them to a canonical UUID. Service tests that use `"daily-id"` / `"task-id"` stay: those ids are not `.`/`..`, and a hyphen is left as-is by `quote(..., safe="")`.

6. **OpenSpec.** This is a specified-behaviour change (new 400 contract; Todoist "Complete a task" currently says "with the opaque id"), so a change is required. `spec-check` would not fail without it, but `docs/features/README.md` and `tasks/todo.md` (#308 item) require a delta.
   - This plan; change `openspec/changes/0101-task-id-hardening/` with `proposal.md` (links to this plan and #308), `tasks.md`, and spec deltas: **ADDED** id-validation requirements under `specs/integrations/todoist/` and `habitica/` (`SHALL` first line, body under 500 characters, `Enforced:` and `Tests:` under scenarios). The ADDED requirement covers 400 for malformed ids that reach the view, no upstream call, and 404 with no upstream call for empty ids and decoded slashes that fail routing.
   - **MODIFIED** Todoist "Complete a task" to drop "opaque" and to make the 503-without-account scenario conditional on a valid id (malformed ids return 400 even with no account). The same 503 qualification on Habitica "Complete a task". Preserve the other existing scenarios in each MODIFIED requirement.
   - Archive on this feature branch with `openspec archive 0101-task-id-hardening` before finishing. Close the #308 item in `tasks/todo.md`. Leave the "OpenSpec baseline triage" item alone. `docs/features/0099_SPEC_REVIEW.md` has no `task_id` lines to remove.

7. **Out of scope.** Other Todoist/Habitica functions do not interpolate request values into upstream URLs the same way (only fixed paths and query `params`). Do not widen the change. `docs/api.md` was initially left out; after the PR review it was updated in this change (id format and the `400` response for both complete endpoints).

- **P2 OpenSpec must qualify 503 scenarios (accepted):** see decision 6.
