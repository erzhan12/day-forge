# Feature 0050 — Calendar-name matching in Travel Rules

## Description

Extend `TravelRule` with an optional `calendar_name` field so rules can match
by the source calendar (e.g. "all events from calendar 'Work' → category work")
in addition to the existing keyword-in-title matching. Keyword rules take
priority over calendar-name-only rules.

## Backend

### Model: `backend/calendar_sync/models.py`

Add field to `TravelRule`:

```
calendar_name = CharField(max_length=200, blank=True, default="")
```

Empty string = "match any calendar" (current behaviour preserved).

**Also relax `keyword`** — it is currently `CharField(max_length=100)` with
implicit `blank=False` (`models.py:62`). A calendar-only rule stores
`keyword=""`, which a Django `ModelForm`/admin would reject. Change to
`CharField(max_length=100, blank=True, default="")` so calendar-only rows are
valid at the model layer, not just the DB layer.

Migration: one migration with **two operations** — `AddField(calendar_name)`
**and** `AlterField(keyword, blank=True, default="")`.

**Cross-field validation (review):** with both `keyword` and `calendar_name`
now `blank=True`, a Django **admin** ModelForm could persist a both-blank rule
(the API's at-least-one check lives in the parser, not the model). Add
`TravelRule.clean()` raising `ValidationError` when both trim to empty, so the
admin form (which calls `full_clean`) enforces the same invariant. Note
`clean()` is not called on a bare `.create()`/`.save()`, so it does not
double-validate the API path — it targets the admin/ModelForm surface only.

### Admin: `backend/calendar_sync/admin.py`

Minor (P3): add `calendar_name` to `TravelRuleAdmin.list_display` (`admin.py:27-29`)
so calendar-only rows don't render blank in the admin changelist.

### Serialization: `backend/calendar_sync/travel_rules.py`

- `serialize_travel_rule()` — add `"calendar_name": r.calendar_name` to the dict.

**Key-presence gating is critical (review — two near-misses):** both parsers
must treat `keyword` and `calendar_name` as *present-key-only* reads, exactly
like the existing `category`/`order` branches (`if field in data:`). Two traps
if this is done the create-shaped "always `data.get()` into `cleaned`" way:
  1. **CREATE regression:** the current create parser reads `keyword`
     unconditionally (`data.get("keyword")`, line 97). If `calendar_name` is
     read the same unconditional way, every existing **keyword-only** POST that
     omits `calendar_name` gets `None` → `_clean_calendar_name(None)` → 400. The
     from-event flow and its tests (`test_from_event.py:443-447`) never send
     `calendar_name`, so this breaks the whole feature's existing path. Gate on
     `if "calendar_name" in data:`.
  2. **PATCH wipe:** an order-only PATCH must not blank `calendar_name`. If the
     patch parser injects `calendar_name=""` whenever the key is absent, an
     order-only or keyword-only PATCH silently wipes a calendar-only rule's
     constraint. Keep the existing `if "keyword" in data:` gating and add the
     same `if "calendar_name" in data:` branch.

- `_parse_create_payload()` — add a `calendar_name` branch **gated on
  `if "calendar_name" in data`** (max 200, strip). Then relax the keyword
  requirement: instead of the unconditional `_clean_keyword` at line 97, clean
  `keyword` only when present, and enforce the "at least one of keyword /
  calendar_name is non-empty after strip" check on the resulting `cleaned`
  values (400 when both empty/absent).
- `_parse_patch_payload(data, rule)` — add `calendar_name` gated on
  `if "calendar_name" in data`, same as keyword's existing branch. Re-validate
  the "at least one" invariant against the **merged** state:
  `keyword_final = cleaned.get("keyword", rule.keyword)` /
  `calendar_final = cleaned.get("calendar_name", rule.calendar_name)`; reject
  (400) when **both** are empty after strip. The `.get(field, rule.field)` merge
  is only correct *because* omitted keys stay out of `cleaned` (present-key
  gating above). The `travel_rule_detail` view (`travel_rules.py:258`) must be
  updated to pass `rule` to the parser.
  - **Accepted gap (concurrency):** two concurrent PATCHes each blanking a
    different field can still leave both empty (read-then-save TOCTOU). This is
    the same self-limiting race already documented+accepted for the per-user
    count check in this file (`travel_rules.py:173-177`); do **not** add a DB
    CHECK constraint or row lock for it — match the existing pattern and note it.

### Existing validation helpers

- `_clean_keyword()` — must stop hard-erroring on empty when `calendar_name`
  will be set. The current helper returns a 400 on blank/whitespace/non-string
  (`travel_rules.py:50-52`). Do **not** call it unconditionally; instead clean
  keyword and calendar_name independently (both may legitimately be `""`), then
  enforce the "at least one non-empty" check on the **cleaned** values.
  - **Present-but-empty strings (review):** the UI always sends **both** keys,
    e.g. a calendar-only add POSTs `{"keyword":"", "calendar_name":"Work"}` and
    a keyword-only add POSTs `{"keyword":"dentist", "calendar_name":""}`. A
    present `keyword:""` must therefore NOT 400 on its own — only the final
    both-empty check may 400. Keep `isinstance(str)` + max-length validation for
    a present key, but treat empty/whitespace-after-strip as `""` (contributes
    "nothing" to the at-least-one check), not as a hard error. Same for a
    present `calendar_name:""`.
- New `_clean_calendar_name(value)` — **guard `isinstance(value, str)` first**
  (mirror `_clean_keyword` line 51), else a `null`/list/number body calls
  `.strip()` and raises → 500 instead of a clean 400. Then strip, enforce
  max-length 200, return cleaned. Whitespace-only strips to `""` (counts as
  "not provided" for the at-least-one check).

### Matching: `frontend/src/utils/travelRules.ts`

`matchTravelRule(rules, title)` → `matchTravelRule(rules, title, calendarName = "")`
(**default the 3rd param to `""`** so the existing 2-arg tests at
`travelRules.test.ts:37-63` keep compiling/passing; guard `rule.calendar_name`
with `?? ""` before `.trim()` in case an older cached rule lacks the field):

Define one **case-insensitive equality** primitive
`calEq(a, b) = a.trim().toLowerCase() === b.trim().toLowerCase()`. The two
passes apply it with **different empty-semantics** (see the critical note):

1. **Pass 1 — keyword rules**: iterate in order; skip rules whose `keyword`
   trims to empty. For a surviving rule, the keyword must substring-match the
   title AND (if `rule.calendar_name` trims to **non-empty**)
   `calEq(rule.calendar_name, calendarName)`; if `rule.calendar_name` is empty,
   apply **no** calendar constraint (empty = "match any calendar"). Return
   first hit. **A rule whose keyword matches but whose calendar constraint fails
   must `continue` to the next rule — NOT `return null`** (review) — otherwise a
   `{dentist, Work}` rule would abort pass 1 for a Home-calendar dentist event
   and hide a later `{dentist, ""}` rule that should match.
2. **Pass 2 — calendar-only rules**: iterate in order; skip rules whose
   `keyword` is **non-empty** (after trim) **and** skip rules whose
   `calendar_name` trims to **empty**. For the rest, match on
   `calEq(rule.calendar_name, calendarName)`. Return first hit.
3. Return `null`.

**CRITICAL empty-semantics (review — P1):** the empty case is NOT symmetric
between passes, so a single shared `calendarMatches` helper returning
`empty → true` is wrong:
  - Pass 1 empty `rule.calendar_name` = "match any" (skip the constraint).
  - Pass 2 empty `rule.calendar_name` = **skip the rule** (a rule with empty
    keyword AND empty calendar_name is degenerate — the API's at-least-one
    invariant forbids creating it, but a whitespace-only-keyword row, or an
    older row, can still reach pass 2 with `calendar_name=""`). If pass 2 did a
    bare `calEq("", "")` it would match **every** event that has no calendar
    name (`calendarName=""`), silently hijacking matching. Explicitly guard
    `rule.calendar_name.trim() !== ""` before the `calEq` in pass 2. This also
    keeps the existing whitespace-keyword skip test (`travelRules.test.ts:53-58`)
    green: that row has `calendar_name=""` so pass 2 skips it and the intended
    keyword rule still wins in pass 1.

**Case handling (review):** the backend stores `calendar_name` strip-only (no
case fold), and provider names are mixed-case (Google `summary`, CalDAV display
name). Both passes MUST use `calEq` — an earlier draft left pass 1 unspecified,
which would make a keyword+calendar rule miss `Work` vs `work` while a
calendar-only rule hit.

This guarantees keyword rules always beat calendar-only rules regardless of
`order` values.

**Precedence vs the reorder UI (review):** the two-pass design overrides the
existing "top rule wins / ascending `order`" contract *across* classes — a
calendar-only rule at `order=0` still loses to a keyword rule at `order=99`.
The reorder ↑/↓ buttons in `TravelRulesList.vue` therefore become a visible
no-op when moving a calendar-only rule above a keyword rule. Acceptable, but
the Settings copy/hint must state the precedence (keyword rules always match
first) — see the UI section below.

### Caller: `frontend/src/pages/Schedule.vue`

`handleAddToSchedule(ev)` currently calls
`matchTravelRule(travelRules.value, ev.title)` (`Schedule.vue:274`). Change to
`matchTravelRule(travelRules.value, ev.title, ev.calendar_name)`.

**Google discoverability note (review):** matching against `ev.calendar_name`
is correct for both providers — for Google it is the calendar `summary`
(`gcal_sync/service.py:588`), for CalDAV the calendar display name. But
`ExternalEventsPanel.vue:136-137` shows the `account_label` (email) chip for
Google events and only falls back to the `calendar_name` chip when
`account_label` is empty (Apple). So a Google user never sees the calendar-name
string the rule matches on and cannot copy it from the panel. Not a
matching-correctness bug — a UX/discoverability gap. Out of scope to fix the
panel here, but the Settings hint should tell users the calendar name is the
exact Google/Apple calendar name (e.g. "Work"), not the account email.
