# Feature 0082 — Preserve past template blocks in AI drafts

## Context

GitHub issue #202 is caused by LLM inference, not backend filtering. `build_draft_user_message()` supplies both `Current local time: {now:%H:%M}` and every template entry, while draft Rule 2 permits routinely skipped blocks to be dropped. With no explicit instruction protecting already-started template blocks, the model can treat the current time as a cutoff and omit `Gym 07:30` when generating at 12:00.

Required behavior:

- Generating a draft at 12:00 for a weekday whose template contains Gym 07:30 produces a draft that includes the 07:30 Gym block.
- Included past blocks default to completed=false (user marks them done manually).
- Past blocks still respect the working-day window and non-overlap rules.
- Test asserts a past-time template block survives into the generated draft/prompt.

## Decision and scope

Ship **Option A: prompt-only**.

This matches established repository practice:

- Feature 0074 fixed model behavior by changing prompt wording and deterministically testing the rendered prompt.
- Feature 0080 likewise confines an LLM classification correction to its system prompt and substring-based prompt tests.
- `backend/tests/test_ai_prompts_draft.py` already treats `build_system_prompt_draft()` and `build_draft_user_message()` as pure, offline-testable functions.

Do not implement Option B reconciliation now. Python reconciliation would require defining template-to-action identity, deciding whether history-based time shifts still count as the same block, and resolving collisions introduced by re-added blocks. That complexity is unnecessary while the model already receives every template entry and only lacks an explicit instruction. Reserve reconciliation for a follow-up only if repeated real-model verification shows the configured draft model still drops eligible past blocks after Option A.

No frontend, API schema, database model, migration, or draft-apply algorithm changes are required.

## Prompt semantics

The fix has two prompt-only parts. Both are pure-function edits; no schema, model, migration, API, or apply-algorithm change.

### Part 1 — make the draft prompt date-aware (`build_draft_user_message()`)

`ai_generate_draft` accepts **any** ISO date (`backend/ai/views.py` parses `date` with no "is today" restriction), and the frontend drafts non-today dates in practice (the auto-draft watcher fires on date change; `frontend/scripts/playwright/draft-prompt-history-suffix.mjs` drafts a date three weekdays out). But `build_draft_user_message()` renders only `Current local time: {now:%H:%M}` — **the current local date is never emitted**. The model therefore cannot tell whether the `Schedule date:` line refers to today, a future day, or a backfilled past day.

A keep-past rule keyed purely on "template `start_time` earlier than the current local time" is therefore incoherent for non-today drafts: on a *tomorrow* draft generated at 20:00 it would arbitrarily protect every pre-20:00 block while leaving later ones droppable; on a *backfilled past* date it would protect only the morning blocks though the entire day is past.

Emit the current local **date** alongside the time on that line, and annotate it as context, so the model can compare it against the existing `Schedule date:` line.

**Pin the exact rendered line — prefix-preserving:**

```
Current local time: HH:MM on YYYY-MM-DD (context only — not a cutoff)
```

The date and annotation are **appended after** the existing `HH:MM`, deliberately. The repo's only assertion on this line is `backend/tests/test_ai_prompts_draft.py:154` (`assert "Current local time: 07:30" in msg`), which is a substring check on the label-plus-time prefix; appending after the time keeps it passing. Consequently **no existing test breaks**, and GREEN stays a single pass to green rather than a simultaneous fix-and-migrate.

The `YYYY-MM-DD` value is `now.date()` — the *current local date* — never `schedule.date`. `now` already arrives as a tz-aware datetime carrying its own date (`backend/ai/views.py` resolves it via `timezone.localtime(...)` before calling `run_draft`), so Part 1 needs no signature change anywhere.

Required semantics:

- The comparison the rule asks for is well-defined only when the schedule date equals the current local date.
- Future schedule date → no block is past; the keep-past clause is inert.
- Past schedule date → the whole day is past; every otherwise-valid template block is protected.

**Wording constraint (hard):** `backend/tests/test_ai_prompts_draft.py::test_draft_add_schema_unchanged_requires_explicit_times` asserts `"auto" not in prompt.lower() and "automatic" not in prompt.lower()` against `SYSTEM_PROMPT_DRAFT`. The chat prompt's existing annotation ("context only — the backend, not you, chooses where an automatic untimed add is placed") therefore **cannot** be copied into the draft system prompt. Any new draft **system-prompt** prose must avoid the substrings `auto` and `automatic` entirely. (The assertion targets the system prompt only, but keep the user-message annotation free of them too so a future assertion widening does not break.)

### Part 2 — revise Rule 2 in `build_system_prompt_draft()`

Revise Rule 2 in place rather than adding a detached, contradictory rule. Intended semantics:

1. Current local date/time is context only. It is never an **omission** cutoff — it may not be used as a reason to leave a block out. It *is* used for one thing only: identifying which template blocks are already past and therefore retention-protected.
2. A template block must not be omitted or moved merely because its template `start_time` is earlier than the current local time **on a schedule dated today** (or because the whole schedule date is already past).
3. Every otherwise-valid past-time template block must remain represented in the draft because it is needed for manual completion recording and downstream analytics.
4. For past-time template blocks, this requirement overrides Rule 2's permission to drop routinely skipped blocks.
5. Rule 2 may still:
   - shift a past block when recent history provides consistent evidence, provided the block remains in the draft;
   - drop routinely skipped template blocks that are not already past.
6. The working-day window and non-overlap requirements remain hard constraints. The keep-past instruction must not authorize an out-of-window or overlapping action.
7. The response schema is unchanged: the model still emits only `type`/`title`/`start_time`/`end_time`/`category`.

Use wording equivalent to the following. It deliberately **retains** the existing history-shift and routine-skip permissions (the revision narrows them, it does not delete them), states the Rule 3 precedence, and states the non-move requirement:

> Look at the recent history. If the user has consistently shifted a block, reflect that in the draft. If a block has been routinely skipped **and is not already past**, you may drop it. The current local date and time are context only — never a reason to leave a block out; use them solely to tell which template blocks are already past. When the schedule date is today, always include every otherwise-valid template block whose start_time is earlier than the current local time; when the schedule date is already past, treat the whole day this way. Past blocks must stay in the draft so the user can record them afterwards. For those past template blocks, this requirement overrides the permission above to drop routinely skipped blocks — but it never overrides an active user rule, which still takes precedence. Do not move, shift or omit a block solely because its time has passed. Working-day-window and non-overlap rules still apply, and the add schema is unchanged — emit only the listed fields.

**Marker-format constraint:** the rule text is spliced out by tests using the `"\n2. "` / `"\n3. "` line-start anchors (the real prompt has `2. ` and `3. ` only at line starts — `backend/ai/prompts.py:218` and `:221`). The Rule-3 precedence clause inside Rule 2 must therefore refer to active user rules **in prose** and must not introduce a literal `3.` token, which would truncate the slice.

### Schema-key hazard (must be neutralised in the wording)

`validate_action_shape` rejects any `add` carrying a key outside `_ADD_ALLOWED_KEYS = {"type", "title", "category", "start_time", "end_time", "duration_minutes"}` (`backend/ai/schemas.py:27`, error raised at `schemas.py:102-104`), which fails the **entire** draft as a parse error. Motivating the rule with "completion analytics" risks nudging the model into emitting a helpful `"completed": false` key and 502-ing the whole request. Therefore:

- Do **not** use the words `completed` / `completion` in the new draft rule text; say "so the user can record them afterwards" instead.
- Keep the explicit "the add schema is unchanged — emit only the listed fields" clause in the rule (semantics item 7).
- `TimeBlock.is_completed` defaults to `False` (`backend/schedules/models.py:217`) and `_apply_add` never sets it, so the required persisted value needs no model cooperation at all.

### Precedence against active user rules

Rule 3 ("Respect every active rule … Higher-priority rules take precedence on conflict") is **unchanged and still wins**. The keep-past instruction overrides only Rule 2's history-based drop permission, never an explicit active user rule. State this in the revised Rule 2 so the two do not read as a standoff.

### Documented boundary — template size vs. action cap

Templates permit up to `MAX_TEMPLATE_BLOCKS = 50` entries (`backend/templates_mgr/api.py:48`) while a draft response is rejected above `MAX_ACTIONS_PER_COMMAND = 20` actions (`backend/ai/schemas.py:20`, enforced at `schemas.py:289`). A template of 21+ blocks therefore cannot be fully realised in one draft regardless of this change — the conflict is pre-existing (Rule 1 already calls the template "the baseline shape of the day") and is **not** introduced or worsened here. Do not attempt to resolve it in this feature; it is recorded so the "always include every past block" wording is understood as bounded by the existing action cap.

## Deterministic and real-model verification boundary

The authoritative automated test is the pure rendered-prompt test; it consumes no LLM tokens and follows the repository’s established prompt-only testing pattern.

`LLM_DRAFT_CAPTURE_PROMPT_PATH` can optionally confirm end-to-end that the `Current local time: 12:00 on YYYY-MM-DD (context only — not a cutoff)` line and the `Gym 07:30` template line reach `run_draft()`, but it cannot inspect the new system instruction because the capture hook writes only `user_message`. A true assertion that the generated response includes Gym requires a real provider call. The existing Playwright draft scripts do not cover that exact assertion without scenario changes, so do not expand them in this change. After implementation, an optional targeted manual run may seed today’s weekday template with Gym 07:30, generate after noon, and inspect the response/persisted block; this consumes real draft-model tokens and is not a deterministic CI gate. Acceptance criterion #1 of issue #202 is behavioural and the deterministic suite can only prove the instruction reaches the model, not that the model obeys it — record the outcome of one such manual run in the PR description before the issue is closed, and escalate to Option B reconciliation only if that run shows the block still dropped.
