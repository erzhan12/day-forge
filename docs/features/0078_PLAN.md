# Feature 0078 — Public `/privacy/` and `/terms/` pages

The Google OAuth consent screen for the `dayforge.habitreward.org` deployment
(Google Cloud project `clear-radio-500612-j0`, OAuth client `day-forge`) was
published to production. Its Branding config points at:

| Field | URL | Status before this change |
|---|---|---|
| Application home page | `https://dayforge.habitreward.org/` | resolves (`root_redirect`) |
| Privacy policy | `https://dayforge.habitreward.org/privacy/` | **404** |
| Terms of Service | `https://dayforge.habitreward.org/terms/` | **404** |

`backend/day_forge/urls.py` had no `privacy` or `terms` entry. A published
consent screen whose policy links 404 is a review risk and, more immediately, a
dead end for any user reading the consent screen before they have an account.

## Decisions

| Decision | Choice | Why |
|---|---|---|
| Auth | **Unauthenticated** | The consent screen is read by people with no account, and by Google's reviewers. These become the only page routes besides `root_redirect` without `@login_required`. |
| Rendering | **Plain Django templates**, not Inertia pages | Static content with no props. A Django template renders with JS off, needs no `frontend/dist`, and cannot be broken by a deploy that skipped the frontend build. |
| Layout | New `legal/_layout.html`, **not** `base.html` | `base.html` is `INERTIA_LAYOUT`; it boots the Vue bundle and loads `{% static %}` assets from `frontend/dist`, which does not exist before `npm run build`. |
| Styling | Inlined `<style>` with `prefers-color-scheme` | Same reason — no dependency on a built stylesheet. |
| Contact address | `LEGAL_CONTACT_EMAIL` env var, default `""` | The pages are public, so the address is published to crawlers; it must not be hardcoded in the tree. Unset is a supported state with a real fallback, so **no system check** — the divergence from the `*_E001` pattern is deliberate. |
| Methods | `GET` + `HEAD` | Crawlers and link checkers probe with `HEAD`, and Django's `require_http_methods` does not fold `HEAD` into `GET`. |
| Discoverability | Footer links on the Login page | Reviewers commonly check that policy links are reachable from the app, not only from console config. |

## Changes

**Create:**

- `backend/templates/legal/_layout.html` — standalone shell: header, revision
  date, cross-links, shared contact block, inlined light/dark CSS.
- `backend/templates/legal/privacy.html` — see § Privacy content below.
- `backend/templates/legal/terms.html` — service description, account
  responsibilities, acceptable use (including "don't paste secrets or other
  people's personal data into the assistant"), third-party integrations,
  AI-output disclaimer, no-uptime-commitment, termination, warranty and
  liability disclaimer.
- `backend/tests/test_legal_pages.py` — access, method, rendering, contact
  fallback, and disclosure-content coverage.
- `frontend/tests/Login.test.ts` — the footer links stay plain anchors at the
  right hrefs.

**Modify:**

- `backend/schedules/views.py` — `LEGAL_LAST_UPDATED`, `_render_legal`,
  `privacy_view`, `terms_view`. The docstring states the missing
  `@login_required` is intentional, so a future reader does not "fix" it.
- `backend/day_forge/urls.py` — two `path()` entries under `# Pages`.
- `backend/day_forge/settings.py` — `LEGAL_CONTACT_EMAIL`.
- `frontend/src/pages/Login.vue` — footer links (plain `<a>`, not Inertia
  `<Link>`: an Inertia visit would XHR the route and get Django HTML where it
  expects a page payload).
- `frontend/vite.config.ts` — proxy `/privacy` and `/terms` to Django, without
  which the footer links 404 against the Vite dev server.
- `.github/workflows/deploy.yml` — pass `LEGAL_CONTACT_EMAIL` through the
  existing `optional()` helper. The deploy writes `.env` wholesale, so a var
  omitted there is erased on the droplet.
- `.env.example`, `.claude/rules/project.md` — document the var and the
  public-page conventions.

## Privacy content

Derived from what the code actually does, not from a generic template:

- **Stored**: username + password hash, session/CSRF cookies (no tracking
  cookies), schedules and time blocks, categories, templates, rules, time zone
  and day-window settings, UI preferences, daily reviews.
- **AI audit rows**: latest user message stored *verbatim* plus a SHA-256
  transcript fingerprint — hence the explicit "do not type secrets into the
  assistant" warning (CLAUDE.md privacy note, PRD §6.5).
- **Encrypted at rest** (Fernet, key from the environment): CalDAV server URL /
  username / app password, Todoist token, Habitica user ID + token, Google
  refresh and access tokens.
- **LLM egress**: draft generation sends template + rules + recent-day summaries;
  chat re-sends the **entire visible transcript every turn**, with clearing the
  thread named as the mitigation (CLAUDE.md chat privacy note).
- **Never sent to the LLM**: Todoist/Habitica task text and calendar event
  titles — display-only, per features 0020/0021/0022/0024.
- **Google-specific section**: the exact scopes (`calendar.readonly`, `openid`,
  `userinfo.email`), the fact that `calendar.readonly` cannot write, the
  five-minute server-side event cache, the **Limited Use** disclosure referencing
  the Google API Services User Data Policy, and both revocation routes
  (Settings, `myaccount.google.com/permissions`).
- **Retention/deletion, security, children, changes, contact.**

`test_legal_pages.py::TestPrivacyDisclosures` pins each load-bearing phrase, so
a reword cannot silently drop a statement the consent-screen review depends on.
The assertions run against whitespace-collapsed prose, so they constrain wording
rather than line wrapping.

## Verification

- `uv run pytest backend/tests/test_legal_pages.py -v`
- `uv run ruff check backend/`
- `cd frontend && npx vue-tsc --noEmit && npx vitest run`
- Manual: `curl -i https://dayforge.habitreward.org/privacy/` from a logged-out
  session must return `200`, not a `302` to `/accounts/login/`.

### Local environment caveat (not caused by this feature)

The container this was implemented in runs Python **3.14.0rc2**, on which
`pydantic` 2.13 raises `TypeError: _eval_type() got an unexpected keyword
argument 'prefer_fwd_module'` at import. Because `backend/ai/service.py` imports
`openai` (which imports pydantic) and `day_forge/urls.py` imports `ai.views`,
**every** test that touches the URLconf fails at collection — including
pre-existing files such as `test_root_login_redirect.py` on an unmodified
checkout. It is an interpreter/dependency mismatch in the sandbox, not a
regression. CI runs a release Python and is unaffected. To run URLconf tests
locally under rc2, put a stub `openai.py` (exposing `APIError`,
`APITimeoutError`, `AsyncOpenAI`) on `PYTHONPATH`; do not commit it.

## Out of scope

- A cookie-consent banner — there are no tracking cookies, only the session and
  CSRF cookies strictly necessary for the app to function.
- A governing-law / jurisdiction clause in the Terms. Naming a jurisdiction is a
  legal choice for the operator, not a code decision; the Terms ship without one.
- Any change to what the application actually collects or transmits. This
  feature documents current behaviour; it does not alter it.
