# 0074 — Chat prompt: higher-priority rules take precedence on conflict

## Context

The multi-turn **chat** system prompt (`backend/ai/prompts.py:build_system_prompt_chat`,
Hard rules ~`:94-144`) tells the model to respect active rules and to use a rule to
fill an omitted duration *instead of* asking (Hard rule 2, `:96-104`). But it never
states how to resolve a **conflict between two active user rules** by priority.

The **draft** prompt already does: *"Higher-priority rules take precedence on
conflict."* (`prompts.py:171`). The chat prompt lacks the equivalent.

Observed failure: with rules `DURATION` (highest priority — "if I don't say how
long, default 25 min") and `CLARIFY` (lower priority — "if start/duration/gap is
ambiguous, ask instead of guessing"), the chat model asked *"How long should the
Kick-off block be?"* on `add Kick-off at 1030` — it followed the lower-priority
CLARIFY over the higher-priority DURATION. The rules reach the model correctly and
in priority-desc order (`ai/views.py:103` `.order_by("-priority", "id")`,
rendered under `Active rules (priority desc):`), so this is purely a **missing
conflict-precedence instruction** in the chat prompt.

Note the two separate numbering surfaces — do not conflate them:
- **AI prompt** renders rules `1., 2., 3.…` in priority-desc order, so the highest-
  priority rule is item **`1.`** (earlier = higher).
- The **Settings UI** badge (feature 0073) shows a 0-based rank where **`0` = top =
  highest**. This is display-only and unrelated to the prompt text.

The clause must therefore anchor on **list position / "priority desc"**, not a bare
number, to avoid any 0-vs-1 ambiguity.

## Scope (backend prompt string + its test)

- `backend/ai/prompts.py` — `build_system_prompt_chat` Hard rules only.
- `backend/tests/test_ai_prompts_command_chat.py` — add an assertion that the
  precedence clause is present.

Out of scope: the draft prompt (already has the clause), `ai/views.py`, the rule
query/ordering, the `priority` field, the frontend, and any change to *which* rule
is highest. No LLM/behavioral test (non-deterministic) — we assert the instruction
text is present.

## Change

Add a precedence clause to the chat Hard rules, anchored on the rendered
`Active rules (priority desc):` ordering. Extend **Hard rule 2** (it already governs
rule-respect and the ask-vs-fill decision) with a sentence such as:

> Active rules are listed highest-priority first (see `Active rules (priority
> desc)`). When two active rules conflict, obey the higher-priority (earlier-listed)
> one — e.g. a rule that supplies a default value overrides a lower-priority rule
> that says to ask when that value is missing.

Keep it consistent with the draft's shorter phrasing where practical; the added
"earlier-listed / default overrides ask" detail directly resolves the observed
DURATION-vs-CLARIFY case. Do not change any other Hard rule, the two-add-mode /
duration-resize sections, or the `serialise_prior_turns` privacy wording.
