# Feature 0030 — AI batch mutations: final-state planner (issue #38)

## Context

AI batch mutations fail because overlap validation runs sequentially against
**transient intermediate state** instead of the **final requested schedule**.
Concrete failing command: **"move all blocks starting at or after 1pm one hour
later"** — HTTP 400 with `action_index=0` and `"block would overlap existing
block"` even when the LLM emitted correct target IDs/times and the final
schedule would be valid. DB rollback is correct; the validation boundary is wrong.

**Architectural mandate (do not merely sort actions chronologically/topologically
or prompt the LLM for special order):** introduce a two-phase final-state
mutation engine:

```
LLM actions
  → normalize to internal mutations
  → build complete candidate schedule in memory
  → validate candidate schedule as a whole
  → persist the accepted diff in one transaction
```

The model describes intent; the backend owns ordering and safety.

**Retained:** atomic rollback for invalid finals; `AIInteraction.actions_json`
records original model intent; command and chat share apply path; existing
day-window / 5-min-grid / ownership / model validation; undo unchanged.
**Out of scope:** #109 (`update` action), #110 (configurable schedule window),
#111 (partial field outcomes / conflict questions), auto-cascade of unmentioned
blocks.

**Concurrency safety boundary:** the pre-LLM apply-context fingerprint covers
every mutable server-owned input rendered into the command/chat prompt:
prompt-visible schedule/block state plus the ordered active Rules. Although #38
only writes times, those fields can change which `task_id` or duration the model
selects (for example, "move Gym", "move all work blocks", "remove completed
blocks", or a Rule supplying a default 30-minute duration). Applying an action
after one of them changed would be applying stale semantic intent, not merely a
safe time-only diff.

### Modified — schedule mutation lock protocol

**`backend/schedules/api.py`**

The fingerprint check is not sufficient if a non-time `block_detail` PATCH
already holds a stale model instance: current `block.save()` emits a full-row
UPDATE and can overwrite AI times after waiting for the AI transaction to
commit. Close that lost-update race as part of #38:

- For every PATCH path, enter `transaction.atomic()`, lock the parent
  `Schedule` first, then re-fetch/lock the target `TimeBlock` (and all schedule
  blocks when the time-overlap scan needs them). This matches the executor's
  parent → children lock order and ensures a prompt-visible title/category/
  completion edit either commits before the AI locked snapshot (→ fingerprint
  mismatch) or runs after the accepted AI diff.
- Persist only fields present in the validated `pending` map via
  `save(update_fields=...)`; never let a title/category/completion/sort-only
  PATCH write stale `start_time`/`end_time` columns. Preserve the current
  action-supplied-only granularity behavior and
  `full_clean(exclude=["start_time", "end_time"])`.
- Move `locked_schedule.mark_active_on_edit()` before leaving the PATCH atomic
  block. A failed status transition rolls back the block update; do not retain
  the current post-commit status call.
- Handle a target deleted while waiting for the locks with the existing
  ownership-safe 404. Do not broaden this slice to DELETE semantics: a DELETE
  writes by primary key rather than replaying stale model fields and therefore
  cannot resurrect/overwrite AI times.

`reorder_blocks` must join the same lock protocol. Its current
`select_related("schedule__user").select_for_update()` is a joined lock whose
PostgreSQL row-lock acquisition order is not the explicit parent → children
order required above, and its cross-schedule-before-ownership checks leak
whether a guessed foreign block id exists. Replace that resolver with:

1. Resolve only requested rows owned by `request.user` in an ownership-filtered
   preflight query. If the owned id set is not exactly the requested id set,
   return the same 404 for missing and foreign ids.
2. Only after every id is known-owned, return 400 when the owned rows span
   multiple schedules.
3. Inside `transaction.atomic()`, explicitly lock that one owned `Schedule`
   first, then materialize all its `TimeBlock` rows under
   `select_for_update().order_by("id")`. Do not use a joined
   `select_related(...).select_for_update()` that can lock parent/user rows as a
   side effect.
4. Re-check requested-id membership against the locked child set so a delete
   between preflight and lock becomes the same 404. Build candidates and persist
   only after this under-lock recheck.
5. Call `locked_schedule.mark_active_on_edit()` after successful block saves but
   before leaving the same atomic block. Remove reorder's post-transaction
   status call.

This preserves 400 for blocks from two different schedules **only when both
schedules and all requested blocks belong to the authenticated user**. Mixed
own+foreign and own+nonexistent requests must be indistinguishable 404s.

## Algorithms

### 1. Canonical apply-context fingerprint (concurrent-edit guard)

**Inputs (mutable server-owned state shown to command/chat LLM):**

- `schedule.id` and `schedule.date` (identity/context; not `schedule.status` —
  status is neither rendered into the prompt nor used to interpret #38)
- Per block (all blocks on the schedule): `id`, `start_time`, `end_time`,
  `title`, `category`, `is_completed`
- Active user-owned Rules: `id`, `text`, `priority`, ordered by
  `(-priority, id)`. Activation/deactivation changes set membership, so
  serializing a redundant `is_active=True` field is unnecessary and would risk
  an async deferred-field load if the queryset projection drifts.
- **Omitted:** `sort_order` (not rendered as data in the prompt and not consumed
  by planner validation/persistence)
- Hard-coded day-window bounds (`DAY_START` / `DAY_END` from `ai/prompts.py`)
  are **not** part of the fingerprint until #110.

Why non-time fields are included: prompt builders render title, category, and
completion. A concurrent change can alter the semantic target selected by the
model even when the resulting action only writes times. Examples: "move Gym",
"shift all work blocks", "remove completed tasks". Ignoring those changes would
violate the fingerprint's stale-intent guarantee.

Why Rules are included: they are rendered into the same trusted prompt context
and fill omitted duration/gap/start defaults. A Rule edit during the LLM call
can therefore change the meaning of the generated actions even when blocks are
unchanged.

**Canonicalization:**

1. Sort blocks by `(id,)` ascending and Rules by `(-priority, id)`.
2. Serialize to JSON with `sort_keys=True`, `ensure_ascii=False`, stable time
   strings (`HH:MM:SS` from `time.isoformat()`).
3. `sha256(payload).hexdigest()` (same pattern as `_transcript_sha256` in
   `views.py`).

**Lifecycle:**

- Computed in async view from the exact pre-LLM `current_blocks` + `rules`
  passed to the service → `expected_fingerprint`.
- Recomputed during apply after locking `User`, `Schedule`, blocks, and
  re-reading active Rules.
- Mismatch → HTTP 409 `schedule_changed`, apply nothing, `AIInteraction.success`
  stays `False`, and the failed AI apply performs no status transition (a
  concurrent edit may of course have changed status independently).
- Accepted non-empty batch → diff + `Schedule.status` transition commit
  atomically; only then is the audit row marked `success=True`.
- **Skipped when `parsed_actions` is empty:** fingerprint guard applies only when
  there are mutations to apply. Empty-batch no-op turns (command chit-chat /
  out-of-window guard, chat thanks) never enter `_apply_actions_sync` and never
  compare fingerprints — preserving established 200 + `success=True` semantics.

**Writer serialization required for the guarantee:**

- AI apply locks `User` → parent `Schedule` → all child `TimeBlock` rows, then
  reads active Rules protected by the user lock.
- `block_detail` PATCH must use the same parent-first order before re-reading
  the row it will save. A non-time PATCH must additionally issue a
  column-scoped UPDATE (`update_fields=pending.keys()`).
- `reorder_blocks` first performs an ownership-filtered id resolution (no
  foreign-id oracle), then locks the single resolved parent → children without
  joined `FOR UPDATE` side effects, and re-checks ids under lock.
- Each touched forward-mutation path performs
  `locked_schedule.mark_active_on_edit()` before its transaction commits.
  Status is part of the accepted mutation, not a best-effort follow-up write.
- Supported Rule POST/PATCH/DELETE locks `User` before touching Rule state, so
  membership/text/priority cannot change between the apply recheck and commit.
- This yields a valid serial order in both directions:
  - PATCH commits first → locked fingerprint sees semantic/time changes and AI
    returns 409 without applying;
  - AI commits first → PATCH re-reads the accepted times and changes only its
    requested fields.
- Merely re-reading without a lock is insufficient: a stale full-row save can
  wait behind the AI row lock and then silently restore pre-AI times after the
  AI already returned success.

### 2. Normalize parsed actions → internal mutations

For each `(action_index, action)` in `result.parsed_actions`:

| `type` | Internal mutation |
|--------|-------------------|
| `add` | `CreateMutation(index, title, category, start, end)` |
| `remove` | `DeleteMutation(index, task_id)` |
| `move` / `resize` | `UpdateMutation(index, task_id, new_start, new_end)` via shared `_compute_move_resize_times` rules |

**Same-block chains (deterministic; deliberately order-sensitive):**

- Group mutations by `task_id` (creates have no id until persist), retaining
  original `action_index`.
- Evaluate each target's chain in original list order against an in-memory
  working copy. This preserves the existing meaning of intentionally chained
  edits without doing any ORM writes.
- Multiple `move`/`resize` actions merge through that working copy: later
  explicitly supplied fields win. A bare `move` preserves the block's
  **effective duration at that point in the same-target chain**, rounds it up
  per feature 0026, and records the derived end as coming from that action.
  Supplied/derived provenance follows the effective start/end fields: if a
  later action overwrites a boundary, the superseded boundary (and a wrap flag
  attached only to it) is no longer validated as part of the final state.
- A `remove` discards all earlier edits for the target. Any later action on the
  removed id — including a duplicate remove — is contradictory and returns
  `PlanError` at the first post-remove `action_index`.
- `add` never collides on `task_id`.

Unknown `task_id` (not in snapshot, not removed earlier in batch) → `PlanError`
with that action's index and the existing message *"Referenced block no longer
exists; it may have been deleted. Please retry."* (no id enumeration).

**Order-invariance scope:** permutations of actions that target different
existing blocks must produce the same final time mapping; deletes and
remove+add validation also cannot depend on transient list order. Creates use
`action_index` for temporary identity and final `sort_order`, so permutation
comparisons involving creates compare their title/category/time multiset while
ignoring generated ids, sort order, and provenance.
Same-target chains are intentionally ordered because "resize, then move while
preserving the resized duration" is not equivalent to the reverse. Successful
permutation tests compare canonical final block fields; they must not compare
raw diff objects because source `action_index` provenance necessarily changes
when the input list is permuted.

### 3. Build complete candidate schedule in memory

1. Start `candidate: dict[int, BlockCandidate]` from snapshot blocks (value copies).
2. Apply all `DeleteMutation`s (drop ids from candidate).
3. Apply all `UpdateMutation`s (set `start_time`/`end_time` on candidate entries).
4. Collect `CreateMutation`s as new `BlockCandidate` entries with temporary
   negative ids (`-(action_index + 1)`, never `-action_index`, because index zero
   would otherwise produce non-negative id `0`) for overlap checks only.
5. Unmentioned blocks retain snapshot times.

Steps 2–4 consume the normalized/grouped result, so inter-target action order
cannot expose transient overlap state. Same-target chain order and create
`action_index` remain only for the explicit semantics/provenance described above.

### 4. Validate candidate as a whole

Run once on the final block set (not per-action against transient state), but
collect violations with provenance before choosing the one error to expose.

**Global selection rule:** represent each violation as
`(source_action_index, precedence_rank, stable_candidate_key, detail)` and return
the lexicographically smallest tuple. Thus the lowest effective source
`action_index` wins across independently-invalid actions, matching the current
"first action in the batch fails" behavior without depending on persistence
order. `stable_candidate_key` (real/temp id pair ordering) breaks otherwise
equal ties and must never depend on dict/query iteration.

**Within one effective action/candidate, preserve today's validation
precedence:**

- `move` / `resize`: effective midnight wrap → supplied/derived day window →
  supplied-field granularity → interval (`start < end`) → final overlap →
  model-level defense.
- `add`: category/title defensive checks → day window → granularity → interval
  → final overlap → remaining model-level defense. The service schema normally
  rejects category/title/range shape earlier, but direct planner/executor tests
  and defense-in-depth paths remain deterministic.

Specific rules:

- A duration-preserving bare move reports
  `"moved block would extend past midnight"` before generic interval failure,
  but only if its derived end is still effective in the final same-target chain.
- Day-window and granularity checks apply only to effective times supplied by
  the action (or derived from a supplied bare-move start). Inherited off-grid /
  clamp-to-day boundaries skip those two checks (feature 0026); same-target
  values overwritten later are not validated.
- Pairwise non-overlap runs across all candidates with
  `schedules.http.times_overlap`. An overlap involving changed/created
  candidates uses the lowest effective source index in the pair and the
  `"block would overlap existing block"` detail.
- Interval/model/overlap corruption involving only unchanged snapshot rows has
  no natural provenance, but the planner must still reject an invalid final
  schedule. Assign `min(batch action_index)` as the envelope fallback and rank
  inherited-only integrity violations after action-derived violations at that
  same index. This is defensive handling for legacy/admin/direct-ORM rows
  (model `save()` does not automatically call `full_clean()`); it must return a
  stable 400, never `None`/500.
- Model/schema-level constraints mirrored from the current pipeline (stripped
  create title, max 255, category, interval, etc.) run in memory without ORM
  writes. `parsed_actions` has already passed
  `ai.schemas.validate_action_shape`; document that as the planner input
  precondition while retaining cheap defensive checks. Persistence
  `full_clean` remains rollback-only defense in depth, not the first expected
  validation boundary.

Genuine invalid **final** schedules fail here and apply nothing.

### 5. Deterministic persistence diff

Compare candidate vs locked snapshot:

- **deletes:** ids in snapshot not in final candidate (real positive ids only)
- **updates:** same id, any of `start_time`, `end_time` changed (title/category
  unchanged in #38 scope)
- **creates:** candidate entries with temporary negative ids → new `TimeBlock`
  rows

`MutationDiff` exposes explicit `deletes`, `updates`, and `creates` groups and
persists them in that order inside the existing atomic transaction. Every entry
retains enough source provenance to map defense-in-depth failures to one stable
`action_index`.

### 6. Error envelope mapping

| Planner / executor outcome | HTTP |
|----------------------------|------|
| `PlanError(action_index, detail)` | 400 `{errors: {action_index, detail}}` |
| Fingerprint mismatch (non-empty batch only) | 409 `{errors: {detail: "schedule_changed"}}` |
| Empty `parsed_actions` (no-op turn) | 200; skip apply + fingerprint; `success=True` |
| `ValidationError` at persist (defense in depth only) | 400 same envelope, `action_index` from originating diff entry; transaction rolls back |
| Unknown / cross-user `task_id` during planning | 400 same no-enumeration detail |
