# Feature 0029 — Open-at-boundary notification miss (issue #113)

## Context

Opening the Schedule page exactly on a block **start** or **end** minute silently
misses that boundary notification. Users often open the schedule at the start of
a work block; missing the alert in that moment makes the opt-in desktop (#100) and
sound (#56) channels feel unreliable for their primary use case.

This is distinct from the intentional **enable mid-minute → no retroactive fire**
behavior documented in feature 0019, and distinct from issue #112 (background
resume / long-sleep stale replay) — **do not fold #112 into this fix**.

### Root cause (grounded in current code)

1. `Schedule.vue` calls `useNowMinutes(toRef(props, "date"))` early in setup
   (~L113). `useNowMinutes` watches `viewedDate` with `{ immediate: true }`, so
   on today `enterToday` samples wall clock immediately and sets `nowMinutes` /
   `nowDate` before later setup continues.
2. `useSoundNotifications` / `useDesktopNotifications` install later (~L472–480),
   each calling the shared `useBlockBoundaryDetector`.
3. `useBlockBoundaryDetector` watches `nowMinutes` **without** `{ immediate:
   true }`, so the already-populated minute is never observed at registration.
4. The detector's first subsequent tick is typically the **next** minute (60s
   sampler). With `lastSeenMinute === null`, the first-tick `inWindow` predicate
   is exact-match-only (`boundary === now`). If the page opened at 09:30 for a
   09:30 block, the first detector tick is 09:31 → the 09:30 notification is lost.

Both notification channels share one detector implementation; a single fix in
`useBlockBoundaryDetector.ts` restores both.

## Algorithm (after fix)

The crossed-since-last-sample state machine is unchanged; only the **first
invocation timing** moves earlier.

On `useBlockBoundaryDetector` registration, the `nowMinutes` watcher runs once
immediately (in addition to every subsequent minute change):

1. **Disabled gate** — if `!enabled.value`, return without advancing
   `lastSeenMinute` (unchanged).
2. **Off-today gate** — if `nowMinutes` or `nowDate` is `null`, return without
   advancing (unchanged).
3. **Eligible window** (`inWindow`):
   - `prev === null` (first sample for this cursor): `boundary === now` only —
     fires boundaries exactly at the current minute, never earlier same-day
     boundaries.
   - `now <= prev`: fire nothing (clock backward step).
   - else: half-open `(prev, now]`.
4. For each block, evaluate start/end minutes via `timeToMinutes`; dedupe with
   `fired` Set keys `start|end:${block.id}:${date}:${boundaryMinute}`.
5. Set `lastSeenMinute = now`.

**Schedule open at 09:30** (block start 09:30, notifications on): `useNowMinutes`
sets `nowMinutes = 570` before detector mounts; immediate watch runs with
`prev = null`, `now = 570`, start boundary 570 ∈ window → **one** notification /
chime.

**Schedule open at 14:00** (block 09:00–10:00, notifications on): immediate watch
runs with `now = 840`, `prev = null`; start 540 and end 600 fail `boundary ===
now` → **no** back-fill (same as test 8 today).

**Enable mid-minute** (0019 intentional behavior): toggling `enabled` on resets
`lastSeenMinute` to `null` but does **not** re-trigger the `nowMinutes` watcher
until the next minute tick → still no retroactive fire for boundaries earlier in
the disabled gap (test 13 preserved).

`watch(nowDate)` reset and per-channel independent cursors are unchanged.

## Out of scope

- Issue **#112** — background tab resume / long-sleep stale boundary replay.
  Do not add visibility/focus listeners or coalesced-gap replay logic here unless
  unavoidable; prefer a focused registration-time prime.
- Second `setInterval` for notifications (forbidden by 0019 / 0028 / RULES.md).
- Backend, Service Worker, or notifications while Schedule is not mounted.
- Changing the mid-minute **re-enable** no-backfill rule from 0019.
