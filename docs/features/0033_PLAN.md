# 0033 — Suppress stale block-boundary notification burst after long same-day suspension

Fixes GitHub issue #112.

## Context

After a long **same-day** background suspension (device sleep, lunch break,
heavily throttled hidden tab), the shared block-boundary detector replays
**every** block start/end boundary in the half-open window `(lastSeenMinute,
now]` on the first resumed sample. `now` has jumped hours ahead of
`lastSeenMinute`, so the detector fires a burst of obsolete desktop
notifications and sounds for blocks that already started/ended.

Root cause (verified against `main`):

- `frontend/src/composables/useNowMinutes.ts` samples the wall clock with a
  plain `setInterval(tick, 60_000)` (`NOW_UPDATE_INTERVAL_MS` at L5; the
  `setInterval` call is at L54 in `enterToday`). Two distinct mechanisms delay
  or drop ticks: (a) **background timer throttling** — Chromium's intensive
  throttling after ~5 min hidden aligns wake-ups to ~1-minute buckets (per
  `0019_PLAN.md` L288–291), coalescing a handful of minutes at a time; (b)
  **device sleep / OS suspension** — the timer stops entirely and can resume
  hours later. The multi-hour gap that produces the burst is (b), not (a).
  There is **no** `visibilitychange` handling anywhere in the sampler, the
  detector, or the consumers.
- `frontend/src/composables/useBlockBoundaryDetector.ts` `inWindow` (L99–103)
  fires every boundary in `(prev, now]`. First tick after resume: `now` jumps
  hours ahead of `prev` (`= lastSeenMinute`) → every leapt boundary fires.
- The only existing resets of `lastSeenMinute` are on **date change**
  (`watch(nowDate)`, L61–64) and on **enable-toggle**
  (`watch(enabled)`, L69–71). Nothing resets it on a visibility/suspension gap.

Scope nuance (do not regress): an **overnight** resume past midnight
self-protects — the sampler's `tick()` sees `viewedDate !== today`, calls
`leaveToday()` (nulls `nowMinutes`/`nowDate`), and the detector's off-today
guard (L88) suppresses everything; the subsequent date-change reset clears the
cursor. **The bug is confined to SAME-DAY gaps.** The fix must not touch the
overnight/off-today path.

Interop invariants the fix must preserve:

- **Immediate-registration (issue #113 / feature 0029):** the `prev === null`
  branch fires only boundaries exactly at `now`, no back-fill. This governs a
  genuine first tick (registration / enable-toggle), and the fix must leave it
  untouched. Note: post-resume behaviour is **not** this branch — the fix routes
  a suspension resume through a *clamped* `(now-5, now]` window (Design #2), not
  a `lastSeenMinute = null` reset, so recent boundaries still fire.
- **Modest coalescing (feature 0019):** normal one-minute ticks and modest
  delayed (few-minute) coalesced ticks must still fire every leapt boundary via
  `(prev, now]`. Test #7 (`frontend/tests/useBlockBoundaryDetector.test.ts`,
  the `569 → 573` = **4-minute** jump) locks this in and must keep passing.

## Design decisions (made here, with justification)

**1. Where gap detection lives — the detector, not the sampler.**
The detector already owns `lastSeenMinute` (per-consumer cursor) and already
computes the `(prev, now]` window inside `watch(nowMinutes)`. Deriving a clamped
`effectivePrev` from `prev` and `now` (both already in scope at L86–90) is a
self-contained, per-consumer change with **no new plumbing** between sampler →
consumers → detector — it only narrows the window the detector already builds.
The sampler stays a dumb wall-clock source; the sound and desktop channels each
apply the clamp independently (correct, since they have independent cursors).

**2. Staleness horizon + clamp, not an all-or-nothing reset: `MAX_COALESCE_GAP_MINUTES = 5`.**
Add a module-level constant. The rule operates on the **effective** window
start, not a binary replay/suppress switch:

```
effectivePrev = prev === null ? null : max(prev, now - MAX_COALESCE_GAP_MINUTES)
```

`inWindow` then evaluates `(effectivePrev, now]` (or exact-`now` when
`effectivePrev === null`). Semantics, stated precisely against the **half-open**
window (the boundary exactly at the lower edge is excluded, matching the
pre-existing `(prev, now]` convention): **a boundary fires only if it is
strictly newer than `now - MAX_COALESCE_GAP_MINUTES` (i.e. age in
`0 .. MAX_COALESCE_GAP_MINUTES - 1` minutes); a boundary at or older than
`now - MAX_COALESCE_GAP_MINUTES` (age ≥ `MAX_COALESCE_GAP_MINUTES`) is stale and
never fires.** The exact-`now - MAX_COALESCE_GAP_MINUTES` minute is deliberately
excluded (test #23 pins this). So:
- Normal cadence / modest coalescing (`now - prev <= 5`): `max(prev, now-5) = prev`
  → window is exactly the existing `(prev, now]` → **unchanged replay**.
- Suspension resume (`now - prev > 5`): window is clamped to `(now-5, now]` →
  fires only boundaries strictly newer than `now-5` (ages 0..4), suppressing the
  multi-hour burst.

**Why clamp, not `effectivePrev = null` (fire only exact-`now`).** A binary
null-reset introduces a discontinuity at the threshold: a 5-minute gap replays
5 boundaries, a 6-minute gap replays *none* (dropping even a boundary at
`now - 1`). Two independent reviewers flagged that this narrows feature 0019's
background-coalescing contract (`0019_PLAN.md` L288–298) for the 6-minute-to-
modest range with no principled "stale vs coalesced" threshold. The clamp
removes the cliff — the window widens with the gap up to
`MAX_COALESCE_GAP_MINUTES` and then holds that width while advancing, so
boundaries drop out of the firing set one minute at a time as the gap grows
rather than all at once at a threshold — and gives the constant a real
product meaning (a boundary-staleness horizon) instead of a value reverse-fitted
to test #7.

Justification of the value `5` against test #7: its jump is `573 - 569 = 4`,
`max(569, 573-5=568) = 569 = prev`, so test #7 stays on the exact existing
`(569, 573]` replay path and **keeps passing unchanged**. `5` covers "briefly
backgrounded, timer coalesced a handful of minutes via Chromium's ~1-minute
intensive-throttling buckets" (full replay wanted) while treating anything
at or older than 5 minutes (age ≥ 5) at resume as stale (device-sleep / lunch / long-throttle
burst suppressed). The value is a product staleness threshold; it is
deliberately `> 4` so the existing modest-coalescing contract is honoured, not
silently narrowed.

**3. No `visibilitychange` listener — the elapsed-jump clamp is sufficient for
burst suppression (issue #112's actual goal).**
The bug being fixed is a *burst of stale* notifications; suppression happens
purely as a function of the `now - prev` gap the detector already observes, so a
`visibilitychange` listener adds nothing to it. Adding one would (a) require new
wiring from the sampler or a new `document` listener inside the detector and
(b) risk double-handling with the elapsed-jump clamp (the resume tick and the
visibility event would both try to reason about the same gap). A single
elapsed-jump clamp on the value the detector already observes is the minimal,
race-free fix. (Documented as an explicit rejected alternative in the code
comment so a future reader does not re-add the listener.)

**Latency caveat (explicitly out of scope, deferred to SW/Push).** A
`visibilitychange` wake *does* usually fire, and a listener could make the
detector resample *sooner* after resume. Not adding one means the post-resume
sample waits for the next `useNowMinutes` interval tick — up to one sampler
period (`NOW_UPDATE_INTERVAL_MS` = 60s). The effect is *delivery latency*, not a
dropped notification: a boundary that passed shortly before the resume tick is
still inside the clamped `(now - MAX_COALESCE_GAP_MINUTES, now]` window and fires
(just up to ~1 minute late) — this is exactly what test #22 pins. A boundary is
only suppressed once the resume tick lands at least `MAX_COALESCE_GAP_MINUTES`
minutes after it (age ≥ N), at which point it is genuinely stale (the intended behaviour).
This bounded resume latency is an inherent limitation of the 60s-polling model,
identical to the pre-fix behaviour and to normal foreground jank; reliable
low-latency background delivery is the deferred Service Worker / Push item (out
of scope per the issue). The clamp changes only *which* stale boundaries are
suppressed, never the sampler's timing.

**4. Interaction with immediate-registration and midnight reset — no regression.**
The clamp computes `effectivePrev` locally and never mutates `lastSeenMinute`
(still assigned `= now` at the end of the body as today). `max(prev, now-5)` only
diverges from `prev` when `prev !== null` **and** `now - prev > MAX_COALESCE_GAP_MINUTES`
(a strictly forward jump, since `now - prev > 5 > 0`). It therefore:
- Never changes the first tick (`prev === null` → `effectivePrev = null`,
  exact-`now`, unchanged).
- Never changes a backward step (`now <= prev` → `max(prev, now-5) = prev`, and
  the existing `inWindow` backward-step branch still returns nothing).
- Never touches the off-today / midnight path (that path returns at L88, before
  `effectivePrev` is computed).
For a suspension jump the tick is evaluated over the clamped window
`(now-5, now]`; a boundary exactly at `now` still fires (it is the upper,
inclusive end of the half-open interval — `effectivePrev < now <= now`), and a
genuine first tick still fires exact-`now` via the `prev === null` /
`boundary === now` registration branch. No new code path.

## Tests

### `frontend/tests/useBlockBoundaryDetector.test.ts`
The existing harness (`mountDetector`, `tick`) drives the detector with plain
refs and needs no changes. Add new cases (numbered after the current highest,
#17):

- **`18. multi-hour same-day jump does not replay stale boundaries`** — enable
  true; blocks with start/end boundaries strewn across the morning (e.g.
  `block(1, "09:00", "10:00")` → 540/600, `block(2, "11:00", "12:00")` →
  660/720). `tick(590)` to prime `lastSeenMinute = 590` (no boundary at 590).
  Then `tick(840)` (14:00 resume, jump `840 - 590 = 250 > 5`). Assert
  `onBoundary` **not** called for any of 600/660/720 — i.e. `not.toHaveBeenCalled()`
  (all leapt boundaries suppressed; none equals 840).
- **`19. resume jump fires only boundaries within the staleness horizon`** —
  prime at `prev`; put an **earlier stale** boundary well beyond the horizon
  (inside `(prev, now]` but `< now - 5`, e.g. at `now - 30`) **and** a boundary
  exactly at `now`. Jump far (`> 5`) so `effectivePrev = now - 5`. Assert the
  exact-`now` boundary fires once and the `now - 30` boundary does **not** fire.
  Must fail on `main` (the unclamped `(prev, now]` fires both) — this is the RED
  that both proves the bug and pins "only recent boundaries survive a resume".
  (The earlier stale boundary is essential: without one, the pre-fix window and
  the clamped window would fire the same single boundary and the test would
  pass pre-fix, testing nothing.)
- **`20. modest coalesced jump (== horizon) still replays every leapt boundary`**
  — prime at `prev`, then `tick(prev + 5)` (delta exactly `MAX_COALESCE_GAP_MINUTES`,
  so `effectivePrev = max(prev, prev) = prev`) with boundaries inside
  `(prev, prev+5]`; assert every one fires. Guards the lower side of the horizon
  so the constant can't be silently tightened.
- **`21. one-minute forward tick still fires its boundary`** — a plain
  `prev → prev+1` step that crosses a boundary fires it (regression guard that
  the clamp never trips on normal cadence).
- **`22. a boundary within the horizon of a big jump still fires`** — prime at
  `prev`; jump far (`>> 5`) to `now` with a boundary at `now - 2` (inside the
  clamped `(now-5, now]`). Assert it fires. This is the clamp's distinguishing
  behaviour versus a plain exact-`now` reset (which would wrongly suppress it)
  and pins that recent boundaries are preserved across a suspension resume.
- **`23. first over-horizon minute is dropped by the half-open lower edge`** —
  prime at `prev`; `tick(prev + 6)` (delta `MAX_COALESCE_GAP_MINUTES + 1`, so
  `effectivePrev = prev + 1`). A boundary at `prev + 1` (`== effectivePrev`, and
  `== now - 5`) must **not** fire (excluded by the half-open `(effectivePrev, now]`);
  a boundary at `prev + 6` (`== now`) fires. Pins the exact `> horizon` clamp
  edge so it can't drift. Must fail on `main` (unclamped window fires `prev + 1`).
- **Explicitly assert test #7 (the 4-minute `569 → 573` jump) is unchanged** —
  it already lives in the file and must keep passing verbatim (delta 4 `<= 5`,
  so `effectivePrev = max(569, 568) = 569 = prev`; identical `(569, 573]` window).
  Do not modify it.

Optionally add a `visibilitychange`-resume simulation case: since the detector
observes only `nowMinutes`, a "visibility resume" is faithfully modelled by a
large forward `tick()` jump — assert it behaves identically to case #18. This
satisfies the acceptance criterion "simulate ... a `visibilitychange` resume"
at the unit-under-test boundary (the detector never reads `document.hidden`).
