# 0046 — Rules priority fix (auto-bump default, compaction, disabled-arrow tooltip)

## Context

Three linked items from `tasks/todo.md` § UX/Rules around the Rules list
(`frontend/src/components/RulesList.vue` + `backend/templates_mgr/api.py`):

1. **Auto-bump default priority for new Rules.** Today `RulesList.vue`
   `addRule()` (line ~44) hardcodes `createRule({ text, is_active: true,
   priority: 0 })`, so a second rule collides at priority `0`. The sort is
   `order_by("-priority", "id")`, so two rules at `0` order by `id` and the ▲/▼
   arrows look like a no-op until the user clicks once. The default should be
   `max(existing.priority) + 1` so each new rule lands on top with a unique
   priority. Preferred: compute the default **backend-side** so it is a single
   source of truth consistent across curl and the frontend, rather than the
   frontend reading the current list and computing before POST.

2. **Compact Rule priorities to `0..N-1` on add/delete** so values stay small
   and never drift toward the `MAX_PRIORITY` (1_000_000) cap. Example: start
   `[r1=0, r2=1]`, delete `r1`, add `r3` → without compaction you get `[r2=1,
   r3=2]`; over many add/delete cycles a user sees "Priority 47" on the only
   rule. Compaction runs backend-side, in the same transaction as the create /
   delete mutation. The frontend picks up the renumbered values via its
   existing "changed" emit → partial reload of the rules list.

3. **Disabled-arrow tooltip on a single Rule.** With one rule both ▲ and ▼ are
   disabled (`:disabled="idx === 0"` and `:disabled="idx === localRules.length
   - 1"` are both true). They are silently greyed out. Add a `title` attribute
   ("Add another rule to reorder") so the affordance is self-documenting.

## Design decision: compaction vs. hiding the badge

The todo raises an alternative — hide the numeric priority badge entirely
(users only care about ▲/▼ ordering). **This plan implements compaction** (the
primary ask) and **keeps the badge**. Rationale: compaction makes the badge
meaningful and small (`0..N-1`), which is a strictly better outcome than hiding
it; hiding is not needed once numbers no longer drift.

## Design decision: WHEN compaction runs (the key tension)

Compaction renumbers rows to a contiguous `0..N-1`, but the frontend
`bumpPriority` swap mutates two specific priority values via two sequential
PATCHes. These must not fight. Resolution:

- **Compaction runs ONLY on create and delete** (the two collection-mutating
  paths), NOT on PATCH/reorder. The PATCH path (`rule_detail` PATCH branch) is
  left untouched, so `bumpPriority`'s two-PATCH swap behaves exactly as today.
- After a create, the new rule is assigned the **highest** priority (top of
  list, item 1) and then the whole set is normalized to `0..N-1` preserving the
  existing `-priority, id` order. After a delete, the surviving rules are
  normalized to `0..N-1` preserving the same order.
- **Ordering contract is preserved**, only the integer values change.
  `bumpPriority` reads live priorities from the reloaded list each time it
  runs, so it never depends on stale pre-compaction values.

### Interaction with the `bumpPriority` same-priority ±1 bias branch

`bumpPriority` (RulesList.vue ~line 95) has a branch: when a neighbour shares
the same priority it PATCHes `priority ± 1` instead of swapping. With
compaction, freshly-created and freshly-deleted lists are always contiguous and
**unique** (`0..N-1`), so the equal-priority case can only arise transiently
between a swap's two PATCHes or after manual API tinkering. Keep the ±1 bias
branch as-is (defensive; harmless), because a raw PATCH does **not** trigger
compaction, so the frontend can still momentarily observe equal priorities
mid-swap. Do NOT remove it — removing it would regress the manual-PATCH edge
case that has no compaction backstop.

## Backend changes — `backend/templates_mgr/api.py`

### New helper: `_compact_rule_priorities(user)`

A module-level helper called **inside** the existing `transaction.atomic()` +
`User.objects.select_for_update()` blocks (the row lock already serializes
concurrent writers for this user, so the read-modify-write of priorities is
race-safe). Algorithm:

1. Fetch `Rule.objects.filter(user=user).order_by("-priority", "id")` — the
   canonical display order.
2. Walk the list from the top; assign each row the next descending priority so
   the resulting set is contiguous `0..N-1` with the **top rule getting the
   highest** value (`N-1`) and the bottom getting `0`. This preserves the
   `-priority, id` order exactly.
3. `bulk_update` only the rows whose priority actually changed (skip no-ops to
   avoid needless writes).

Assigning top = `N-1` (descending) rather than top = `0` keeps the semantic
"higher priority number = higher in list", matching the existing
`order_by("-priority", ...)` and the GET contract in `docs/api.md`.

### `rules_collection` POST branch (~line 333)

Currently: parses payload (which may carry an explicit `priority`), then under
`transaction.atomic()` + `select_for_update`, count-guards against
`MAX_RULES_PER_USER`, then `Rule.objects.create(user=..., **cleaned)`.

Change: default-priority behavior for the **create** path.

- In `_parse_rule_create_payload` (~line 172): `priority` remains **optional**
  and, when supplied, is still bounds-checked against
  `MIN_PRIORITY`/`MAX_PRIORITY`. **Do not** inject a default here — the
  create-view needs the locked row set to compute `max+1`, and the parser has
  no `user` / lock context. Leave `cleaned` without a `priority` key when the
  client omits it (this is the signal to auto-assign).
- In the POST branch, inside the existing atomic + `select_for_update` block,
  after the count guard:
  - If `"priority"` is **absent** from `cleaned`: compute `new_priority =
    (max existing priority for this user) + 1`, defaulting to `0` when the
    user has no rules (use `Rule.objects.filter(user=...).aggregate(Max(...))`
    or an ordered `.first()`; either is fine under the lock). Assign it.
  - Create the rule.
  - Call `_compact_rule_priorities(user)` so the whole set (including the new
    top row) is normalized to `0..N-1`. Re-fetch the created rule (or read its
    post-compaction priority) before serializing so the 201 response body
    reflects the compacted value.
- The response is still `JsonResponse(_rule_to_dict(rule), status=201)` — but
  `rule.priority` now reflects the post-compaction value. **Note:** because
  compaction renumbers, an explicit client-supplied `priority` on create is
  honored only for *initial ordering placement*, then normalized — document
  this in `docs/api.md` (see below).

### `rule_detail` DELETE branch (~line 368)

Currently: under `transaction.atomic()` + `select_for_update`, fetch the rule
(404 if cross-user/missing), `rule.delete()`, return `{"ok": True}`.

Change: after `rule.delete()` and still inside the same atomic block, call
`_compact_rule_priorities(user)` so survivors renumber to `0..N-1`. Response
unchanged (`{"ok": True}`) — the frontend reloads the list to observe the new
values.

### PATCH branch — unchanged

`rule_detail` PATCH stays as-is (no compaction) so the `bumpPriority` swap and
manual priority PATCHes keep working against explicit values.

## Edge cases to keep in mind

- **Empty list:** first create with no `priority` → `max+1` defaults to `0`;
  compaction of a one-element list yields `{0}`. Cover in Slice 1/3.
- **Explicit `priority` still honored for placement:** a client POSTing
  `priority: 50` places the row at the top by value, then compaction renumbers;
  the `TestRulePriorityBounds` tests that POST explicit in-range/out-of-range
  values must still pass (out-of-range still 400 at the parser before any
  create/compaction). Verify `test_create_accepts_priority_at_max` still
  passes — note it asserts the *stored* value equals `MAX_PRIORITY`; **this
  test will break under compaction** (the value gets normalized). Update it to
  assert the row lands at the top after compaction (or split into a
  placement-order assertion) — call this out during Slice 3 and adjust the
  assertion rather than the production behavior.
- **Concurrency:** compaction runs under the same `select_for_update(User)`
  lock as create/delete, so two concurrent writers for one user serialize; no
  new lock needed.
