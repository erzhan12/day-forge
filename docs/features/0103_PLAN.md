# 0103 — Keep PiP category colour current after a Settings edit (issue #213)

Approved plan for a behaviour fix (issue #213), implemented on branch `fix/213-pip-settings-category-colour`.

Investigation baseline: `origin/main` @ `86cfdfc`. A temporary local reproduction test (not committed) confirmed the bug.

Feature number **0103** is the next free numbered plan (`docs/features/` currently ends at `0102_PLAN.md`). The historical heading "0103 hardening" in `docs/archive/TODO_HISTORY.md` refers to issue #103 / #119, not a feature plan, and does not occupy this number.

## Goal

If the user opens the focus-indicator PiP on Schedule, navigates to Settings, and changes the active block's category colour, the open PiP rail and fill must use the new colour immediately. They must not have to return to Schedule. Production colour calculation (`getCategoryColor`, `FocusIndicatorView`) stays unchanged.

## Root cause

The PiP is owned at the app root (`FocusIndicatorHost` wrapping the Inertia page in `frontend/src/app.ts`). The controller paints the rail from its own copied catalogue, `retainedCategories` (`useFocusIndicatorController.ts`).

That copy is written only by `publish` / `publishIfGenerationMatches`. The only publisher is Schedule: a deep watcher on `date`, `effectiveBlocks`, `categories`, and the saved time zone, plus `onBeforeUnmount` (`Schedule.vue`). Both paths no-op when `publicationGeneration` has moved on (Login, null user, account switch).

Settings is the only page that mutates category colours. After a successful PATCH it calls `router.reload({ only: ["categories"] })` (`SettingsCategoriesPanel.vue`, `useCategories.ts`). That updates the Settings page's Inertia props. Schedule is unmounted, so nothing publishes the new catalogue to the controller. The retained snapshot, including the old colours, is intentionally kept across ordinary navigation (spec: "Route change").

The already-specified path "repaint when only the colour changes" works only while Schedule remains mounted and receives the new `categories` prop (`scheduleFocusIndicator.test.ts`). Issue #213 is the Settings path of the same requirement.

`categories` is not a shared Inertia prop. It is included on Schedule, Settings, and Analytics, and omitted on Login (`{ errors: {} }` plus shared `auth_user_id`). Legal pages are not Inertia. A root watcher that treats a missing catalogue as "clear colours" would therefore fire on Login, and must not fight the existing session-clear rules. `auth_user_id` is always *shared* by `InertiaIdentityMiddleware` (`null` or the user's pk), but it is not an Inertia `AlwaysProp`. In locked `inertia-django` 1.2.0, a partial reload's `only` list also filters shared props (`PropsResolver._excluded_by_partial_request`). The client then keeps the previous `auth_user_id` (`mergeProps`). So `router.reload({ only: ["categories"] })` today can apply a new catalogue while leaving a stale identity in place.

## Chosen approach

Add a watcher inside `useFocusIndicatorController` (the root owner already calls `usePage()`) that, when a retained schedule snapshot exists, replaces **only** `retainedCategories` with a copy of the current page's category catalogue, provided all of the following hold:

1. `page.component` is an initialized string and is not `"Login"`. Absence of a component is not logout and is also not a catalogue refresh.
2. `page.props?.auth_user_id` is not `null` or `undefined`.
3. A snapshot is currently retained (`retainedDate !== ""`). This is the same signal `clearSnapshot()` already resets.
4. `hasValidCategoryCatalog(page.props.categories)` is true.

Do not write `retainedDate`, `retainedBlocks`, or `retainedTimeZone` from this watcher. Do not go through `publish` / `publishIfGenerationMatches` (those APIs always take date and blocks). Copy with the existing `copiedCategories` helper.

Register this watcher after the existing session watcher, both with `flush: "sync"`. The guards above must be sufficient on their own and must not depend on registration order. On Login or account switch the session watcher increments `publicationGeneration`, calls `clearSnapshot()` (so `retainedDate === ""`) and closes the PiP. The catalogue watcher then sees no retained snapshot and must not write, even if a leftover or not-yet-replaced `props.categories` is still on the page object (account switch on Schedule can change `auth_user_id` before the new user's props arrive). If the catalogue watcher happens to run first in the same tick, the session watcher still clears everything afterwards.

Null-safety: `page` or `page.props` may be unset at boot (`FocusIndicatorHost` already tests this). Watch `() => page?.props?.categories`.

Schedule's reactive publisher stays: while Schedule is mounted it still publishes date, blocks, a valid catalogue or `[]` for an invalid one, and the time zone. That path must keep working. The unmount publisher is kept unchanged (see below). `FocusIndicatorHost.vue` stays a thin provider shell.

### Schedule unmount still publishes its last catalogue

Inertia's Vue adapter writes the new `page` object in `swapComponent` *before* Vue unmounts the previous page component. A `flush: "sync"` root watcher can therefore copy the incoming page's catalogue, after which Schedule's `onBeforeUnmount` currently republishes its own `props.categories` and overwrites it.

Leave that unmount publication as it is. If it were omitted, a Back/Forward step *away from Schedule* would let the restored entry's historical catalogue win. Schedule's unmount write keeps the last Schedule catalogue for that step. It does not cover later history steps: Inertia's popstate restores an entry's stored props without refetching, and when Schedule is not the page being left, the root watcher copies that historical catalogue (see the edge case below).

The leftover race is narrower and accepted: navigating away from Schedule onto a page that already carries a *newer* catalogue (for example a colour changed in another tab) will have that newer catalogue overwritten by Schedule's unmount write, until a later category reload while Schedule is unmounted (the #213 path) updates it. Do not delete the unmount publisher.

Issue #213 itself (colour changed on Settings after Schedule is already gone) does not go through this unmount path and is fixed by the root watcher alone.

### Why not publish from Settings after reload

That alternative would inject the PiP controller into Settings (or into `useCategories`), wait for the async `router.reload` to settle, and still miss any other authenticated page that already carries a live catalogue (Analytics today; a future editor tomorrow). It also has a sharper lifecycle problem: Settings is unmounted on Login, but a late reload callback could still try to publish. The root already owns the snapshot and already watches the page for session boundaries; syncing the catalogue there keeps a single owner. Settings continues to do only PATCH + `reload({ only: ["categories"] })`.

## Edge cases

- **Login:** session watcher clears the snapshot and closes the PiP with intent. Catalogue watcher is a no-op (`Login`, and/or `retainedDate === ""`). Existing tests remain authoritative, including "does not restore the departing publisher snapshot after the root clears it for Login". The new guard tests in "Tests" must be able to fail if the `retainedDate !== ""` guard is missing (they must not assert only `indicatorActive` / next-block, which do not depend on the catalogue).
- **Account switch while the component stays Schedule:** same clear path. A stale pre-switch catalogue still sitting on `page.props` must not be copied back. Replace the whole `page.props` object in one assignment in the test, as Inertia does, so both sync watchers see the new user id and a new catalogue reference in the same tick. Once the new Schedule (or Settings) payload arrives and Schedule publishes a new snapshot, normal publish + catalogue sync resume for the new user.
- **Null / undefined `auth_user_id`, or uninitialized `page.component`:** do not treat these as catalogue updates, and do not treat an uninitialized component as logout. A retained snapshot plus an authenticated user plus a new valid catalogue must *not* change colours while `page.component` is `undefined`.
- **Page without `categories` (Login today):** `hasValidCategoryCatalog` is false; do not clear the retained catalogue along this path. Login already cleared it. This also means a hypothetical authenticated page that omitted `categories` would keep the last good colours rather than dropping to the built-in fallback.
- **Malformed catalogue** (empty, wrong shape, missing sink/default, duplicate ids — the `hasValidCategoryCatalog` rules), **while Schedule is unmounted**, a snapshot is retained, and no session boundary has occurred: ignore it; keep the last valid retained catalogue. This is an intentional difference from a *mounted* Schedule, which still publishes `[]` for an invalid `props.categories` and thereby clears retained colours. The root watcher must not wipe a good retained catalogue just because the current unmounted page's prop is bad or absent.
- **Recolour of a non-active category:** rail unchanged.
- **Rename / reorder / add category:** no PiP text change (titles come from blocks; slugs are forbidden in PiP). Catalogue copy may update; appearance stays the same unless a colour field also changed.
- **Delete category:** out of scope to remap retained *blocks*. After the Settings reload the new catalogue no longer has that slug, so `getCategoryColor` / `effectiveCategory` falls back to the sink colour. Retained blocks still carry the old slug until the user returns to Schedule and it republishes remapped blocks. Accept this; do not invent a block rewrite in the controller.
- **Analytics (and any other authenticated Inertia page that includes `categories`):** if a snapshot is retained, a valid catalogue on that page updates colours the same way. Analytics does not mutate categories; this is coverage, not a new UI path.
- **Partial reloads that omit `categories`:** Inertia keeps the previous `props.categories` reference; the watcher does not fire. Date/blocks stay whatever Schedule last published.
- **No snapshot yet** (Settings visited before any Schedule publish this session): watcher does not write. Later Schedule publish supplies date, blocks, and catalogue together.
- **Boot with missing page props:** no throw, indicator inactive.
- **Back / Forward history restore, and Schedule unmount:** Inertia can restore a previous page's props from history without refetching. If Schedule's unmount stopped writing categories, the new root watcher would then keep that historical catalogue on the Back step away from Schedule. This plan **leaves the unmount publication unchanged**, so that Back-from-Schedule keeps Schedule's last catalogue as today. That protection covers only leaving Schedule. Accepted limitation: a later Back/Forward step between non-Schedule entries copies the restored entry's historical catalogue (example: Analytics(blue) → Settings, recolour to rose → Schedule → Back → Back; the first Back keeps rose via the unmount write, the second restores the older Analytics entry and the PiP reverts to blue until the next Schedule publish or category reload). Current `main` would keep rose there, because it has no root watcher. The second accepted limitation is the complementary race: Schedule → Settings/Analytics when the incoming page already has a newer catalogue (for example another tab recoloured) will be overwritten by Schedule's unmount write until a later categories reload while Schedule is unmounted. A mounted Schedule that itself lands on a history restore still republishes whatever props it receives, as today. Do not add a freshness token in this change.
