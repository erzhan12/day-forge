# 0059 — Configurable AI quick-input suggestions (GitHub issue #154)

## Context

The `dark_4a` AI chat currently renders three hardcoded quick-input prompts from `CHAT_SUGGESTIONS` in `frontend/src/components/ChatResultChip.vue`. `CommandBar.vue` handles a chip click through `useSuggestion(text)`, which correctly prefills `draftInput` without submitting. Because both the bottom dock and `ChatSidebar.vue` render the same `CommandBar.vue`, configuration must be resolved once through the existing per-user `ui_preferences` seam and consumed by both variants.

Store the ordered prompt list in `UserPreferences` and expose it through the existing `GET/PATCH /api/user/preferences/` endpoint and authenticated Inertia props. No new endpoint and no AI-generation behavior are required.

## Required behavior

### Implementation constraints

- Persist suggestions per user through the existing preferences/settings API or a dedicated preference field.
- Keep the current three prompts as defaults for users without saved customization.
- Validate trimmed, non-empty strings and enforce sensible per-item length and total-count limits.
- Preserve current behavior: clicking a suggestion PREFILLS the chat input WITHOUT immediately submitting.
- Do NOT make suggestions model-generated (they are static affordances, never an AI response).
- Ensure date navigation, thread clearing, and theme switching do NOT reset customized suggestions.

### Acceptance criteria

- Settings renders an editable, reorderable list of AI quick-input suggestions.
- Changes persist across reloads and sessions for the authenticated user.
- The dark_4a chat reads suggestions from saved settings, falling back to defaults.
- Restore defaults works without duplicating entries.
- Backend validation and frontend component/API tests cover save, invalid input, ordering, fallback defaults, and chip-prefill behavior.

## Data and validation contract

Use these canonical defaults, preserving their current order:

1. `Plan my remaining day`
2. `Add a focused work block`
3. `Make room for a break`

Define the following limits in `backend/templates_mgr/preferences.py` and mirror them in the frontend utility:

- Maximum suggestions: **8**
- Maximum length per trimmed suggestion: **120 characters**
- Minimum count: **0**; a saved empty list intentionally hides all suggestions.

The three default strings and both numeric limits are duplicated across `backend/templates_mgr/preferences.py` and `frontend/src/utils/chatSuggestions.ts`. Follow the codebase's existing anti-drift convention for cross-language constants: paired **SYNC ALERT** cross-reference comments on both sides (as used for `models.py` ↔ `types/index.ts`), and/or a pinned-equality test asserting the frontend `DEFAULT_CHAT_SUGGESTIONS` equals the backend defaults exactly so Restore-defaults and unset-GET cannot silently diverge.

Add `UserPreferences.chat_suggestions` as a nullable `JSONField` with `default=None`. The states are distinct:

- `NULL`: no customization saved; resolve to the three built-in defaults.
- `[]`: an intentional saved choice to show no suggestions.
- Non-empty list: the user’s saved prompts in persisted array order.

PATCH validation is backend-authoritative:

1. If `chat_suggestions` is absent, leave it unchanged and process other recognized preference fields normally.
2. If present, require a JSON array via an explicit `isinstance(value, list)` check **before** iterating (mirroring the load-bearing `isinstance(theme, str)` guard at `api.py:525-530`). A bare string is iterable, so `for s in value` without this guard would silently persist one-character chips and return 200; the Red suite must include a bare-string `chat_suggestions` value asserting `400`.
3. Reject more than eight entries.
4. Require every entry to be a string.
5. Trim each string before validation and persistence.
6. Reject strings empty after trimming.
7. Reject trimmed strings longer than 120 characters.
8. Preserve array order exactly; do not sort or append defaults.
9. Return `400` through `_prefs_response` with an error under `chat_suggestions` for all invalid shapes or values.
10. Validate every recognized field before writing, so a combined theme/suggestions PATCH cannot partially persist.
11. Continue accepting unknown fields only when at least one recognized field is valid, matching the endpoint’s existing behavior.

Repeated restore operations must replace the saved list with a fresh copy of the canonical defaults. They must never append or merge. Arbitrary duplicate user-entered strings need not be deduplicated; rendered rows/chips must therefore use index-aware keys. **Restore-defaults intentionally writes an explicit snapshot of the current defaults, not `NULL`** — PATCH rejects `null`, so there is deliberately no UI affordance to return to the unset/`NULL` "track future default changes" state. This is acceptable because the defaults are a static three-item list; if that assumption changes, a "clear customization" path accepting `null` would be needed.

On read, `normalize_chat_suggestions` returns the defaults only for structurally invalid persisted data — `None`, a non-list, or a list whose entries are not all strings — while preserving a valid empty list. A structurally valid list of strings is passed through **display-only even if it violates the count/length caps** (legacy or externally-written rows that exceed 8 entries or 120 chars are shown, never rewritten on read); the caps are enforced only on the PATCH write path, so read-side normalization never performs a write-on-read. Read-side normalization **trims each entry and drops those empty-after-trim**, so a stored `["", "x"]` never renders a blank, label-less chip button; if dropping leaves an empty list, that is a valid "show nothing" state (it does not fall back to defaults, since the list was structurally valid — only `None`/malformed triggers the defaults fallback).

`UserPreferencesDTO` (a `@dataclass(frozen=True)`, **not** a tuple) must gain a `chat_suggestions: tuple[str, ...]` field constructed as a `tuple(...)` **copy** of the normalized list — never the raw `JSONField` list. Holding a tuple copy prevents a mutable alias to the ORM value (which would reopen the write-on-read/aliasing hole the frozen DTO exists to close).

Serialization must run `normalize_chat_suggestions` on **every** emission path — the three sites do not share one code path today, so each must be wired explicitly:
- **GET** (`api.py:497-499`) inlines `{"theme": prefs.theme}` from the DTO returned by `get_user_preferences`; extend to add `"chat_suggestions": list(prefs.chat_suggestions)` (DTO field is the already-normalized tuple).
- **PATCH response** (`api.py:551`) calls `_prefs_to_dict(prefs)` where `prefs` is the freshly-saved **ORM row** (`api.py:481` signature is `UserPreferences`, not the DTO). After a `theme`-only PATCH the row's `chat_suggestions` is still `NULL`, so `_prefs_to_dict` must return `normalize_chat_suggestions(prefs.chat_suggestions)` — a naive `list(prefs.chat_suggestions)` would `TypeError` on `NULL` into an unhandled 500 that bypasses `_prefs_response` and its `Cache-Control`. Add a regression test: a `theme`-only PATCH by a user with `NULL` suggestions returns 200 with `chat_suggestions` = defaults and the `private, no-store` header.
- **Inertia props** (the three views) build from the DTO via `list(dto.chat_suggestions)`.

Character-limit semantics: **120** is measured as Python `str` length (Unicode code points) and the backend is authoritative. The frontend must mirror this by validating against **code-point** count (`[...value].length`, not `value.length`), because a native `maxlength="120"` / raw `.length` counts UTF-16 code units and would hard-block a backend-valid 120-emoji prompt (240 units) client-side — contradicting backend-authoritative validation. Do **not** rely on native `maxlength` as the hard cap; use it only as a coarse advisory (or omit it) and enforce the real limit with an explicit code-point check that matches Python.
