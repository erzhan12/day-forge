# 0083 — Chat must not replay the previous request (issue #219)

## Context

Live chat on schedule 2026-09-23: turn 1 `add Momentum (Personal)` added `Momentum`; turn 2 `Notes` added `Momentum[2]`. The audit row for turn 2 (`turn_count` 3) shows the model emitted `{"type":"add","title":"Momentum[2]","category":"personal"}` — title and category replayed from turn 1, `[2]` supplied by the user's active "same name → add [N]" Rule. "Notes" appears nowhere in the output. Model `gpt-4o-mini`, temperature 0, so the replay is deterministic for this transcript.

Root causes, verified in code:

1. `backend/ai/prompts.py:build_system_prompt_chat` (48–195) never says that user requests inside the "Untrusted prior transcript" were already executed. Hard rule 6 (158–162) tells the model *not* to treat `Assistant (claimed):` lines as commitments, so turn 1 reads as unexecuted; the bare-name default (78–91) and rule 2 exception (iii) (143–150) are weaker than a concrete Rule example that literally matches the transcript.
2. `backend/ai/service.py:run_chat` (293–405) builds `[system, context+flattened transcript, latest turn]` (328–346) and validates only shape; `backend/ai/views.py:ai_chat` (1054–1235) applies any shape-valid action via `_apply_actions_sync` (690–771). Nothing checks that an `add` originates from the latest user turn.
3. `frontend/src/composables/useChat.ts:237` stores assistant `content` as `ask ?? explanation` and the wire mapping (197–200) sends only `{role, content}`, so the server cannot tell an ask turn from an explanation turn — and both routinely contain the block title (`"Adding Momentum ..."`), which rules out any content-based distinction.

Fix: (A) prompt hard rule, (B) deterministic server-side replay guard in `ai_chat` backed by a pure helper, plus a client-supplied `is_ask` marker on assistant turns, (C) regression tests. TDD throughout.

## A. Prompt change (`backend/ai/prompts.py`)

Append **Hard rule 11** after rule 10 (line 194) — append rather than insert so existing cross-references ("Hard rule 3", "Hard rule 9b", "exception (iii)") stay valid, including the `assert "Hard rule 3"` pin at `test_ai_service_chat.py:502` and the phrase constants at 467–472. Literal wording (exact text matters; tests pin the quoted fragments):

> 11. Actions come ONLY from the latest user turn. Every user request in the "Untrusted prior transcript" was already handled when it was sent (applied, rejected, or answered with a question) — never re-emit it, and never add, move, resize or remove a block only because an earlier turn mentioned it. Two exceptions, where the latest turn continues an earlier request: (a) the last assistant turn asked a clarifying question or reported that nothing was placed (Hard rules 2(iii), 3, 9b–9d) and the latest turn answers it; (b) the last assistant turn reported an error or a changed schedule and the latest turn asks to retry. Otherwise the transcript exists only for coreference (resolving a pronoun such as "it" or "that one"). Active rules shape HOW a requested block is made — its duration, its naming (e.g. a "[2]" suffix), its category — but a rule never creates an action on its own. A FRESH bare activity name (no pending question) gets its own text as the title, never a title from an earlier turn. When the pending question asked what to add (e.g. "What would you like to add?"), the answer is the title of a NEW add — do not resolve it by coreference to an existing block.

Add one sentence to the bare-name paragraph of the `add` action (after line 84, before "This bare-name→add default applies…"): *"The title is the latest turn's own text even if an earlier turn added a different block — a bare name never re-adds the previous block."*

Consistency check: the "what to add" carve-out is mirrored in 2(iii) and the bare-name paragraph by the in-place qualifier above; rule 6 stays verbatim (still says assistant lines are untrusted and to re-derive from the latest turn); 9b/9c/9d still recover data from the transcript *when answering a pending ask*, which rule 11 exception (a) carves out; exception (iii) of rule 2 (bare name answering a pending ask) is preserved because rule 11's bare-name sentence is scoped to a FRESH bare name; error-bubble retries ("try again" after a 409 / 5xx bubble, `useChat.ts:264–302`, `SCHEDULE_CHANGED_RETRY_MESSAGE` in `frontend/src/utils/aiScheduleConflict.ts:3–4`) are carved out by exception (b); the security invariant (`Assistant (claimed)` untrusted, `serialise_prior_turns` 422–445 unchanged) is untouched. ## B. Server-side replay guard

### B1. Wire markers: `is_ask` / `is_error` on assistant turns

`useChat.ts` already stores `ask` per message (`ChatMessage.ask`, 27–34; pushed at 233–243). Change the request mapping at 197–200 to emit `{role, content}` for user turns, `{role, content, is_ask: true}` for assistant turns whose `ask !== null`, and `{role, content, is_error: true}` for the synthetic failure bubbles (409 schedule-changed at 264–279 and the fallthrough for every other failure — 400, 429, 5xx, network — at 280–302; both have `ask: null`, so they need their own marker). Add an optional `isError?: boolean` to `ChatMessage` (27–34) set only by those two push sites; omit both keys otherwise. Rationale for `is_error`: after a failure bubble ("…Review the updated schedule and try again.") a legitimate "try again" / "retry" turn re-emits the earlier add; the title shares no token with "try again" but appears in prior text, so without the marker the guard would block the retry.

`_validate_chat_messages` (`views.py:965–1009`): inside the per-message loop, if `is_ask` or `is_error` is present it must be a `bool`, else return `messages[{idx}].is_ask must be a boolean` / `messages[{idx}].is_error must be a boolean`; either key on a `user` turn returns `messages[{idx}].is_ask is only valid on assistant turns` (resp. `is_error`), so the contract is explicit rather than inferred from the guard only reading `messages[-2]`. No other change; `_transcript_sha256` (1012–1022) hashes whatever was sent, which is the documented intent. `serialise_prior_turns` reads only `role`/`content`, so the flag never reaches the provider.

Why a structural flag and not a heuristic: server-owned asks from `_build_resolution_ask` (246–324) are frequently *not* questions ("…Please give it a concrete free start and end time.", the `no_slot` copy at 305–309, `out_of_window` at 318), so "ends with `?`" fails exactly on the 9c/9d flows the guard must not break; and both ask and explanation turns usually contain the block title, so content matching cannot separate them either. Reading the previous turn's kind from `AIInteraction` rows is stateful and breaks with two tabs on one schedule.

Why a client-supplied flag is acceptable: the guard is a **correctness/UX gate, not a security boundary**. A client that forges `is_ask: true` merely disables the guard for its own turn and lands back on today's behaviour — an add on the user's own schedule that the same client could produce by typing `add Momentum[2]`. It grants nothing beyond what the user can already do; the only security-relevant invariant (no privileged `assistant` role forwarded) is untouched. State this in code comments, `RULES.md`, and `docs/api.md`.

### B2. Pure helper — new module `backend/ai/replay_guard.py`

Pure: stdlib only (`re`, `unicodedata` if needed) — no Django and no `schedules.*` imports (unlike `ai/free_slot.py`, which imports `schedules.http` → Django), so the unit tests need no DB or settings. Exposes a reason-code constant `"replay_guard"`, an ask-copy constant/builder, and one entry point that takes `(parsed_actions, messages)` and returns the tuple of offending action indices (empty ⇒ apply as usual).

Algorithm, step by step:

1. **Pending-ask skip / error-retry widening.** If `len(messages) >= 2`, `messages[-2]["role"] == "assistant"` and `messages[-2].get("is_ask") is True` → return empty (guard off for this turn). If instead `messages[-2].get("is_error") is True`, walk back over the **failure chain**: collect every user turn `F` that is immediately followed by an `is_error` assistant turn, going backwards from `messages[-3]` while the pattern `(user, is_error assistant)` repeats (covers "try again" failing twice). The chain is **contiguous only**: stop at the first turn that does not fit the pattern; `k` is the index of the earliest turn in that contiguous chain (never an earlier, unrelated failure). The guard stays ON with two changes: the failed turns `F` (and their error bubbles) are **excluded from the step-B prior text** (prior text becomes `messages[:k]`), and — if `k >= 1` and `messages[k-1]` is an `is_ask` assistant turn — the chain began as the answer to that pending ask: the ask turn itself is also dropped from the prior text (`messages[:k-1]`), and a title that is **traceable to the ask text** (step-A style any-token match against `messages[k-1]["content"]`, using the same stopword-only fallback as step A) is allowed, so a failed 9c/9d answer can be retried. **Exception:** when the ask text starts with the guard's own pinned prefix (`I did not change the schedule:`), ask-text traceability is disabled — the guard ask quotes the *rejected* title, so treating it as evidence would let the next retry re-apply exactly that replay. The request turn `messages[k-2]` stays in the prior text: one user message can apply some adds and trigger an ask for another (`views.py:1218–1233`), so dropping it would erase the only evidence of the siblings that already landed. Server asks name the skipped block (`views.py:305–318`); a model ask that does not name it costs one extra guard ask (accepted, R9 class). Step A is otherwise unchanged (latest turn only). There is no full skip here: `[Momentum ✓, add Gym 09:00, ask "Gym does not fit…"(is_ask), 14:00 ✗(is_error), try again] → Momentum[2]` is flagged while `→ Gym 14:00` passes; `[add Momentum, Gym 09:00 → Momentum ✓ + ask about Gym(is_ask), 14:00 ✗, Notes] → Momentum[2]` is flagged (Momentum is in `messages[k-2]`, not in the ask text). Net effect: a title that appears only in the failed request(s) has no replay evidence and passes — a retry ("try again", "ещё раз") of a request that was never applied (400 aborts the whole batch; 409 `schedule_changed` writes nothing); a title that also appears *before* the failure chain is still a replay and is flagged — so `add Gym after Momentum` failing, then `Notes` → `Momentum[2]` is blocked, and `[add Momentum ✓, add Momentum ✗, Notes] → Momentum[2]` is blocked. Accepted cost: an intentional repeat of an existing title whose apply failed ("add Momentum" when Momentum exists → 409 → "try again") gets one extra ask. Residual: a first-time title that failed and is then replayed on an unrelated turn (`add Momentum` ✗ → `Notes` → `Momentum`) passes — it creates no duplicate, since the failed add never applied. Not a full skip for `is_error`, unlike `is_ask`: an error bubble does not ask anything, so there is no answer to coreference. Rationale: the latest turn is an answer ("later", "14:00", "yes", "Gym", "work", "make it 15 minutes"); by rules 2(iii)/3/9b–9d the model legitimately recovers the block title from the transcript, so *any* traceability test against the latest turn would false-positive. This covers flows (a): direction answer, 9c re-emitted timed add, 9d `no_slot` retry, "which block?" and category answers, and the concrete-suggestion "Move it to 11:00–12:00?" acceptance.
2. **Normalise each `add` title** (only `type == "add"`; move/remove/resize/update are ignored — see B4): strip one trailing duplicate-counter suffix matching `\s*\[\d+\]\s*$` (so `Momentum[2]` → `Momentum`, but `GridBot[Note]` is kept whole), casefold, collapse internal whitespace, strip. Tokenise with `\w+` on the casefolded text (Unicode-aware, so Cyrillic works) and keep only **significant** tokens: contain at least one letter (a time answer `14:00` must never "explain" a title) and are not in a small fixed function-word set (English + Russian articles, prepositions, conjunctions, pronouns and chat verbs: e.g. `a an the for of to in on at and or with my me it add please` / `и в на с для по к у а или мне добавь`). Without the stopword filter, `Plan for Friday[2]` on latest `add notes for later` would pass step A via `for`.
   **Token match** (used by steps A and B): two tokens match if they are equal, or if both are ≥ 4 chars, share a common prefix `p` with `len(p) ≥ max(4, len(shorter) − 2)`, AND each token extends past `p` by at most 2 chars (`len(a) − len(p) ≤ 2` and `len(b) − len(p) ≤ 2`). This absorbs common plural/case inflection (`meetings`↔`meeting`, `обеда`↔`обед`, `тренировку`↔`тренировка`) without a stemmer, while rejecting compounds/derived words (`work`↔`workout` — remainder 3, `work`↔`workshop`, `notes`↔`notebook`, `plant`↔`planning`); `notes`↔`momentum` never match. Known residual: remainder-1/2 pairs of *different* words (`plan`↔`plant`, `read`↔`ready`) still match — this only ever lets a replay through (today's behaviour) and needs the model to replay exactly such a near-homograph; longer Russian endings (`тренировками`, remainder 3) fall back to an extra ask.
3. **Step A — traceable to the latest turn?** Normalise/tokenise `messages[-1]["content"]` the same way. The title is traceable if **any** significant title token matches a latest-turn token, or if the title has no letter tokens at all (emoji/number-only titles: cannot judge → permissive). A title whose letter tokens are *all* stopwords (`IT`, `On`, `Me`) is not permissive: for that title only, switch to **unfiltered** letter tokens on every side — the title, the latest turn in step A, the ask text in the failed-answer carve-out (step 1), and the prior text in step B — so `add IT` → `IT` passes step A (latest `it` kept) and `Notes` → `IT[2]` after `add IT` is still caught. Traceable ⇒ this add is fine. "Any-token overlap", not "all tokens", is deliberate: it keeps `schedule a workout` → `Workout`, `add gym` → `Gym Session` (rule-driven naming), and `coffee w/ John` → `Coffee with John` out of the guard. The trade-off is a known false negative — `Notes` → `Momentum Notes[2]` passes — accepted because such a block at least carries the user's word and is not a copy of the previous block.
4. **Step B — replay evidence?** Only for adds that failed step A. Build the prior text by joining `content` of `messages[:-1]` (user *and* assistant turns — an explanation like "Added Gym Session" is valid evidence). The title is a replay if the whole normalised title matches the normalised prior text with word boundaries (`(?<!\w)` … `(?!\w)`, `re.escape`d), or if **all** of its significant tokens (non-empty set) match some prior-text token. Replay ⇒ record the action index. Not a replay ⇒ allowed: an unexplained but never-seen title (e.g. a translation `Обед` → `Lunch`, or a model paraphrase on turn 1) has no evidence of being replayed, and rejecting it would be a pure false positive. With `len(messages) == 1` the prior text is empty and step B is always false, so first turns are never flagged.
5. Return the offending indices. The view treats a non-empty result as a violation for the whole turn.

Wording of the guard ask (server-owned, English like every `_build_resolution_ask` string; stable prefix pinned by tests): `I did not change the schedule: "<title>" is not something you asked for in your last message. What would you like to add?` where `<title>` is the first offending action's raw title truncated to ~60 chars. Server-owned explanation for the same response: `Nothing was changed.` — the model's own explanation ("Adding Momentum[2] …") is deliberately *not* echoed because it would contradict the ask in the transcript.

### B3. View wiring (`backend/ai/views.py:ai_chat`)

Insert the guard between the chit-chat early return (1171–1182) and the apply block (1184–1201), i.e. after the audit row is created (1148–1154) so `actions_json` keeps the model's intent. Not inside `_apply_actions_sync`: the guard needs the transcript, must run before the lock/fingerprint round-trip (409 is irrelevant when nothing will be written), and belongs next to the other server-owned ask logic (`_build_resolution_ask`).

On violation:

- **All-or-nothing**: apply no action from this turn, including well-formed siblings. Justification: the actions are one model output for one turn; an untraceable add proves the model misread that turn, so a sibling move/remove in the same output is just as suspect (it could equally be replayed from turn 1). Partial application would also trigger the frontend's undo push + reload (`useChat.ts:246–257`) while the transcript says "nothing changed". This matches the existing structural-failure semantics (whole batch aborts) but as a `200` ask, not a `400`, because the user needs a conversational recovery, not an error.
- Build `outcomes`: one `ActionOutcome` per parsed action (`mutation_planner.py:177–186`), `status="skipped"`, `reason_code="replay_guard"`, `task_id=None` for adds (`_ADD_ALLOWED_KEYS`, `schemas.py:27`, has no `task_id`) and the action's `task_id` for non-add siblings, `skipped_fields=("title","category","start_time","end_time")` for adds and `()` otherwise; serialise with `action_outcome_to_dict` (209–220).
- Audit: `_mark_success(interaction, outcome_payload)` (210–225) — the request completed with a server-owned ask, same as the clarifying branch, and `outcomes_json` records *why* nothing was applied. Add a `logger.warning("AI chat replay guard tripped (user=%s, schedule=%s, interaction=%s, actions=%s)")` with the offending indices only — no titles or message text in logs, consistent with the existing warnings (1195–1200).
- Response (same shape as the clarifying-question branch at 1159–1168): `blocks: None`, `explanation: "Nothing was changed."`, `ask: <guard ask>`, `applied: false`, `partial: false`, `outcomes: <skipped list>`. The only contract delta vs. the existing ask variant is a non-empty `outcomes`; `useChat.ts` does not read `outcomes`, so no frontend branch changes.

Ordering note: because the guard runs before `_apply_actions_sync`, a stale snapshot plus a replayed add returns the guard ask, not `409 schedule_changed` — pinned by `test_guard_precedes_fingerprint_check`. This matches the existing clarifying-ask branch (1157–1168), which also returns `200` without a fingerprint check or a frontend reload; the concurrent edit still surfaces as `409` on the next turn that actually applies. Amend `docs/api.md:428` ("only when `parsed_actions` is non-empty" → "…and the replay guard did not trip") and `RULES.md:163` ("Skipped when `parsed_actions` is empty" → "Skipped when `parsed_actions` is empty or the replay guard tripped").

Follow-on turn: the frontend stores the guard ask with `ask` non-null → next request carries `is_ask: true` → step 1 skips the guard → the model, now under rule 11 and 2(iii), resolves "yes, add Notes" / "Notes" as the answer. If it replays again, the response is applied (guard off) — accepted residual risk; noted below.

### B4. Scope decisions

- **Adds only.** move/remove/resize/update reference a `task_id` that must exist in the current `Existing blocks` listing (rule 3); a replayed one would target a real block, and its "traceability" cannot be judged lexically (the user says "move it later"). Extending the guard there would produce false positives with no precedent from the issue.
- **No new settings/env var.** The guard has no tunables; adding a kill switch would need `.claude/rules/project.md` + `settings.py` churn for a deterministic pure function.
- **`serialise_prior_turns` unchanged.** Labelling flagged turns `Assistant (claimed, asked)` for the model is a possible later improvement; out of scope to keep the transcript-security tests (`TestUntrustedTranscript`, `test_ai_service_chat.py:111–164`) untouched.

## Risks / open questions

- **Residual replay on the follow-up turn.** After the guard's ask, the next turn runs with the guard off (`is_ask`). If the model replays again while "answering", it applies. Mitigation is rule 11 + the pending-ask phrasing ("What would you like to add?") that names the expected answer; monitor audit rows. A stricter variant (allow only titles traceable to the latest turn *or* to the ask text) is possible later.
- **Stale frontend tabs** after deploy send no `is_ask`, so a legitimate 9c/9d answer gets the guard ask once; a reload fixes it. Acceptable for a single-deploy SPA; pinned by `test_pending_ask_without_flag_is_enforced`.
- **Rule-authored titles with no user token** (e.g. a rule "call deep work 'Flow'": first `deep work` → `Flow` passes, a repeat `deep work` → `Flow[2]` is flagged because "Flow" is in prior text). Accepted: one extra clarifying turn, then `is_ask` lets the answer through. Using active-rule text as traceability evidence was rejected: the #219 user's own Rule contains "Momentum", so it would whitelist the exact replay this feature blocks.
- **Word-style duplicate conventions** (a Rule appending ` copy` / ` II` / ` bis` instead of `[N]`): the extra token is absent from prior text, so step B returns not-replay and such a replay applies silently. Accepted false negative, same class as `Momentum Notes[2]`; the guard strips only the `[N]` convention observed in #219. Digit-only variants (`(2)`, ` 2`) are covered because digit tokens are dropped.
- **Short-word inflection and cross-language repeats** (`gym`↔`gyms` below the 4-char prefix floor; `Обед` → `Lunch[2]` after an earlier `add Lunch`) are flagged: one extra ask. Pinned by unit tests so the behaviour is intentional, not incidental.
- **`is_error` covers every failure bubble** (400, 409, 429, 503, network), not only retryable ones. It only removes the failed turn(s) from step-B evidence, so it is permissive-only; do not narrow it to 409 (breaks 5xx retry) — note in RULES.md.
- **Lost-response duplicate**: a network failure (`result.status === undefined`, `useChat.ts:281–285`) after the server already committed the apply still yields an `is_error` bubble; a "try again" then re-emits a title that only exists in the excluded failed turn, so it applies twice. No worse than today (the guard is permissive here); the "failed add never applied" premise holds for 400/409/5xx responses, not for a lost response. Note in RULES.md next to the `is_error` entry.
- **Whitespace-free scripts** (CJK): `\w+` yields one token per run, so step A misses partial overlaps; step B still requires prior evidence, so the failure mode is an occasional extra ask, not a silent replay.
- **False positives** remain possible when the user intentionally asks for a copy with no lexical overlap ("again", "one more") — the ask resolves it in one extra turn. Accepted per the issue's acceptance wording ("unless the user requests that copy").
- **Playwright**: no script change. `ai-chat-clarifying-question.mjs` (190–210) and `ai-chat-single-turn-apply.mjs` (25) drive the UI and only assert the turn-1 request body (a single `{role:"user", content}` entry), so the new keys on later assistant turns are invisible to them.
- **English-only server strings**: the guard `ask` and `explanation` are server-owned English, like every `_build_resolution_ask` string, while model asks follow the user's language (`prompts.py:119`). Note in RULES.md as the third English-only chat string for any later i18n pass.

## Addendum D — Implicit "add" for command-less turns (user-approved after live test)

**Why.** Live test on the worktree (audit row 268): with Hard rule 11 in place, `gpt-4o-mini` still answered `Notes` with `add Momentum[2]` ("per rules"). The replay guard blocked it (`reason_code: replay_guard`), but the user then got a clarifying ask instead of a `Notes` block. User requirement, verbatim intent: "if it is unclear what to do and there is no explicit instruction, try putting the word add / добавить in front of it, and if the sentence then makes sense, execute it — 99% of my commands are like that."

**What.** A deterministic, server-side rewrite of the **latest user turn as sent to the LLM** (never the stored transcript, audit row, or response): when the latest turn carries no explicit instruction, prefix it with an add verb before `run_chat` builds the message array.

- Prefix: `add ` when the text contains no Cyrillic letters; `добавь ` when it contains Cyrillic.
- The model then sees e.g. `add Notes`; if the resulting sentence makes no sense, the model's normal clarifying-ask path handles it (no extra logic).

**When NOT to prefix** (leave the turn unchanged), checked on the casefolded, trimmed text:
1. Pending ask or error retry: `messages[-2]` is an assistant turn with `is_ask: true` (the turn is an answer; keeps 2(iii)/9b–9d flows intact) or `is_error: true` (a retry after a failure bubble; added after external review — otherwise `try again` became `add try again`).
2. Explicit command verb present as a whole word anywhere in the text: English `add, move, remove, delete, make, resize, rename, shift, extend, shorten, cancel, clear, schedule, put, set, change, swap, split, merge, undo, retry, try, repeat, reschedule, postpone, delay, push, pull, bump, replace, update, edit, create, insert, plan, fill, organize, reorganize, rearrange, optimize, free, skip, drop, complete, finish, list, show, tell, explain, summarize, describe` — `check`/`review` deliberately excluded since they start common block titles (and simple inflections: `-s`, `-ed`, `-ing`); Russian stems matched as word prefixes: `добав, перенес, перенос, сдвин, удал, убер, убр, сдел, измен, переимен, продл, сократ, отмен, очист, постав, поменя, запланир, повтор, спланир, распланир, планир, отлож, передвин, заполн, освобод, пропуст, заверш, созда, покаж, расскаж, объясн, напомн`.
3. Question: ends with `?`, or starts with `what, when, how, why, which, who, where, is, are, can, could, should, do, does, что, когда, как, почему, зачем, какой, какая, какие, где, кто, сколько, можно`.
4. Short reply / chit-chat / greeting / retry token (whole text, casefolded with edge punctuation stripped, equals one of; list extended after external review with `bye, good morning, good afternoon, good evening, good night, thanks a lot, again, пока, доброе утро, добрый день, добрый вечер, спокойной ночи, ещё раз, еще раз`): `ok, okay, thanks, thank you, thx, yes, no, yep, nope, sure, cool, great, hi, hello, hey, да, нет, ок, окей, спасибо, привет, хорошо, ладно, отлично`.
5. Empty after trimming.

**Where.** A pure helper in `backend/ai/replay_guard.py` (or a sibling pure module `backend/ai/implicit_add.py` — implementer's choice, keep stdlib-only) returning the text to send; call it in `backend/ai/service.py:run_chat` where `latest_user_turn` is taken from `messages[-1]["content"]` (service.py ~326). `run_chat` has the full `messages` list including `is_ask`, so condition 1 is available there.
