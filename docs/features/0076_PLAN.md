# Issue #194 — Pin the Production SSH Host Key

The `deploy` job currently trusts a key discovered at runtime via TOFU (`.github/workflows/deploy.yml:126-127`). Replace that behavior with a required repository secret before any production application secrets are materialized, while preserving the existing Compose and `.env` generation flow.

## 1. RED — establish the workflow policy checks

Before editing, run `actionlint .github/workflows/deploy.yml` and `ruby -ryaml -e 'YAML.parse_file(ARGV.fetch(0))' .github/workflows/deploy.yml` as the YAML syntax baseline. Add `actionlint` to the implementation verification if it is not already available; no pytest/vitest coverage applies to this workflow-only change.

Establish the expected failing policy checks against the current workflow:

- `! rg -n 'ssh-keyscan|StrictHostKeyChecking=accept-new' .github/workflows/deploy.yml` must fail because `ssh-keyscan` is still present.
- `rg -n 'name: Pin SSH host key' .github/workflows/deploy.yml` must fail because the pinning step does not yet exist.
- `test "$(rg -c 'StrictHostKeyChecking=yes' .github/workflows/deploy.yml || echo 0)" -eq 5` must fail because none of the five `ssh`/`scp` invocations is strict yet. (The `|| echo 0` guard is required: `rg -c` prints nothing and exits 1 on zero matches, which would otherwise make `test` fail with an `integer expression expected` shell error instead of a clean count mismatch.)
- Create a temporary, untracked structure verifier that parses `jobs.deploy.steps` and asserts the sequence `Install SSH key` → `Pin SSH host key` → `Copy deployment files to droplet` → `Write .env, pull image, restart stack`; it must fail in RED because the pin step is absent.

Document and run a one-time negative SSH test from a trusted machine using a generated, unrelated host key:

```
bad_dir=$(mktemp -d)
ssh-keygen -q -t ed25519 -N '' -f "$bad_dir/key"
awk -v host="$SERVER_HOST" '{print host, $1, $2}' "$bad_dir/key.pub" > "$bad_dir/known_hosts"
if ssh -o BatchMode=yes -o StrictHostKeyChecking=yes \
       -o "GlobalKnownHostsFile=/dev/null" \
       -o "UserKnownHostsFile=$bad_dir/known_hosts" \
       "$SSH_USER@$SERVER_HOST" true 2>"$bad_dir/err"; then
  echo "UNEXPECTED: bogus pin accepted"; exit 1
fi
grep -qi 'host key verification failed' "$bad_dir/err"
```

Structure the probe as an `if ! ssh ... ; fi` (as above), **not** as `ssh ...; test $? ...` — under a `bash -e` shell the failing `ssh` would abort the script before the assertion ever runs. Require the failure to be **specifically** a host-key verification failure (assert the message in stderr), not merely any non-zero exit — a routing/timeout/auth error would satisfy a bare `! ssh` while proving nothing. `GlobalKnownHostsFile=/dev/null` is mandatory in this probe because the *trusted operator machine* very likely has the real droplet key in its own `~/known_hosts` or system-wide `/etc/ssh/ssh_known_hosts`, which would otherwise mask the bogus pin. This probe executes only `true`, performs no transfer, and establishes the expected fail-closed behavior before workflow changes.

## 2. GREEN — workflow pinning

### `.github/workflows/deploy.yml:112-248` — `deploy` job

- Remove the entire `Add server to known_hosts` step at lines 126-127. Do not leave any `ssh-keyscan` usage or introduce `StrictHostKeyChecking=accept-new`.
- Immediately after `Install SSH key` (lines 121-124), add `Pin SSH host key`, before `Copy deployment files to droplet` and therefore before the application-secret environment and `/tmp/day-forge.env` creation at lines 138-236.
- Expose the secret **only via a step-level block-style `env:` mapping** and reference it in `run:` as the shell variable `"$SSH_KNOWN_HOSTS"`:

  ```yaml
  env:
    SSH_KNOWN_HOSTS: ${{ secrets.SSH_KNOWN_HOSTS }}
  ```

  Use block style, not a flow mapping — `env: { SSH_KNOWN_HOSTS: ${{ ... }} }` is invalid YAML (the `${{` opens a nested flow mapping inside the flow mapping) and would fail the `actionlint`/YAML-parse gate. Do **not** inline-interpolate `${{ secrets.SSH_KNOWN_HOSTS }}` into the `run:` body: that is the repo's established secret-handling convention (see the comment at `deploy.yml:165-166` and the env blocks at `139-163`), it avoids shell quoting/injection hazards, and it preserves multi-line secret values (an inline splice would break a multi-line `known_hosts`). Then implement the following fail-closed order:

  1. Create `$HOME/.ssh` with `mkdir -p` (idempotent — `webfactory/ssh-agent` at `deploy.yml:121-124` already creates `~/.ssh` on the runner, so a bare `mkdir` would fail the step under GitHub's default `bash -e` on every matching-key run).
  2. Set the directory mode to `700`.
  3. Require the secret itself to be non-empty with `test -n "$SSH_KNOWN_HOSTS"` **before** writing it. This is an explicit, executable guard step — not merely descriptive prose — and it must appear in the step body ahead of the write.
  4. Write it with `printf '%s\n' "$SSH_KNOWN_HOSTS"` to `$HOME/.ssh/known_hosts`, replacing rather than appending.
  5. Set the file mode to `600`.
  6. Require `test -s "$HOME/.ssh/known_hosts"`.

  The explicit `test -n` (step 3) is necessary because `printf '%s\n'` given an empty value still writes a newline, which alone would satisfy the `test -s` in step 6. A pathological whitespace-only secret (e.g. a lone space) would pass both `test -n` and `test -s`; this is an accepted residual gap — such a `known_hosts` carries no valid host key, so the first strict `ssh` in *Copy deployment files to droplet* still fails closed before any secret is materialized. GitHub's default `bash -e` shell aborts the step on any of these failing guards.

- Add `-o StrictHostKeyChecking=yes -o "UserKnownHostsFile=$HOME/.ssh/known_hosts"` directly to all five network invocations:

  - SSH directory creation at line 135.
  - Compose-file SCP at line 136.
  - Production `.env` SCP at line 237.
  - Remote `DEBUG=0` check at line 239.
  - Remote deployment heredoc SSH at line 240.

- The five workflow invocations deliberately use only `StrictHostKeyChecking=yes -o UserKnownHostsFile=...` and **do not** need `GlobalKnownHostsFile=/dev/null` (unlike the §1 operator probe): the ephemeral `ubuntu-latest` runner has no pre-existing `/etc/ssh/ssh_known_hosts` entry for `SERVER_HOST`, so there is nothing for a global file to mask. The asymmetry with the probe is intentional, not an oversight — the probe runs on a trusted operator machine that legitimately already knows the host.
- Prefer per-invocation options over a shared string environment variable: the duplication keeps every trust boundary locally auditable and avoids unsafe shell word-splitting. Write `UserKnownHostsFile` as an **explicit shell-quoted absolute path** — `"UserKnownHostsFile=$HOME/.ssh/known_hosts"` — rather than relying on a literal `~`; `$HOME` expands to the absolute runner home unambiguously and side-steps any doubt about tilde handling inside an option token.
- Keep each of the five `ssh`/`scp` invocations on a **single physical line** (with its two added `-o` options). Do not wrap for length with a `\` continuation — the §4 count/joint-regex gates match per physical line and a wrapped invocation would read as a false RED. The heredoc `ssh` at line 240 is the longest; keep it one line.
- Preserve the Python `.env` builder, required/optional secret handling, remote destination paths, Docker login, image pull/restart commands, and health-check behavior unchanged.

Because the first strict SSH connection occurs in `Copy deployment files to droplet`, an empty pin aborts in the preceding step, while a wrong pin aborts before the workflow reaches the step that creates `/tmp/day-forge.env`.

## 3. GREEN — operator documentation

### `deployment/README.md:26-63` — §2 secrets

- Add an `SSH_KNOWN_HOSTS` row near `SSH_PRIVATE_KEY` and `SERVER_HOST`.
- Document capture from a trusted machine with `ssh-keyscan -t ed25519,ecdsa,rsa "$SERVER_HOST"`; runtime discovery inside the deploy workflow is forbidden.
- Show the expected line shape: `<ip> ssh-ed25519 AAAA...`. **Recommend pinning the Ed25519 key alone** (one line): Ed25519 is universally offered by modern OpenSSH, keeping the secret to a single line whose fingerprint the operator actually verifies. If ECDSA/RSA lines are also included so the client can negotiate them, the operator **must verify every included key's fingerprint** — otherwise an unverified ECDSA/RSA line captured over a hostile network becomes a second, un-attested trust anchor that a later negotiation could select, silently reintroducing the TOFU gap this change removes.
- Require verification of the captured Ed25519 fingerprint against `ssh-keygen -lf /etc/ssh/ssh_host_ed25519_key.pub` (and the matching `ssh_host_ecdsa_key.pub` / `ssh_host_rsa_key.pub` for any additional pinned lines), executed through an already-trusted connection or droplet console.
- Note that `ssh-keyscan -H`/hashed host entries are supported, but plaintext IP entries are easier to inspect and rotate.
- State that each `SSH_KNOWN_HOSTS` entry's host field must be keyed by the **exact `SERVER_HOST` string** the workflow uses (the droplet IP, implicit port 22). A hostname-keyed or `[host]:port`-keyed entry will not match the lookup and hard-blocks every deploy at the first strict `ssh` — capture with the same `"$SERVER_HOST"` value the secret `SERVER_HOST` holds.
- Add a host-key rotation procedure: regenerate host keys on the droplet, recapture them from a trusted machine, verify the fingerprints, replace `SSH_KNOWN_HOSTS`, then run the next deployment. Treat this as the same operational class as rotating `SSH_PRIVATE_KEY`.
- Keep §3b’s existing bind-mount preparation commands (`deployment/README.md:107-115`) unchanged; clarify only that the host-key secret must be prepared before the workflow can perform its SSH-based directory setup.
