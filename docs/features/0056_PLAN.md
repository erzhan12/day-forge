# 0056 — Settings topic navigation (GitHub issue #155)

## Context

The Settings page (`frontend/src/pages/Settings.vue`) is a single long scroll
of unrelated controls: `DesignSelector`, notification toggles,
`DayWindowEditor`, templates/rules editors, and four integration connect flows
(Apple CalDAV, Google OAuth, Todoist, Habitica) plus
`ExternalCalendarPlacementToggle` and `TravelRulesList`. The backend route
`/settings/` (`backend/templates_mgr/views.py::settings_view`) and its Inertia
props (`templates`, `rules`, `travel_rules`, `schedule_window`,
`ui_preferences`) stay unchanged — this is a **frontend presentation refactor
only**.

Reorganize into **six topics** with **one selected panel at a time**, **URL-hash
navigation** (`/settings/#integrations`), **state preservation across topic
switches** during the session, and **no backend/API/persistence changes**.

### Product decisions (verbatim from issue #155)

**Desktop:** 224px sticky left navigation; text labels only (no icons/badges);
active item gets strong background/accent rail and visible keyboard focus;
centered Settings shell ~**1040px** wide (224px nav + 32px gap + main content
up to ~760px); nav stays visible while topic content scrolls.

**Mobile:** sticky, visibly labeled topic `<select>` dropdown; same
one-selected-topic model and selected value as desktop.

**Topics:**

1. **Appearance** — design/theme selector (`DesignSelector`).
2. **Schedule** — global day start/end (`DayWindowEditor`).
3. **AI Assistant** — configurable quick-input prompts from #154 and future AI
   preferences. **#154 is not landed** (static 4a-only suggestions live in
   `ChatResultChip.vue`; no Settings UI yet). This topic still ships as a real
   panel with a placeholder ready for #154.
4. **Notifications** — `SoundNotificationToggle`, `DesktopNotificationToggle`.
5. **Integrations** — Apple Calendar, Google Calendar, Todoist, Habitica,
   `ExternalCalendarPlacementToggle`. **Do not** include travel-time rules here.
6. **Templates & Rules** — weekday/weekend `TemplateEditor` cards, `RulesList`,
   `TravelRulesList` (moved out of the old “External Calendars” section).

No Account topic until meaningful account controls exist beyond logout.

**Navigation behavior:**

- Keep `/settings/` route; hash is authoritative (`#appearance`, `#schedule`,
  `#ai-assistant`, `#notifications`, `#integrations`, `#templates-rules`).
- Default to **Appearance** when hash is absent or unknown.
- Update hash on topic change; browser Back/Forward restores topic.
- App links may deep-link to a topic (e.g. reconnect → `#integrations`).
- Preserve each section's unsaved local state while switching topics (keep
  panels mounted, hidden when inactive).
- Keep existing per-control persistence; no global Save button; no leave-warning.

**Accessibility:** semantic `<nav>` with real hash `<a href="#…">` links;
`aria-current="page"` on active topic; Tab + history work; after keyboard
topic selection move focus to the panel heading; mobile `<select>` gets a visible
label; minimal/no animation; respect `prefers-reduced-motion` if any transition
is added.

**Scope exclusions:** no new backend models/migrations, no settings API changes,
no changes to persistence behavior of existing controls.

### Composable (hash sync + focus)

**Create `frontend/src/composables/useSettingsTopic.ts`**

Algorithm (red → green target for unit tests):

1. **Init:** `activeTopic = resolveSettingsTopicFromHash(window.location.hash)`.
2. **On mount:** register `hashchange` listener → re-resolve hash into
   `activeTopic`; register `popstate` is unnecessary because hash changes fire
   `hashchange` for Back/Forward.
3. **On nav link click:** rely on native `<a href="#slug">` navigation (hash
   updates, `hashchange` fires). If the clicked topic is **already** active
   (including hashless `/settings/` resolving to Appearance), `preventDefault`
   — otherwise `#appearance` on a hashless URL pushes a redundant history
   entry and Back stays on Settings. Do not intercept with `@click.prevent`
   for actual topic changes unless testing requires it. Topic hashes (`#integrations`) do **not** match panel
   heading ids (`settings-topic-integrations`), so the browser will not
   native-scroll to the heading. After `activeTopic` changes, `nextTick` then
   scroll the active panel heading (or `.settings-main`) into view / reset
   window scroll so a user who was deep in a long panel is not left looking
   at empty space. Apply this for pointer **and** keyboard topic changes.
4. **Programmatic set** (mobile `<select>`): call `setTopic(id)`, which
   assigns `window.location.hash = "#" + slug` **and** updates `activeTopic`
   synchronously. Do **not** rely solely on `history.replaceState()` for
   topic changes — it can update the URL fragment without dispatching
   `hashchange`.
   **OAuth exception:** after handling `?google=connected|error`, do **not**
   `replaceState` the query and then assign `location.hash` — that pushes a
   synthetic history entry, so Back lands on `/settings/` (Appearance) instead
   of leaving the callback. One atomic `replaceState` to
   `pathname + remainingSearch + "#integrations"` **and** set `activeTopic`
   synchronously (same as `setTopic` but without a second history mutation).
   Today's strip at `Settings.vue` ~164–173 stays, with the hash included in
   that same `replaceState` URL.
5. **Focus management:** keyboard intent is **one-shot**. The composable
   returns `markKeyboardIntent()`; pass it as a prop into `SettingsNav` and
   `SettingsTopicSelect` (they cannot call `useSettingsTopic()` themselves).
   Arm only on **Enter** on a desktop nav `<a>` (Space does **not** activate
   links in browsers — arming on Space leaves the flag set so a later pointer
   or history change would steal focus). Consume the flag in that same
   Enter handler even if the topic is already current (no-op activation must
   not leave intent armed). On mobile `<select>` `change` that actually
   changes the topic, **do** `markKeyboardIntent` is the wrong tool — instead
   call heading `.focus()` directly after `setTopic` (headings stay
   `tabindex="-1"`, so they are not in Tab order; without this, keyboard
   users on the select cannot reach the heading). Touch users get a one-time
   heading focus ring per topic change; that is acceptable. Do **not** arm on
   Tab, arrows, or Space on nav links. When `activeTopic` changes **and** the
   consumed desktop-nav flag was true, `nextTick` →
   `document.getElementById("settings-topic-" + id)?.focus()`.
   Pointer clicks on desktop nav, Back/Forward `hashchange`, Tab-then-pointer,
   and programmatic OAuth landing must **not** move focus.
6. **Return:** `{ activeTopic, topics: SETTINGS_TOPICS, setTopic(id), markKeyboardIntent() }`.
   `setTopic` updates hash (mobile `<select>` adapter). `markKeyboardIntent` is
   the only way children arm focus.

## Algorithms

### Hash resolution

```
INPUT: rawHash from window.location.hash (may be "", "#", "#FOO", "#integrations")
1. slug = rawHash.replace(/^#/, "").trim().toLowerCase()
2. IF slug is empty OR slug not in SETTINGS_TOPICS[].hash → RETURN DEFAULT_SETTINGS_TOPIC
3. RETURN matching topic id
```

### Panel visibility + a11y

```
Settings.vue controls visibility (single useSettingsTopic() instance):
FOR each panel P with topic id T:
  visible = (activeTopic === T)
  v-show on wrapper in Settings.vue = visible
  hidden attribute = NOT visible
  (optional) inert = NOT visible when browser supports it
ONLY visible panel's heading is in the accessibility tree and focusable.
Panel SFCs do not call useSettingsTopic() or own v-show.
```

### State preservation

All six panel roots stay in the DOM for the Settings session lifetime (Inertia
page mount → unmount). `v-show` keeps Vue component instances and reactive form
state alive. Do **not** use `v-if` per topic. Unmount only happens when leaving
`/settings/` entirely (existing behavior).
