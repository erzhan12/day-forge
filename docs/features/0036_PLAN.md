# Feature 0036 — Rate-limit the account-connect endpoints (CalDAV + Todoist + Habitica)

## Context

GitHub issue #65, deferred from PR #63 (feature 0020). `claude-review`
flagged `POST /api/todoist/account/` as having no rate limit (a token
brute-force surface); `POST /api/calendar/account/` has the identical
gap. **`POST /api/habitica/account/` (feature 0024, added after the issue
was filed) has the same gap** — it too verifies a user-supplied
`api_token` against the upstream provider on every POST. All three verify
credentials against the upstream provider on every POST, so an
authenticated user can drive an unbounded number of upstream verification
calls. This feature adds a per-user fixed-window rate limit to **all
three** connect endpoints symmetrically, mirroring the existing
`ai_cmd_rl` / `ai_draft_rl` / `ai_chat_rl` `cache.incr` pattern, and
returns `429` when the budget is exceeded.

Scope is the three credential-verifying connect POST handlers
(CalDAV, Todoist, Habitica). The GET (status) and DELETE (disconnect)
methods on the same URLs are **not** rate-limited — they touch no
provider and are cheap.

**`gcal_sync` (Google Calendar, feature 0022) is explicitly out of
scope.** It uses OAuth, not a submitted secret: `POST`-less — the
`connect` view mints a CSRF `state` and 302-redirects to Google, and
`callback` exchanges a single-use, provider-issued authorization `code`.
There is no user-supplied credential to brute-force, so the
token-guess fixed-window limiter does not apply. (Google's own quota
plus the one-time `code` bound the surface.) The shared helper is still
designed so a future non-OAuth provider is a one-liner to add.

## Key design decisions (resolve the issue's internal tension)

The issue text writes the key as a single shared `connect_rl:<user_id>`
yet also names **two** separate env vars
(`CALDAV_CONNECT_RATE_LIMIT_PER_HOUR` /
`TODOIST_CONNECT_RATE_LIMIT_PER_HOUR`). A single shared bucket with two
different per-hour limits is contradictory — one counter cannot honour
two distinct thresholds. **Resolution: per-provider keys, per-provider
limits** (which also generalises cleanly to the third provider,
Habitica).

- Key shape: `connect_rl:caldav:<user_id>`,
  `connect_rl:todoist:<user_id>`, and `connect_rl:habitica:<user_id>`
  (namespaced by provider slug so the counters are independent). This is
  a deliberate divergence from the issue's literal `connect_rl:<user_id>`
  string, driven by the per-provider-env-var requirement that is also in
  the issue. The `connect_rl:` prefix is preserved so the keys remain
  visibly a family.
- Each provider reads its own limit env var, so an operator can tune
  CalDAV, Todoist, and Habitica independently (they have different
  upstream cost / abuse profiles).
- `KEY_PREFIX = "dayforge"` (configured on the **Redis** `CACHES['default']`
  branch in prod; the LocMem dev/test fallback has no prefix) namespaces
  all of these transparently, exactly as it does for `ai_cmd_rl:*` — no
  change needed there. Tests read the counter via `cache.get(...)` under
  the LocMem pin, where the prefix is absent for both keys alike, so the
  assertions are unaffected.

**Sync vs. async / atomic-incr concern.** The AI views are `async def`
and must bridge to the **sync** `cache.incr` via `sync_to_async` because
Django `RedisCache`'s async `aincr` is a non-atomic read-modify-write
that also resets the window TTL (see the memory note + the docstring on
`ai.views._consume_rate_limit`). **The connect views (`account`) are
plain `sync def`.** Therefore the connect helper calls `cache.add` +
`cache.incr` **directly** (no `sync_to_async` bridge, no `aadd`/`aincr`).
On Redis, sync `cache.add` is `SET key 1 EX 3600 NX` (anchors the window
TTL to the first call) and sync `cache.incr` is an atomic `INCR` that
preserves the TTL — both cross-worker-atomic. This is strictly simpler
than the AI path and has none of the async-atomicity footguns; the plan
must NOT copy the `sync_to_async` bridge into the sync connect views.

**Known limitation (inherited, out of scope).** Django's `RedisCache.incr`
is internally `EXISTS` *then* `INCR` (`django/core/cache/backends/redis.py`),
so the compound op is not atomic across those two round-trips: if the key
expires in the sub-millisecond gap, `INCR` recreates it *without* a TTL
(counter then never resets → that user is eventually stuck at 429). `INCR`
itself is atomic, so concurrent increments never lose counts — only this
narrow expiry race matters. This is a **pre-existing property of the shared
cache backend**, identical to the already-shipped `ai_cmd_rl` limiter this
plan mirrors; 0036 neither introduces nor fixes it (a fix would require a
Lua/pipeline `INCR`+`EXPIRE NX` diverging from the mandated pattern). The
`ValueError`-reseed branch covers the common eviction case; the LocMem test
suite cannot reproduce the Redis-only race and is not expected to.

**Placement order inside the POST handler.** Consume the rate-limit token
**after** input validation (oversized-body guard, JSON parse,
`validate_account_payload`) but **before** the upstream
`service.verify_credentials(...)` call. (Note this is validate-then-consume;
the AI `ai_cmd_rl` decorator actually consumes *before* body validation,
while draft/chat consume after preconditions — the connect endpoints
deliberately follow the validate-then-consume shape so malformed requests
return `400`/`413` without burning a token.) The abusable step (upstream
credential verification) is gated regardless. A
successful or failed verification both consume one token (the abuse
vector is the verification call itself, regardless of outcome).

## Shared helper location

Create a small provider-agnostic module so `calendar_sync`,
`todoist_sync`, and `habitica_sync` import it without a circular
dependency and without any app depending on another. The `ai` app's
helper lives inside `ai` and is async-only, so it is not reusable here.

**New file: `backend/schedules/ratelimit.py`** (the `schedules` app is
already the shared low-level utility home — `schedules.http` is imported
by all three connect views today via `from schedules.http import
reject_oversized_body`, confirming this is the established shared-import
direction with no circular-dependency risk).

Contents:

- `CONNECT_RATE_LIMIT_WINDOW_SECONDS = 3600` — module constant, mirrors
  `ai.views._RATE_LIMIT_WINDOW_SECONDS`.
- `def consume_rate_limit(key: str, limit: int) -> bool` — sync. Takes a
  fully-formed cache key and a limit. Returns `True` when within budget
  (caller proceeds), `False` when exceeded (caller returns 429). Body:
  `if cache.add(key, 1, WINDOW): count = 1` else `try: count =
  cache.incr(key) except ValueError: cache.set(key, 1, WINDOW); count =
  1`; `if count > limit: logger.warning(...); return False; return True`.
  This is the sync mirror of `ai.views._consume_rate_limit`, including
  the `ValueError`-reseed branch (`RedisCache.incr` raises `ValueError`
  on a missing key if the entry evicts mid-window).
- `def rate_limited_response() -> JsonResponse` — returns
  `JsonResponse({"errors": {"detail": "Rate limit exceeded. Try again
  later."}}, status=429)`, byte-identical to
  `ai.views._rate_limited_response` so the frontend `useHttp.ts` envelope
  contract holds uniformly.
- `def connect_rate_limit_key(provider: str, user_id: int) -> str` —
  returns `f"connect_rl:{provider}:{user_id}"`. Centralises the key shape
  so all three call sites can't drift.

## Env vars + import-time validation

`backend/day_forge/settings.py` — add three vars in the CalDAV, Todoist,
and Habitica blocks respectively, next to their existing
`*_CACHE_TTL_SECONDS` / `*_REQUEST_TIMEOUT` vars:

- `CALDAV_CONNECT_RATE_LIMIT_PER_HOUR = int(os.environ.get(
  "CALDAV_CONNECT_RATE_LIMIT_PER_HOUR", "20"))`
- `TODOIST_CONNECT_RATE_LIMIT_PER_HOUR = int(os.environ.get(
  "TODOIST_CONNECT_RATE_LIMIT_PER_HOUR", "20"))`
- `HABITICA_CONNECT_RATE_LIMIT_PER_HOUR = int(os.environ.get(
  "HABITICA_CONNECT_RATE_LIMIT_PER_HOUR", "20"))` (Habitica block,
  ~line 332, next to `HABITICA_CACHE_TTL_SECONDS` /
  `HABITICA_REQUEST_TIMEOUT`)

Default `20` connects/hour/user: generous for a human reconnecting or
correcting a typo'd credential, tight enough to blunt brute-force. State
the default in the plan; the implementer picks the exact number but must
document it.

**Import-time validation.** The existing CalDAV/Todoist/Habitica numeric
vars (`*_CACHE_TTL_SECONDS`, `*_REQUEST_TIMEOUT`) already raise
**`ValueError`** at import time on `<= 0` — the Todoist block comment at
`settings.py:312` is explicit: *"ValueError, NOT ImproperlyConfigured"*,
and the Habitica block (`settings.py:334-342`) follows the same shape.
Follow that established local precedent exactly: add `if
CALDAV_CONNECT_RATE_LIMIT_PER_HOUR <= 0: raise ValueError(...)` and the
Todoist + Habitica analogs, right after each assignment. (Most AI
`LLM_*_RATE_LIMIT_PER_HOUR` vars are unvalidated, though
`LLM_CHAT_RATE_LIMIT_PER_HOUR` *is* import-validated at
`settings.py:242-252`; either way the adjacent CalDAV/Todoist `<= 0`
`ValueError` guards are the closer precedent, so match the block we're
editing, not the AI block.) A `<= 0` limit would make the endpoint
permanently return 429, which must fail loudly at boot, not silently
brick the connect flow.

## Tests

Test files already exist:
`backend/tests/test_calendar_sync_views.py`,
`backend/tests/test_todoist_sync_views.py`, and
`backend/tests/test_habitica_sync_views.py`. All use the same fixture
shape: `user` (creates a `User`), `auth_client` (logged-in Django
`Client`), an autouse settings fixture, and an `account` fixture. The AI
suite's `TestRateLimit` in `backend/tests/test_ai_views.py` (esp.
`test_returns_429_once_budget_is_exceeded` and
`test_counter_stored_under_expected_key`) is the pattern to copy: set the
limit low via the `settings` fixture, drive N successful POSTs, assert the
(N+1)th returns 429, and read the counter directly via
`cache.get(f"connect_rl:<provider>:<user.id>")`.

Because these connect POSTs verify credentials against the provider, the
successful-post path must **mock `service.verify_credentials`** (patch it
to a no-op / return `None`) so the test exercises the rate limiter, not a
real network call. The existing view tests already mock the service layer
(`unittest.mock.patch` on `todoist_sync.service` /
`calendar_sync.service` / `habitica_sync.service`), so reuse that
fixture/patch style. Habitica's `verify_credentials(api_user_id, token)`
takes two positional args (the view passes `cleaned["api_user_id"],
cleaned["api_token"]`); for the failed-verify case mock it to raise
**`service.HabiticaAuthError`** (→401, as the existing
`test_post_auth_failure_maps_to_401` does) — NOT the base
`service.HabiticaError`, which is unmapped and returns 500.

Add a `TestConnectRateLimit` class in each of the three files with:

- **`test_returns_429_once_connect_budget_exceeded`** — set the provider's
  limit to a small N via `settings`, mock `verify_credentials` to succeed,
  POST valid credentials N times (assert 200), then the (N+1)th POST
  returns 429 with `"rate limit" in resp.json()["errors"]["detail"].lower()`.
- **`test_429_short_circuits_before_verify_credentials`** — set limit to
  1, exhaust it, then assert the over-budget POST returns 429 **and**
  `verify_credentials` is NOT called on the rejected request (assert the
  mock's call count did not increase past the budget). This proves the
  limiter gates the abuse vector.
- **`test_counter_stored_under_expected_key`** — assert
  `cache.get(f"connect_rl:caldav:{user.id}")` (resp. `todoist` /
  `habitica`) is `None` before the first POST and increments
  `1, 2, ...` per successful POST.
- **`test_failed_verify_still_consumes_token`** — the load-bearing
  security case. Mock `verify_credentials` to *fail* (raise the
  provider's auth/invalid-credentials error → 401/502), set the limit to
  a small N, POST N times (each fails upstream), then assert the (N+1)th
  POST returns **429** and the counter key incremented on the failed
  attempts. This locks the design invariant at line "*a successful or
  failed verification both consume one token*" — without it, a wrong
  consume-on-success-only implementation passes every other test while
  leaving the brute-force surface (the feature's whole reason to exist)
  wide open.
- **`test_400_body_does_not_consume_token`** — parametrize over all three
  pre-consume validation paths: (a) missing required field → 400 from
  `validate_account_payload`, (b) oversized body → 413 from the
  `reject_oversized_body` guard, (c) malformed JSON → 400 from the JSON
  parse. For each, assert the counter key is still `None` afterwards,
  proving *every* validation branch precedes consumption (not just the
  payload validator).
- **`test_get_and_delete_not_rate_limited`** — with the limit set to 1,
  drive several GET (status) and DELETE (disconnect) calls and assert none
  return 429 and the counter key stays `None` (only POST consumes).

Also add the helper-level unit tests in a new
`backend/tests/test_ratelimit.py` (all three are wired into Cycle 1 RED):

- **`test_consume_rate_limit_allows_within_budget_then_blocks`** — add
  the key, `incr` up to the limit → returns `True`, over the limit →
  returns `False`. The baseline budget-boundary assertion.
- **`test_consume_rate_limit_reseeds_on_incr_value_error`** — mirror
  `test_ai_views.py::test_cache_incr_value_error_reseeds_counter`:
  monkeypatch `schedules.ratelimit.cache.incr` to raise `ValueError`
  after a first `add`, and assert the helper reseeds (returns `True`, key
  back to `1`). This covers the mid-window-eviction branch that the
  view-level tests won't naturally hit.
- **`test_consume_rate_limit_preserves_window_ttl`** — inspired by
  `test_ai_views.py::test_increment_preserves_window_ttl` (feature 0015
  regression) but with a **stronger assertion**: capture the LocMem
  `cache._expire_info[make_key(key)]` deadline right after the first
  `consume_rate_limit` (the `add`), then again after a second
  `consume_rate_limit` (the `incr`), and assert the deadline is
  **unchanged** (`ttl_after <= ttl_first`, i.e. non-increasing). Do NOT
  copy the AI test's bare `ttl_remaining > 1800` check — that only
  catches a reset-to-*short*-default bug and would silently pass a
  sliding-window implementation that re-anchors the TTL to the full 3600
  on every call (3600 > 1800). The non-increase assertion catches both.

Note: the unit suite pins `CACHES['default']` to LocMem via conftest, so
these `cache.get(...)` reads work exactly as they do in the AI suite;
`KEY_PREFIX` is transparent to `cache.get`.

## What could break / risks to watch

- **Double-consume on retry after a transient upstream failure.** A user
  whose `verify_credentials` legitimately fails (e.g. iCloud 504) and who
  retries burns a token per attempt. Default 20/hr leaves ample headroom;
  documented as accepted behaviour (the abuse vector is the verification
  call, so counting failures is correct).
- **Non-Redis deploys** get per-worker counters (limit × workers
  effective). Same well-understood caveat as every other cache-backed
  counter in the app; no `ai.E001`-style boot block here because AI may be
  disabled. Documented in `project.md`.
- **Import order:** the `<= 0` guards must run at settings import; place
  them immediately after each assignment, matching the existing
  `*_CACHE_TTL_SECONDS` guard style, so a misconfigured deploy fails at
  boot not at first request.
