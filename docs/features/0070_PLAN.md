# Fix #182 — Per-Request Timezone for AI Placement and Prompt Context

Day Forge currently interprets AI “current time” in UTC because no user timezone is activated. Accept an IANA timezone from each browser request, resolve it without changing Django’s global timezone, and use it for chat placement plus chat/draft prompt context. Keep all stored datetimes and Django settings unchanged.

## Request and Placement Algorithm

1. At request time, the frontend obtains the IANA identifier from `Intl.DateTimeFormat().resolvedOptions().timeZone`.
2. Chat sends `{ messages, client_tz }`; draft sends `{ client_tz }`.
3. `_resolve_client_tz(raw)`:
   - Accepts only strings; guard non-strings (including `None`) before touching `ZoneInfo`.
   - Resolves valid strings with `zoneinfo.ZoneInfo`.
   - Treats missing values, non-strings, empty/unknown zones, and ALL malformed keys as invalid input. The `except` must catch more than `ZoneInfoNotFoundError`: a key with `..` or a leading `/` (e.g. `".."`, `"/UTC"`) raises `ValueError`, and an over-long key within the 100 KB body cap can raise `OSError`/`ENAMETOOLONG` from the filesystem lookup — catch `(ZoneInfoNotFoundError, ValueError, OSError)` (or broadly guard) so none of these escape as a 500.
   - Returns the configured fallback timezone on every invalid-input path. Compute the fallback DEFENSIVELY: attempt `ZoneInfo(settings.TIME_ZONE)`, but if even that raises `ZoneInfoNotFoundError` (host with neither a system IANA db nor the `tzdata` package), fall back to `datetime.timezone.utc` so the "never 400/500" invariant is unconditional and the fallback path can never itself raise.
   - Never propagates client-input errors or causes a 400/500 response.
4. `ai_chat` resolves the timezone once and uses it for both downstream paths:
   - Prompt context: `timezone.localtime(timezone.now(), client_tz)` is passed to `run_chat(...)`.
   - Apply context: the resolved timezone is threaded into `_apply_actions_sync`.
5. Change `_apply_actions_sync` from `(schedule, result, *, expected_fingerprint, interaction_id=None)` to `(schedule, result, *, client_tz, expected_fingerprint, interaction_id=None)`.
6. Inside `_apply_actions_sync`, retain the timestamp sampling at `views.py:742` under the existing `transaction.atomic()` and row locks. Sample a fresh `timezone.now()` there, convert it with `timezone.localtime(..., client_tz)`, and pass the result unchanged to `_earliest_start(locked_schedule.date, window, now_local)`.
7. Do not reuse the earlier prompt timestamp for placement. Feature 0067’s freshness invariant remains intact; only the timezone used to interpret the fresh instant changes.
8. `ai_generate_draft` parses its optional body after oversized-body and date validation:
   - Empty body, invalid JSON, non-object JSON, or an object without a usable `client_tz` produces the UTC fallback.
   - These body shapes do not return 400 or 500 and continue through the normal draft flow.
   - A resolved timezone is used in `timezone.localtime(timezone.now(), client_tz)` before calling `run_draft(...)`.
9. Do not call `timezone.activate()`, mutate global timezone state, persist a user timezone, or alter planner/window behavior.

## Phase 1 — Backend Timezone Resolver and Pure Floor Tests

### RED — Write and Run Failing Tests First

Before editing production code, add tests in `backend/tests/test_ai_views_chat.py` and run them to confirm failure because `_resolve_client_tz` does not exist:

- Malformed-but-string keys that raise a NON-`ZoneInfoNotFoundError` exception also fall back without raising — explicitly parameterize `".."`, `"/UTC"` (→ `ValueError`). This is the guard that a naive `except ZoneInfoNotFoundError` would miss.
- **Deterministic branch coverage via monkeypatch (not string fixtures).** Because `tzdata` is present, an over-long key just raises `ZoneInfoNotFoundError`, so a raw over-long string does NOT reliably exercise the `OSError` arm and no string can force the fallback-construction to fail. To actually cover both promised safety branches, monkeypatch the resolver's `ZoneInfo` symbol: (a) make `ZoneInfo(raw)` raise `OSError` and assert the resolver still returns the fallback tz without propagating; (b) make BOTH `ZoneInfo(raw)` and `ZoneInfo(settings.TIME_ZONE)` raise `ZoneInfoNotFoundError` and assert the resolver returns `datetime.timezone.utc` (the last-resort). Without these two monkeypatched tests the `OSError` catch and the last-resort UTC fallback are unverified dead code.
- No invalid raw value raises out of the resolver.
- Add a DST automated case: resolve a DST-observing zone (e.g. `Europe/Berlin`) and assert `timezone.localtime(<fixed winter UTC instant>, tz)` and `timezone.localtime(<fixed summer UTC instant>, tz)` yield the two different offsets — proving DST correctness comes from `ZoneInfo`, not manual arithmetic.
- **(Regression/characterization guard — NOT fail-first RED, since `_earliest_start` is unchanged.)** Add a direct `_earliest_start` characterization using one fixed **tz-aware UTC** instant converted through the resolved `Asia/Almaty` timezone. Assert the local floor is rounded forward from the local wall clock and differs from the UTC-derived floor. This documents WHY the fix matters; it passes independently of the new resolver.
- **(Regression/characterization guard.)** Add a SECOND `_earliest_start` characterization for the midnight date-flip branch (`views.py:341` `schedule_date != now_local.date()`). CRITICAL — make it behaviorally discriminating: with the default `06:00` window start, a UTC+5 (`Asia/Almaty`) local time of `00:30` is BEFORE the window start, so `_earliest_start` returns `window.day_start` (06:00) — the SAME 06:00 the UTC-`None` path plans from, so the test would not distinguish the bug from the fix (clamp at `views.py:362-363` `if rounded < window.start_minutes: return window.day_start`; `mutation_planner.py` window-start default). Instead pick a setup where the LOCAL time lands AFTER the window start while the UTC instant is a DIFFERENT calendar date — e.g. `Pacific/Kiritimati` (UTC+14): UTC `20:00` on day D is `10:00` on day D+1 local. With `schedule_date = D+1`: at the DIRECT `_earliest_start` level, the UTC-interpreted `now` (date D) hits the `schedule_date != now.date()` → returns **`None`** (NOT `06:00` — `_earliest_start` itself never returns the window start here), while the local-interpreted `now` (10:00 on D+1) returns `datetime.time(10, 0)`. So the direct-unit assertion is `None` vs `time(10, 0)`. The `06:00` effective floor is produced ONE layer down, where `plan_mutations` converts `earliest_start=None` into `base_min = window.start_minutes` (`backend/ai/mutation_planner.py:993-995`); assert the resulting `06:00`-vs-`10:00` PLACEMENT difference at the Phase-2 endpoint test (through `plan_mutations`), not at the direct `_earliest_start` unit level. Alternatively use a custom `00:00` day-start window so the Almaty `00:30` local floor stays in-window and above start.
