# 0047 — Atomic reorder swap for rule lists (0026-followup)

## Context

`TravelRulesList.bumpOrder` and its sibling `RulesList.bumpPriority` each reorder
two adjacent rows by firing **two sequential `PATCH updateRule` calls** with no
atomicity. A first-succeeds / second-fails sequence leaves two rows sharing the
same ordering value. It self-corrects on the next successful reorder and the
equal-value branch nudges by ∓1, so it is **not user-blocking** — the accepted
gap recorded in `docs/features/0026_REVIEW.md` (raised by claude-review on PR #99).

This feature closes that gap by adding a **dedicated atomic swap endpoint per
model** — one shared swap mechanism, two thin parallel views — and repointing
both frontend components at it. Fixing both siblings together (per the todo)
avoids re-diverging them.

### Decision: two parallel endpoints, one shared helper (NOT one endpoint)

Researched the two models; they cannot share a single endpoint:

| | `templates_mgr.Rule` (RulesList) | `calendar_sync.TravelRule` (TravelRulesList) |
|---|---|---|
| App | `backend/templates_mgr/` | `backend/calendar_sync/` |
| Ordering field | `priority` (IntegerField) | `order` (IntegerField) |
| Sort direction | `-priority, id` (desc — high = top) | `order, id` (asc — low = top) |
| URL prefix | `/api/rules/` | `/api/calendar/travel-rules/` |
| Serializer | `_rule_to_dict` (`templates_mgr/api.py`) | `serialize_travel_rule` (`calendar_sync/travel_rules.py`) |
| Existing locking | `select_for_update` on User (feature 0046 `_compact_rule_priorities`) | **none** — `travel_rule_detail` has no `transaction.atomic()` |
| Bounds | `MIN_PRIORITY`/`MAX_PRIORITY` | `MIN_ORDER=−1_000_000` / `MAX_ORDER=1_000_000` |

Different apps, fields, URL prefixes, serializers and sort semantics mean one
shared endpoint would need per-model branching on model class + field name +
serializer — more coupling than value. Instead: **one shared, model-agnostic
swap helper** invoked by **two thin per-model views**, each owning its URL,
serializer and validation. This is the same "shared mechanism, parallel
surface" shape the two apps already use (`travel_rules.py` explicitly mirrors
`templates_mgr.api`).

The swap operates on **adjacent rows by value**, so it is field-name-agnostic
and direction-agnostic: it swaps the ordering-field value of two given rows in
one transaction. Direction/adjacency math stays in the frontend (where it
already lives); the endpoint just receives two rule ids and swaps their values
atomically.

## Shared swap helper (data layer)

New module-level helper, model-agnostic, callable from both views. Location:
`backend/schedules/http.py` (already the shared home for `is_plain_int`,
`reject_oversized_body`, `VALID_CATEGORIES` — imported by both `templates_mgr.api`
and `calendar_sync.travel_rules`).

Signature (conceptual, no code): `swap_ordering_field(user, model, order_field,
id_a, id_b)`:

1. Open `transaction.atomic()`.
2. Take the per-user row lock the same way feature 0046 does:
   `User.objects.select_for_update().get(pk=user.pk)`. This serialises
   concurrent reorders for the same user (matching `_compact_rule_priorities`'s
   locking contract) so the read-modify-write of the two ordering values is
   race-safe. **Note (SQLite):** as documented in `docs/api.md` line 63,
   `select_for_update` takes no real row lock on SQLite — same caveat as
   `reorder_blocks`; the atomicity guarantee (both writes commit or neither)
   still holds via the transaction, which is the property this feature buys.
3. Fetch both rows scoped by `user` (`model.objects.get(pk=id, user=user)`);
   any missing / cross-user id → return a sentinel the view maps to `404`
   (id-enumeration convention — 404 not 403, matching existing detail views).
4. Read `getattr(a, order_field)` / `getattr(b, order_field)`, swap them,
   `model.objects.bulk_update([a, b], [order_field])` (single statement, both
   rows or neither).
5. Return the two refreshed rows so the view can serialize the response.

The helper does **no** direction/adjacency logic and does not care whether the
field sorts asc or desc — it only swaps two values the caller chose.

## Backend — per-model views + URLs

### `backend/templates_mgr/api.py` — `rules_swap` view

- New `@login_required @require_http_methods(["POST"])` view.
- `reject_oversized_body` guard, `json.loads` body.
- Parse body: expect two rule ids (e.g. `{"a": <id>, "b": <id>}`); validate
  both are plain ints via `is_plain_int` and `a != b` (else `400`
  `errors.body`).
- Call `swap_ordering_field(request.user, Rule, "priority", a, b)`; on the
  not-found sentinel return `404` `{"errors": {"detail": "Not found."}}`.
- **Do not** call `_compact_rule_priorities` here — a swap of two contiguous
  `0..N-1` values keeps the set contiguous, and running compaction would be a
  no-op at best. (The 0046 invariant that compaction runs only on create/delete
  stays intact.)
- Response `200` `{"rules": [_rule_to_dict(a), _rule_to_dict(b)]}` (both
  swapped rows, so the client can reconcile without a full refetch — though the
  components will just `emit("changed")` and let the parent reload).

### `backend/calendar_sync/travel_rules.py` — `travel_rules_swap` view

- Same shape as `rules_swap` but `swap_ordering_field(request.user, TravelRule,
  "order", a, b)` and `serialize_travel_rule`.
- **Locking upgrade:** `travel_rule_detail` currently has no `transaction.atomic`
  / `select_for_update`; the shared helper introduces the User row-lock for the
  swap path only. Existing `travel_rule_detail` PATCH/DELETE are left unchanged
  (out of scope).
- Response `200` `{"travel_rules": [serialize_travel_rule(a), serialize_travel_rule(b)]}`.

### `backend/day_forge/urls.py`

Add two routes next to the existing collection/detail routes:

- `path("api/rules/swap/", templates_api.rules_swap, name="rules_swap")` —
  placed **before** `api/rules/<int:pk>/` so the literal `swap/` segment can't
  be captured as a pk (mirrors the `blocks/reorder/` vs `blocks/<int:pk>/`
  ordering precedent).
- `path("api/calendar/travel-rules/swap/", calendar_travel_rules.travel_rules_swap,
  name="travel_rules_swap")` — placed **before**
  `api/calendar/travel-rules/<int:pk>/`.

## Frontend — composables + components

### `frontend/src/composables/useRules.ts`

Add `swapRules(a: number, b: number): Promise<RulesListResult>` — `POST
/api/rules/swap/` with `{ a, b }`, returning the `{rules: [...]}` list result
(same envelope handling as `listRules`).

### `frontend/src/composables/useTravelRules.ts`

Add `swapRules(a: number, b: number): Promise<TravelRulesListResult>` — `POST
/api/calendar/travel-rules/swap/` with `{ a, b }`.

### `frontend/src/components/RulesList.vue` — `bumpPriority`

Replace the two-PATCH swap body. Keep the existing adjacency math (sort by
`-priority`, find `idx`, compute `swapIdx`, bail on out-of-range). Then:

- **Distinct-value branch** (`neighbour.priority !== rule.priority`): call
  `swapRules(rule.id, neighbour.id)` once; on `ok` `emit("changed")`, else set
  `rowError`. Removes the `ruleResult.ok !== neighbourResult.ok` split-landing
  path entirely — a single call can't half-succeed.
- **Equal-value branch** (`neighbour.priority === rule.priority`, legacy rows):
  keep the existing ∓1 single-PATCH nudge via `updateRule` (it is already
  atomic — one call — and handles the degenerate tie). No change needed there.

### `frontend/src/components/TravelRulesList.vue` — `bumpOrder`

Same transformation. Keep the ascending-`order` adjacency math and the
DIRECTION-FLIP comment. Distinct-`order` branch → single `swapRules(rule.id,
neighbour.id)`; drop the split-landing "if exactly one PATCH landed" re-emit
comment/branch. Equal-`order` branch keeps its existing ∓1 `updateRule` nudge +
`rowError`-on-failure behaviour.
