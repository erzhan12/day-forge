## Data and API Design

### Category model

Create one `Category` row per `(user, slug)` with:

- `user`: foreign key to the owning user.
- `slug`: immutable `CharField(max_length=32)` matching ASCII `[a-z0-9-]+`.
- `label`: trimmed display name with a bounded length and case-insensitive per-user uniqueness.
- `color_id`: key into the shared palette.
- `sort_order`: integer used by Settings, dropdowns, prompts, and analytics.
- `is_sink`: true only for the seeded `other` row.
- `is_new_block_default`: true for exactly one row.

Database defenses:

- Unique `(user, slug)`.
- Functional uniqueness for `(user, Lower(Trim(label)))`, supplemented by service-level `casefold()` comparison.
- Conditional unique constraints permitting at most one sink and at most one default per user.
- Check constraint requiring a sink row's slug to be `other`.
- No uniqueness constraint on `color_id` or `sort_order`.

The service layer guarantees at least one sink and default. The API never permits clearing `is_sink`, creating a sink, editing a slug, or setting the default flag to false without selecting another row.

**Concurrency reality — `select_for_update` is a no-op on SQLite.** This deploy runs SQLite (`backend/day_forge/settings.py:75-79`), where Django's `select_for_update()` is silently ignored (the existing lock at `backend/ai/views.py:689` is already a no-op). Correctness therefore must NOT depend on row-lock semantics. It rests on: (1) the `(user, slug)` unique constraint plus an `IntegrityError`-catch-and-re-query fallback on the seed path, (2) `transaction.atomic()` wrapping every multi-row mutation (seed, delete-remap, default promotion) so a partial write rolls back, and (3) SQLite's single-writer serialization of concurrent write transactions. Retain the `select_for_update()` call as a correctness upgrade for a future Postgres deploy, but the plan's guarantees do not rely on it. The `async def` AI views (`backend/ai/views.py:722` `ai_generate_draft`, `:960` `ai_chat`) must invoke the catalog loader/mutators through the existing `sync_to_async` boundary (every ORM touch there is already wrapped) or they raise `SynchronousOnlyOperation`. Existing category-bearing writers that today lock schedule-only or nothing (`_apply_draft_sync` at `backend/ai/views.py:688-689` locks only `Schedule`; `mark_reviewed` in `backend/analytics/views.py:265` locks the schedule; template writes at `backend/templates_mgr/api.py:273` and travel-rule writes at `backend/calendar_sync/travel_rules.py:261,313` lock nothing) keep their current lock scope — do NOT add a later user-row lock, which would invert the `User`-then-`Schedule` ordering that `_apply_actions_sync` already uses (`backend/ai/views.py:640-642`) and deadlock on a lock-supporting backend. Instead they re-validate the category set inside the same `transaction.atomic()` immediately before persistence, so a slug deleted mid-request is caught by revalidation. **On SQLite this preserves logical correctness — no stale slug is ever persisted:** write transactions serialize, so either the write commits first and delete-remap's rewrite then catches its string reference, or the delete commits first and the write's in-transaction revalidation rejects/folds the now-missing slug. The `(user, slug)` uniqueness constrains only `Category` rows and cannot by itself stop a template/travel-rule *string* reference from resurrecting a deleted slug — the in-same-transaction revalidation is what does. **Honest caveat on the failure mode:** because these writers open a *deferred* `BEGIN` and read before they write, the losing writer under true contention attempts a shared→exclusive lock upgrade and can surface `OperationalError: database is locked` (a retryable 500), rather than a clean reject/fold. This is NOT a correctness hole (nothing stale is written) and NOT newly introduced by this feature — it is the same write-contention profile every concurrent write in this codebase already has on the sync-runner/SQLite deploy. The global remedy (out of scope here) is `transaction_mode="IMMEDIATE"` or a whole-transaction retry wrapper applied uniformly; do not claim the per-writer `atomic()` alone makes contention *error-free*, only that it makes it *correct*. **Residual Postgres window (documented follow-up, out of scope for this SQLite deploy):** under true concurrency a Postgres deploy would need the delete-remap and these string-ref writers to `SELECT … FOR UPDATE` the owning-user row in a consistent order to close the TOCTOU gap; note it as a Postgres-migration task, do not implement conflicting locking now.

**Scope of "user-first locking" in Phase 2A GREEN:** the instruction to apply user-first locking applies ONLY to the new category CRUD / delete-remap / default-selection services — NOT to the existing schedule/AI/analytics writers above, which retain their current scope per this note.

## Core Algorithms

### Seed on first read

1. Query the user's categories ordered by `sort_order`, then primary key.
2. If any row exists, return that list without silently filling a partial catalog.
3. If none exists, open `transaction.atomic()` and take the user-row `select_for_update()` (a real lock on Postgres, a no-op on SQLite — do not rely on it for correctness).
4. Re-query inside the transaction.
5. If still empty, create Work, Personal, Health, and Other with orders `0..3`, the seeded palette mapping, `other.is_sink=true`, and `work.is_new_block_default=true`. Prefer per-row `Category.objects.get_or_create(user=…, slug=…, defaults=…)` (Django wraps each create in a savepoint) **or** an explicit nested `transaction.atomic()` savepoint around the create — do NOT catch `IntegrityError` inside the *same* atomic block without a savepoint, because a raised-then-swallowed error poisons the SQLite transaction and the subsequent re-query fails with `TransactionManagementError`.
6. **Race fallback (required because the lock is a no-op on SQLite):** if a concurrent first-read already seeded the four rows, the `(user, slug)` unique constraint raises `IntegrityError`; the savepoint rolls it back cleanly, then re-query and return the rows the other request created rather than surfacing a 500. **`OperationalError: database is locked` is the other arm and needs a different remedy:** because both seeders open a *deferred* `BEGIN` and re-query (a read) before inserting, the loser attempts a shared→exclusive lock upgrade and SQLite returns `SQLITE_BUSY` *immediately* — the busy-handler/`timeout` is bypassed for this upgrade, so a busy-timeout value does NOT make the second writer wait. The mandatory defense is a **bounded retry that restarts the whole seed transaction** from scratch (on retry the re-query now sees the committed rows and returns them), and/or configuring the SQLite connection with `transaction_mode="IMMEDIATE"` (Django 5.1+, takes the write lock at `BEGIN` so the upgrade race never occurs). Do NOT describe `OPTIONS={"timeout": …}` alone as sufficient here.
7. Refetch and return the ordered rows.

The `settings.py` `DATABASES["default"]` currently sets no `OPTIONS` (`backend/day_forge/settings.py:75-79`); if `transaction_mode="IMMEDIATE"` is the chosen defense it is added there, so `settings.py` is an edit point for this phase. The transaction-restart retry is the portable alternative and does not require the settings change.

Use this loader for the list endpoint, page props, validation, analytics, and AI. Each request loads it once and passes the resulting catalog downward. Async callers invoke it via `sync_to_async`.

### Slug generation and collision handling

1. Trim and validate the label before generating a slug.
2. Apply ASCII slugification, trim surrounding hyphens, and use `category` if transliteration produces no characters.
3. Truncate the base to 32 characters and remove any trailing hyphen.
4. Under the owning-user lock, compare against existing slugs.
5. Use the base if free; otherwise try `-2`, `-3`, and subsequent suffixes.
6. Before appending a suffix, truncate and re-trim the base so the complete slug remains at most 32 characters.
7. Persist the chosen slug once; PATCH never accepts or regenerates it.

### Per-request validation and defaults

1. Load the user catalog once and derive a slug set, sink row, and default row.
2. Check that submitted category values are strings before set membership; lists, objects, numbers, booleans, and null return HTTP 400.
3. Validate explicit slugs against the catalog.
4. For ordinary block creation (`create_block`, `backend/schedules/api.py:127`) with an omitted category, use the catalog **default**.
5. For `create_block_from_event` (`backend/schedules/api.py:256`) with no travel-rule override, use the **sink** — this path shares the `data.get("category", "other")` idiom with `create_block` today, so when the ordinary-create default change is applied, `create_block_from_event` must be given the sink, not the new-block default. Likewise for missing template/restore values and empty travel-rule overrides: use the sink.
6. Preserve `TravelRule.category == ""` as “no override”; it must never select the new-block default.
7. Immediately before persistence, revalidate the catalog inside the same `transaction.atomic()` when a request can race with category deletion (the transaction + revalidation, not lock exclusion, is what makes this safe on SQLite).

### Delete-remap transaction

For a non-sink category:

1. Start one transaction and lock the user, target category, and sink category.
2. Refuse deletion if the target is the sink.
3. Update all owned live `TimeBlock.category` values matching the deleted slug to the sink slug.
4. Lock the user's templates; clone each `blocks` list and replace exact matching `category` values, then bulk-update only changed templates.
5. Update exact matching `TravelRule.category` values; leave `""` untouched.
6. Lock the user's `DailyReview` rows. For both minute maps:
   - Clone the map.
   - Remove the deleted key, treating its absent or malformed value defensively as zero.
   - Fold those minutes into the sink key: read the sink's current value defensively as zero when it is **absent or malformed** (not only when the deleted key is malformed), then write `sink = sink_minutes + deleted_minutes`.
   - Persist only changed reviews.
7. If the target was the new-block default, promote the sink by **clearing the old default flag before setting the sink's flag** within the same transaction, so the at-most-one-default partial unique constraint (immediate on SQLite) never sees two `is_new_block_default=true` rows mid-write.
8. Delete the category.
9. Leave harmless `sort_order` gaps; subsequent creation appends after the current maximum and reorder swaps explicit values.
10. Roll back every remap and flag change if any step fails.

The Settings deletion is a preference mutation and creates no schedule undo snapshot.

### Default-selection (PATCH `is_new_block_default=true`)

Setting a new default via PATCH must, inside one `transaction.atomic()`, **clear the currently-flagged default row before setting the target row's flag** — same reason as delete-remap step 7: the immediate at-most-one-default partial unique constraint would otherwise `IntegrityError` if the new row is saved while the old still carries the flag. The API rejects a request that tries to set the only default's flag to `false` without naming a replacement.

### Stale client-held undo after category deletion

`frontend/src/composables/useUndo.ts` snapshots each block's `category` slug. After a category is deleted its slug no longer exists in the catalog, so a later undo/`restore_blocks` replay carries a now-unknown slug. `restore_blocks` (`backend/schedules/api.py:753`) must treat an unknown **string** slug in a restore payload as the sink (lenient replay of previously-valid state) rather than returning 400 — otherwise every undo referencing the deleted category fails permanently. This leniency is scoped to the restore path only: a **non-string** category value still returns 400 everywhere, and direct create/PATCH of a block with an unknown slug still returns 400. Add a test for restore-after-delete folding the deleted slug to the sink.

### Color resolution and unknown stored slugs

1. Find the category row for the stored slug.
2. If absent, substitute the user's sink row.
3. Resolve the effective row's `color_id` through the fixed palette.
4. Use the same effective row for the displayed label.
5. In analytics aggregation, initialize the accumulator with every current catalog slug at zero. For each block, resolve its stored slug to an **effective slug** — the slug itself if it is in the catalog, otherwise the sink slug — and add the block's minutes to `accumulator[effective_slug]`. Do NOT use plain `setdefault(unknown_slug, ...)`, which would create a stray key and leave the unknown minutes stranded outside the sink; the whole point is that an unknown stored slug folds INTO the sink total, not into a new key.
6. **Frozen/reviewed `DailyReview` maps** (`backend/analytics/views.py` returns persisted minute maps unchanged for reviewed schedules): when serving analytics, normalize each persisted map by folding any key not in the current catalog into the sink key (same effective-slug rule) before the frontend renders it. This is required because the frontend intentionally ignores stale keys (`CategoryBreakdown` renders one row per current catalog slug) — without server-side folding, an unknown slug's minutes silently vanish from a historical review instead of contributing to the sink.
