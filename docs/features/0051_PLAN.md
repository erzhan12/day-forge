# 0051 — Fix connect rate-limiter bypass during cache-expiry race (issue #136)

## Context

`backend/schedules/ratelimit.py::consume_rate_limit` is the shared synchronous
fixed-window connect rate limiter. It is consumed by the three credential-
verifying connect endpoints:

- `backend/calendar_sync/views.py:126-128` (`CALDAV_CONNECT_RATE_LIMIT_PER_HOUR`)
- `backend/todoist_sync/views.py:119-121` (`TODOIST_CONNECT_RATE_LIMIT_PER_HOUR`)
- `backend/habitica_sync/views.py:91-93` (`HABITICA_CONNECT_RATE_LIMIT_PER_HOUR`)

The limiter anchors a one-hour window with `cache.add(key, 1, 3600)`. When the
key already exists, `add` returns `False` and it increments via the atomic
`cache.incr(key)` (Redis `INCR`, TTL-preserving). If the key expired/evicted in
the gap between `add` and `incr`, `RedisCache.incr` raises `ValueError`; the
recovery path currently calls **unconditional** `cache.set(key, 1, 3600)`
(`ratelimit.py:35`).

### The bug

`cache.set` is a blind overwrite. Under expiry/eviction contention, N concurrent
callers can each take the `except ValueError` branch and each `set` the counter
back to `1`, then each read `count == 1` and proceed. They do **not** atomically
establish and share a single replacement window — every caller resets the
counter, so a burst of credential guesses can exceed the intended per-user
hourly `limit` and drive extra upstream authentication attempts.

### The fix (per issue #136)

Replace the unconditional `set` in the recovery path with an atomic
`cache.add(key, 1, 3600)`:

1. If `add` succeeds, **this** caller wins the race and established the fresh
   window; `count = 1`.
2. If `add` fails, another concurrent caller already recreated the window; retry
   `cache.incr(key)` so this caller increments the **shared** counter instead of
   resetting it.
3. Keep the retry **bounded** so a second immediate expiry/eviction between the
   recovery `add` and the retry `incr` cannot loop forever — after the bound is
   exhausted, fail safe.
4. Preserve the intended fixed-window TTL (`CONNECT_RATE_LIMIT_WINDOW_SECONDS =
   3600`) on the recreated counter. Correctness under concurrency still assumes
   an atomic backend (Redis in production); the `schedules.W002` /
   `warn_ineffective_cache_for_connect_rate_limits` check
   (`backend/schedules/checks.py:62`) already surfaces LocMem/FileBased/Dummy.

This mirrors the `cache.add`-anchored window pattern already documented in
`backend/ai/views.py::_consume_rate_limit` (which anchors with `aadd`). Note:
the async `ai.views._consume_rate_limit` recovery branch has the *same*
unconditional-`aset` shape, but issue #136 scopes this change to the sync
`schedules/ratelimit.py` limiter and its three connect callers. Leave the async
AI limiter untouched (out of scope; flag only).

## Files to change

### `backend/schedules/ratelimit.py`
- Rewrite the `except ValueError` recovery branch of `consume_rate_limit`
  (`lines 21-36`). New algorithm:
  1. `if cache.add(key, 1, WINDOW): count = 1` (initial anchor — unchanged).
  2. `else:` attempt `count = cache.incr(key)`; on `ValueError` enter a bounded
     recovery loop (small constant, e.g. `_MAX_RESEED_ATTEMPTS`, suggest `3`):
     - `if cache.add(key, 1, WINDOW): count = 1; break` — this caller reseeded
       the shared window.
     - `else:` another caller reseeded first — retry `cache.incr(key)`; if that
       succeeds, `count = <result>; break`; if it raises `ValueError` again
       (re-eviction), continue the loop.
  3. If the loop exhausts all attempts without settling a `count`, fail closed:
     return `False` (do **not** silently allow). This preserves the "no more
     than `limit`" guarantee under pathological repeated eviction.
  - Keep the existing `logger.warning("... key evicted mid-window; reseeding
    ...")` on entry to the recovery path (security-relevant signal).
  - Preserve `CONNECT_RATE_LIMIT_WINDOW_SECONDS` as the TTL everywhere.
  - Keep the final `if count > limit: log + return False` / `return True` block.
- Add a module-level constant `_MAX_RESEED_ATTEMPTS` (e.g. `3`) with a short
  comment explaining it bounds the reseed retry against repeated eviction.
- Update the `consume_rate_limit` docstring to describe the add-then-retry-incr
  recovery (one caller establishes the shared window; others increment it) and
  the bounded fail-closed behaviour.

## Algorithm (recovery path, step by step)

```
add(key, 1, WINDOW) succeeds?
  yes -> count = 1                      # first caller anchors window
  no  -> incr(key)
           success -> count = result    # normal in-window increment
           ValueError (key gone) ->
             log warning
             for attempt in range(_MAX_RESEED_ATTEMPTS):
                 add(key, 1, WINDOW) succeeds?
                   yes -> count = 1; break        # THIS caller reseeded shared window
                   no  -> incr(key)
                            success -> count = result; break  # follow reseed by peer
                            ValueError -> continue            # re-evicted, retry
             else (loop exhausted) -> return False            # fail closed
count > limit -> return False
else          -> return True
```

Coverage split (be precise about what each test proves):
- The **race test** (Slice 1, key stays present) proves the recovery path
  never blindly `set`s over a live shared counter: every recovery caller's
  `incr` advances the *same* counter, so the number returning `True` never
  exceeds `limit`. It does **not** exercise a winning recovery `add` (the key
  is never missing in it), so it does not by itself prove the single-winner
  reseed.
- The **rewritten eviction test** (`..._reseeds_via_add_after_genuine_eviction`)
  is what proves the recovery `add` wins against a genuinely missing key and
  reseeds the shared window to `1`. Together they cover the full invariant:
  exactly one `add` establishes each fresh window; all other callers increment
  that shared counter.

`test_consume_rate_limit_race_recovery_callers_share_one_window`
- Purpose: prove that when several callers each hit the `add`→`incr` eviction
  race against **one shared, still-present key**, every recovery caller
  increments the **shared** counter rather than blindly resetting it to `1`
  (the regression against the current unconditional `set`). Note this test's
  key stays present throughout, so it exercises the *loser* branch (recovery
  `add` fails → retry `incr`); the winning recovery `add` (missing key) is
  covered by the eviction test and the single-winner contention test below.
  Use `limit=3` and 6 total `consume_rate_limit` calls against one key.
- **Single unambiguous monkeypatch mechanism** (no real threads): wrap
  `schedules.ratelimit.cache.incr` in a **one-shot-per-call** wrapper. The
  wrapper keeps a "pending raise" flag that is armed at the top of every
  `consume_rate_limit` iteration (the test arms it before each call). When armed,
  the wrapper raises `ValueError` on its **first** invocation and clears the
  flag; any further `incr` in that same iteration delegates to the real
  `cache.incr`. This forces **every** caller whose initial `add` fails to enter
  the recovery branch exactly once and then reach the retry `incr`. (This
  replaces the earlier contradictory "once per caller" / "very first incr ever"
  wording — there is now one rule: first `incr` per armed call raises, retry
  delegates.)
- Deterministic sequence (all 6 calls against the same key, arming the flag
  before each):
  - Call 1: key absent → initial `add` succeeds → `count=1`, happy path, **no
    `incr`**, returns `True`. `get(key)==1`. (This call does not exercise
    recovery; it just anchors the window.)
  - Calls 2–6: key present → initial `add` fails → first `incr` raises (armed) →
    recovery loop → recovery `add` fails (key still present) → retry `incr`
    delegates to the real counter → yields `2, 3, 4, 5, 6` respectively.
- Expected `count` observed per call: `1, 2, 3, 4, 5, 6`; with `limit=3` the
  first three calls (`count` 1,2,3) return `True` and calls 4–6 (`count` 4,5,6)
  return `False`.
- Assert: the number of `consume_rate_limit(...) is True` results is **exactly
  `limit` (3)** and never exceeds it.
- Assert: after the run, `cache.get(key)` is `> limit` (specifically `6`),
  proving all recovery callers advanced one shared counter rather than each
  resetting to `1`.
- This test should FAIL against the current unconditional-`set` implementation:
  there each recovery caller's `except` branch `set`s the counter back to `1`
  and returns `True`, so all 6 calls return `True` (`> limit`) and
  `cache.get(key)` ends at `1`, not `6`.

## Out of scope (flag only)
- `backend/ai/views.py::_consume_rate_limit` has the analogous unconditional
  `aset` recovery branch (async). Issue #136 scopes the fix to the sync
  `schedules/ratelimit.py` limiter; note the parallel for a possible follow-up
  but do not change it here.
- **Residual `RedisCache.incr` non-atomicity (pre-existing, not introduced by
  this fix).** Django's `RedisCacheClient.incr` does a non-atomic `EXISTS` then
  `INCR`. If the key expires *between* those two ops, `INCR` recreates it with
  value `1` and **no TTL** (a persistent counter) instead of raising
  `ValueError` — so it never reaches this recovery path, and the window can then
  never expire, potentially blocking a user until manual eviction. This is the
  **opposite** failure direction from issue #136 (over-blocking, not bypass), is
  inherent to Django's backend regardless of this change, and cannot be closed
  at the application layer without a Lua/`INCR`+`EXPIRE`-NX script or a different
  backend. Left as a documented follow-up; the plan's "TTL-preserving" wording
  for `incr` refers to the common in-window case, not this expiry-race edge.
