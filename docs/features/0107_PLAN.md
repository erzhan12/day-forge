# 0107 — WHOOP morning summary via the export API and MCP

Let the planning coach (Claude, through the day-forge MCP connector) fetch last night's WHOOP sleep and recovery itself instead of the user pasting the numbers every morning.

MVP output for `get_whoop_day("2026-11-23")`:

```
## whoop · 2026-11-23
recovery: 73% · RHR 56 · HRV 31.1 · SpO2 95%
sleep: 21:49–06:57 · asleep 7:43 / need 8:16 · deep 1:16 · REM 1:18 · eff 97% · disturbances 9
strain (prev day): 16.4 · workouts: HIIT 15.2, walk 4.6
```

The design copies `gcal_sync` (OAuth connect/callback, Fernet-encrypted tokens in SQLite, locked token persist) and `get_daily_report` (stateless MCP forward of the export Bearer). Three WHOOP specifics differ from Google and are called out below: refresh-token rotation on every refresh, rejection of concurrent refreshes (so refresh must be single-flight, unlike `gcal_sync`), and a fixed 8-character `state`.

## WHOOP API facts (checked against developer.whoop.com on 2026-11-23)

- OAuth: authorize `https://api.prod.whoop.com/oauth/oauth2/auth`, token `https://api.prod.whoop.com/oauth/oauth2/token` (`authorization_code` and `refresh_token` grants). A refresh token is issued only with scope `offline`.
- **Rotation:** each refresh returns a new refresh token and invalidates the previous access token; the new refresh token must be used next time. Confirmed in step 0: every refresh of grant B rotated the refresh token.
- Requesting `offline read:recovery read:cycles read:sleep read:workout` returns exactly those scopes (step 0). `GET /v2/recovery?limit=1` also exists as a collection endpoint (used by the grokbot helper).
- **Concurrency:** of simultaneous refresh requests the first succeeds, the rest fail.
- `state`, when generated by the client, must be exactly 8 characters.
- Access token lifetime comes from `expires_in` (sample 3600 s). Expired/invalid → 401. Refresh-token lifetime is not documented.
- API v2, base `https://api.prod.whoop.com/developer`: `GET /v2/activity/sleep`, `GET /v2/cycle`, `GET /v2/cycle/{cycleId}/recovery`, `GET /v2/activity/workout`. Collections take `start`, `end`, `limit` (≤25), `nextToken`; return `records` + `next_token`, newest first.
- Default rate limit: 100 requests/minute, 10,000/day. The tool makes about 4 calls per run.
- Scopes requested by Day Forge: `offline read:sleep read:recovery read:cycles read:workout` (no profile/body data).
- The working grokbot helper sends a custom `User-Agent` on both token and API calls; keep doing so.

## Design

### `whoop_sync` app

- `WhoopAccount`: `user` (OneToOne), `refresh_token_encrypted`, `access_token_encrypted`, `access_token_expiry`, `scopes`, `last_verified_at`, `created_at`, `updated_at`. `__str__` never shows tokens.
- Settings check: if **any** `WHOOP_OAUTH_*` is set, all four must be set and the Fernet key valid (`E001`). With none set, WHOOP is disabled and boot is unaffected — unlike `gcal_sync.E001`, WHOOP is not a hard production dependency.
- HTTP via `httpx` (already a backend dependency), timeout from settings, custom `User-Agent`.

### Token lifecycle

1. Use the cached access token while it is valid for more than 120 s.
2. Otherwise take a single-flight refresh lock in the shared cache: `cache.add("whoop_refresh:<account_id>", 1, timeout=WHOOP_REQUEST_TIMEOUT + 5)`. Redis is already required whenever AI is enabled, as it is in production. A database row lock is not used: it would hold the SQLite writer across a network call.
3. The lock holder reloads the row (another request may have refreshed already), refreshes over the network, then persists access token, expiry and the **rotated refresh token** in one transaction on a reloaded row, and releases the lock in `finally`. Persist immediately after the response: a rotated refresh token that is received but never saved forces a reconnect.
4. A request that does not get the lock polls the row (about every 250 ms, up to the lock timeout) until a fresh access token appears, then uses it. If none appears, the export returns 502 (a transient failure to retry), never 409.
5. If the lock holder's refresh call fails with 400/401, reload the row once: if a fresher token is stored, use it; otherwise raise `WhoopAuthError` (→ export 409 "reconnect required").
6. If the refresh response lacks `refresh_token`, keep the stored one.
7. An API 401 triggers one forced refresh (through the same lock) and one retry.
8. Tokens, codes and provider response bodies are never logged.
9. Record the divergence from `gcal_sync` in `RULES.md` (External integrations): WHOOP refresh is single-flight because the provider rotates and rejects concurrent refreshes.

### Mapping a date to WHOOP records (Asia/Almaty, UTC+5)

1. **Sleep:** query `/v2/activity/sleep` from D−1 12:00 to D 12:00 in the user's zone; drop `nap=true`; take the longest remaining record. Bed/wake times are rendered with the record's own `timezone_offset`.
2. **Recovery:** WHOOP starts a cycle at sleep onset, so `sleep.cycle_id` is the new day's cycle; fetch `/v2/cycle/{cycle_id}/recovery`.
3. **Previous day's strain:** the cycle that ended at this sleep's start (`/v2/cycle?end=<sleep.start>&limit=2`, pick the one ending there) → `score.strain`.
4. **Workouts:** `/v2/activity/workout` within that previous cycle's start/end → `sport_name`, `score.strain`.
5. Formatting: `asleep` = light + slow-wave + REM; `need` = sum of `sleep_needed` components; `eff` = `sleep_efficiency_percentage`; `disturbances` = `stage_summary.disturbance_count`; SpO2/RHR/HRV from the recovery score.
6. Partial states render explicitly: `recovery: pending` (`PENDING_SCORE`), `sleep: none recorded`, `unscorable`.

### Export view `GET /api/export/whoop/<date>/`

Markdown only in the MVP. Auth via `resolve_export_owner`. Every response `Cache-Control: private, no-store`. Status codes: 200 summary; 400 bad date; 401 auth; 404 WHOOP not connected; 409 reconnect required; 429 WHOOP rate limit; 502 WHOOP unreachable/5xx. Provider bodies never reach the client.

## Privacy and security

- WHOOP data is health data. It is not cached, not stored (only tokens are), not logged, and not sent to the AI chat/draft providers. Update the privacy page with one line naming WHOOP and what is read. The wording must not claim the data never leaves Day Forge: it reaches Claude through the user's own MCP connector. Bump `LEGAL_LAST_UPDATED` (`backend/schedules/legal_views.py:16`) and pin the new statement in `backend/tests/test_legal_pages.py`.
- Secrets: client id/secret and the Fernet key only in `.env` locally (gitignored, betterleaks CI) and in GitHub secrets for production (`deploy.yml` writes the server `.env`). Tokens only as Fernet ciphertext in SQLite.
- The export token gains read access to WHOOP summaries (D1); revoking it revokes both reads.

## Out of scope

Settings UI, disconnect endpoint, webhooks, JSON format, history/trends, multiple WHOOP accounts per user, sharing WHOOP data with the AI chat.
