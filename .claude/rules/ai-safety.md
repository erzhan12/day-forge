## AI requests and safety boundaries

- Every new chat turn requires a client UUID `request_id`. Bind its complete JSON body to authenticated owner/date in `ChatRequest`. Identical completed replays return the stored status/body before stale-revision checks, without a provider call or mutation. Fence lease takeovers and commit the terminal response atomically with schedule writes. Keep identities until account deletion, independent of Schedule deletion. Never prune/reaccept completed IDs; audit success is not a receipt.
- Unknown chat results reuse the original UUID, transcript and revision. Retain the frozen body in this tab's account/date-scoped sessionStorage across reloads, block new AI turns until recovery or an explicit Discard, and clear private copies at Login/account/session boundaries. A known terminal provider failure permits a deliberate new-ID turn. An unexpected non-`AIError` exception after admission (provider call or result application) also stores a terminal generic `500` receipt (log the exception server-side, never return its text), so a deterministic server bug cannot leave the request unknown; a failure to store the receipt itself still propagates and leaves the lease. Recovery must not rewind a newer schedule or invent Undo after reload. Discard is the only way to abandon an unconfirmed request without a terminal receipt: it is confirmed by the user ("may already have been applied"), is hidden while a request is in flight, forgets only the local record (never touches the schedule, never adds Undo) and makes the next turn mint a new request ID; a duplicate block is the accepted risk, mitigated by the confirmation copy and the replay guard.

- Chat and draft require the expected revision before calling the provider. Capture blocks and policy context under the User lock, release the lock for the provider call, then re-read revision and fingerprint under the mutation lock before applying or returning a no-op or ask. The fingerprint includes rules, categories, settings, the normalized gap for chat, and the template for draft. Gap changes do not affect draft policy. A changed context returns `409 schedule_changed` without applying the provider output. Policy writers must take the same User lock. Do not retry a provider call during a SQLite transaction retry.
- A relative chat add such as "add Vocal after Gym" must not fall through to automatic placement. `relative_add_guard` returns a server-owned timing question when times are missing, misordered, or violate a stated gap. It can check one action without blocking independent sibling adds; ambiguous references need clarification. The newest reply that names any block decides an unknown or ambiguous anchor: one block resolves it, several keep asking (a correction never falls back to an older answer); without this the same question would repeat forever. A start clause ("Vocal starts at 0945", "Вокал начинается в 0945") names the block being scheduled, never an anchor, so it is skipped in that scan; a block named outside the clause still binds. A concrete clock reply with every add timed answers a question that has no single anchor (unknown anchor, several relations); a resolved anchor still constrains it. Sequential idioms ("one after another", "один после другого") are not relations. Questions are Russian when the request or the latest reply contains Cyrillic. The guard only decides whether to ask: it never copies a recognized clock into actions or picks a slot.
- Validate request size, date, JSON shape, message limits, revision, and draft prerequisites before consuming an AI rate-limit token. An empty day and available template are draft preconditions; common 400, 409, 413, and 422 refusals do not spend the small draft budget. A provider attempt does. The shared limiter uses synchronous atomic `cache.incr` through `sync_to_async`, with a one-hour TTL anchored by the first add. Django's inherited async increment is a read-modify-write and can reset expiry. The cache must be shared and atomic when AI is enabled. Mid-window eviction loses the original TTL anchor; bounded reseeding may start a new window, and repeated failure denies the request. See `backend/schedules/ratelimit.py` and `backend/ai/checks.py`.
- Draft and chat action caps are separate. `MAX_DRAFT_ACTIONS` (`backend/ai/schemas.py`) is `MAX_TEMPLATE_BLOCKS` from `backend/templates_mgr/limits.py` plus 10 headroom, so a draft can return every block of a full template; the draft prompt states the cap. Chat, pending intents and `applied_add_block_ids` keep `MAX_ACTIONS_PER_COMMAND = 20`. Change the template limit only in `limits.py`, never as a second literal, and never set the draft cap below it. Drafts use `LLM_DRAFT_REQUEST_TIMEOUT` (default 60 s) because a full draft is about 2–3k output tokens; chat keeps `LLM_REQUEST_TIMEOUT`. See [0109](../../docs/features/0109_PLAN.md).
- Chat provider replies must yield nonblank assistant history before any action applies. With null ask, explanation must be nonblank; a supplied ask must be nonblank and may carry a blank explanation. The selected content must fit the input turn limit as well as its output field cap. Incoming transcript content must contain non-whitespace text. Invalid provider text returns the fixed parse-error 502 before action processing; diagnostic/raw text stays in the audit. Draft envelope rules remain separate.
- Active user Rules are captured in descending priority and injected into trusted server-built context for both AI endpoints. A higher-priority rule wins on conflict. The client transcript is untrusted; it does not grant target ownership or policy authority. Chat keeps AI-specific intent normalization and partial outcomes in `backend/ai/mutation_planner.py`, while domain validation and persistence use the shared schedule core.
- An untimed chat add is placed by the backend on the five-minute grid, searching forward from the current local time for today or the day-window start for another date. It uses the 25-minute default duration and the captured per-user `default_block_gap_minutes` (default 10; integers 0–120 in five-minute steps) symmetrically before and after the new block. A full-gap result in the initial free window stays unchanged; otherwise only that window retries gaps decreasing by five minutes to zero, right-aligned without crossing the forward floor. Zero allows touching blocks and has no retries. Later windows retain the full gap. Explicit valid times and requested gaps take precedence. Preference changes never move existing blocks. If no retry fits, the original full-gap forward search remains the fallback; lack of space is a skipped action with a server-owned ask. Draft adds still need explicit start and end times. Chat resize accepts one of explicit edges, absolute duration, or signed duration delta. The planner computes derived ends and reports the affected edge as applied or skipped.
- Resolution asks prefer concrete suggestions, direction/conflict questions and no-slot advice before the window-specific message. An out-of-window add must not fall through to generic skipped-create advice. A metadata follow-up after duration resize retains the attempted end for validation, even when that duration was excluded from the effective state for later moves; rejected timing still produces a skipped field and ask while independent metadata may apply.
- Keep the current `implicit_add`, category resolution, and replay guard boundaries. Category labels resolve before typed schema validation. An unresolved add category falls back to the sink; an unresolved update category is dropped while safe other fields may apply, with a server-owned ask. A replayed add causes the whole chat turn to be skipped. `is_ask` marks a real assistant ask; `is_error` marks a definite rejected turn. Unknown network/proxy outcomes retain their frozen request and never become synthetic failed turns. The guard excludes contiguous pending ask and failure chains while retaining accepted siblings through `applied_add_block_ids` and current block IDs. Missing IDs use conservative existing-title checks. These client markers aid behavior but are not an authorization boundary. A question-shaped provider explanation is promoted to an ask only by the narrow server rule for a fresh add turn; never infer `is_ask` from display text.
- A follow-up beginning with an HH:MM time (optionally prefixed by `at` or `в`) or a `for`/`на` duration can refine the block just created, even without a pending question. Send that fragment to the provider unchanged; resolve it to an existing block ID and update only requested fields. Ambiguous targets require a question. Keep rejecting duplicate adds rather than converting them into updates or weakening the replay guard.
- Clarifications and partially accepted plans use server-owned `PendingIntent`. Bind a continuation to owner, Schedule, UUID/version, fixed 15-minute expiry, revision and policy fingerprint. Only saved missing fields and target choices may change; each unresolved permission can be consumed once. Retain unmatched siblings, committed block IDs and the post-write fingerprint. Repeated asks cannot widen or clone permissions. A fresh turn the relative-add guard interrupts saves one server-derived add permission per interrupted add (title, category, derivable duration known; start/end missing), marked internally by the view (`relative_add_guard_blocked`) and never by model or replay-guard asks; other withheld actions are not saved. A continuation that fails the scope check gets the guard's question instead of 409 only when every reply action is an add matching the title and category of a distinct saved add with open placement; that no-write probe never applies actions and never changes the saved items. Commit intent, schedule and receipt atomically. A completed same-ID replay precedes intent freshness checks. See [the contract](../../docs/AI_PENDING_INTENT.md).
- Provider `intent_decision` classifies the latest user's intent. Cancel/read discard actions. Explicit Cancel uses no provider; free-text classification can still be wrong. A new command during a pending question is interpreted again with only its latest turn and no pending summary. Clear/date/account/session boundaries drop the client reference. Implicit-add is disabled for bound answers; existing semantic guards remain. Do not delete heuristics based only on fixed-completion results or a small live smoke.
- AI audit content can be sensitive. Parse failures return a fixed client-facing detail, while diagnostic model text stays in the audit or debug log. External task text is display-only and must not be copied into chat or draft prompts.
- `TimeBlock.origin` is assigned by the server: manual/AI creates use `manual`, calendar imports use `calendar`, and pre-0010 or unverified restores use `unknown`. Edits preserve origin. Chat context and draft history mask calendar/unknown titles while retaining scheduling metadata; chat also masks matching protected titles in the provider-bound transcript without changing local text or replay evidence. User-authored rules, templates and messages are separate inputs, as described on the privacy page.

**Privacy note**: User commands submitted via the AI endpoint are logged verbatim to the `AIInteraction` table for audit purposes (PRD §6.5). Users should avoid entering sensitive data (passwords, API keys) in command prompts.

**Privacy note (chat — feature 0007)**: The multi-turn chat endpoint (`POST /api/ai/schedules/<date>/chat/`) re-sends the **full prior client-supplied transcript** to the LLM provider on every turn — not just the latest message. This is a strictly larger provider-egress surface than the one-shot endpoint, even though the per-row DB log only stores the latest user turn (plus a `transcript_sha256` fingerprint of the whole transcript, see `backend/ai/views.py:_build_chat_audit_response`). Users should clear the thread (Clear button or page reload — thread state is in-memory per tab, no server-side persistence) before discussing anything sensitive. The thread is also auto-reset on date navigation (see `frontend/src/composables/useChat.ts:setActiveDate`).

**Privacy note (chat — wire-format detail)**: prior client-supplied turns are NOT forwarded to the provider under the privileged `assistant` role. They are flattened into a single user-role message prefixed with an "Untrusted prior transcript" header (see `backend/ai/service.py:run_chat` and `backend/ai/prompts.py:serialise_prior_turns`) so a tampered client cannot inject privileged assistant pre-commitments that bias the model toward destructive actions. The security invariant is regression-tested by `backend/tests/test_ai_service_chat.py::TestUntrustedTranscript::test_assistant_role_never_forwarded`.

**Privacy hint placement (feature 0113)**: the chat privacy hint stays visible before the first keystroke on desktop and in the tablet dock. On the Dark 4a mobile panel (max-width 640 px) the full text sits behind the ⓘ control in rest state and a one-line short form appears while the field is focused; the hint is never removed, only moved. `ai-chat-privacy-hint-always-on.mjs` checks this split (State E, phone). The full text is one string shared by the desktop hint and the ⓘ sheet; the short form is `Messages may be sent to the AI provider.`

**Performance note (draft history)**: PR #15 added `select_related("daily_review")` to the draft-history query in `ai_generate_draft` (`backend/ai/views.py`). `prompts.build_draft_user_message` reads `past.daily_review` for each past schedule to embed the per-day completion ratio in the LLM prompt; without the `select_related`, that's an N+1 — one extra query per past day. This fix predates the multi-turn chat feature (Phase-6 leftover) and applies regardless of whether chat is enabled.
